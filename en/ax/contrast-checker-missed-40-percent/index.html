Our contrast checker passed while skipping 40% of the text: make it print how much it measured

"Passes in all three themes" turned out to mean 40% of the text was never measured. The checker now reports how many fragments it measured and why it dropped the rest, and fails a case that measures less than it declares.

By SugarMount · Testing and release · 8 min read · Last updated October 25, 2026

We had assumed that a contrast check passing in the light, dark and sunset themes meant every piece of visible text had been measured. On September 10, 2026, commit 8dacf19 in our P2P chat app (Flutter) counted what the checker actually did: of 9,318 text fragments, 3,762 (40.4%) never produced a contrast ratio, and the old checker never said it had left them out. The inventories summarized in the same commit message found that only 70 of 245 screen states had ever been rendered in a real theme, and 58 of 116 interactions had never been touched by a test or a finger.

Sources: the messages of commits 67edc8d, 8dacf19 and d01cc23 (all 2026-09-10) in the P2P chat app repository, plus its verification reports. The screen-state, interaction and string inventories landed in 67edc8d; the harness integrity report landed in 8dacf19. Every number was re-checked against the repository on October 21, 2026.

Only 5,556 of 9,318 fragments produced a contrast ratio

Skipping text behind a dialog or an emoji is reasonable, and most of the drops were of that kind. Nothing logged them, though. These counts come from the fixed checker running 149 cases in each of the 3 themes (447 runs); the right-hand column records how the old checker had treated each group.

The commit message says 3,762 fragments (40%) were "silently discarded"; by the table, 3,318 vanished without a trace, and 444 were measured against the wrong pixels instead of being dropped.

Paragraphs behind a barrier were never collected, emoji hit a continue, and off-screen fragments got return null from _evaluate. None of these paths kept a count. The last of them was these two lines:

final finding = _evaluate(f, bitmapA, bitmapB);
if (finding != null) findings.add(finding);

Whenever _evaluate returned null, the fragment disappeared, and the caller saw only "0 failures".

The completeness check compared files, so 209 states were invisible to it

A second guard failed the same way. A meta test was meant to keep the theme-matrix catalog complete, but it only checked that every screen file under lib/ appeared in the catalog at least once. When the inventory was taken, the catalog's 20 cases rendered 36 of 245 states (15%), so 209 states could go missing without that test noticing.

This round started from inventories extracted from the code, not from pass totals.

The fixed meta test compares per state and requires a written reason for every exclusion. Deleting dead surfaces brought the total to 239 states, and the catalog grew to 149 cases. (Three tests that rendered dead code had been padding the "passes in three themes" count; they went too.)

Measuring again found a 3.28:1 snackbar and a 36.5 dp send button

The chat screen's error snackbar picked a red background and left the text color to Material's default, which in the light and sunset themes came out at 3.28:1, under the 4.5:1 WCAG AA minimum for body text. White on a darker red gave 6.54:1. The send button's InkWell sat inside a Transform.scale animation, so the tap area shrank with the icon to 36.5 × 36.5 dp; with the InkWell moved outside, it measured 47.66 × 47.85 dp.

Three reported defects (the permission dialog's guidance, a message bubble's text and a native splash) turned out to be artifacts of how they were sampled, and were withdrawn instead of fixed.

What the AI-built harness missed, and the rule the operator works by

The checker and the catalog were built by an AI coding agent one commit earlier, in 67edc8d. That commit promised contrast "from rendered pixels rather than from declared alpha values", and it did measure pixels. What it never counted was how much it measured.

The AI also produced a wrong verdict. The agent that expanded the catalog reported the permission dialog's guidance at 1.02:1, effectively invisible. In fact the case had captured the first frame of the route fade, at opacity 0, and the checker measured the text against the lobby underneath: a green status dot on a peer tile. With a 600 ms settle frame, all three themes passed at 8.07 to 12.08:1.

All three commits carry an AI co-author trailer, and agents wrote the reports too. What came from a person was a rule: the operator works on the basis that a test which still passes with its guard removed is a fake test. Section 7 of the harness report is that rule pointed at the checker. One case was put back on its old text-free placeholder screen. With the new checks off, 4 tests passed having measured 0 of 0 candidates; with them on, 3 failed on "0 measured fragments < declared minimum of 1".

Don't let a contrast check print only "pass". Print the measured count, the dropped count and the reason for each drop, and fail when the measured count falls below what the case declares. The general method, from the same app, is written up in 3,066 green tests hid a line that breaks opening the database: checking tests by deleting the guard.

The disabled-button exemption was built so it can't hide anything

The last three failures were disabled buttons in the fingerprint dialog while it saves, at 1.83 to 1.91:1. WCAG 1.4.3 has no contrast requirement for inactive UI components, and Material's own disabled styling sits around 1.9:1. Thirty-three minutes later, commit d01cc23 added the exemption with four limits:

  • "Disabled" is decided from the widget tree before any pixel is captured: the nearest ancestor control must have a null callback. A washed-out color can never make something count as disabled.
  • Only below-minimum contrast is exempt. Invisible or unpainted text still fails on a disabled button, and so does anything under 1.5:1.
  • Exempted fragments stay in the drop list with their measured ratio.
  • A permanent test paints an active and an inactive button the same grey. Only the inactive one is exempt.

Across 149 cases the exemption fires in exactly one. After that commit, flutter test reported 2,475 passed, 4 skipped, 0 failed.

Measuring it yourself

Any checker that measures contrast from rendered pixels can be audited in the same order, whatever the framework.

  1. Find every path where a fragment can leave the checker: return null, continue, filter conditions. Give each one a reason and put the fragment in a list. At 8dacf19 the checker had ten reasons, including off-screen, behind a barrier, occluded, clipped, pictographic and not painted.
  2. Print one accounting line per case. If candidates do not equal measured plus dropped, the checker has a bug.
  3. Assert a floor. Each case must measure at least one fragment to pass, and a case allowed to measure zero needs a written reason of 20 characters or more. Don't pin exact counts: one changed letter turns the case red, and the easiest fix for the next person is to lower the number.
  4. Run the revert experiment. Swap one case for a screen with no text, then run it with the new checks off and on. It should pass with them off and fail with them on. Turn the settle frame off too and see whether "not painted" comes back.
  5. Measure completeness against a state list. Extract screen × state pairs from the code's branches, give each an id, and check that every id has a case that renders it or a reason it is excluded.

In this app, three --dart-define switches cover steps 2 and 4:

flutter test test/theme_matrix/ --dart-define=Y2_TRACE=true
# #Y2# <case>|<theme>|measured=..|candidates=..|fail=..|inactivePass=..|discard=offScreen:..,behindBarrier:..

flutter test test/theme_matrix/ --dart-define=Y2_NO_INTEGRITY=true
# turns off the floor and the "nothing unpainted" assertions; with no hidden unmeasured case, the pass count stays the same

flutter test test/theme_matrix/ --dart-define=Y2_NO_SETTLE=true
# turns off the shared 600 ms settle frame

In the harness report from 8dacf19, the run with the settle frame and the checks on gave 903 passed and 3 failed (the disabled buttons above), and turning only the checks off gave the same 903 and 3. At that point no unmeasured case was hiding. The rest of what runs before a release is in What to check before shipping an AI-built Android app: the release gate and an R8 crash. Two things are still open. The 1,575 fragments behind barriers are all dropped even when a sheet covers only half the screen, and every number here comes from widget-test pixels that have not yet been compared with device screenshots.

FAQ

Can text be unreadable even when an automated contrast check passes?

Yes. If the checker silently drops fragments it could not measure, the result still says "0 failures". In this app, 3,762 of 9,318 text fragments got no contrast ratio, and before the fix nothing said they had been dropped.

Does the WCAG contrast minimum apply to disabled buttons?

No. WCAG 1.4.3 sets no contrast requirement for text in inactive UI components. Decide "inactive" from the missing callback, or the exemption becomes a place to hide real failures.

Is it fine to skip emoji and text behind a dialog?

Yes, as long as the result prints how many were skipped and why. In this app, skipping the 1,575 fragments behind barriers and the 876 emoji was correct.
