Several AI agents in one repository: give every shared file exactly one owner

Two sessions shared one working tree, and one commit carried off 50 files the other was still writing. Since then we split parallel work with a table that names one owner for each shared file.

By SugarMount · Working with agents · 8 min read · Last updated November 13, 2026

Many agents, one repository 3/6

Run several Claude Code sessions or subagents and they will edit the same repository at the same time. On September 23, 2026, a release-fix commit in our utility app repository picked up 50 files that another session was still writing for the next app. Sixteen days later, the family calendar app AXFamily wrote an owner for every shared file into its plan first, then merged 13 feature branches in a little over two minutes. The table did not remove hand merges, but it told us in advance where they would happen.

A release fix swept in 50 files from another session

On the evening of September 23, two sessions were running in one working tree of the utility app repository. One was finishing release 1.0.3 of the photo compression app; the other was building the next app, Flip & Rotate Image. At 10:24 pm the release session committed. Its message covered a release crash fix, a launch-check script and an analytics default, with no word about the flip app. The commit actually changed 74 files, and 50 in the flip app's folders plus 5 in the image engine were the other session's unfinished code. The other session's memory note called it being swept in "git add -A style."

The launch-check script added in that commit ran ./gradlew --stop. Gradle's documentation says this stops every daemon of the same version. A session building our Korean spacing app on the same PC used that same Gradle version, and two of its clean builds that day died with "stop command received." Each session suspected the other, but across both repositories' history that script is the only place --stop ever appears. The line was replaced with --no-daemon 15 days later.

In one working tree, git cannot tell your changes from theirs

Two sessions in one working tree never produce a conflict for git to report. Their changes land in the same index, and whoever commits first becomes the owner of every file in the tree at that moment. Without an owner per file, an agent has no way to know whether it changed a file itself. The Gradle daemon had the same shape: not a file, but something every session on the PC shared, and any session could stop it.

The flip-app session wrote down rules that day. Re-read shared files right before editing them and change only the part you need. Never commit, stash, reset or run gradlew --stop. Builds can be killed by another session, so trust the timestamps in the test result files, not the exit code. Those rules are now in the agent instructions for every project, along with running long Gradle builds with --no-daemon.

Worktrees did not stop hand merges in the wiring file

A git worktree is an extra checkout of the same repository in its own folder, so each agent can work on its own branch. When this repository was created on September 20, four base tasks (file handling, image engine, ads and billing, analytics) went to subagents in one worktree each, and four branches were merged within 12 minutes. Three of those merges needed AppContainer.kt, the file that wires dependencies, resolved by hand. The repository wires each app by hand in that one file instead of using a DI framework, so every base task had to add its own lines there.

Worktrees keep work in progress apart. A wiring file that every task adds a line to still conflicts at merge time. The game repository handled this with an "exclusive files" column per workstream when deciding how many AI coding agents to run at once, and AXFamily added the shared wiring files that column had left out.

AXFamily's plan named an owner and a workaround for each shared file

AXFamily's release plan of October 9 put this first: "One base agent lays down every shared file first. After that, nobody edits those files." Its conflict-rule table, shortened:

Shared fileOwnerWhat other packages do instead
API contract schema and generated codeBase agentNever touch it; queue contract requests for the base agent
Database security rules, index fileSecurity-rules packageKeep test data in their own folder only
Server function list, error codesBase agentEvery planned function is registered up front as a stub; each package fills in its own handler file
App skeleton (dependencies, router, manifest, Gradle)Base agentRoutes and ad settings ship as files in the feature folder, collected by a registry
Combined translation fileMerge toolEach feature writes only its own fragment file; the tool combines them
CI workflowsBase agentAdd one check file and it is discovered automatically
Gradle builds and devicesNobodyOne at a time regardless of worktree, --no-daemon

The base agent laid these files down one after another, then 12 packages worked in parallel inside their own folders. Coordinating by conversation had mixed 50 files; worktrees alone had needed 3 hand merges out of 4. A single session doing everything in sequence would have had no conflicts, but 12 packages one by one; that time was never measured.

Seven of 13 merges needed a hand; translation fragments, none

Early on October 10, 13 feature branches went into the integration branch in 2 minutes 11 seconds: the plan's 12 plus a design-system branch. Listing, with git show --cc, the files where each merge had to combine both sides finds such hunks in 7 merges.

  • Four app-screen packages: the combined translation files and three Dart files generated from them. CI demanded "if the combined file differs from the fragments, run the merge tool and commit," so every branch committed its own regenerated copy. The fragment files never appear in any of the 13 merges.
  • The media package: the server function list and error codes. It added a function that was not among the 16 stubs, and it and the account package each edited the same error-code line.
  • Two app packages: the index file owned by the security-rules package.
  • The rest were test files.

Checking each branch's changed files against the table shows that 8 of the 13 branches edited a file someone else owned. "Nobody edits those files" did not hold. Small edits, two lines in a dependency file or four in the manifest, merged silently; only edits to the same line by two branches showed up as hand merges.

Where git stayed quiet, contracts drifted

Sixteen minutes after the merges, a minimal fix repaired six pairs of packages. The app's paid-access check disagreed with the billing server's rules, and two packages each declared their own ad-consent type. All were different files, so git saw no conflict, and an integration review then confirmed 12 more defects. The table had owners for files but none for concepts such as "guardian" or "current family." Those 12 are covered in the 12 defects an integration review found after 13 parallel branches. Use an owner table to cut text conflicts, and leave contract drift to an integration review.

One table before you split the work, two commands after you merge

Write down the shared files and their owners before you decide how many agents to run. Sessions sharing one working tree get no commit rights.

  1. Find the files every task adds a line to: DI container, router, endpoint list, dependency files, combined translations, CI config, database indexes.
  2. Give each file one owner, and on the same row write how others contribute instead (fragment files, their own files picked up by a registry). Add rows for shared things that are not files, such as builds and devices.
  3. Have the owner lay down the wiring files first, with every planned name registered as a stub.
  4. Files a tool generates, like a combined file, are rebuilt after the merge by the integrator. This site follows the same rule (one --check gate for a static site that agents co-edit).
  5. If sessions must share a working tree: re-read right before editing, edit only the part you need, no commit, stash, reset or --stop, Gradle with --no-daemon, and judge success by the timestamps in test result files.
  6. After merging, count where the table leaked.
    # files where a merge combined both sides
git show --cc --format= <merge> | grep '^diff --cc'
# files a branch changed, to compare with the table
git diff --name-only $(git merge-base <base> <branch>) <branch>

At AXFamily the first command found the 7 hand-resolved merges, and the second found the 8 branches that edited someone else's files. How to write rules like these into an instruction file is in how to write AGENTS.md.

The combined translation file is still committed, and concepts still have no owner

AXFamily's development branch still holds the combined translation file and three generated Dart files, and CI checks that they are current. Moving them to an integrator-only rebuild has not happened yet. Whether adding "concept" rows (guardian check, current family) to the owner table reduces integration defects has not been tried either.

FAQ

Can two Claude Code sessions run in the same working tree?

They can, but do not let a session commit unless asked. After one session's commit carried off 50 files another session was writing, sessions in a shared tree no longer commit, stash, reset or run gradlew --stop.

Do git worktrees remove conflicts between parallel agents?

They stop work in progress from mixing, but a wiring file that several tasks edit still conflicts at merge time. On September 20, 3 of 4 merges needed the dependency wiring file resolved by hand.

Does gradlew --stop stop builds in other projects?

Yes, if their daemons run the same Gradle version. Gradle's documentation says so, and two clean builds in another repository on the same PC died with "stop command received." Run long builds with --no-daemon.

Sources: git history of both app repositories, AXFamily's release plan (October 9, 2026) and the sessions' memory notes. Hand merges were recounted with git show --cc on October 28, 2026, and the September 20 merges rechecked on November 13.
