Claude Code data analysis: a 130% payback was 76%

A Claude Code data analysis put our ad payback at 130% by dividing a GA4 number by a Google Ads number; with both sides from GA4 it was 76%, after the budget had already gone up.

By Stephen · Testing and release · 10 min read · Last updated November 21, 2026

Citing a calculation that ad spend was coming back as 130% in ad revenue, a Claude Code agent advised raising the daily budget for our Korean spelling app one step, and the operator did so the same evening. Two days later the same agent recalculated and got 76%. The numerator and the denominator had come from two different tools.

Two weeks before that, an ad experiment the agent had proposed ran four days past its verdict date, the day set to decide whether to keep it or switch it off. Both times, the first thing to expose the mistake was a question from the operator. Verdict checks have since moved to a run that starts every morning, and late verdicts still turn up.

A 130% payback behind a budget raise

On the evening of October 15 the operator asked the agent to pick up the Google Ads analysis for the app. Installs had risen since an audience signal, built from spelling-related searches and users of rival spelling apps, was attached to the campaign a week earlier. The agent first filtered GA4 (Google Analytics 4, which counts users inside the app) down to this campaign and produced a table: 12.7 new users a day arriving from ads.

A few minutes later the operator downloaded the Ads check sheet for it, and the agent computed payback from that sheet's cost per install (CPI). It divided the long-run ad revenue of one ad-driven user, measured in GA4 in September, by that CPI and got "about 130%". The only caveat it attached was that revenue from the newly arrived users had not been measured yet, so the figure was an estimate. When the operator asked whether the conclusion was to raise the budget, the agent said yes, by one step only, with the 130% among its reasons. A minute later the operator replied that the budget was going up, and the next day's cost data showed the raise in effect from that day.

For the next two days the agent's reports compared one line against the baseline and put the decision off by another day. On the morning of October 17 the operator pushed hard: was it going to keep doing this half-heartedly? Analyse it properly and come back with a decision to raise or cut. Four minutes later the agent reported that the extra spend had not added a single user who ran a spelling check, and that payback computed on one source was 76%.

The same report said: "The roughly 130% payback I gave on 10-15 was a wrong calculation, and I recommended the raise on that number." The operator decided that afternoon to go back to the old budget, and the change was made that evening.

The numerator came from GA4, the denominator from Ads

Payback here is the ad revenue one user brings in, divided by the ad spend it took to acquire one new user. In the 130% calculation the numerator was revenue GA4 measured by following the group of users who arrived from ads in September (a cohort), and the denominator was spend divided by installs as Google Ads counts them.

For the same week (October 8 to 14), Ads counted 21 installs a day; GA4 counted 12.7 new users who arrived from ads and opened the app. The install counts differ by a factor of 1.65, and the two tools also logged slightly different daily spend, so the GA4 cost per new user comes out about 1.7 times the Ads CPI.

Multiply 76% by 1.7 and you get 130%. Both calculations used the same numerator, so the whole gap sits in the denominator.

The agent's first suspicion was the numerator: was it fair to apply September users' revenue to new users? When the new users were measured two days later, their revenue so far, less than ten days' worth, was close to that of the September users. The denominator had carried no caveat.

Six minutes before the 130%, the same session had already put the GA4 cost per new user in a table, and then did not use it.

That commit put the gap down to how Ads decides which installs to credit to an ad (attribution), for example after a YouTube ad view, and wrote that money calculations use GA4. The same day the agent's memory got a rule: do money math only within one source, and before recommending a raise, have same-source evidence that ad revenue exceeds the spend.

Two weeks earlier, a verdict date four days gone

On the night of September 20 an experiment the agent had proposed in a revenue analysis went live in the AdMob console. It capped the app-open ad (the full-screen ad shown when a user comes back to the app) at one per user per 10 minutes, aiming for fewer "too many ads" complaints and fewer uninstalls.

That night the agent also started WATCH.md, a file listing running experiments and their verdict dates, and the cap's verdict date went in as September 27. The rule: switch it off if revenue fell by more than a set amount, or if the uninstall rate did not move.

September 27 passed. That afternoon another session even added a new experiment row to the same file and committed it, and every session that edited the file before the operator's question on the night of October 1 left the verdict log at the bottom a single empty row.

On the night of October 1 the operator sent an AdMob screenshot: match rate and revenue were both down, analyse it. The agent opened WATCH.md first and straight away wrote, "Three experiments are past their 09-27 verdict date and the verdict log is empty."

App-open impressions had fallen 35% at an unchanged price per impression, and the uninstall rate had not moved, so the rule said switch it off. The operator turned the cap off in the console and sharply blamed the agent for the drop in revenue. The agent agreed it had proposed the experiment, owned the four unjudged days after the verdict date, and wrote, "Relying on people to remember verdict dates failed this time."

Daily-check records stop on October 11

The frequency cap was a console setting, so it left no trace in code, builds or tests. That is why, on the day WATCH.md was created, the agent's instructions got a line: if you are going to look at ad or subscription numbers, read this file first. That line only fires when someone asks about ad numbers.

The next morning, with the operator's go-ahead, the agent created three scheduled verdict runs and a memory rule. They used the scheduling feature inside the Claude Code session (CronCreate), with the caveat that they "only run while this session stays open".

The scheduled verdicts ran on time, and a daily check added after them found, on its first run, the R8 optimisation release (the first build with the R8 code shrinker's optimisations on) ten days past its verdict date. The earlier verdicts had covered only the three ad experiments due on September 27 and did not mention this one.

The last daily check from that session is dated October 11. The next verdict date then passed, and the agent judged it only when the operator asked it to run the analysis on October 15.

The Google Ads asset-strength verdict (the grade Ads gives ad creatives) came nine days late. The scheduled verdict on October 6 noted it as an experiment another session had set up and moved on; the agent first said on October 15 that the value came only from an Ads script the operator alone could run.

Of the 26 verdict-log rows whose planned date can be traced to a calendar date, 17 were judged after it, four of them by a single day. Of the 22 rows due after the memory rule, 13 were late, 9 of them by more than a day.

Checking verdict dates and ratios

  1. When you start an experiment, write for each row a calendar verdict date, the verdict rule, and which way it falls if nobody looks that day. Experiments that cost revenue default to off.

  2. The same day, query the metric the rule depends on once. One November 7 verdict ended unjudged because the metric was never registered in GA4.

  3. Make the first step of a scheduled run "list every row whose verdict date is before today and has no entry in the verdict log". Don't wait for someone to ask.

  4. Run that job outside the session. On Windows, start it from the OS scheduler, as in Schedule Claude Code with Windows Task Scheduler.

  5. If a verdict needs data the agent cannot fetch itself (such as an ad console script's output), ask a person for it before the verdict date.

  6. When producing a ratio, write the source next to the numerator and the denominator ([GA4], [Ads]). If they differ, don't decide on it.

  7. Put the two tools' install counts for the same period side by side and look at the ratio first. Here it was 1.65 (our puzzle game campaign case is in Google Ads for a puzzle game: CPI 30x break-even).

The 76% numerator is September users' revenue

The 76% numerator is the long-run revenue of ad-driven users who arrived in September; for the new users we had less than ten days of revenue as of October 17. The reason Ads and GA4 count differently is the analysis doc's reading of how Ads counts, not something we checked. With 13 to 21 installs a day, depending on the tool, a few days can swing the ratio a lot.

The most recent late one, due November 15, was judged two days later. Finding out how the run checked the list of verdict dates each day means reading its run logs, which we did not open for this note.
