Claude Code fix: Naver spelling highlights missing

The missing highlights were errors at the end of a sentence. A request tag the server folded into the correction and a strict length check each dropped them; after fixing both with Claude Code, all 31 errors in the saved responses get colour.

By Stephen · Android development · 8 min read · Last updated November 17, 2026

Type "이거 어떻해" (a common misspelling of "what do I do") into the SugarSpeller app and it used to show no highlight at all. The chat-style screen went further and told the user there were no spelling errors. Naver, the Korean portal whose spell checker the app calls, was returning the right correction the whole time. Replaying the colouring logic from before the September 13, 2026 fix on saved server responses, only 17 of the 31 errors Naver flagged got colour.

Every one of the 14 misses was the last error in its sentence. The causes were a string appended to the request body and one comparison that filters out ranges reaching the end. If your app paints corrections from an external spelling or translation service, look at those two places first.

Short sentences came back with no colour at all

The app has two screens: Chat, which shows results as message bubbles, and the older Classic screen with separate input and output boxes. At 18:14 KST on September 13, 2026, the operator asked Claude Code to investigate: highlighting did nothing in Chat and was unreliable in Classic, and Naver should be analysed first.

The agent's first suspect was the response parser. It fetched live Naver responses and ran them through the app's regular expression; every corrected word and error type came out correctly, so parsing was ruled out. Its second suspect was how Classic matches each response to its chunk (long input is split into chunks). Ten measured sentences produced zero mismatches.

At 18:27 the agent tested what it called its last hypothesis: a short sentence whose only error is at the end. The result came a minute later: of 10 short sentences, Naver found errors in 7, and all 7 got zero colour. The pair below is that case as it was later saved in the repository's test data.

A tag and an operator erased the same error

To tell which chunk a response belonged to, the app appended a tag (in Chat, the message's unique ID and chunk number; in Classic, the chunk number and a hash of the sentence) to the text it sent. Naver read the tag as part of the last word and returned it inside the em element that marks the corrected span.

The app stripped the tag only from the corrected sentence it displays. The list of corrected words still held "어떡해-…-0", so indexOf, which looks up the word's position in the displayed sentence, returned -1 (not found), and an error the app can't locate gets no colour.

Chat counted the corrected words it managed to find on screen, and when that count was zero it said "no spelling errors". Classic used Naver's own error count field, errata_count, so it reported the right number and showed no colour.

The second defect had nothing to do with the tag. Colour was applied only when buffer.length > key + text.length: the displayed sentence had to be longer than the word's start position (key) plus the word's length (text.length), meaning the range had to end before the last character. "이거 어떡해" is 6 characters and the corrected word ends at character 6, so 6 > 6 is false and nothing was painted. A short sentence often has one error, at the end, which leaves the screen with no colour.

Because both defects remove the same error, fixing one barely helps.

Both defects predate any AI-co-authored commit in the repository. Appending an identifier to the request text (then a hash of the sentence) first appeared in December 2020, in the original screen that later became Classic (6baa0ae).

The comparison came in April 2021 with commit 3ad9ba4, titled as a fix for an IndexOutOfBoundsException in the colour-span call. A guard written to stop an out-of-range crash also blocked ranges that end exactly at the end.

In August 2025, when Chat was rebuilt with Claude Code, two commits (02cbb15 and 5f082f8) copied both habits into the new screen: the new request code appended the tag, and the new colouring loop used the same comparison.

Start with a short sentence whose only error is the last word

  1. Check a short sentence whose only error is the last word. If nothing is highlighted, look at the next two places.

  2. In the request builder, look for an order number, hash or UUID appended to the text being checked. Move it into the HTTP client's request tag or the callback closure.

  3. Find the range check right before colouring. If it reads length > end or end < length, it should be end <= length. The grep below only finds the length > start + length form this app had; check length > end, end < length and Java's length() separately.

    grep -rnE '(length|size) *> *[a-z]+ *\+' app/src/main

  4. Save real responses as test data files. Assert that the error-count field equals the number of coloured ranges, that each range's substring equals the corrected word, and that ranges don't overlap.

  5. Revert the fixed line for a moment and confirm the tests fail. If they still pass, they won't catch the bug when it comes back.

The 26/26 check was never in the repository

At 20:41 the agent committed e9cd771, fixing both defects and Chat's error count, and reported that a live cross-check on 18 sentences now coloured every error. The report also listed the number of passing unit tests.

At 22:13 the operator asked whether the Naver tests were all committed. The agent replied that only 10 pure-logic tests were in the commit; the live cross-check depended on response files in a scratch folder and had been deleted as a one-off.

Eleven minutes later commit 9ed4dca landed. It stores verbatim server responses in the repository as a fixture (fixed test data): 23 sentences sent without the tag, and the same sentences sent the old way with the tag attached. A mutation check, temporarily reverting the fix, showed 9 tests failing when end-of-string ranges are dropped again.

On November 16, 2026, a Python port of the same comparison run over this fixture gave 17 of 31 again. All nine zero-colour sentences have a single error, in the last word: five were written for exactly that case, and the other four mix in a line break, a long number, a Latin word or a trailing space.

The chunk number now rides in the request tag

Never put identifiers into the body you send to an external API. The app now carries the chunk number in the OkHttp request tag, a value that never leaves the device and comes back with the response callback. It dropped the old approach of stripping the tag from the response with regular expressions: those patterns could also delete a user's 13-digit numbers or long Latin words, which is what the long-number and Latin-word sentences in the chart contain.

What changedPrevious behaviour, and why it went
a range that ends at the last character is colouredthe old comparison; the final error was always dropped
a word that isn't found is skipped and the search position keptthe position was left at -1; the next word was searched from the start and colour landed in the wrong place
both screens count errors with errata_countcount of words found; a miss turned into "no errors"
one shared colouring class (SpellHighlighter)three copies (Chat, Classic, Daum); fixing one let the others drift

The same evening the Daum checker (another Korean portal) turned out to be failing outright; that story is in Daum spell check failed: OkHttp and a JS redirect.

The fixture is one day of responses

If Naver changes its response format, the offline tests keep passing while the app breaks again, and since this is not a public API there is no notice of such changes.

No response seen so far has put a line break or a character like < inside a correction span. The current code turns &lt; back into < only in the displayed sentence, so such a response would leave &lt; in the corrected word and < on screen, and the word would not be found. The mobile responses have only ever used two error types (spacing and spelling); the colours for the other two are untested against real data.

Still to check: fetch the same 23 sentences from the live server and compare the format with the fixture, and look for a sentence that puts a special character inside a correction span.

FAQ

Why does only the last word miss its highlight in Naver spell check results?

In this app there were two causes. A tag appended to the request ended up inside the last correction span, so the word could not be located, and a comparison refused any range ending at the last character. Both only hit the error at the end of a sentence.

Can a SpannableString span end exactly at the string length?

Yes. The end index is exclusive, so an end equal to the length colours up to the last character. Only an end beyond the length throws IndexOutOfBoundsException.
