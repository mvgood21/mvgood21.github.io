Run Claude Code every day with Windows Task Scheduler: a three-file kit and what a real harness added

Put a runner script, a job file and a prompt file in one folder, register the runner with Task Scheduler, and Claude does the job at the same time every day while you are logged on, leaving a log and a status file.

By SugarMount · Working with agents · 11 min read · Last updated November 11, 2026

Windows harness series, part 4 of 5 · previous: part 3, Docker Desktop · next: part 5, game-app marketing

On November 11, 2026, a hand-run of the hello job below got an answer from Claude in 11 seconds, and the runner wrote start and end lines to a log plus a status file. A copy with a 3-second limit was killed at 3 seconds. No coding needed: you paste in three files.

A schedule set up inside a chat session stops when you close that session (part 1, the overview). Task Scheduler starts a fresh Claude at the set time, with no cloud server; it runs only while you are logged on.

One folder, three files

Task Scheduler, which ships with Windows, is the clock. The runner run-job.ps1 does the work: it reads the job file jobs\hello.json and feeds the prompt prompts\hello.md to claude -p, Claude Code's headless mode: one request, one answer, no chat window.

Open the PowerShell window you used in part 2 and paste these two lines. $HOME is PowerShell's name for your user folder. The runner creates logs and state on its first run.

New-Item -ItemType Directory -Force "$HOME\harness\jobs", "$HOME\harness\prompts"
cd $HOME\harness

The runner script

In the same window, type notepad $HOME\harness\run-job.ps1. Notepad asks whether to create the new file; choose Yes, paste the script exactly as shown, then press Ctrl+Shift+S (Save As) and set Encoding to "UTF-8 with BOM". Without the BOM (a 3-byte marker at the start), the built-in PowerShell 5.1 reads the file as the legacy ANSI code page and garbles the Korean text.

param([Parameter(Mandatory = $true)][string]$Name)
# 작업 하나를 실행한다: 작업 정의를 읽고, 겹침을 막고, 시간 한도를 걸고, 로그를 남긴다.
$ErrorActionPreference = 'Stop'
$root = $PSScriptRoot
$job  = Get-Content "$root\jobs\$Name.json" -Raw -Encoding UTF8 | ConvertFrom-Json
New-Item -ItemType Directory -Force "$root\logs", "$root\state" | Out-Null
$log  = "$root\logs\$Name.log"
function Write-Log($msg) { Add-Content -Path $log -Value "[$(Get-Date -Format 'yyyy-MM-dd HH:mm:ss')] $msg" -Encoding UTF8 }

# 1) 같은 작업이 아직 돌고 있으면 건너뛴다
$mutex = New-Object System.Threading.Mutex($false, "Global\my-harness-$Name")
if (-not $mutex.WaitOne(0)) { Write-Log '이전 실행이 아직 돌고 있어 건너뜀'; exit 5 }

try {
    # 2) 전용 설정 폴더(로그인 정보가 대화용 Claude와 섞이지 않게)
    if ($job.configDir) { $env:CLAUDE_CONFIG_DIR = $job.configDir.Replace('~', $HOME) }

    # 3) claude -p 인자: 프롬프트는 인자가 아니라 표준 입력으로 넣는다
    $claudeArgs = @('-p', '--model', $job.model)
    if ($job.allowedTools -and $job.allowedTools.Count -gt 0) {
        $claudeArgs += @('--allowedTools', ('"' + ($job.allowedTools -join ',') + '"'))
    }
    $promptFile = "$root\$($job.prompt)"
    $outFile    = "$env:TEMP\my-harness-$Name.out"
    $cmdLine    = 'claude ' + ($claudeArgs -join ' ') + " < `"$promptFile`" > `"$outFile`" 2>&1"

    Write-Log "시작 model=$($job.model) timeout=$($job.timeoutSeconds)s"
    $sw = [Diagnostics.Stopwatch]::StartNew()
    $p  = Start-Process -FilePath 'cmd.exe' -ArgumentList '/c', $cmdLine -WorkingDirectory $root -WindowStyle Hidden -PassThru

    # 4) 시간 한도: 넘으면 claude와 그 자식 프로세스까지 끈다
    if (-not $p.WaitForExit([int]$job.timeoutSeconds * 1000)) {
        & taskkill.exe /PID $p.Id /T /F | Out-Null
        $status = 'timeout'; $code = 1
    } else {
        $code = $p.ExitCode
        $status = if ($code -eq 0) { 'ok' } else { 'error' }
    }
    if (Test-Path $outFile) { Get-Content $outFile -Encoding UTF8 | Add-Content -Path $log -Encoding UTF8; Remove-Item $outFile }
    Write-Log ("종료 status={0} exit={1} ({2:N0}s)" -f $status, $code, $sw.Elapsed.TotalSeconds)

    # 5) 마지막 결과를 상태 파일로 남긴다(감시자가 이 파일만 본다)
    @{ job = $Name; status = $status; exitCode = $code; finishedAt = (Get-Date).ToString('s') } |
        ConvertTo-Json | Set-Content -Path "$root\state\$Name.json" -Encoding UTF8
    exit $code
}
finally {
    $mutex.ReleaseMutex()
}

The kit is published as tested, so its comments stay in Korean. What they say:

  • Line 2 and 5): "run one job: read its definition, prevent overlap, apply a time limit, write a log", then write the result to state\hello.json.
  • 1) "Skip if the same job is still running": a named mutex, a "busy" flag Windows keeps, makes the runner exit 5.
  • 2) and 3): use the configDir folder; feed the prompt on standard input (the channel a program reads instead of the keyboard), because as an argument it got read into the tool list.
  • 4) "Past the time limit, kill claude and its child processes", the programs Claude started.

Exit codes: 0 success, 1 timeout, 5 skipped. In the log, 시작 is "start" and 종료 is "end".

Job file and prompt

A job is a JSON file plus a prompt file. Open notepad $HOME\harness\jobs\hello.json the same way, paste, and save as UTF-8. Its description reads "job for checking that things work".

{
  "description": "동작 확인용 작업",
  "prompt": "prompts/hello.md",
  "model": "haiku",
  "allowedTools": [],
  "timeoutSeconds": 300
}

The model is haiku because a self-check needs little judgment. An empty allowedTools means Claude can't read files or run commands and can only answer. The prompt, prompts\hello.md, says in Korean: "You are the self-check job of a game-app marketing harness. Use no tools. Along with the words 'harness check', write on one line the three numbers a game-app marketer should look at first each morning." You can write the prompt in English.

너는 게임 앱 마케팅 하네스의 동작 확인 작업이다. 도구는 쓰지 않는다.
"하네스 동작 확인"이라는 말과 함께, 게임 앱 마케팅 담당자가 아침에 가장 먼저 볼 숫자 세 가지를 한 줄로 적어라.

Type Get-ChildItem $HOME\harness -Recurse to confirm the three files are in place.

First run by hand

Run it by hand before scheduling; scheduled runs show no window.

cd $HOME\harness
powershell -NoProfile -ExecutionPolicy Bypass -File .\run-job.ps1 -Name hello
Get-Content .\logs\hello.log

-ExecutionPolicy Bypass lets this one process run the script without changing the PC's policy, and -NoProfile skips your personal PowerShell profile so the hand-run matches the scheduled run. If the last log line reads 종료 status=ok exit=0 ("end"), it worked.

Claude didn't make up numbers. Since the prompt told it not to use tools, it said it couldn't fetch data and gave only a one-line template with empty slots for yesterday's installs, cost per install (CPI) and D7 ROAS. The state file state\hello.json records the job name, status, exitCode and end time.

The time-limit test used a job named t3 with timeoutSeconds set to 3. After 3 seconds the runner killed Claude and logged status=timeout exit=1.

configDir is more than login

When the kit was first written, configDir was just an option for keeping logins apart; the runner's own comment says so ("so the login doesn't mix with your chat Claude"), and hello ran without it. Its answer then ended with three lines the prompt never asked for: "done", "result" and "what's left for the user". That summary rule comes from the operator's personal instruction file for interactive Claude (the global CLAUDE.md), and the scheduled job followed it too.

With CLAUDE_CONFIG_DIR set, Claude Code uses that folder instead of ~/.claude for settings, login and instruction files. So a job with a configDir follows the instructions in that folder, not your chat ones. The real harness's dedicated folder has the same summary rule copied in, and a real job's answer on Nov 10 ended with it; to drop the format you edit the instruction file in that folder. hello2, pointed at that folder, finished in 5 seconds without the summary, but that is one run, so it isn't evidence either way.

The bigger reason to separate folders is login (first table row below). The scheduled hello.json (backslashes doubled inside JSON):

{
  "description": "동작 확인용 작업",
  "prompt": "prompts/hello.md",
  "model": "haiku",
  "allowedTools": [],
  "configDir": "~\\.claude-harness",
  "timeoutSeconds": 300
}

Log in to the dedicated folder once. In a new PowerShell window, run the line below; when Claude opens, sign in with /login, then close the window.

$env:CLAUDE_CONFIG_DIR = "$env:USERPROFILE\.claude-harness"; claude

Registering the task

Paste the whole block into PowerShell at once; it runs the hello job every day at 9:05. A trailing backtick continues the line. This is a shortened version of the registration code in SugarMount's harness installer.

$runner   = "$HOME\harness\run-job.ps1"
$action   = New-ScheduledTaskAction -Execute 'conhost.exe' `
              -Argument "--headless powershell.exe -NoProfile -ExecutionPolicy Bypass -File `"$runner`" -Name hello" `
              -WorkingDirectory "$HOME\harness"
$trigger  = New-ScheduledTaskTrigger -Daily -At 9:05
$settings = New-ScheduledTaskSettingsSet -StartWhenAvailable -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries `
              -MultipleInstances IgnoreNew -ExecutionTimeLimit (New-TimeSpan -Hours 1)
$principal = New-ScheduledTaskPrincipal -UserId "$env:USERDOMAIN\$env:USERNAME" -LogonType Interactive -RunLevel Limited
Register-ScheduledTask -TaskPath '\my-harness\' -TaskName 'hello' -Action $action -Trigger $trigger `
  -Settings $settings -Principal $principal -Force
SettingWhat it does and why
conhost.exe --headlessNo window; without it a console flashes up each run (Windows 11).
-StartWhenAvailableA run missed while off or asleep happens once after waking.
-AllowStartIfOnBatteries, -DontStopIfGoingOnBatteriesStarts on battery and keeps going when unplugged; the Windows default is no start on battery.
-MultipleInstances IgnoreNewA new start is ignored while the last run is still going.
-ExecutionTimeLimit 1 hourLonger than the runner's 300 seconds, so the runner stops Claude first and logs it.
-LogonType Interactive, -RunLevel LimitedOnly while logged on, no admin rights, no stored password; Claude uses your profile's login.
-ForceRerunning replaces the task of the same name.

To test, check and remove it:

Start-ScheduledTask -TaskPath '\my-harness\' -TaskName 'hello'
Get-ScheduledTaskInfo -TaskPath '\my-harness\' -TaskName 'hello'
Unregister-ScheduledTask -TaskPath '\my-harness\' -TaskName 'hello' -Confirm:$false

The first line runs it now. About a minute later, the second should show LastTaskResult 0 and logs\hello.log a fresh pair of lines. The third removes the task.

A marketing job sketch

The sketch below writes a morning report on a game app from yesterday's GA4 numbers. It's an illustration written for this note and has not been run. It assumes you export the numbers from GA4 into a data folder and create a reports folder. Copy hello.json and change prompt, model (sonnet) and allowedTools (["Read", "Write"]). The prompt outline:

You are the morning-report job of a game-app marketing harness.
1. Read data\ga4-yesterday.csv. If it is missing, write only "no data" in the report and stop.
2. Put new users, users who started the first level and users who cleared it in a table.
3. Use only numbers that are in the file. Give every ratio as a fraction too.
4. Write reports\ga4-(yesterday's date).md. Do not change ad budgets or campaigns; list changes as suggestions only.

To schedule it, rerun the registration block with -Name hello and -TaskName 'hello' changed to ga4-daily and a time of your choice.

What the real harness added

SugarMount's harness passed 130 commits by Nov 11; most of what it has beyond the kit traces back to an incident or a review finding.

SafeguardWhy it existsIn the kit
Dedicated config folderSep 10: a chat /login overwrote the scheduled jobs' authThe configDir field
Wait to the end-p stopped subagents after 10 minutes; the runner now waits (1ac160a)No
Locks and run limitA review: long lock waits (up to 19 minutes) could hit the limit, so it gained 3600 s (64eaaeb)Same-job overlap only
Kept work treesJobs work in a git worktree (a second checkout); a dead run's leftovers go to a rescue branchNo
Guard hookBlocks risky commands; with unreadable config it blocks (fail-closed, a69692b)No tools allowed
WatcherEvery 15 minutes, reports failures and missed runs from state filesWrites the state file only
Runtime copy and release gateAn uncommitted edit stopped everything (next section, 6fdc641)No

A guard hook is a check script Claude Code calls right before Claude uses a tool (a PreToolUse hook); if it exits with code 2, that call is blocked. How the list of blocked actions came about is in Running an AI marketer on a schedule four times a day: the permission table that leaves money, accounts and policy to a person.

The 38-hour stop

At first the harness ran straight from the folder where it was being developed (the harness repo). Before every job, a preparation script called prepare checks the harness code for uncommitted changes, edits not yet recorded in git with a commit, and exits with code 3 if it finds any. With an in-progress harness edit left uncommitted, every scheduled job exited 3 at prepare from 19:37 on Nov 4 until 09:38 on Nov 6, about 38 hours; the app dailies failed on the mornings of Nov 5 and 6.

The Korean-spelling app's daily also exited 3 on Nov 4, a day earlier, for a different reason. On Nov 3, -p had stopped background subagents 10 minutes after the last turn, leaving changes in the work tree, and prepare refused to start on top of them. The "wait to the end" and "kept work trees" rows came out of that.

The check did what it was built to do. Development and operations shared one folder, so a half-finished edit stopped production. Since Nov 7, scheduled jobs run from a runtime copy, a separate checkout used only for operations, and harness-release, which runs every 15 minutes, moves a commit there only after it passes the gate checks.

Don't run production from the folder you're editing. For the kit, edit a copy of run-job.ps1 elsewhere, run it by hand, then copy it in; a half-edited runner called at 9:05 can't even write a log line.

Still open

If you registered the kit, look after 9:05 the next day for a new start and end pair in logs\hello.log and a finishedAt of today in state\hello.json. If neither is there, first check whether the PC was logged on at 9:05. The Task Scheduler register, start, check and remove commands were not run while writing this note; the first scheduled run is the next thing to confirm.
