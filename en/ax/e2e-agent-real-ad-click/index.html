Claude Code tapped a real AdMob ad during E2E

Our AdMob test-device setup applied only to debug builds, so a Claude Code agent testing a release APK on a real phone saw live ads and clicked one of them once.

By Stephen · Android development · 10 min read · Last updated November 19, 2026

A Claude Code agent was tapping through an Android app on a real phone when an interstitial ad came to the front, and its next tap landed on the ad. AdMob counts live impressions and clicks on a developer's own device as invalid traffic.

The setting that sends test ads to our development phones applied only to debug builds, so the release APK served live ads. The agent's screen-check guard read only the package name, so it took an ad screen opened inside the app for the app itself, and the tap that hit the ad never went through that guard at all. The next day the setting went into every build, but banners inside our own screens and ads from other networks are still not fully covered.

Chrome opened from behind an interstitial

On the afternoon of September 28, 2026, the agent installed a release APK of our Korean spell checker SugarSpeller on a Galaxy S21 and walked through the whole check flow. Its script force-stopped the app and relaunched it through a share intent for every check.

One agent command dumped the screen, read the coordinates of the result bubble and sent a tap there. The tap landed at 16:19:55, when the dump finished, and a tenth of a second later logcat showed Chrome opening a shopping advertiser's page. When the agent dumped the screen again, the script stopped with "foreground is not our app": Chrome's first-run screen was in front.

After Chrome was closed, an interstitial in the Google Mobile Ads SDK's AdActivity was still up inside the app. The agent wrote that it would close the ad with BACK only and never tap it. After BACK, a second ad screen was underneath, from another ad network, Liftoff (formerly Vungle). Twenty-nine minutes later it told the operator it had clicked a real ad once, an invalid click, and recorded the same in the changelog's incident line.

The guard only checked the package name

At 14:56 that day the agent had added a guard to its screen dump and screenshot script. It read the topResumedActivity line, the activity in front, and carried on if the app's package name appeared there. Ad SDK screens run inside the app's process, so that line reads like com.sugarmount.sugarspeller/com.google.android.gms.ads.AdActivity and passes. The guard also sat only in front of the dump and screenshot commands; the tap that clicked the ad was a raw command that never went through it.

The guard changed twice within two minutes of the click.

TimeRuleWhat happened
14:56 (v1)Continue if the app's package name is on the front-screen lineAd screens passed. Taps ran outside the guard
16:20 (v2)Stop if the name contains AdActivity or gms.ads; move taps into the script, only with numeric coordinates more than 250 px below the topAfter BACK, Liftoff's VungleActivity underneath was not on the name list
16:21 (v3)Continue only if the front screen is one of the app's own classes; otherwise stop and close with BACKAt 16:44 it blocked a tap in front of a Liftoff ad

The v2 assumption was that ad screens can be recognized by name. With mediation, where several ad networks bid for the same slot, each network brings its own screen name, and an unlisted one appeared 13 seconds after v2 went in. v3 lists what is allowed instead of what is blocked. The agent also removed the force-stop from each check that day, because every relaunch showed an app-open ad.

The test-device list was wired to debug builds only

The app had a test-device list in code, but a September 11 fix applied it only inside a BuildConfig.DEBUG check, which is true only in debug builds. A release APK on a real phone skipped the list entirely, and the S21 was not on it anyway.

The next night, while instrumentation tests (Android tests that launch the app on the phone itself) ran on the S21, the operator asked whether the account would get suspended, since ads kept showing during testing. The agent first answered that the instrumentation tests were debug builds using test ad units, so there was no risk. That was wrong. This app's debug build deliberately uses the real ad units so the bidding partners can be verified, and a comment in the same file said so. The logcat the agent then checked had three copies of the SDK hint that only unlisted devices get: call setTestDeviceIds to get test ads on this device.

Twenty-seven minutes after the question, commit ec5f400 moved the call out of the debug condition. Only listed devices get test ads, so real users are unaffected. The commit added the S21 and a unit test checking that the S21 is on the list and that the configuration carries the whole list.

The two days of developer-phone testing also show in AdMob reporting. When we pulled daily banner requests again, September 29 alone had more than twice the usual thousand or so requests, and the match rate (the share of ad requests that actually got an ad) fell below half.

Our October 1 monitoring note says all of the extra requests came from version 1.6.024 and puts them down to the S21 and S23 running instrumentation tests against real ad units. In the raw data, every unmatched request on September 28 and 29 but one came from that version too. That version number was shared by the development builds and the Play release at the time, so the version alone does not single out the devices.

The S23 was on the list and still got live ads. Resetting a phone's advertising ID also changes the test-device value the SDK uses, and the code still held the value from before the reset. The agent said the test-device ID is the MD5 of the advertising ID and computed it, but the result did not match the log, and neither did an MD5 of the Android ID. On the operator's instruction, the code got the value the SDK printed in logcat.

We put the test-device list in every build and the console

Five fixes came up. The agent objected to two from the operator's side, and the operator stopped the build flag the agent was writing.

OptionRaised byOutcome
Turn the app's debug constant on for testing and off for releaseOperatorAgent objected: the constant also forces a premium subscription, and forgetting to turn it off would give every user test ads and free premium
Build flag for test ad units that fails the Play upload (AAB) build if left onAgentOperator stopped it mid-test and switched to console registration. Never built (not in the repository as of November 18)
Switch the debug build to test ad units(Sep 11 review)Dropped: test units skip mediation, so bidding partners can't be verified
Watch a few live ads to check, then shipOperator questionAgent objected: live impressions and clicks on a developer device are invalid traffic at any count
Apply the code list to every build and register devices in the consoleAgent, operatorChosen. Code in ec5f400; console registration left to the operator

On the morning of September 30 the operator asked whether the S21 was registered as an AdMob test device too. The agent said only in code. The code list only covers builds that contain it. If an older version from Play is installed on a developer phone, only the test-device registration in the AdMob console protects it. The console takes the raw advertising ID and the code takes the SDK hash, so both values went into a per-device table in the repository docs (4595dce).

An ad ID file copied into a worktree

About a week later the same risk came in by another route in our puzzle game Arrow Knots. The game keeps its real ad IDs in one settings file that git ignores, and a release build uses the file whenever it exists. At 01:28 on October 4, the Claude Code session handling ads got the IDs from the operator and, without asking, copied the file into another session's working folder (a git worktree). Twenty-one minutes later that session built what it took to be a test release APK.

At 02:06 that session passed on the ad session's warning that random-tap testing must never run on a real-ID build, wrote that its own workspace had no real-ID file and would build with test ads only, so it was safe, and then installed the APK on an S20. A file check in the same command printed that the file was there. The session uninstalled the app without ever opening it, moved the file aside, and rebuilt with test ads. No ad request or click happened.

The game's test-ads flag only allowed test IDs when the file was missing; it did not ignore a file that was present. Commit 68d501e the next day made the build read the file from its original location through a build argument, so a worktree never needs a copy. Our block puzzle, built in the same days, has a test-ads flag that ignores the file entirely; what its real-ID check still missed is in Why R8 kept 5 AdMob test IDs in a release AAB.

The September 30 check still logged the Liftoff app-open ad as live

The tap guard only checks whether the front screen is one of our activities, so it cannot see a banner or native ad placed inside our own screen. If coordinates happen to land on a banner, the guard lets the tap through. That is why the order below puts test-device registration ahead of the tap rule.

The code list only covers AdMob ads. At 08:57 on September 30 the operator said the console registration was done, but the records do not say which consoles or which devices. In the S21 check that followed, AdMob served test ads; the Liftoff app-open ad was still live and did not close with BACK, so the app was force-stopped to close it. The session judged it live from what was on screen and asked the operator to recheck the test-device setting in the Liftoff dashboard.

Register test devices before any device E2E

Do not run automated taps on a real device with any build that can serve live ads. This is the order we put together from this incident. Of these, using the logcat value and applying the list to every build (steps 1 and 2) are already in the app repository's rules, and tapping only on our own screen (step 5) and never copying the real-ID file into another worktree (step 6) are already in the agent's memory.

  1. Connect the device, launch the app once, and copy the value from the setTestDeviceIds(Arrays.asList("…")) line in logcat. Don't compute it.

  2. Add that value to the app's test-device list and keep the MobileAds.setRequestConfiguration call outside any build-type condition. Add a unit test that checks the device is on the list.

  3. Register the same phone's raw advertising ID as a test device in the AdMob console and in each mediation partner's console.

  4. Relaunch the app, check that ads carry the test-ad label, and confirm the "to get test ads on this device" line no longer shows in logcat.

  5. Inside the tap script's tap command, tap only if the activity name from adb shell dumpsys activity activities | grep -m1 topResumedActivity starts with one of the app's own classes, such as <package>/.; otherwise send BACK. Relaunch the app only when you must.

  6. Keep the real ad ID file in one place and pass its path to the build. Never copy it into another session's worktree.

  7. The next day, check match rate and request counts in the AdMob report. Leaked developer-device traffic shows there first.

Random-tap crash hunting is in VIBRATE crash and the fresh-install monkey test; we run that only on test-ad builds as well.
