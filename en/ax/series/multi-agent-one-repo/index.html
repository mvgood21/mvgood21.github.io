Many agents, one repository: where parallel work collided

On October 3, 2026 we were told hundreds of agents were fine, yet only three code-writing Claude Code agents ever ran at once. Six parts on that limit and where parallel work collided.

6 parts

What this series found

  • October 3, 2026 produced 59 commits, but no more than three code-writing agents ran at the same time. The limit came from 4 GB of free memory and two shared test phones, not from the number of agents allowed. (Part 1: three at a time)
  • Five subagents cut off by usage limits on September 7 to 10 left reports that were mostly empty sections, even though they had created them first. What made a handover possible was what the work left on disk anyway: logs, screenshots and edited files. (Part 2: subagent briefs)
  • In a shared working tree, one release-fix commit swept up 50 files another session was writing (September 23). With a table naming one owner per shared file, 7 of 13 later merges still needed hand work, but we knew in advance where. (Part 3: the file owner table)
  • Thirteen branches passed agent review and CI. A review of only the merged code confirmed 12 defects, and 10 of them were broken contracts between two packages. (Part 5: integration review)
  • A release review ran 84 agents and had three others try to refute each finding. Twenty findings survived and were fixed, one of them a crash; the cross-review after the fixes confirmed nothing new. (Part 6: refutation review)

This series is for developers running several Claude Code subagents or sessions against one repository. If you are deciding how many to launch, start with Part 1; if you are writing a subagent brief, Part 2; if sessions have already mixed up each other's files, Part 3. Part 4 is about one --check command that guards a static site several sessions edit before every commit. Parts 5 and 6 are two ways to review code built in parallel and read best together.
