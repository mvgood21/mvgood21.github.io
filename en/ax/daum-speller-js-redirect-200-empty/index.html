Daum spell check failed: OkHttp and a JS redirect

The page that hands out the key switched to a JavaScript redirect, OkHttp never got the key, and the server answered every check with HTTP 200 and an empty body. Daum was a backup path and nothing counted failures, so no one noticed.

By Stephen · Android development · 8 min read · Last updated November 15, 2026

On the night of September 13, 2026, we found that one of the two portal spelling checkers used by SugarSpeller had not succeeded once. The app sends text to two Korean web portals, Naver and Daum (run by Kakao); Naver goes first and Daum is the backup. Daum's server answered every request with HTTP 200 and an empty body.

No one noticed because the app counted the failure nowhere and Daum was not the everyday path. With Daum switched on as the primary checker, the Chat screen would quietly show Naver's result instead. The records do not tell us when it started.

A coloring request led to a 259-byte page

The app has two screens: Chat, the default, where checks go back and forth as message bubbles, and Classic, the older layout with an input box and a result box. That evening the operator asked for the error highlighting to work: it did nothing in Chat and misbehaved in Classic, and both portals' responses should be read properly and turned into colors, Naver first. The working theory was that the response-parsing code was wrong. For Naver it was, and commit e9cd771 fixed that at 20:41 KST.

After the operator said to finish cross-checking Naver and move on, at 22:25 the AI coding agent (Claude Code) fetched the portal page the app loads to get its key. The key here is an authentication value the app must send with every check request. The page body was 259 bytes: a single location.replace() line.

The same check request the app sends then came back with status 200 and a body of size 0. A minute later the agent reported that Daum was "100% dead right now". Having narrowed down the cause, the agent finally checked in the code that the key-fetching function was called. The launch screen called it.

The app sent requests with no valid key

At launch the app downloads the portal's key page, pulls a key out of the HTML, and stores the session cookies set on that response. The page had stopped doing that. It returned one line of JavaScript pointing the browser at a mobile address, with no HTTP 3xx status. OkHttp follows redirects that arrive as a status code plus a Location header; it does not run scripts inside HTML. The app received HTML with no key and no cookies.

When the key was missing, the app carried on. Since commit f11e6e2 on June 12, 2024, the code had held a hard-coded default key, and the app sent checks with it. Daum's server, given a stale key or no session cookie, does not return an error message. It returns 200 and nothing else. The session cookie expires after one day (86,400 seconds), so a key fixed in the code could never pass on its own: the check also needs a fresh cookie from the key page.

Which portal goes first is set by remote config (a Firebase Remote Config value changed without shipping an app update), and the default is Naver. Chat retries once on the other portal when a check fails. With Daum as primary, Chat silently switched to Naver and Classic showed an error toast on every check. When Naver failed and Chat fell back to Daum, the fallback failed too and the user saw an error.

Naver had the same shape. An expired key produced HTTP 200 with an error inside the JSON, the app treated it as a parse exception, and kept failing with the expired key. Commit e9cd771 fixed that the same day by clearing the key and fetching a new one.

Two February changes didn't surface the failure either

On February 26, 2026, two commits co-written with an AI coding agent touched this path. 68c458d replaced the exception with a single "pattern not found" log line and carried on with the existing key. The same day, 6da3f51 added the fallback that retries a failed check on the other portal.

Each change was reasonable, but neither raised a missing key as a failure. After 68c458d that spot became a one-log-line branch, and on September 13 the app went through that branch. With Daum as primary, 6da3f51's fallback covers Daum's failure with Naver's result. We don't know whether the page had already changed in February, or whether Daum was ever switched on as primary through remote config.

There was also no way to see a failure rate. A release-watch note from October 4 says the check failure rate could not be measured, because the success event carried no such value.

Fetching the key from the mobile page, reading an empty body as expiry

Commit 0b74357 (22:44 KST, September 13) stopped trying to follow the redirect and requests the mobile address the script points to. That response carries both the key and the session cookies, and, as the commit message notes, the existing key-extraction code worked on it unchanged.

The agent also proposed giving Classic the same Naver-to-Daum fallback that day; it was not added and still doesn't exist. Another dead path, a Classic failure branch that called Daum with a different hard-coded key, had already been removed in the Naver commit.

The same commit fixed highlighting as well. To tell requests apart, the app appended an ID string (a short tag per request) to the text it sent, and Daum treated that string as one more word and returned it inside the correction. Replaying 28 saved real-server responses, Daum had flagged 12 errors; the old code colored 6 of them and the new code colors all 12.

The next day a release-only bug blanked Daum's results again. That one is in 203 unit tests missed a release-only blank result: R8 and Gson field names.

Both fixes shipped in version 1.6.017 together with a font fix, described in Android showed some Hangul as blank gaps: NanumSquare's cmap claimed 11,172 syllables but drew only 2,479.

What to check in apps that rely on outside responses

If you keep an unofficial endpoint as a backup, check every day that it still works, separately from user-visible failures.

  1. For each outside API, define success by the body. An empty body, a missing required field or an error field is a failure even with status 200.

  2. If a key or token can't be found in the response that should carry it, fail right there. Don't keep a default key in the code.

  3. Fetch the key page once with an HTTP client that doesn't run scripts (the app's own OkHttp setup, or curl -L). If the body is a single line of script a few hundred bytes long, the app is getting the same thing.

    curl -sL -o body.html -w '%{http_code} %{size_download}\n' <key page URL>

  4. Give the fallback path its own events: the primary failure reason, the fallback attempt and the fallback result.

  5. Save real server responses to files and cross-check parsing and on-screen rendering against them.

Failures are now counted, fallback rescues are not

After a drop in checks could not be explained with the data we had, the October 10 release added a failure event, spell_check_fail. It records which portal failed, why, where the text came from and on which screen. The reason value key covers Naver's error JSON, Daum's 200-with-empty-body and a failed key fetch.

The rule is one event per failure the user actually saw. When Chat's fallback rescues a check, nothing is logged. The success event does record which portal answered, so a Naver failure rescued by Daum shows up as a Daum success. But the state in this incident, Daum dead while Naver works, would still be invisible with today's events.

The September 13 Naver and Daum fixes and the October analytics commit were also co-written with an AI coding agent, and the rule of not counting rescued failures came from that analytics commit.

From October 30 to November 6 there were 20 failures against 4,406 checks, 0.45% across both portals.

A CAPTCHA would break this fix too

The portal does not publish this as an API, so if it changes the page again the same thing can happen. In mid-October the on-device instrumented tests for two versions each had three failures, and the cause was the key page serving a CAPTCHA to the development machine's IP address. When that happens the app gets no key. The code is written so that a failure the user sees then is logged with reason=key, but we have not confirmed that it is actually recorded that way during a CAPTCHA.

Reading an empty body as an expired key rests on what we measured from this one server. A fresh key and cookie returned JSON; a stale key or a missing cookie returned an empty body. An empty body for any other reason will also send the app to fetch a new key. Naver, which reports errors in JSON, needed a different rule.

Next to check: split the failure event by portal, which we have not done yet, to get Daum's failure rate, add a separate event that counts fallback attempts, and decide whether Classic gets a fallback at all.
