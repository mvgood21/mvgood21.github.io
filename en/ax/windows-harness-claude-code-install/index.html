Install Claude Code on Windows and run it headless: one PowerShell line and a config folder for jobs

Claude Code installs on Windows with one PowerShell line and no administrator rights. Scheduled jobs should then get their own login in a config folder separate from the one you chat with.

By SugarMount · Working with agents · 10 min read · Last updated November 11, 2026

Windows harness series, part 2 of 5 · Previous: what the harness is and what it handles · Next: installing Docker Desktop

By the end of this part you can send Claude a question from a PowerShell window in one line and get an answer back. Installing needs no administrator rights. On 2026-11-11 we re-ran the version checks and the first question with these exact commands in a fresh PowerShell window on the PC that runs our harness.

The last step creates a second config folder used only by scheduled jobs. Scheduled jobs that shared the chat config folder once stopped when a chat /login overwrote their credentials, which is why this step lives in the install guide.

Opening PowerShell and pasting a command

PowerShell is the command window that ships with Windows. Click Start, type PowerShell, and pick Windows PowerShell from the results. Every command in this part runs without administrator rights, so don't choose "Run as administrator" (part 3 needs an administrator window once).

What you see: each input line starts with PS followed by the current folder, and the cursor blinks at the end. That line is where commands go. If the line doesn't start with PS, you are in Command Prompt (CMD), not PowerShell. The two accept different commands, and most of the errors below come from mixing them up.

To run a command from a grey box here, select the text, copy it with Ctrl+C, click the PowerShell window, paste with Ctrl+V and press Enter. Multi-line boxes can go in one line at a time. When a command finishes, the PS line comes back.

The official Claude Code setup page lists Windows 10 1809 or later or Windows 11, at least 4 GB of RAM, an x64 or ARM64 machine, and an internet connection.

Git for Windows is recommended; Python can wait for part 5

Git for Windows is recommended, not required. When Claude Code runs a command it uses one kind of shell window, and per the official docs it picks its Bash tool (running Git Bash) when Git for Windows is present and a PowerShell tool when it isn't. Our harness records its work as git commits, so this PC has it. Search for "Git for Windows", download the installer from its official page, and follow the on-screen steps.

Neither this part nor the minimal harness in part 4 needs Python. The real harness's GA4 and AdMob helper scripts are written in Python (part 5); if you only use the part 4 kit, you can skip it. If you use the Windows installer from python.org, tick "Add python.exe to PATH" near the bottom of its first screen.

After installing, open a fresh PowerShell window and check both. On 2026-11-11 this PC printed git version 2.45.2.windows.1 and Python 3.12.3. If you get anything other than a version number, the install didn't finish.

git --version
python --version

Use the PowerShell install command

The official docs give three ways to install. The PowerShell command goes into PowerShell, the CMD command into Command Prompt, and the three differ in how updates arrive.

MethodUpdates
PowerShell install command (recommended by the docs)Automatic, in the background
CMD install commandAutomatic, in the background
WinGetNot automatic; run winget upgrade Anthropic.ClaudeCode yourself

Install with the PowerShell command. Scheduled jobs run while nobody is watching, so automatic updates suit them better than WinGet, where someone has to remember to upgrade. Every other command in this guide also goes into PowerShell.

irm https://claude.ai/install.ps1 | iex

What you see: press Enter and the install runs. Wait for the PS line to come back, then look above it for a warning that starts with Setup notes:. If you're in Command Prompt instead, use the CMD version below. The exact errors you get from the wrong window are in the FAQ at the end.

curl -fsSL https://claude.ai/install.cmd -o install.cmd && install.cmd && del install.cmd

If you see Setup notes, add one folder to PATH

PATH is the list of folders Windows searches when you type a command name. The installer puts claude.exe in %USERPROFILE%\.local\bin (a .local\bin folder inside your user folder) but leaves PATH alone, and prints the Setup notes: warning instead. If you saw it, run these two lines in order. They append that folder to your own account's PATH.

$currentPath = [Environment]::GetEnvironmentVariable('PATH', 'User')
[Environment]::SetEnvironmentVariable('PATH', "$currentPath;$env:USERPROFILE\.local\bin", 'User')

PowerShell windows that are already open don't pick up the new PATH. Close PowerShell, open a new window, and check.

claude --version
claude doctor

The first prints the version; here it was 2.1.322 (Claude Code). claude doctor checks the installation and settings without opening a chat session, so run it first when the version prints but something still seems off.

The first login needs a paid plan

Claude Code requires a Pro, Max, Ultra, Team or Enterprise plan, or a Console account (the developer Console, with API credit paid in advance). The free Claude.ai plan doesn't include it, so with only a free account this series stops here.

Make a folder for the harness files first and start claude from inside it. $HOME is your user folder. The minimal harness in part 4 uses this same harness folder. mkdir prints a small table describing the new folder once; that's normal.

mkdir $HOME\harness
cd $HOME\harness
claude

On first run, Claude Code prompts you to log in and you authenticate in the browser. The docs don't walk through each screen in between, so we won't either: follow the prompts, and once the chat screen opens you can close the window. The login stays in your everyday config folder.

The first claude -p question, and Korean text that turned into ??

A headless run uses claude -p to hand Claude one task and exit, with no chat screen. Every scheduled job in our harness that needs Claude's judgment runs this way. You can put the question in quotes after the command, but the harness feeds it through standard input (the channel that receives the previous command's output via |). While building the harness we put the question after the flags once, and it landed after --allowedTools (the list of tools to approve automatically) and was read as more tool names.

$OutputEncoding = [System.Text.Encoding]::UTF8
echo '게임 앱 광고 지표 CPI를 한 문장으로 설명해 줘.' | claude -p --model haiku

The question in that example is Korean ("explain the game-ad metric CPI in one sentence"), because our apps are Korean. An English question works the same way.

The first line, $OutputEncoding, sets PowerShell to UTF-8 (the way computers store text, including Korean) when it hands text to another program. Windows PowerShell 5.1, the version built into Windows, defaults to ASCII here, so non-English characters arrive as question marks. On 2026-11-11, in a newly opened Windows PowerShell window, the Korean word for "game" arrived as ??; with the UTF-8 line first it arrived intact. If you will ever type anything other than plain English, always enter that line first. The double asterisks around the answer's first words are Markdown bold markers that Claude added, printed as is.

--model picks the model. The harness uses opus for the daily jobs that involve the most judgment, sonnet for fixed on-screen tasks such as posting, and haiku, the lightest, for self-checks, and it names a model in every job so a change of default can't shift its behaviour. haiku is enough for a first test. Afterwards, the line below shows the exit code (the number a program leaves when it ends); 0 means success. The runner in part 4 (the script that actually runs each scheduled job) uses that number to tell success from failure.

$LASTEXITCODE

Nobody is there to click "approve" in a headless run. Tools that need approval, such as editing files, are refused unless they're listed in --allowedTools. The question above uses no tools, so it finished without an allow list.

Scheduled jobs log in from their own config folder

Claude Code keeps its login, settings and personal instruction file in the .claude folder and .claude.json under your user folder. Set the environment variable CLAUDE_CONFIG_DIR to the absolute path of another folder and all of that moves there. Our harness gives scheduled jobs a folder of their own.

On 2026-09-10, before the harness moved to its current Windows setup (the move is described in Leaving WSL for native Windows: a checklist for moving a Claude Code dev environment), /login was used in a chat window to switch accounts. That overwrote the credentials the scheduled jobs shared from the same config folder; the jobs couldn't re-authenticate on their own and stopped.

On 2026-11-11, preparing this series, we ran the part 4 kit's hello job with its optional configDir field left empty, and the answer ended with a "done / result / what's left for you" summary the prompt never asked for. The chat setup's personal instruction file (the global CLAUDE.md) in the shared config folder asks for exactly that summary after every task. Separating the folder hadn't kept it out of the real harness either: the instruction file in its dedicated folder carries a copy of the same line, and a game social-posting job's answer on 2026-11-10 ended with the same summary. Scheduled jobs follow the instructions in their dedicated folder, so those instructions need to be kept separately and written for scheduled work (part 4).

Give scheduled jobs their own config folder from day one, and don't copy your chat instruction file into it. The main reason for the separate folder is still a login overwrite like the one on 2026-09-10. To create it, set the variable for the current window only and start claude. If you get the same login prompts as in the first-login step, follow them; if the chat screen opens straight away, type /login.

$env:CLAUDE_CONFIG_DIR = "$env:USERPROFILE\.claude-harness"
claude

A value set with $env: disappears when the window closes, so your everyday Claude keeps using its usual folder. Scheduled jobs reach the new folder through the configDir field of the job file in part 4. Some of what you've connected for chat doesn't carry over to the dedicated folder (part 5 covers this).

What to confirm before part 3

You're done with this part when a new PowerShell window prints a version for claude --version, the first headless question returns an answer with exit code 0, and the second login in the job folder has gone through. If you installed with WinGet, decide when you'll run the upgrade command. Jobs registered the part 4 way only run while you're logged on to Windows, so this setup doesn't fit a PC you can't leave on and logged in.

Part 3, installing Docker Desktop, prepares for a server that collects data every day. If you just want the minimal harness running first, skip to part 4 and register it with Task Scheduler.

FAQ

Why do I get "'irm' is not recognized"?

You pasted the PowerShell install command into Command Prompt. Open PowerShell from Start and paste it there, or use the CMD curl command in that window.

What does "The token '&&' is not a valid statement separator" mean?

The reverse: the CMD install command went into PowerShell. In PowerShell, use irm https://claude.ai/install.ps1 | iex.

The install finished but Windows can't find claude.

%USERPROFILE%\.local\bin isn't on your PATH. Run the two lines in the PATH section, open a new window, and try claude --version again.

Can I use Claude Code on the free plan?

No. You need a Pro, Max, Ultra, Team or Enterprise plan, or a Console account with prepaid API credit.
