Nine auto-compactions in a 13-day Claude Code session, and the memory index line that came back after each one

No compaction summary said why the ad budget was 2,000 won a day, and the likeliest source of the October 17 mistake was a stale "2,000 won each" line in the memory index, reloaded after every compaction.

By SugarMount · Working with agents · 12 min read · Last updated November 3, 2026

A marketing session ran for 13 days and was auto-compacted nine times; each time the agent carried on from one summary of roughly 10,000 to 14,000 characters, two to five recently read files, and the memory index (MEMORY.md). The session was a Claude Code run handling ads and promotion for two of our Android games from October 9 to October 21, 2026. All nine summaries listed the user's messages; none gave the reason the operator had set the budget to 2,000 won instead of the runbook's 25,000. The index was reloaded ten times, at the start and after each compaction, and its ad lines said "2,000 won each" until the night of October 17.

Sources: five Claude Code session logs (jsonl), 14 memory files and their index, the ad runbook and the ad plan document. Counts were redone from the logs on November 2, 2026. Times are Korea Standard Time. Ad account and campaign identifiers are left out.

Nine auto-compactions, one summary page each

The session log has nine messages that begin "This session is being continued from a previous conversation", and nine compact_boundary records. All nine have trigger "auto"; nobody typed /compact. Each boundary record stores token counts before and after, and what survived was 2.6% to 8.2% of what was there before. Three of the nine happened on October 17, a day the agent spent in Chrome moving between the Play store listing and the Google Ads console.

Every summary had the same sections, including "All user messages", "Pending Tasks", "Current Work" and "Optional Next Step". Ads first came up on October 11; of the eight summaries after that, five mention a budget amount or whether a campaign was on or off. The word "runbook" appears in none of the nine, and neither does the reason the campaigns were split by language (Korean creatives shown to non-Korean speakers waste impressions).

Two other things came back right after each compaction. Recently read files were re-attached, two to five each time. The ad memory file was among them only after compactions 3 and 5. The memory index came back too, as instructions on the next user turn: ten times in all, once at the start and once after each compaction. From October 19 on, the global CLAUDE.md came back with it four times.

For comparison we counted two more sessions: an app development session that ran six days (September 20 to 25) and a game development session (September 30 to October 9). In both, the user ran /compact by hand five times, and each produced one continuation. Token counts right before those manual compactions ranged from 253,498 to 832,659, the summaries ran 9,317 to 20,634 characters, and all ten had the same four sections. None of the ten /compact commands had instructions after it.

To count the same things in your own sessions, run these three lines on a session log. Logs live under ~/.claude/projects/<working folder name>/, one jsonl per session.

grep -c '"subtype":"compact_boundary"' <session>.jsonl   # compactions
grep -c '"isCompactSummary":true' <session>.jsonl        # continuation summaries
grep -c '"type":"AutoMem"' <session>.jsonl               # times the memory index was loaded

This session gives 9, 9 and 10.

The 25,000 won budget came from a session with no compaction

When this note went into our backlog, the claim was "after a summary the agent fell back to the runbook values and got told off." The logs put that event on the night of October 8. At 21:56 the operator opened two Claude Code sessions at once, each driving Chrome to build a Google Ads app campaign: one for Arrow Knots, one for Block Turn. Neither session was ever compacted.

  • 21:57 The operator told the Arrow Knots session: 2,000 won a day, no target cost per install (CPI), all countries. In the same minute the Block Turn session read the runbook its brief pointed to.
  • 22:07 The Block Turn session asked whether to keep the runbook's target CPI of 1,400 won and daily budget of 25,000 won, since those were set for the US.
  • 22:11 The operator replied "analyze it properly and go ahead", with nothing about budget.
  • 22:14 The agent typed 25000 into the daily budget, and 700 won as the target CPI (not the runbook's 1,400 either).
  • 22:22 The operator repeated the instruction, sharply: 2,000 won a day, no CPI, all countries.
  • 22:23 The agent wrote a memory file.

The agent's mistake was at 22:14: it asked about the budget, got "go ahead", and read that as approval of the runbook value. The 2,000 won instruction had gone to the other session 17 minutes earlier, at 21:57, and two sessions do not share context. One level further back, both the runbook and the ad plan document said 25,000 won. The runbook was a plan to measure US install costs, spending a 100,000 won cap over four days, and the plan the game development session wrote at 19:19 that day said "25,000 won a day for 14 days". The operator's new decision was in no file at all.

That game development session's last manual compaction, at 00:47 on October 9, produced a summary that still said "ad plan: KR, 25,000 won/day", 2 hours 25 minutes after the Block Turn session had been corrected to 2,000 won at 22:22.

October 17: Arrow Knots KR called "running" while paused

At 08:08 on October 17 the marketing session's agent read the Ads console: Block Turn KR running at 4,000 won a day, Arrow Knots KR at 2,000 won, both English campaigns paused. At 08:41 it advised the operator to pause Arrow Knots KR or move its budget to Block Turn KR.

At 09:12 the agent edited that very ad memory file, adding only a note about account linking. The line from October 11, "all four ad groups run until Nov 2", stayed. What was still right in that file was the decision not to use the runbook values; its amounts (2,000 won each) and its status no longer matched the console that morning. The summary from compaction 3 at 10:07 said "all 4 game campaigns paused (by the user or the other session)"; the one from compaction 4 at 17:49 had no ad status at all.

None of the five files re-attached after compaction 4 was an ad memory file. At 19:24, on the next user turn, the memory index was reloaded, and its two ad lines read "English (Southeast Asia) / Korean, 2 campaigns, 2,000 won/day each, no tCPI (overrides the runbook)" and "2 campaigns per language (KR / SEA EN), 2,000 won each, no tCPI". The index had said the same since the session started.

Fourteen minutes later, at 19:38, the agent wrote "creative swap on a running campaign" for Arrow Knots KR into the posting log and the backlog, and at 20:31 asked the operator whether to add the new Arrow Knots creatives "to the KR campaign that is running now". The operator said yes. That made three places calling the campaign running. Only after opening the campaign, at 20:39, did the agent report that it had been wrong and the campaign was paused; in the same report it noted that Block Turn KR was running at 4,000 won while its own notes said 2,000. At 21:08 the operator set the record straight: only Block Turn KR was running, at 4,000 won, and Arrow Knots was off. The agent said it had fixed "my note that still said 2,000 won each", and it changed three places: the Block Turn memory file, the Arrow Knots memory file, and the two ad lines in the index. The Block Turn file got a dated status line:

Status as of 2026-10-17 (confirmed by the user): of the four campaigns, only Block Turn KR runs, at 4,000 won/day; the rest are paused. Do not resume a paused campaign without the user's decision.

The summary from compaction 5 at 22:12 included the status table and a note that the agent had wrongly said "running", and the index reloaded after it read "as of 10/17 only Block Turn KR runs at 4,000 won, the other 3 paused".

The log does not say what the agent based "running" on. It may have remembered seeing Arrow Knots KR at 2,000 won in the console at 08:08. But that observation had become "all 4 paused" in summary 3 and was gone from summary 4, while the index came back 14 minutes before the mistake with the same "2,000 won each" wording the agent later used about its own notes. We take the index as the likelier source.

13 of 14 memory files end with Why and How to apply

This memory is the folder Claude Code keeps per working folder, ~/.claude/projects/<working folder name>/memory/, with MEMORY.md as a one-line-per-file index. As of November 2 the home folder's memory holds 14 files and a 14-line index. Thirteen end with Why: and How to apply:; the one without is a reference note about a plugin account. The ad memory was first written at 22:23 on October 8 and edited five more times through October 18. Its gist, minus identifiers and the operator's tone:

Block Turn install campaigns: one per language, 2,000 won/day each, no target CPI
Do not use the runbook §2 values "US, tCPI 1,400 won, 25,000 won/day".
Why: the user gave this instruction more than once and the runbook was followed instead.
How to apply: when setting or changing this campaign, the user's instruction beats the runbook.

No summary held the reason for overriding the runbook, yet in 13 days the marketing session never tried to set 25,000 won or a 1,400 won target CPI. It had read this file on October 11 while drafting an ad plan, and the index line's "(overrides the runbook)" came back at the start and after compactions 1 to 4. The October 17 fix rewrote that line as a status line, so the last five reloads carried no such phrase.

Write the reason for a decision into a memory file the moment it is made; do not count on a summary to carry it. And for anything a person can change outside the conversation, like an ads console, trust neither the summary nor the memory.

The runbook, /compact instructions, CLAUDE.md, the index

One option is to change the runbook to 2,000 won. But its §2 numbers belong to a US cost experiment (100,000 won over four days), while what actually ran was a different experiment split by language, English in Southeast Asia and Korean in Korea. The §2 values were never changed, and the logs do not say why. The memory file says not to use them.

Picking compaction points by hand did not stop a decision from another session going missing. The two comparison sessions compacted manually ten times, and the game development session's manual summary still carried the 25,000 won plan. A decision made in another session cannot reach a summary unless it enters this session as a message or a file. Relying on the summary's list of user messages fails for the same reason: the 2,000 won instruction was a message in the neighboring session, and the operator pausing a campaign in the console was not a message at all. Adding instructions after /compact about what to keep is something we have not tried; all ten manual compactions here ran without any.

The global CLAUDE.md was also reloaded with the index after compactions 6 to 9 (from October 19 on). Since it comes back the same way, we expect status written there to go stale the same way. For the same-session mistake on October 17, the alternative the logs support is taking status out of the index. What came back just before the mistake was an index line that mixed the decision with amounts, while the dated status line lived only in the file body. We recommend index lines that hold the decision and the file name, with amounts and on/off status kept, dated, in the file body.

A different working folder means a different memory

Claude Code kept memory per working folder. Sessions opened in the game repository's folder wrote to a separate memory folder, and its ad status file said "on 10-17 the user paused everything; Block Turn KR resumed the same day at 4,000 won".

If a session finishes without compaction and nothing else runs alongside it, you will rarely need any of this. A status line with a date and "confirmed by the user" is only right until the next change.

What to do when a decision departs from the docs

  1. When the operator gives a value that differs from a document, create one memory file on the spot: the decision, the document and value it overrides ("do not use"), Why:, then How to apply:.
  2. Put only that file's decision in the MEMORY.md index, as one line. Leave amounts and on/off status out of it.
  3. Keep current status, such as which campaigns are on, on a separate line in the file body with a date and "confirmed by the user", plus what must not change ("do not resume a paused campaign without the user").
  4. Put this in How to apply: "before any console action that spends money, read the current console values; if they differ from this file's status line, fix the file first." When Arrow Knots KR was turned back on on October 18, the memory and index were updated that same evening.

The runbook still says 25,000 won, and the index still holds status

On November 2 the runbook's §2 and the ad plan document still say 25,000 won. The index's Block Turn line on the same day still carries status ("as of 10/18 Block Turn KR 4,000 won and Arrow Knots KR 2,000 won running"), so by step 2 that line is the first one to cut back to the decision. The exact time Arrow Knots KR was paused is not in the session logs, so we could not measure it.

FAQ

What is left after Claude Code auto-compacts a session?

In this session, one summary of about 10,000 to 14,000 characters plus two to five recently read files. All nine summaries had sections for user messages, pending tasks, current work and next step, and the tokens after compaction were 2.6% to 8.2% of those before.

Does Claude Code memory survive compaction?

The index did. In this session MEMORY.md was loaded ten times, at the start and after each of the nine compactions. Memory file bodies came back only after compactions 3 and 5, as recently read files.

Does running /compact by hand give a more accurate summary?

These logs do not show that. Ten manual compactions without instructions produced summaries with the same four sections, and the game development session's summary still carried a 25,000 won plan that another session had already replaced.
