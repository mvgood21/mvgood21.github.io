Silently skipped tests keep CI green: three crypto cross-checks and an integration test that went stale for six days

Make a required test fail in CI instead of skipping. Our three crypto cross-check tests skipped when a Python module was missing, and the CI job had no step to install it.

By SugarMount · Testing and release · 8 min read · Last updated November 8, 2026

The skip count from flutter test was 13 on September 11, 13 and 15, 2026. One of those 13 was a relay integration test that had been broken for six days. Outside the 13 sat three crypto cross-check tests that would join them if one Python module was missing. On the night of September 15 we added an install-and-check step to CI, so in CI those three can no longer drop out unnoticed for lack of the module.

Sources: git history of our Flutter peer-to-peer chat app (commits b559ba0, 32ce058, cab4bed, 7048e46), its CI workflow, the test files and the September 15 E2E report. Skip counts were recounted from the tree at commit 7048e46; the tests were not rerun. Checked November 3, 2026.

Three crypto tests outside the 13 skips

Recounting the skip: declarations at commit 7048e46 gives 13 tests that drop out when an environment variable or server is missing: 9 soak tests (BOS_SOAK), 2 signaling server integration tests, 1 DB benchmark and 1 live two-process E2E. The September 13 record of 3,160 passed / 13 skipped is covered in What "100% E2E pass" really meant; the September 15 release cross-check read 3,186 passed / 13 skipped.

The three crypto tests run when they find the Python cryptography package and skip when they don't. On September 15 the development machine had it (version 50.0.1) and all three ran; the skip count of 13 recorded since September 11 matches the 13 environment-gated tests, so nothing suggests these three were among the skips.

The CI Flutter job installed only SQLite before testing

The cross-check recomputes the app's X25519, HKDF, AES-256-GCM and frame layout with Python cryptography and compares the results. According to the file's header comment, it is the only test that can catch both sides being wrong in the same way, and the same comment settles what happens without the module:

// External-process dependency: this test SKIPS (it does not fail) when
// `python3 -c "import cryptography"` does not succeed, so it is safe on
// machines and CI images without the module.

Until September 15 the CI Flutter job installed nothing but SQLite before running flutter test. From there to a green check:

  1. The CI job looks only at the exit code of flutter test.
  2. That exit code ignores skips; the count appears only as ~N on the result line.
  3. The test skipped without the module, and CI had no step that installed or checked it.
  4. Nothing compared the skip count against a baseline, so 13 turning into 16 had nowhere to raise an alarm.

"Safe" in a comment, and a browser guard the same day

That comment and the test arrived in commit b559ba0 at 10:45 on September 11, co-authored by Claude. At 14:32, commit 8f5a0a5, also co-authored by Claude, fixed message eviction guards that sat behind an environment variable CI never set, so switching eviction off left 659 tests green (that commit's story is in 3,066 green tests hid a line that breaks opening the database). 8f5a0a5 also gave the CI web step a guard that fails loudly when no browser exists. The same rule never reached the crypto test written four hours earlier.

On September 15 the operator asked whether the E2E tests were done. Checking showed that since the UI redesign of September 13 and 14, only the in-process E2E tests had been running; everything else was skipping behind environment gates. That night the gates were opened one at a time, and at 22:12 commit 7048e46 added this step to CI:

- name: Ensure python cryptography exists (the crypto cross-check must never silently skip)
  run: |
    python3 -m pip install --quiet --upgrade cryptography || true
    python3 -c 'import cryptography; print("cryptography", cryptography.__version__)' || {
      echo "::error::(message: cryptography is missing, so the cross-check would skip and CI would pass)"
      exit 1
    }

While skipped, the relay test fell behind two rules

The relay integration test, one of the 13, had not been touched since September 6. On September 9 two rules landed in production: a fingerprint gate that refuses to send when no approval hook is wired (df1dddc, 684ff8c), and a room binding that drops frames whose roomId is not the session's room (684ff8c, 6c99027). When the test finally ran against a live signaling server on September 15, it hit both. sendMessage without the hook was refused with "Peer identity is not verified yet", and a message sent to the literal 'room-relay' was dropped with no error.

Commit 32ce058 at 21:13 put it as "the product is right and the test is stale" (translated from Korean). The fix wired an approval hook into the test and read the room the handshake had bound through debugSessionRoomId, rather than copying the naming rule into the test where the next rule change would break it again. With the server running, all 13 tests in test/integration passed.

The device smoke test (emulator, API 35) stalled on the settings screen the same night. tester.pageBack() looks for a back button by the English tooltip "Back", and since the app was pinned to Korean that tooltip reads "뒤로" (Korean for "back"). Finding the widget with find.byType(BackButton) made it pass 2 of 2 (cab4bed).

Why a skip-count check or "always fail" falls short

The judgment below is our own analysis while writing this note; the repository has no record of it. Failing the build when the skip count differs from 13 would catch 13 becoming 16, but not a test that is always skipped going stale, which is what the relay test did (the count was 13 on all three recorded dates). Making the test fail whenever the module is missing would turn the whole suite red on any development machine without it, the case the original comment chose skipping to avoid. What the repository added was a CI step guard, and the commit says it follows the same pattern as the browser guard on the web job.

Starting the signaling server inside CI to run the integration tests was also possible. It wasn't done, and no reason is recorded. Instead, the commands for the three kinds CI does not run (live two-process, signaling integration, device smoke) went into section 4.1.1 of the deployment doc, to be run by a person before each release.

GitHub Actions sets CI=true on every run. If the test stops skipping when it sees that value, a missing prerequisite turns the run red on the spot, and development machines behave as before. We have not run this in the repository; it is a proposal.

final onCi = Platform.environment['CI'] == 'true';

test('bidirectional cross-check against python cryptography', () async {
  // ...
}, skip: onCi ? false : skipReason);

The branch uses dart:io, so it cannot go into a test that runs in a browser. This repository's web step runs only test/web/ in the browser, which does not include the crypto file.

One skip path the guard misses, and no CI run on record

The guard in 7048e46 checks only that python3 runs and the package imports. The test has three skip paths, and one of them, failing to find tool/crypto_vectors/cross_check.py within the working directory or the four folders above it, sits outside the guard. CI runs from the repository root, so the script is found today, but nothing pins that down.

The repository keeps no results from the CI Flutter job, and the deployment doc says the CI web step could not be run locally, so a green CI run has not been demonstrated yet. So we could not confirm that these three tests were ever actually skipped in CI. Since 7048e46, if the module still cannot be imported after the install attempt, the CI job stops with exit 1.

Four steps to find required skips and make them fail

  1. Find them with grep -rn "skip:" test/ and grep -rn "markTestSkipped" test/ (why the skip count belongs in every report is covered in What "100% E2E pass" really meant). Line counts are not skip counts: this app's 17 skip: lines become 13 only after dropping the 3 conditional crypto lines, 1 line that skips only on the web and runs on the VM and 1 helper parameter, and counting 1 relay group line as 2 tests. The 6 markTestSkipped calls are decided at run time.
  2. Mark each one required or optional. Required means no other test would catch what it catches, such as a cross-check against an independent implementation or a real server path.
  3. For required tests, add a CI step that installs and verifies the prerequisite, or stop skipping when CI=true as in the snippet above. With this app's guard, if the install fails and the module is absent, the check command turns CI red.
  4. Put tests CI cannot run on a pre-release checklist with the command and the date of the last run. When a long-skipped test fails on its first run back, check whether the test went stale before blaming the product; all 3 failures in this app were stale tests.

Still open: the test's own skip condition and two-device E2E

The crypto cross-check file has not changed since September 11, so it still skips without the module. Once a CI=true branch is added, a GitHub Actions run should show the same skip count as the development machine. There is also no automated E2E across two devices yet.

FAQ

Does a skipped test make flutter test fail in CI?

A skip never fails the run: the exit code stays 0 and the count shows up only as ~N on the result line. This app's own records list a run with 13 skipped as 0 failed.

How do I fail a GitHub Actions step when a Python module is missing?

Install it, then run python3 -c 'import module'; if that fails, print an ::error:: line and exit 1. The install command can carry || true, but the check must not.
