Claude Code scheduled runs: state left behind

One Claude Code scheduled run exited 0 but left two uncommitted files that blocked the same app's next runs, so the next run now moves leftovers to a rescue branch and carries on.

By Stephen · Working with agents · 10 min read · Last updated November 21, 2026

A Claude Code run on our unattended harness finished with exit code 0, and the same app's next runs then refused to start. The run had ended with two files half edited, and from the next evening a second, harness-wide cause landed on top, so that app did not run for three days. A week later, over about a day, four social posting runs posted nothing, and those runs also exited 0.

Both runs exited cleanly; what stopped the next ones was the state they left behind: the git work tree in the first case, the browser connection in the second.

The subagent was stopped 10 minutes after the commit

On November 3 at 09:05 KST, the morning job (the "daily") for our Korean spelling app started. It runs as claude -p, the print mode that takes one prompt, answers, and exits without a chat window. At 09:11 the agent committed the day's checks as 890de43 and handed the production of two short videos to a subagent running in the background. Its last message, in Korean, said: commit pushed; when the video agent finishes, it would continue with an independent review, the queue, and the Notion report.

The next line in the log was printed by Claude Code itself.

In the version we ran then, if background tasks were still running 10 minutes after the last turn, -p stopped them and exited. The notice also named the environment variable that makes it wait to the end, CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0. The run was logged as a normal exit 10 minutes and 7 seconds after the commit. The subagent had been editing the video generator script and a production log CSV, and both files stayed uncommitted in the work tree.

One app stopped 30 hours before the rest

Before each run, the harness checks the work tree in a step called prepare. Uncommitted changes make it refuse with DirtyWorktree and exit 3. The README at the time said these changes are not cleaned up automatically. The spelling app's 14:00 social run on November 3 was the first one refused, and four runs in total failed to start for this reason alone.

From the evening of November 4 a second cause stacked on top: uncommitted edits in the harness's own code stopped every app's jobs for about 38 hours. That stall is covered in Schedule Claude Code with Windows Task Scheduler. The alerts on the mornings of November 5 and 6 said the same thing for all three apps, "exit 3, prepare failed", which reads like one big outage.

The game and utilities apps ran normally until their evening runs on November 4, while the spelling app had been stuck since 14:00 the day before, 30 hours earlier, for a different reason. Committing the harness code would not have freed it; the two files would still have been in its work tree. The harness README at the time said that after a DirtyWorktree exit 3, "that repo's jobs keep stopping the next day too", and that a person has to clean up. The November 4 alert did list only the spelling app as failing, but it gave no reason.

The repository shows the result: one commit on November 3, none on the 4th or 5th, and no videos produced or posted in between.

The next run guessed wrong too

On the morning of November 6, the two leftover changes were committed to a separate branch (004f642), and less than a minute later the harness runner got a setting that waits for subagents to finish (1ac160a). A few minutes after that the scheduler re-ran the spelling app's daily, and it finished normally. The rescue commit came from a chat session, but the records do not say which conversation it was or who reset that day's run state before the re-run.

The restarted run described the gap in its notes: the leftover changes "appear to have been reverted before the 11-06 start; only the q005 and q006 mp4 files remain". In fact they had been moved to a branch, not reverted, and the work tree had gone back to the original commit. The run's own commit, e795981, sits on top of the November 3 commit, not the rescue commit. All the November 6 run could see was the work tree and the app's own notes, and nothing in them mentioned the rescue branch.

Four social runs saw only a different browser

The second incident began on the evening of November 11. Social runs post to TikTok, Instagram and YouTube by driving a dedicated harness Chrome through the Claude in Chrome extension. That evening's first run posted normally, but from the next run until the following evening, four social runs across the three apps reported "only Browser 1 was connected" and posted nothing. In the connected Chrome, TikTok showed a login screen. It was not the harness browser.

The rule at the time said to look for the harness browser's device ID (the unique value the connection list shows for each browser) and, if it was missing, to skip rather than pick another. The social runs followed it and left Browser 1 alone. But the rule only covered the error the tool raises when several browsers are connected and none is selected; with exactly one browser connected, the tool went straight to it without asking (harness record). On the night of November 12 an indexing job took that path and opened Search Console in a Chrome signed in to a different account. The rule and the reports called the harness browser "Browser 2", but that label follows connection order, and the morning after reconnection the harness Chrome was "Browser 1".

The rule changed that night (e9fc042). Before the first Chrome step a job lists the connected browsers, looks only at the device ID, and calls no Chrome tool at all if that ID is missing. A run a few minutes before the change noted that the harness browser was connected again. Nobody recorded who reconnected it or how.

The game and utilities runs wrote each failed channel into their posting queue table, for example "2026-11-12 20 Instagram failed: Chrome not connected", and committed it. The next runs filled those cells first: utilities posted its two missing channels on November 13, and the game had posted all three planned channels by November 14. The spelling app's run did not touch its queue and made no commit, so the next day's daily noted "no posting record or commit for the 11-12 14:00 social run" and held off judging.

If a scheduled run uses subagents, do not rely on a prompt rule alone. Force the wait in the runner's settings and the cleanup in the next run's prepare step.

Checks for the end and start of a run

The harness now moves a leftover work tree to a rescue branch in the next run's prepare step, checks the browser before the first Chrome step, and writes unfinished work where the next run reads it. The steps below add an end-of-run check on top (step 2 is not in this harness yet):

  1. Set CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0 in the runner's environment and give every job a timeout. A Background tasks still running line in the log means the run left work unfinished.

  2. Count a run as complete only when git status --porcelain is empty and nothing is left unpushed. Otherwise record the leftover file list as the failure reason.

  3. In the next run's prepare step, do not delete a dirty tree. Commit it to a branch such as harness-rescue/<time>-<job>, reset to the base commit, then continue, and put the file list and branch name in the alert.

  4. For jobs that need a browser, call the Claude in Chrome tool list_connected_browsers before the first Chrome step and pick with select_browser only when the expected device ID is there. If it is not, call no Chrome tool. Ignore display names.

  5. Write unfinished work where the next run reads it, as "date hour channel failed: reason", and commit it. The next run starts from those cells.

If you call claude -p straight from Task Scheduler without a harness, steps 1 to 3 fit around the call like this. We ran the rescue and completion parts in a scratch repository on November 21 with PowerShell 5.1: two leftover files moved to the rescue branch and left the tree clean, and an edited file or an unpushed commit made the script exit 4.

$env:CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS = '0'

# Before the run: move leftovers to a rescue branch instead of deleting them
if (git status --porcelain) {
  $b = "harness-rescue/$(Get-Date -Format yyyyMMdd-HHmm)-daily"
  git switch -q --create $b
  git add -A
  git commit -q -m "rescue: leftovers from the previous run"
  git switch -q -
}

claude -p "..."

# After the run: done only if the tree is clean and nothing is unpushed
if ((git status --porcelain) -or (git log '@{u}..' --oneline)) { exit 4 }

git add -A also picks up new untracked files, so put large generated output such as videos in .gitignore first. On a branch with no upstream the last line's unpushed check is skipped, so link it with git push -u first. Writing a verdict line at the end of each report is covered in 17 days of a Claude Code harness: how to start.

A dropped browser still needs a person to reconnect it

Waiting for subagents makes runs longer, and a run that hits its timeout is killed by the runner, which can leave the same kind of leftovers. The next prepare step moves them to a rescue branch; if that fails (a commit hook, say), the job stops as before. Rescue branches pile up and a person has to delete them.

Automatic rescue assumes leftovers belong to a dead earlier run. If a person edits in the same work tree the scheduled jobs use, those edits get moved to a rescue branch too, so keep a separate work tree for operations. This harness runs from its own copies, apart from the trees people edit in.

The device ID check stops a job from using the wrong browser; it does not reconnect the right one. On November 12 several alerts asked a person to check the Chrome extension connection, and the browser came back only that night. Runs still exit 0, too: the daily status boards for November 11 and 12 reported "0 failed or missed" and counted these runs as partial failures. Next to check: why the connection dropped, and whether the 10-minute default wait is the same in later Claude Code versions.
