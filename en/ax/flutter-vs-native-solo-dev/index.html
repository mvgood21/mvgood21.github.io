Flutter vs native solo dev: one studio, two picks

The stack followed where each app does its work and how many platforms reuse the same screens; the family app's Flutter choice was accepted only as a two-week spike with exit rules.

By SugarMount · Retrospectives and numbers · 9 min read · Last updated November 14, 2026

In September 2026, SugarMount decided to build its Android utility portfolio in Kotlin, and 15 days later to build a family scheduling app in Flutter. Both decisions were written down with their reasons, so it is possible to see what split them.

The split came down to whether an app's work is concentrated in platform features such as video transcoding, widgets and special permissions or in screens and domain logic, and to how many platforms will run the same screens. An AI agent's research for the family app also produced a person-day comparison; a second agent flagged the same day that its premise and its math disagreed, and recomputing shows the "about the same" verdict rested on an assumption the document never stated.

The utility apps went Kotlin because of platform features

The utility repository's first architecture decision record (ADR, a short file explaining why a choice was made), ADR-0001, was accepted by the operator the day the repository was created. It chose Kotlin, Jetpack Compose and Material 3 for the portfolio (19 apps at the time, trimmed to 14 the next day), one module per app in a single repository, and left iOS undecided.

The first reason was where the cost lives. These apps do their real work in the platform layer: video transcoding with Media3 Transformer, MediaStore, home screen widgets, special permissions. A cross-platform UI layer would save little, because those engines would still be written once per platform. The second reason was iOS. App Store Review Guideline 4.3(a) forbids shipping the same app under multiple bundle IDs, and a family of near-identical utility apps is a Play Store strategy. Setting a ringtone or keeping the screen on while another app runs cannot be done on iOS at all. The record also cites an earlier attempt to port the studio's Korean spell-checker app to Flutter: the UI reached 99.8% and the port stalled at ads, billing and MP4 encoding, never shipping.

iOS was not ruled out for good. Some shared modules avoid importing Android packages so the top one or two apps could later move to Kotlin Multiplatform (sharing Kotlin code across platforms). The decision is to be revisited once five apps are live and there is revenue data, an Apple developer account and a Mac build path.

The family app needed the same screens three times

The family app was planned for Android and a desktop web app first, iOS later. Family members carry different phones, so the same calendar and photo screens have to exist on all three. The agent's stack research compared four options.

OptionVerdictDeciding reason
React Native / ExpoRejectedNot on the official platform list for AdMob (Google's mobile ads); device attestation for Firebase App Check (the app integrity check) must be hand-built; no prior experience
FlutterChosen, conditional on spikesAI, ads and billing SDKs all official; screens written once; about 33,700 lines of prior Dart experience
Kotlin Android + Next.js webFallbackBest Android quality and code reuse, but every feature built twice, three times with iOS
Kotlin / Compose MultiplatformRejectedNo official Firebase SDK; web target still in Beta

Both rejected options hit a gap in official SDK support: AdMob for React Native, Firebase for Kotlin/Compose Multiplatform.

The research also named what Flutter gave up: the utility repository's Kotlin modules for ads, billing, WebP encoding and share handling could not be reused as is, only ported piece by piece through Kotlin platform channels (the bridge Flutter code uses to call native Android code).

The AI estimate's premise and its math disagreed

Section 4 of the research estimated solo maintenance cost in person-days for V0, the first release: 12 Android screens and 6 web screens. Its premise priced one screen at 1.5 person-days on both Android and web, but the table priced only Flutter's web screens at half that, 0.75 days. That is how the totals came out at 27.5 versus 28, "about the same."

A separate agent reviewed the document adversarially that day. Row A7 of its findings called this an "internal inconsistency." Below are part of the table and the A7 row, rendered in English from the Korean original.

The reviewer did not say 0.75 was wrong. If code sharing makes Flutter web screens cheaper, it said, write that into the premise. Apply the stated 1.5 days to Flutter's web screens as well and Flutter's V0 total becomes 32 person-days, so for Android and web alone the Kotlin route comes out cheaper. With estimates that have no data behind them, a gap this small should not pick the stack.

The review section opens with "the body was not edited," and the decision record written the same day, ADR-07, repeated those totals. ADR-07 accepted the other point (A6, iOS cost underestimated) and revised the with-iOS figure to roughly 36 to 38 versus roughly 57 person-days (estimates). The reasons the decision record left are the iOS gap, the official SDKs and the operator's Flutter experience.

The research's opening argument got corrected too. Using planning-stage subscription assumptions, it claimed the condition for launching on iOS would be "met almost immediately," and used that to argue for Flutter. Review finding A4 called that an overstatement. The operator's own rule was to ship iOS only after income "comfortably" exceeds Apple's fee, and that fee alone would take more than half of the operator's monthly fixed-cost cap of 20,000 won (about $14). The decision records moved iOS behind a separate gate whose thresholds the operator sets.

The decision was a two-week spike with exit rules

ADR-07's status column reads "recommended (presumed accepted)," and the same file defines that as a recommendation the operator did not object to. Flutter was not locked in; it was adopted on condition that six risky paths be checked within two weeks. The research wrote the condition and each spike's (a short build to test one risk) pass bar and fallback in advance; ADR-07 carried over the spike list and the exit rule.

SpikeWhat it had to proveIf it failed
S1Receiving shared files: app not running, signed out, many images, PDFNative Kotlin channel; if still failing, Kotlin + web
S2A 1080×2400 screenshot to a readable 20 KB WebP in under 1 sDifferent web encoder, shrink on device
S3AI extraction call with App Check enforcedKotlin + web
S4AdMob Next-Gen (the newer version of Google's ads SDK) banner and consent flow in an R8 build (the tool that shrinks and renames code in Android release builds), plus a monkey testPort the existing Kotlin ad module
S5Local reminders across reboot, Doze, denied exact-alarm permissionKotlin channel
S6Flutter web first load, drag-and-drop upload, KakaoTalk in-app browserSplit only the web to Next.js

The exit rule is also stated as a count: if two or more of S1, S3 and S4 cannot be solved in Flutter, switch to Kotlin Android plus a separate web app; if only S6 fails, split off just the web.

The Next-Gen ads SDK hit the same R8 crash as 16 days earlier

The first spike build ran on October 8 as an R8 release build on an API 35 emulator. S1 passed: shares arrived at the review screen in all four cases. That share handling was written as a Kotlin platform channel, without a Flutter plugin.

S2 passed only for photos. All 10 synthetic photos fit under 20,480 bytes, but four of five dense synthetic school notices stayed slightly over target even at 800 px and quality 20. This is the device screen from that run.

S2 was not part of the exit rule, so it did not affect the stack verdict. The agent listed three options and recommended allowing documents alone up to a hard cap of 24,576 bytes, but because that changes a product requirement, it left the call to the operator.

S4 was only half checked that day. The installed Flutter 3.35.1 could only use the ad plugin's Legacy path (the older version of the SDK), which survived two 3,000-event monkey runs with zero crashes. The app would ship on Next-Gen, so that result could not close S4. Testing Next-Gen meant upgrading Flutter, a global install, so the agent stopped and noted that it needed the operator's consent.

The next day, after moving to Flutter 3.47.7 and switching on Next-Gen, the release build on a Galaxy S21 crashed at launch, three times in a row. The Next-Gen SDK pulls in an old version of Room (an on-device database library) through WorkManager (a background job library). That Room version's keep rule (a rule naming code R8 must not remove) protects database classes but not their constructors.

R8 full mode (the more aggressive shrinking mode) used that gap to strip the constructor of WorkManager's database, and WorkManager failed during startup. The family app fixed it with this one line:

-keep class * extends androidx.room.RoomDatabase { void <init>(); }

The utility apps had hit the same crash 16 days earlier. On September 23 a utility release died at launch for the same reason, and the same kind of rule went into the shared ad module (Pre-release checks for an AI-built Android app covers that release). The family app's spike report and its rule file comment never mention the earlier fix. When you start a new stack, bring over your previous project's keep rules first. Another Next-Gen crash is in GMA Next-Gen ad callbacks run off the main thread.

With that fix and a corrected initialization order, S4 passed with zero crashes in a 2,000-event monkey run on the S21. By October 9, S1 and S4 had both passed, so the exit rule could no longer trigger.

Not for content pages or look-alike app portfolios

Even the family app did not build its whole web presence in Flutter. The research noted that Flutter web ships as a heavy single-page app and that Flutter's own docs advise against it for content sites, so only the signed-in app uses Flutter web; the landing and invite pages are static HTML, partly because invite links open inside KakaoTalk's in-app browser (KakaoTalk is Korea's most widely used messenger).

For a portfolio of near-identical apps, App Store rule 4.3 erases Flutter's main advantage, sharing code with iOS. Without prior Flutter experience, one of the family app's reasons disappears entirely.

S3's App Check part, S5 and S6 still have no verdict

We found no recorded result for S6 (Flutter web) in the family app repository. For S5 (local reminders), the notification feature was built and merged on October 10, but there is no verdict against the S5 bar (reboot, Doze, within one minute of the scheduled time). S3 has a measurement report comparing AI extraction models, and the decision record gained a model and prompt decision made on the operator's instruction, but there is no verdict anywhere on running with App Check enforced.

The October 5 backlog says spike verdicts go into an ADR-07 update; S5 and S6 are not there yet.
