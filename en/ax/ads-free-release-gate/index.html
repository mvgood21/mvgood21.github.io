Claude Code Android: a build gate for zero ads

The zero-ads gate Claude Code built had to read both the release dependency graph and the merged manifest; with the dependency check alone, a build carrying AD_ID passed.

By Stephen · Play Store and monetization · 8 min read · Last updated November 18, 2026

An Android app that ships no ad SDK at all can still request the advertising ID permission. HWP Viewer SugarDoc, our viewer for Korean word-processor files, was built with no ads by decision. Firebase Analytics, which it uses for statistics, pulls in four libraries that declare AD_ID, and the manifest merger copies that into the app. Left alone, the Play Console listing says "no ads, no advertising ID" while the AAB asks for it.

The first gate a Claude Code agent wrote looked only at the dependency graph, and a review agent caught the hole. When we reran the same repository in a throwaway folder on November 18, 2026, a gate that checks dependencies alone passed a build whose merged manifest still had AD_ID.

The first gate checked dependencies only

The three photo apps in the same repository show banner, interstitial and app-open ads. When the viewer started, the agent offered two ad plans (no ad SDK, or one home-screen banner), and early on October 5 (Korea time) the operator picked no ads. The app's config file got one line, adsMode=NONE.

About two hours later an implementing agent built the gate. The release config task verifyReleaseConfig gained rules that every ad id field must be empty and that the release dependency graph must not contain Google Mobile Ads (GMA, Google's ad SDK) or its consent SDK (UMP). The app manifest got four tools:node="remove" lines that strip the advertising-id permissions, and two unit tests reading the merged release manifest guarded those lines.

The workflow instructions said to remove each new guard for a moment and confirm a test fails, and the agent ran several deliberately broken copies. Copies that added an ad id or an ad module were run through verifyReleaseConfig, the task the AAB build depends on; the copy with the remove lines deleted was run through unit tests only and never through that task.

Four review agents started as soon as the implementer finished. The one assigned to rules and gates wrote: "bundleRelease depends on only one gate, verifyReleaseConfig, and it checks the dependency graph but not the merged manifest." Delete the remove lines, build and upload, and the store declares no advertising ID while the AAB has it. The reviewer filed it as minor and noted that the manifest unit tests ran only from the release script, never from the AAB build command.

A fix agent spent about 20 minutes moving the rules into a separate file and adding the merged-manifest check to the same task. Later that morning the operator asked again whether the app really had no ads at all, then set both the ads and advertising-ID answers in Play Console's app content section to "no". The gate, fix included, landed in the repository with commit ca1ade4 on October 8; the dependency-only version was never committed.

How Firebase puts AD_ID back

The viewer's telemetry module depends on Firebase Analytics. In the release dependency graph we pulled again on November 18, firebase-analytics 23.2.0 brings a set of measurement libraries, and among them is play-services-ads-identifier 18.0.0, the library that reads the advertising ID.

The manifest merger report says which library added each permission. With the remove lines gone, AD_ID was declared by four libraries, and two of them added two permissions from Android's newer ad-measurement APIs (AdServices). ACCESS_ADSERVICES_TOPICS, which the app manifest also removes, is declared by nothing in this version; the merger only warned that there was nothing to remove.

The dependency check stays silent because play-services-ads-identifier is not on its deny list. Adding it would block Firebase Analytics itself, so a code comment says it is not an ad SDK and leaves it out on purpose. Permissions live in the manifest, so a check that reads only the dependency list cannot see this path.

When the remove lines go away, four Firebase libraries add AD_ID again, the dependency check stays quiet because those libraries are allowed, and the tests that read the manifest sit outside the AAB build path. The fix agent cut the last link: the merged-manifest check now runs inside verifyReleaseConfig, so bundleRelease fails even with the first three in place.

One app, four states

Without touching the source repository, we unpacked origin/main into a temporary folder and ran the viewer's verifyReleaseConfig four times. The Firebase config file was the fake template the repository ships (without it, every run adds a "google-services.json is missing" line).

StateChangeResultAD_ID in merged manifest
Anonepassno
Bfour remove lines deletedfail, 3 manifest linesyes
CB, plus the manifest check call removedpassyes
Dthe photo apps' ad module addedfail, 3 dependency + 12 manifest linesno

C is close to the gate as first built on October 5: the advertising-id permission is in, and the build succeeds. D goes the other way. The remove lines are intact, so AD_ID is stripped, but the ad SDK, UMP and the WorkManager library the ad SDK pulls in trip the dependency rule, and the manifest rule catches one ad activity and eleven WorkManager components. B is caught only by the manifest check; D trips both layers.

In the same copy, with the manifest check call removed, we also ran the rule tests (./gradlew -p build-logic test). All 15 passed. The tests guard the rule functions; nothing tests that the task calls them.

Wiring both checks into one task

This can live in a convention plugin (a Gradle build-config plugin shared by several modules) or in an app module's build.gradle.kts. Our repository keeps it in the convention plugin every app applies and switches it on with adsMode in each app's config file.

  1. Give the app config an ads mode. With NONE, pass only when every ad id is empty and every ad flag is false.

  2. Walk the release runtime graph (releaseRuntimeClasspath) to the end, collect each external module's group:name, and compare against exact names. Our list has seven: four Google ad SDK artifacts, UMP and two WorkManager artifacts. play-services-ads-identifier is not on it.

  3. Strip the advertising-id permissions in the app manifest.

    <uses-permission android:name="com.google.android.gms.permission.AD_ID" tools:node="remove" />
<uses-permission android:name="android.permission.ACCESS_ADSERVICES_AD_ID" tools:node="remove" />
<uses-permission android:name="android.permission.ACCESS_ADSERVICES_ATTRIBUTION" tools:node="remove" />
<uses-permission android:name="android.permission.ACCESS_ADSERVICES_TOPICS" tools:node="remove" />

  4. In the same task, read the release variant's merged manifest and fail on AD_ID or ACCESS_ADSERVICES_* permissions, GMA meta-data, or GMA, UMP and WorkManager components. This is the step that catches step 3 disappearing. The permission part, taken from the repository:

    // plugin: hand the release variant's merged manifest to the task as an input
onVariants(selector().withBuildType("release")) { variant ->
    mergedReleaseManifest.set(variant.artifacts.get(SingleArtifact.MERGED_MANIFEST))
    releasePackage.set(variant.applicationId)
}
// rule function: match permission names
(elements("uses-permission") + elements("uses-permission-sdk-23")).map { it.name() }
    .filter { it == "com.google.android.gms.permission.AD_ID" || it.startsWith("android.permission.ACCESS_ADSERVICES_") }
    .forEach { problems += "adsMode=NONE but the merged manifest requests $it" }

  5. Make the AAB task depend on it.

    tasks.matching { it.name == "bundleRelease" }.configureEach { dependsOn(verifyReleaseConfig) }

  6. Move the rules into functions with no Gradle types and give each rule a "break it and it fails" unit test. Then run the real project in states A to D and confirm A and C pass while B and D fail; of the broken states, only C should pass.

  7. Find which library adds a permission in build/outputs/logs/manifest-merger-release-report.txt, and what pulls it in with ./gradlew :app:dependencies --configuration releaseRuntimeClasspath.

Don't write the lists from memory. Pull your dependency graph and merger report once; those two outputs are where the lists in steps 2 and 4 come from.

Ad SDKs off the list, and wiring without a test

The gate knows only Google's ad SDKs. The dependency list is seven exact module names, and the manifest prefixes cover GMA, UMP and WorkManager. Another ad network's SDK would pass both layers. We have not tried one in the viewer.

Blocking WorkManager works because the viewer uses none (it even cleans its document inbox without it). An app that needs scheduled work would have to change that line first. The gate hangs off bundleRelease only, so assembleRelease, which builds a release APK, does not run it.

Whether the task calls the rule functions is covered today by the release unit tests the release script runs. They read the same merged manifest, but the AAB build command alone does not run them. Next is pinning state C as a build-logic test, so that deleting the call fails a test.
