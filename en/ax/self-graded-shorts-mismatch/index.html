Claude Code self-graded a wrong-screen short 9/10

A Claude Code session graded its own promo short 9/10 while it showed the wrong app screen, and a stale pass mark kept it queued for 13 days. The maker no longer grades its own work.

By Stephen · Testing and release · 8 min read · Last updated November 23, 2026

Halfway through a 19-second promo short for our Korean spelling-checker app, the caption fixes one word while the app screen behind it fixes a different one. The caption corrects the common misspelling 왠일로 to 웬일로 ("what brings you here"); the app screen corrects 몇일 to 며칠 ("how many days"). The short passed our quality bar at 9/10 and went up on TikTok and YouTube on the afternoon of November 2. The grader was the same Claude Code session that had made the video.

The grading rules changed that night, but the video already carried a pass mark in the posting queue; it stayed there for 13 days and was only stopped on November 15 by a different agent. That agent also reported an error that is not in the video, and the next morning's run copied that claim into the record as the reason for discarding it.

The session that made the video also scored it

The app posts one vertical short a day about a single Korean spelling pair, on TikTok, Instagram and YouTube. A morning run renders the video and appends a row to a queue document; a 2 p.m. run takes the row and uploads it. Both are Claude Code sessions started on a schedule by a small personal runner (the "harness").

On the evening of November 1 the operator introduced a quality bar called Q2: six required items (sound, motion in the first second, text kept out of the platform UI margins, a large real app screen, length and loop, and so on) plus a few scored ones, 10 points in all, with 9 needed to enter the queue. The run that made a video graded it, under the instruction "don't be generous; when in doubt, deduct."

On the morning of November 2 that run wrote a new generator, daily_short_q2.py, and rendered q004. The generator used one fixed screen recording of the real app behind every topic, and that recording showed the 몇일 to 며칠 fix. The run knew this: in the same commit (4a778de) it wrote "limitation: the recording is a fixed real app screen (몇일 to 며칠), so it differs from the topic sentence" into the generator's README, and its final report said:

> Weakness: the app recording is a fixed screen (몇일 to 며칠) and differs from the video's topic. That is why the 9 sits right on the threshold.

The scoring sheet of the day had no required item for "does the screen match the topic." The weakness could not fail the video, and the score landed right on 9. The 2 p.m. run posted to TikTok and YouTube; Instagram failed because the browser denied the site a permission, so that cell stayed empty.

The gate changed that night; the pass mark stayed

Around 10 p.m. the operator asked for a proper fix. The Claude Code session that maintains the harness opened that day's four Q2 videos with ffmpeg, saw that q004 sat on another topic's recording, and rebuilt the gate in commit 427279e.

Stage one is a mechanical check, q2_check.py, that measures resolution, length, silence, motion in the first second and any freeze longer than 1.5 seconds. q004 passes it: all five items are measurements, and none of them reads the sentence on screen. In stage two the run that makes a video no longer grades it; a fresh subagent gets the frames, the topic spec and the scoring sheet. A new required item, M7 "content matches and is factual", joined the list, and any required item at zero fails the video whatever the total.

The new gate applied "from tomorrow's 9 a.m. run". Nobody re-reviewed the 9/10 pass mark on the q004 row that was already in the queue. On November 6 a run logged "q004 M7 defect" in the WATCH file (where experiments and known defects are tracked) and added record_topic.py, which records the app in an emulator for each topic. In that same commit the q004 queue row did not change by a single character.

The defect lived in one file and the pass mark in another, with no step joining them. To the posting run, q004 with its empty Instagram cell remained a passed video waiting to go out.

The agent that caught it added an error that isn't there

On November 11 the posting rule changed to fill empty channel cells one channel at a time. At 2 p.m. on November 15 the run found nothing left for TikTok or YouTube, and q004 was the only Q2 row still missing on Instagram. It dropped the file into Instagram's upload dialog, looked at a half-scale screenshot (784x389), and stopped.

The reason it wrote into the queue was "screen shows 몇일 to 며칠, and the TIP '웬은 웬지에만 써요' is factually wrong." The TIP is the tip caption near the end of the video, at 15.5 seconds, and it actually reads "'왠'은 '왠지'에만 써요": the spelling 왠 appears only in the word 왠지 ("somehow"), which is correct. The harness session on the night of November 2 had pulled the very same frame and raised nothing about the TIP. The next morning's run discarded the row without opening the video and carried the claim into the discard note.

The first draft of this note nearly made the same mistake. The idea we started from was "a spelling app's short got a spelling rule wrong in its TIP, and an independent AI review passed it at 9/10." Both halves were wrong. There was no independent review on the morning of November 2, and the TIP is right: we pulled the 15.5-second frame again from the posted video file. Written from the queue and WATCH records alone, this note would have been the third place to repeat the misreading.

What to do on the day you change a gate

  1. Never let the producing session grade. Give a fresh subagent the frames, the spec and the scoring sheet, and nothing of the maker's opinion or expected score.

  2. Make "the screen content matches the topic" a required item that fails on zero regardless of total. As a deduction it produced a 9.

  3. In the commit that changes the gate, list everything that already passed and is queued or published, run it through the new gate, and strip the pass mark until it does.

  4. Fix the defect log and the queue row in the same commit.

  5. A run that copies another run's record opens the original once before copying it.

  6. Attach a timestamp and a full-resolution frame to any defect claim. Checking this TIP took one command: ffmpeg -ss 15.5 -i q004_ko_9x16.mp4 -frames:v 1 tip.png.

  7. Hand published items to a person as a list.

The app itself is on the SugarSpeller page. We wrote about making one agent's findings survive another agent's refutation in AI code review: fix only what survives refutation.

Two posts and a wrong reason are still out there

The November 16 run did not make anything private itself; it recommended setting the two TikTok and YouTube posts to private "after the user confirms." As of November 22 the repository has no record that this happened. The discard note in the queue still says "TIP factually wrong", so the next run that reads that row can repeat the misreading.

Re-checking frames needs the video file. The mp4s are kept out of git and live only in the harness working tree; this time the November 2 file was still there. The background recording is outside git too, so we have not checked whether the same video can be rebuilt on a fresh checkout. Whether re-reviewing queued rows becomes an actual harness step is not decided yet.
