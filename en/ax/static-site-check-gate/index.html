Keeping a static site safe when several AI agents edit it: one --check before every commit

Commit only when a fresh rebuild would change zero files and the checks report zero errors. That one rule catches the problems that appear only after separate pieces of work are combined.

By SugarMount · Website and search · 9 min read · Last updated November 13, 2026

Many agents, one repository 4/6

When several AI coding agent sessions work in one repository, each can verify its own change and the combined result can still break. This site has no framework: a build script written against the Python standard library generates it, and whoever commits, person or agent, first passes python tools/build.py --check. Between October 5 and 22, 2026, that command stopped a commit four times. Here is what it caught and the rules that came out of it.

Four times --check stopped a commit

--check rebuilds the whole site in memory and asks two questions. Does any output differ by even one byte from the file on disk? Did the checker module, tools/checks.py, report an error? Either one means exit 1, and nothing is written.

outputs = build_all()              # pages, feeds, sitemap, CSS: in memory
changed = [p for p, text in outputs.items()
           if read_file(p) != text]
report = checks.run(ROOT, outputs)  # 106 issue codes
if "--check" in argv:
    if changed or report.errors:
        exit(1)                     # nothing is written
else:
    write_files(changed)

On October 24 a run produced 162 files, ran 106 named checks and took 11.6 seconds. The four stops:

DateWhat failedCause
Oct 5Two files out of date right after the first buildDates read from git state
Oct 18101 gate errors at the redesign integrationMostly the checker miscounting
Oct 19Home page needed 421 KB of fonts, cap 400 KBDaily-changing note titles, merged in by a rebase
Oct 22Two older notes at 482 KB and 473 KB, cap 470 KBOne rare syllable in a new note's title

None of the four shows up when you check a single file. They were caught because the whole output was rebuilt and compared.

Humans and agents write only the body and the data files

Every file has exactly one kind of writer. Condensed from the table in the repository's AGENTS.md, the instruction file agents read before they start:

WriterFiles
Content authors (people or agents)The <title>, description and <main> of hand-written pages (minus build blocks), data JSON
One build-owner sessionThe build code, and the one integration build
The build onlyHead, header, footer, breadcrumbs, JSON-LD, list pages, sitemap, RSS, the dates file, generated CSS

Inside a hand-written page, every spot the build fills is wrapped in a marker such as <!-- build:meta -->. Each build empties and refills only those blocks and leaves the rest of <main> byte for byte. Content authors never run the build; they run the read-only single-file check, tools/checks.py --file.

The first plan did not have this split. An agent wrote the October 18 redesign spec, and it told every work package both to finish with build and --check and to leave generated HTML alone. A second agent, assigned to attack the spec, pointed out the contradiction: the build rewrites the head and footer of every hand-written page, so one session building to verify its work would change some 60 files another session was editing. Since then the integration build runs once, in one place.

Rebase conflicts follow the same rule. On October 19 the conflicted files were all ones the build rewrites: 404.html, the about page, app pages, rss.xml. Do not hand-merge generated files. Pick a side, rebuild, and commit only when --check reports zero.

Test idempotency with tomorrow's date, not with a second build

On October 5 an agent wrote the first build script and ran it. This came back:

45 files, 45 changed
out of date:
  apps/sugarcard/index.html
  sitemap.xml

A second build changed two files, and the third said up to date. The lines that moved were sitemap lastmod dates.

There were two layers of cause. The near one was ordering: the build read dates from git status and git log before writing anything, so its own writes changed the input of the next run. The deeper one was the source of the date itself, which was repository state and the wall clock instead of page content.

That day's fix addressed only the near cause. Two builds on the same day then agreed, but the same input built the next day still moved the dates. A build that converges after two runs is not idempotent.

Thirteen days later the redesign switched to dates derived from a hash of the page body. The redesign spec, also written by an agent, had two loops of the same kind: a date line inside the hashed body, so date and hash kept changing each other, and a CSS version string that hashed the very file the build writes into. The reviewer wrote that --check would "fail once, forever". Both were fixed before any code was written. The date rules are in Every sitemap lastmod had the same date: deriving modified dates from a content hash.

The build's idea of "today" can now be overridden with a SOURCE_DATE environment variable. A run in a scratch copy on October 24:

$ SOURCE_DATE=2026-10-25 python tools/build.py
162 files, 0 changed
$ SOURCE_DATE=2026-12-31 python tools/build.py
162 files, 0 changed

At the first integration, the gate was the one that was wrong

The October 18 redesign was split across 36 agents and took 2 hours 24 minutes. The first --check on the merged result found zero files to rewrite and 101 gate errors.

Most of the 43 font-budget errors were the checker's own mistake. English pages draw © in the system font through CSS, but the checker counted that character and decided the pages needed extra font files. One cost was real: the breadcrumb separator › alone made every page download one more 25 KB font file. The fix aligned the checker's counting with the CSS rules and moved the separator to the system font.

When the gate changes, its tests change with it. That fix added six tests, and each of the eight new guards was removed in turn in a scratch copy to confirm a test failed. As of October 24, every one of the 106 checks is named in a test.

The integrating agent also loosened the gate twice on its own. Two kinds of pages with no cap in the spec got font overruns as warnings only, and the cap on the generated font stylesheet went from 20 KB to 24 KB. It marked both "needs confirmation" in its report; by October 24 nobody had confirmed either.

Another note's title can break a page's font budget

The site's Korean font is split into 92 files, and a page downloads only the files that cover its characters. Note pages are capped at 470 KB, home and list pages at 400 KB. One rare Hangul syllable can pull in a 17 to 40 KB file by itself, so two of the first three AX notes went over and were reworded that evening.

The home page broke for another reason. It listed the three newest note titles, which changed every day, and after the rebase merged another session's work it needed 421 KB. Instead of rewording titles, the home list became links to topic pages, whose names never change. Dropping note titles from the topic cards on the AX notes front page on October 22 had the same reason and took that page from 468 KB to 389 KB.

Also on October 22, a single syllable, 쟀, in a new note's title travelled through the related-notes lists into two older notes and pushed them to 482 KB and 473 KB. Checking the new file alone passes. Rewording the title brought the two pages to 450 KB and 441 KB.

Images are still outside the gate

tools/og.py builds share images from real Play screenshots on a neutral background, and --check does not rebuild or compare them. Running og.py in a scratch copy on October 24 changed 4 of 155 files. Two runs in a row give identical bytes, so the files that differ are the ones committed without going through the generator. The story behind the blank-glyph check in the image tools is in Android showed some Hangul as blank gaps: NanumSquare's cmap claimed 11,172 syllables but drew only 2,479.

Not for browser editing, very large sites or repositories without CI

Teams that write in a browser and expect a preview will not like it; here authors edit the HTML body directly and run commands. A static site generator would not remove the need for this gate: three of the four stops came from checks over the whole output, so you would still build those checks and the date rules yourself.

Large sites pay more. --check rebuilds and compares everything on every run, with no incremental build.

Nothing enforces the gate. The repository has no CI, so it works only if someone runs the command before committing. The gate can also be wrong, and it cannot stop a commit that raises its own caps.

Adding a --check gate to another site, in order

  1. Put a table of who writes which files at the top of your agent instructions, and mark generated files as hands-off.
  2. Wrap every spot the build fills inside a hand-written page in <!-- build:NAME --> markers; the build empties and refills them each time.
  3. Make --check render every output in memory, compare it with disk, run the checks on the same output, and exit 1 if either fails.
  4. Derive dates and version strings from content hashes, and keep date lines and automatic lists out of the hash input.
  5. Test idempotency with two builds in a row, a build dated tomorrow and one dated in the past.
  6. Give every check a fixed code and a test that proves it fires; remove each guard in a scratch copy and confirm a test fails.
  7. Content sessions run only the per-file check; one session runs the integration build once. When generated files conflict in a rebase, pick a side and rebuild.
  8. Check budgets that mix in other pages' text (fonts, size) on the whole output, and keep daily-changing lists off shared pages.
  9. Have a person review any commit that changes a cap.

What we will check next

The next step is a stage in --check that compares og.py output with the committed images. Before that, the app cards that carry text have to become either a listed exception or generator output. The 24 KB stylesheet cap and the two warning-only page types still need a human review.

Frequently asked questions

Do you commit the generated HTML?

Yes. GitHub Pages serves the repository's files as they are, so the build output is the deployment. --check confirms that the committed output equals what the current inputs produce.

How do you test that a static site build is idempotent?

Build twice in a row, then with tomorrow's date and with a past date, and expect zero changed files. For that, the build's "today" has to be overridable through an environment variable.

How do you resolve conflicts when several AI agent sessions edit the same site repository?

Merge only source files such as page bodies and data; for generated files, pick one side and rebuild. Commit only when --check passes on the rebuilt result. On this site, that step is where the home page font overflow first appeared.
