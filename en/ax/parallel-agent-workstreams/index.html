How many AI coding agents can run at once? Memory and test phones set our limit at three

Only three code-writing agents ever ran at the same time. The cap came from 4 GB of free RAM and two shared test phones, not from how many agents we were allowed to start.

By SugarMount · Working with agents · 6 min read · Last updated November 13, 2026

Many agents, one repository 1/6

In Claude Code, a main session can hand work to many subagents at once. On October 3, 2026, while growing the puzzle game Arrow Knots from 300 levels to 1,000, the operator said "use hundreds of agents if you like." The repository logged 59 commits that day, but never more than three code-writing agents ran in parallel. If you are deciding how many agents to start, count the memory one build needs and the devices you can test on before you count agents.

Hundreds allowed, three writing code at a time

A minute after the request, the agent started a design Workflow, the Claude Code tool that runs many subagents from one script. It split the problem by topic (difficulty curve, in-game economy, visual design, store copy, localization) and used 24 agents over 52 minutes. Nothing in that phase touched code, so eleven ran in parallel.

Three minutes after the merged spec was committed, the implementation Workflow began. Forty-one agents shared implementation, adversarial review, fixes and merges for 5 hours 6 minutes. Peak concurrency was three, in the first stage: engine rules, the level generator, and strings plus build config. Later stages ran two at a time or one alone.

The agent chose three on its own. Before starting, it noted 16 cores and 13 GB of RAM with 4 GB free, so it would run Android builds two or three at a time. A workstream agent's memory check during the run agreed:

$ free -g
               total        used        free      shared  buff/cache   available
Mem:              13           8           2           0           2           4

RAM, two phones and a file-owner table set the pace

Build memory was the first wall. The implementation notes capped Gradle at four workers (--max-workers=4) and allowed one Gradle build at a time per workspace. Every workstream had to pass unit tests and a debug build before each commit, so parallel workstreams meant parallel builds. Research and design Workflows never build; the six that ran here reached 11 to 14 agents at once.

The test phones were a Galaxy S21 and an S20, shared by five sessions, including ones from another app repository. So the notes said: no workstream touches a device; E2E happens later, on the S21 only. Over the two days the sessions in this repository received 148 messages from other sessions, and 114 mentioned one of the two phones, mostly turn-taking like "I need it for ten minutes."

Files had owners too. The spec's workstream table had an "exclusive files" column, so the camera workstream edited only its three camera files. Each workstream committed in its own git worktree (an extra checkout of the same repository in a separate folder), and only one integration agent merged into the integration branch. Where shared files still collided is covered in several AI agents in one repository: the file owner table.

"No failures," then a crash on first launch

At 10:27 pm the implementation Workflow reported "all 41 complete, no failures." The final merge agent had passed every JVM test and a debug build. A minute later the app was installed on the S21 and crashed on launch. Android's build tools strip a trailing .gz from asset names, so the level file the code looked for was not in the APK. The fix at 10:31 pm shipped the level files uncompressed and added a regression test that fails on any asset name ending in .gz.

The detailed 33-item E2E took the S21 for 65 minutes after midnight: 31 passed, one failed (stutter when panning a large board) and one could not be checked on a debug build. The Workflow that fixed the ten bugs and design issues it found also ran three agents at a time.

What the agents got wrong was the meaning of "done." Keeping them off the devices was right, but it meant 41 "done" reports only covered JVM tests and compilation, and every device-only defect piled up at the end. What caught it was one phrase in the operator's first request: "install it on the S21 and run E2E too." Later that night the operator freed the S20 as well, and a release-build random-input run (3,000 events, three times) ran alongside the fixes with zero crashes.

Before deciding how many agents to start, count how many builds and how many devices you can run at the same time.

Before you pick a number of agents

  1. Check free memory and decide how many builds can run together. Here it was three, with 4 GB free of 13 GB. That is the cap for agents that change code.
  2. Count research and design work separately. Without builds, 11 to 14 ran at once.
  3. Keep real devices out of the workstreams and agree on who uses which phone when.
  4. Give each workstream a list of files it owns, and let a single integration agent do every merge.
  5. Define "done" as a release build running on a real device. Passing tests did not catch this crash.

Next experiments

  • Does a fourth agent fit? This time free memory was only sampled a few times; next time it gets logged every minute to show whether three was a safe margin or waste.
  • A device lock instead of messages. Replace the 114 phone messages with one lock file (who, until when) and measure how much waiting it saves.
  • Why 14? All five research Workflows stopped at exactly 14 concurrent agents. Whether that is a tool setting is not checked yet.

FAQ

How many Claude Code subagents can run in parallel?

In these logs, research Workflows that never build reached 14 at once. Implementation agents that run Gradle builds were capped at three to fit 4 GB of free RAM.

Does giving each agent its own git worktree remove conflicts?

It reduces git conflicts, but the fight over devices and memory stays. Here an exclusive-files table and a single merging agent handled git, and the two phones were scheduled through messages between sessions.

How were ten workstreams merged in one day?

Stages followed the dependency order. After each stage the integration agent merged the branches one by one, then ran unit tests and a debug build. That produced 11 merge commits in 3 hours 37 minutes on the evening of October 3.

Numbers come from the game repository's git history, its spec and implementation notes, and a script over the Claude Code session logs. Times are Korea time; checked on October 21, 2026.
