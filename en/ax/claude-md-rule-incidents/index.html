Most CLAUDE.md rules came from an incident, and some incidents came back anyway

A reply-language rule went in five minutes after the incident and still broke on five later dates. After a project memory about pkill, that project had no more exit 144, while other projects had 7.

By SugarMount · Working with agents · 11 min read · Last updated November 9, 2026

At 08:39 KST on October 2, 2026, the operator got a status report in English and asked for Korean. Five minutes later another session wrote a Korean-reply rule into the global CLAUDE.md (the global instructions below). Session logs show the rule breaking on October 4, 5, 8, 11 and 24, after it had been attached to those sessions' context. Over the same stretch, calls containing pkill -f kept ending in exit 144: that stopped in the project that got a memory note, and 7 more landed in projects without it.

Sources: rule text from the global instructions, project memory files, Claude Code session logs (jsonl) and the Claude Code documentation. Exit 144 counts were scripted on 2026-11-07 from the 137 logs directly under the project folders, leaving out folders we don't publish, scheduled harness sessions and subagent logs. For Korean relapses we searched the same logs for requests to reply in Korean, kept only sessions where the global file had already been attached, and stopped at October 24. Times are KST.

exit 144 happened more often than the note said

Commands that used pkill -f, or pgrep -f with kill, to stop a process also cut off the agent's own shell. The Bash tool wraps each command in bash -c '...pattern...', so the pattern also matches the calling shell's command line. The call ends in exit 144 and the rest of it never runs. The note says the target survives, but in the 4 cases we checked, the target had stopped. We could not confirm why the value is 144. A SIGTERM usually gives 143, and the shell changed on October 18, so we could not reproduce it.

The agent recorded this in memory at 16:53 on October 4, 2026 and wrote that it happened "twice". The note doesn't say which two it meant. The game project's main session logs do show 2 that day. Counting Bash calls that contain pkill -f or pgrep -f and ended in exit 144 gives 5 in the same project, including 3 from the day before, and 24 across all counted projects from September 14 up to the note. All 31 in the logs, including those after the note, contain pkill -f or pgrep -f with kill; no exit 144 happened without one of them.

From the note until October 18, none of the game project's 1,348 Bash calls ended in exit 144, and none used pkill -f. Two pgrep -f calls remained, for waiting or checking, and neither led to a kill. Our first count missed normal exits and claimed zero such calls; a fact-checking agent found these two.

Other projects had 4 failures on October 5 and 3 on October 11. The documentation scopes auto memory per repository. The note sat in the game project's memory, and a search for pkill in the global instructions finds nothing, so it did not load in sessions elsewhere. The project behind 3 of the October 5 failures wrote its own line to the same effect at 13:21 that day.

The development environment moved on October 18 and the shell changed with it, so later zeros are left out. The game project's zero is also just 14 days in one project. Other projects also had no exit 144 after 15:12 on October 11, so we don't claim the note caused the drop.

The Korean rule broke after it was attached

The operator asked for this to go into the global instructions. In a session with the file attached, the same request came back at 01:23 on October 4. The reply before it had 0 Hangul characters and 1,691 Latin letters.

While drafting this note, Claude's first guess was session age: the relapsing session began on September 30, two days before the rule, so it might never have seen it. The logs rule that out. The global instructions were attached to that session at 11:24 on October 3, right after its first compaction, and the relapse came later. A session started at 11:50 that day, with them attached from the first moment, also answered in English on October 4 and 5. The five dates are days the operator objected in 4 such sessions: 2 in the game project, one each in the spelling and utility apps. Requests at 11:38 on October 3, 21:57 on October 8 and on October 18 are left out because no attachment could be confirmed.

The memory files and logs show several paths. On October 4, replies drifted into English after a run of English messages from other sessions. On October 5 the questions and options in the AskUserQuestion tool were in English. On October 8 a session answering in Korean gave only its final report in English, right after English table output. On October 24 every reply in the turn was in English, from the first one after a Korean question. On October 11 the operator refused an English question in the spelling app project and had it asked again in Korean.

Objection dates only catch days the operator spoke up, so we counted replies too. We took the last reply before the operator's next message, after a Korean message, excluded code, kept replies of 80 or more letters with under 10% Hangul, and read all 55. Five API error and usage-limit messages and 16 internal classifier turns were false positives, so they left the denominator as well. In 16 of the 34, automatic input such as another session's message arrived in between.

Three settings we have only read about

The documentation calls these files "context, not enforced configuration", and to block an action it points to a PreToolUse hook. A reply sentence is not a tool call, so that hook never sees it. Our reading: pkill is one command to avoid, but reply language follows the input around it, as it did on October 4 after a run of English messages. That doesn't explain days like October 24, when the message just before was in Korean.

We checked the three options below in the documentation on 2026-11-07. None is in our user settings now, and we haven't used any of them to enforce a rule.

  • The language setting passes its value to Claude as "an instruction to always respond in that language". That is one more instruction and enforces nothing.
  • A Stop hook runs when Claude finishes responding and receives last_assistant_message; exit 2 keeps Claude going. This is where reply language could be checked. We haven't measured false positives on code-heavy replies or the cost of retries.
  • Bash(pkill *) under permissions.deny in ~/.claude/settings.json applies to every project and also matches subcommands. The documentation says other invocation forms such as bash -c get through, and pgrep -f with kill, 2 of the 31, is not covered.

Two rules where the answer differs by project

Going by exit 144 alone, putting every rule in the global instructions looks easy. The device and commit rules differ by project.

On October 5, 2026, 7 minigame_check checks failed on a Galaxy S21. At 12:17 the agent said it would check on the emulator whether the failures were real, and the same suite passed 58/58 there. The cause was another session launching its own app on the S21 mid-run. The agent wrote this up in project memory that day, with a diagnosis: look in the device logcat for START u0 lines from foreign packages.

The game project's October 5 note calls the emulator a good fallback, while on October 11 the operator told the family app project not to start a PC emulator and to use the S20. Commits work the same way: the global instructions say not to commit unless asked, and on October 22 the game project reversed that and commits after each unit of work.

The documentation warns that instructions given only in conversation can disappear after compaction; Claude Code auto-compaction: what 9 summaries kept covers what survives. If you run one session at a time, you don't need the shared file rule. This record comes from global instructions used by one person; we haven't tried it on instructions shared by a team.

Two rules with no incident on record

The secrets rule went in at 08:55 on October 2, 11 minutes after the Korean rule, at the operator's request, and we found no earlier leak in the source files. The October 8 instruction to ask before anything that costs money or looks odd also became a memory without a recorded incident. Write money and secrets rules before the first incident, because that one is hard to undo.

Five steps after an incident

  1. Write the rule in one line with a Why: the date, the command you ran, the result.
  2. Count the symptom in your session logs. This script counts only tool results that start with the string you pass, so mentions in messages or notes don't count. Change the argument for other symptoms. Passing our unpublished folders as skip arguments gives 31. 
    # python count_results.py "Exit code 144" [folder substrings to skip ...]
import glob, json, os, sys
needle, skip, ids = sys.argv[1], sys.argv[2:], set()
for path in glob.glob(os.path.expanduser("~/.claude/projects/*/*.jsonl")):
    if any(s in path for s in skip):
        continue
    for line in open(path, encoding="utf-8"):
        if needle not in line:
            continue
        try:
            content = json.loads(line).get("message", {}).get("content")
        except (ValueError, AttributeError):
            continue
        for block in content if isinstance(content, list) else []:
            if isinstance(block, dict) and block.get("type") == "tool_result":
                body = block.get("content")
                text = body if isinstance(body, str) else " ".join(
                    x.get("text", "") for x in body or [] if isinstance(x, dict))
                if text.startswith(needle):
                    ids.add(block["tool_use_id"])
print(len(ids))
    Mind the scope: it reads only logs directly under the project folders, skips subagent logs and has no date limit. A relapse that leaves no tool result needs another method. For English replies, pull candidates by the Hangul share of each turn's last reply and read them all.
  3. Pick the scope. If it shows up in two or more projects, use the global instructions; if the right answer differs by project, use project memory.
  4. If the rule bans a specific command, mark it as a deny rule or PreToolUse hook candidate, for example {"permissions": {"deny": ["Bash(pkill *)"]}}.
  5. When it relapses, add the date and the new path to How to apply.

If an incident happens twice, recount it from the logs before you edit the sentence.

The pkill line and relapses after October 24

The pkill line is still not in the global instructions, only in two project memories. By step 3 it belongs there, but exit 144 has not appeared since the shell changed on October 18, so we haven't decided. The five dates are a lower bound: they count days the operator objected, up to October 24. The logs run to November 7, and the table above includes English replies from October 30, October 31 and November 1. The next recount will include scheduled harness sessions.

FAQ

Why does Claude break rules written in CLAUDE.md?

CLAUDE.md is read as context and is not enforced. In our logs, 4 sessions with the global instructions attached still answered in English.

Should a rule go in the global CLAUDE.md or in project memory?

Project memory doesn't load in sessions for other repositories. Use the global instructions when the same incident shows up across projects, and keep only rules whose answer differs by project, such as emulator use, in project memory.

Why does pkill -f give exit 144 in Claude Code?

The pattern matches the calling shell, so the shell gets cut off too. We could not confirm why the value is 144. We find the exact PID instead, using a bracket trick such as grep "[b]lock_full_e2e.py".
