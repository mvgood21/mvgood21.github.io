A permission table for a scheduled AI agent: what it does alone, and which clicks a person makes

We split the agent's work into three lanes in one file: what it does alone, what it does after approval, and the clicks a person makes even after approving. Every scheduled run reads that file first.

By SugarMount · Working with agents · 10 min read · Last updated November 13, 2026

Giving an agent rules and limits 4/5

An AI coding agent such as Claude Code can rerun the same prompt at set times. Those runs happen while nobody is watching, so rules given in chat never reach them; only a file the run reads does. Since October 17, 2026, SugarMount has had the agent market Arrow Knots and Block Turn this way, four times a day, with the final click on money, accounts and policy left to a person. Even an ad restart the operator had approved was blocked by the tool's permission check, and a person switched it on.

The table started with three columns and a list of stop conditions

The schedule is one morning market check and three work blocks a day. The first sentence of the work-block prompt says to read the operating rules file first; the rest says to pick the most urgent item from the to-do list, work on it within the permissions, and update the posting log and the day's report. The permission table is one section of that rules file.

The first column is what the agent may do alone: measurement, analysis, drafts, posting from accounts that already exist, and replying to comments on its own posts. Posting comes with numbers: at most two promotional posts a day, at least three days between posts on the same site, and always say you are the developer. The second column needs the operator's approval: anything that costs money (restarting ads, budget or bid changes, paid services), new sign-ups, logins and CAPTCHAs, policy declarations, and entering a real name or contact details. The third column is what the agent never does: fake accounts, rating manipulation, channels whose cost or eligibility is unchecked, and channels the operator has closed.

Below the table sit five stop conditions, copied as they are into the template further down. When one applies, the agent does not act. It marks the item Blocked and writes the options and a recommendation at the top of the daily report under "needs your decision". The numeric limits worked too: on October 18 the posting log shows "two promotional posts today, limit reached" after the second post, and nothing else went up that day.

Rules given in chat never reached the scheduled runs

It started on the evening of October 8. The operator told the agent to do all of it, and the agent replied that it would begin by creating an ads account and linking Google Play. Five minutes later the operator said: anything that spends money or looks odd, ask first. That one line was the first rule.

It only caught the moment of payment, and the trouble up to October 10 involved no money at all. Reddit had removed all our posts, and on the 10th a Korean community board suspended the account on its first post, as advertising. We traced it to new accounts dropping the same link in several places at once, and set the two-a-day and three-day limits. On October 13 the agent pushed ahead with the Galaxy Store without confirming cost or eligibility; only after two release builds were ready did the portal say Android apps need a paid seller account, and the channel was dropped. So the trigger changed from "payment" to categories, and those became the five stop conditions.

Where a rule lives mattered too. The October 8 rule sat only in the memory of a different working folder, so the marketing session never loaded it (what a long session reloads is in What survives Claude Code auto-compaction: the summary, recent files and the memory index). The only place a rule reliably reaches every run is a file the prompt names. It is the same idea as How to write AGENTS.md: only the rules an AI coding agent gets wrong, except that this table governs work outside the repository.

A tool permission check sits between approval and the click

Claude Code's auto mode asks a permission classifier before it runs a click or a command. In the marketing session the classifier refused 11 actions between October 17 and 20.

The most common reason covered making a Short public, uploading a promo image and saving a store listing. The refusals with no reason hit submitting listing changes for review and a publish step, and the shared-resources refusal stopped a command that would have changed a setting on every connected test phone.

On the afternoon of October 18 the operator said to finish everything, yet the custom store listing's submit and save buttons were refused, and they only passed after the operator asked for the save again. At 17:06 the operator approved the rest of the batch, and a minute later the click on the ad status menu came back with Permission for this action was denied by the Claude Code auto mode classifier. Reason: [Real-World Transactions]. Fourteen seconds later the same reason blocked an emulator boot check that had nothing to do with ads. In the end the operator switched the ad on.

So the approval column really splits in two: work the agent finishes once approved, and clicks a person makes even after approving. Between October 17 and 22 the posting log has seven lines where a permission check pushed the final step to a person. On October 22 an update post on a Korean gaming community sat fully filled in while the operator pressed only the submit button. Do not have the agent hunt for a workaround on a click that spends money, even after approval. Put it in the person's lane from the start, and have the agent say so the moment it is blocked.

Where the agent got it wrong: a report 3 hours 38 minutes late, and log times that were off

The ad click was blocked at 17:07, but the agent told the operator it needed a person at 20:45. In between it said nothing about the block and moved on to the rest of the approved batch, an emulator test, where one connection check waited more than three hours for a reply. That ran against the memory rule it had written 26 minutes earlier: when a check blocks you, do not leave the tab open and move on, ask right away. Now a refused click marks only that item Blocked, and it shows up at the top of that day's report under "needs your decision".

The log times were wrong as well. The posting log records the episode as "18:40 restart attempted, on hold" and "20:00 switched on, running"; the transcript says blocked at 17:07 and reported at 20:45. The agent wrote both lines later, from memory. On October 20 it logged an Instagram share as on hold after the share button was refused; the next day the post turned out to be live already.

It also erred in the timid direction. In the October 18 performance report the agent proposed posting to the community boards only at updates, where views sat around 100 to 200, and dropping one channel if its next video also got zero views. The operator corrected it: free channels grow by steady accumulation. Its memory now says: never propose cutting a channel; when results are weak, propose a different format.

What we dropped, and what we did not use

Asking before every action never fit. The runs happen while nobody is watching, and even now one release approval and one ad decision sat at the top of the daily report for four days. Leaving it all to the tool's permission check failed too: the classifier knows nothing of two posts a day, three days per site or closed channels, it blocked posts the table allows, and 3 of its 11 refusals came with no reason.

Claude Code has its own permission controls: allow and deny rules in settings.json, and hooks that run a script just before a tool call. The user settings for these runs had neither (checked October 23). Those rules match tool names and command patterns. Marketing work is mostly browser clicks, so a click on a publish button looks like any other click to them, and counting two posts a day would need a hook that keeps its own state. Work that a command pattern can catch, such as a release script, is held more firmly by a deny rule than by a document.

Running the agent from an OS scheduler outside the session is the other option. There is no session end and no seven-day expiry, so no runs get lost. The cost is the hand-off: the agent leaves a filled-in browser tab and a person presses the last button, and that flow has to be built separately. This time we used session jobs and kept the expiry date in the table so they get registered again.

When this does not fit

The biggest limit is that the schedule lives inside the session. The registration output read "Session-only (not written to disk, dies when Claude exits). Auto-expires after 7 days." On October 22 the session ended during a move to a new development setup, and the morning check and the morning work block were skipped. If a job must never miss a day, use a scheduler outside the session.

It also fails if nobody reads the daily report. Pending decisions pile up and the important work stops first. The two-a-day and three-day numbers were set for a few Korean gaming boards; other channels need numbers from their own rules. Work full of logins, CAPTCHAs and locked phones stays largely manual whatever the table says.

How to set it up: a permission table template

This skeleton takes the three columns above and splits approval in two, giving four lanes. Copy it into a file and name that file in the first sentence of every scheduled prompt. Write the date of the incident behind each row; later, that date tells you whether the row can go.

# Permission table (every scheduled run reads this file first and follows it)
Schedule expires: YYYY-MM-DD / register again on: YYYY-MM-DD

## 1. Agent alone
- (task) | limit: _ a day, _ days apart per site | added: YYYY-MM-DD

## 2. Agent after approval
- (task) | added:

## 3. A person clicks, even after approving
- status changes that spend money
- final clicks a permission check refused (fill everything in, leave the tab open)

## 4. Never
- (task) | added:

## Stop and ask (if any applies, do not act)
- a kind of work done for the first time
- work on weak evidence
- anything publicly visible
- anything hard to undo
- anything touching money, accounts or policy
-> mark Blocked; options and a recommendation at the top of the report

## When blocked
- login, CAPTCHA or permission denial: Blocked for that item only, move on
- write a permission denial at the top of this run's report
- two failures in a row on one item: stop, "needs your action"

## Logs
- copy times from tool output, not from memory

Our values: lane 1 is two posts a day and three days per site, lane 3 holds ad status changes and publish clicks a permission check refused, and lane 4 holds proposals to cut channels.

What is left

Session jobs have to be registered again every seven days. The next number to count is how many days a "needs your decision" item waits before it is decided; the log already has a four-day case. If that number does not drop, the fix is to change when the report gets read, not to shrink the person's lane.

Frequently asked questions

How long does a Claude Code scheduled job last?

The session jobs used here expire after seven days and stop as soon as the session ends, so the rules file carries a renewal date and the jobs are registered again before they lapse.

Why is the agent's click blocked after a person approved it?

The tool's permission classifier judges each click on its own, apart from any approval in the chat. That is why clicks that spend money sit in the person's lane from the start.

What should an AI agent ask about before acting?

Five things: a channel tried for the first time, work on weak evidence, anything publicly visible, anything hard to undo, and anything touching money, accounts or policy. "Anything that costs money" alone was not enough, because in one case the cost only showed up at the last step.

Sources: the operating rules file and posting log (October 9 to 22, 2026), daily reports, agent memory files and the Claude Code session transcript. Times are Korea Standard Time.
