Claude Code re-review: the bug survived via HTTP

We re-reviewed Claude Code's fixes four times, and the blocker-plus-high count never reached zero. The second pass found a defect the first fix had created; the third found a defect marked closed still open over HTTP.

By Stephen · Testing and release · 10 min read · Last updated November 16, 2026

We sent code fixed by Claude Code agents back through an adversarial review (a review that asks where the code breaks if someone attacks it), and the second pass found a defect the first fix had created; the third found that a defect recorded as closed was still alive through a different connection path. This was SugarMount's P2P chat app (Flutter), during release prep in September 2026, and we ran that review four times.

The second review's defect was where two fixes met; the third's was on an HTTP path the fix never touched and in server docs that promised something untrue. When the third defect turned up, the fix report, the server docs and the server tests all said it was closed.

The lobby lock, found and fixed within 69 minutes of the first fix

The first review (September 8) found 42 issues in the release-prep changes. Each finding carried a severity: Blocker (stops the release), High, Medium or Low, and both blockers were about identity. The app trusted whatever peer id (the identifier for a chat partner) the other side sent, and the signalling server (the lobby service that helps devices on a network find each other) let anyone join under someone else's id.

Five agents split the fix by file, and it landed as one commit at 00:36 on September 9. Ids are now computed from the public key and never change, and the server binds an id to its first claimer. Both were what the first review had proposed.

The second review was done by a separate agent that wrote a report and changed no code, reading that one commit. Put the two fixes together and a permanent id becomes a target: whoever claims it first shuts the real owner out, and the app treats that refusal as fatal and never reconnects, so the owner never shows up in the lobby again. The report noted that before the fix a second join had been allowed, so this lobby lock was a new defect. The round-two fix commit message calls the lock "introduced by the previous round".

The report's first item, forged message bubbles, had fallen between fixes as well. The agent that owned the history sync path had added checks on a message's room and sender, but the live message path belonged to another agent's files and got none. A connected peer could plant a bubble on the other user's screen that looked like their own message. The report called it an item that "fell at the boundary between two agents".

The new claim-expiry rule only covered WebSocket

The fix agent that took the server items (its report is named R8) limited a claim to the life of the connection plus a short grace period. Its report said a permanent lock was no longer possible, the server README and protocol doc said the same, and the server tests passed.

The third review read the 03:38 commit from a frozen copy made with git archive, because the working tree held other agents' uncommitted changes. This is what it put at the top of its "fix now" list. The review documents number their items: round two's start with RR-, round three's with TR-.

Clients reach the server over WebSocket, or over HTTP when WebSocket fails. The rule that lets a claim expire only applied to WebSocket connections. A peer registered over HTTP went down a different branch where the claim never expired, so HTTP requests alone, with no socket open, could keep an id held. A separate review track measured it: all 10 of the owner's WebSocket joins were refused.

It found the same shape in three more places:

  • The server gives an id's first claimer a join secret (the value that proves ownership when it comes back). The path that lets an app recover its id after a restart handed back the existing join secret, so passing a narrow check once was enough to hold that id from any address (TR-2).
  • The web build does not connect devices directly; it uses a relay transport through the server. The handshake change that stops us sending our hello (the first message after connecting, carrying the public key and nickname) to a blocked peer first never reached that transport. The relay transport did not implement the new interface, so it quietly kept the old behaviour.
  • Message timestamps travelled without a time zone, so two devices in different zones failed every hash check on each other's messages. Our two emulators ran on one PC in one zone and could not produce this (TR-26).

The third fix commit, at 10:10, is titled "close the paths the earlier fixes did not cover". HTTP claims now need the join secret, and the recovery path issues a fresh secret.

We had treated a red guard as proof

The rule for this round was that every fix gets a test that fails when its guard is removed. The reviewers checked that claim themselves: round two reran 3 of the fix reports' guard-removal experiments and round three reran 8; every one went red when its guard was removed, and all but one (which failed one test more than reported) matched the reported counts and names. The HTTP lock was there anyway.

Removing a guard only tests the paths that have the guard. The HTTP path never had one to remove, and the third review's test-gap table says the HTTP lock "was never covered in the first place". On the restart path the tests protected the defect: a server test written by the fix agent asserted that a restarted app gets the same secret back, so TR-2 could not show up as a test failure.

Checking tests by deleting guards is covered in 3,066 green tests hid a line that breaks opening the database. The defects in this note are the ones still there after that check passed.

The server fix agent changed only the WebSocket path, then wrote the no-permanent-lock guarantee into its report and the server docs, backed by tests that covered only the path it had changed. An agent caught the defect too, and that reviewer had its own wrong hypothesis: the third reviewer suspected that a rejected hello kept the socket occupied, wrote a test on its copy, found the hypothesis wrong and recorded no defect. Its report gives the reason as running it "so as not to report a guess".

The records show a person's hand in one place, the rules: the operator's shared working instructions now say that after a large fix you run one more adversarial review, look for other paths to the same defect, and grep the number of production callers. Who asked for each rerun we could not confirm, because the session logs from that week are not on this PC.

When you review a fix commit, count whether its guard covers every entrance to the same defect before you ask whether the guard turns red.

Six axes for finding the other entrances

The third review concluded that uncovered paths had been where the defects were, again and again, and that the next round should ask whether each guard applies to every transport and path in production. Grouping the entrances the defects used across the four reviews gives six axes.

The six axes come from this app's shape. Server connections go over WebSocket or HTTP and chat links over TCP or a web relay, which made the transport axis long. We have not used the list on an app with a single transport. Writing the environment axis in a table does not close it; the third review asked for a QA case with the two devices set to different time zones.

The caller axis is not unique to this app. A month later, a device E2E fix commit in AXFamily, our family scheduling app (October 10), notes that nothing passed received photos and PDFs on to the organising screen. That app's merge review is in Every branch passed its AI review, and the merged code still had 12 defects.

  1. For each fix commit, write the defect it blocks in one sentence: what comes in, through which entrance, and what it does.

  2. For each of the six axes, list the entrances that defect could use. Write "none" for an axis that does not apply.

  3. Grep each entrance for the same guard. The third review counted interface implementations, call sites of the limit check, and production callers of each new API. For this app:

    # every class implementing the interface the transports share
grep -rn "implements TransportService" lib/
# production callers of the API that reads older history page by page
grep -rn "getMessagesPage\|MessageCursor" lib/

  4. Give the fix diff to a review agent that took no part in the fix, report only, and have it mark each earlier finding closed, partial or open.

  5. Read the fix agent's tests that lock in current behaviour as correct. A test asserting that the same value comes back can lock in the defect too.

  6. Set the stop condition before you run the review. This app's last review brief set it as: open no new verification areas, fix only blockers and highs, move medium and below to the backlog.

Four rounds, never zero

No round found fewer than 18 issues (chart below), and the blocker-plus-high count never reached zero. Round two read a single fix commit (83 files), and its document has no tally line, so only findings tagged with a severity are counted.

Round four read the latest fix bundle and judged 24 of its 26 findings to be defects that bundle had introduced. Its brief cited the record that every earlier review had found new defects made by the previous fix, and set the stopping point in advance. We stopped on that rule instead of waiting for zero, and the 16 findings rated medium or lower were marked as backlog candidates.

Neither the fix reports' "closed" nor matching guard-removal results held up as proof of closure this time. The fix agents checked their own fixes with guard-removal runs, but there is no record of any of them reviewing its own fix adversarially, so there is nothing to compare.

Round two confirmed the lobby lock and the forged bubble by reading code only; reproducing them with two real clients was left for a later round. Nobody launched the web build to see the relay defect either. Defect reports can be wrong too: the round-four brief counts 5 reported defects withdrawn during the round (contrast, splash screen, simulation artefacts).

Two things are still unchecked: whether any of the 16 findings round four marked as backlog candidates came back through another path, and whether fix commits in this app after September 11 actually wrote out the six axes.
