Six hard rules in one subagent brief, and five agents cut off by usage limits

In the four cases we can check, the report each cut-off subagent had been told to create first was still empty. The next agent picked up the work from the logs, screenshots and edited files left on disk.

By SugarMount · Working with agents · 12 min read · Last updated November 2, 2026

Five subagents working on the store release of our Flutter P2P chat app stopped before finishing. It happened between September 7 and 10, 2026: three hit the session limit, one hit the weekly usage limit, and one stopped for a reason nobody wrote down. Rule 6 of the shared brief said to create the report early and update it as the work went on. In all four cases where a committed copy of the report exists, every body section was still empty apart from the after-fix test's environment section. The agents that took over read git diffs, logcat files and screenshots instead, and the one task with no files on record, a full inventory of UI strings, was measured again from scratch.

Sources: the app repository's git history (e450c09, d464dc4, 7f52466, 9f03e7a, dca6cf9, af912bf, e9d882f, 67edc8d, 8dacf19), the shared brief and the three briefs that followed it, 17 analysis reports and 42 fix reports. Times are commit times in KST, except the start and end of handover work, which come from the reports. Report line counts and finding counts were recounted from git on November 1, 2026.

Five agents stopped between September 7 and 10

The analysis round landed at 23:10 on September 7 as commit e450c09: one shared brief of 33 lines and 17 analysis reports. Report 14, the emulator lab, was a 19-line skeleton. Its header said it was in progress with partial results, and every section read "(in progress)". Forty-seven minutes later, in d464dc4, the same file had 71 lines and a new header: the first agent had left device scripts and two install screenshots and stopped, and a second agent had carried on from there.

At 09:08 on September 8, commit dca6cf9 went in with the message "agent interrupted by session limit; to be continued". The agent consolidating the docs had stopped at the session limit with a 19-line skeleton report. The four docs it had already edited (the project's CLAUDE.md, the release plan, the security notes and the threat model) went into that commit as partial work. The same commit carried the result folders of the lab agent that, by its report, had started the after-fix end-to-end test at 00:24 that day. It had also hit the session limit, and its report had the environment table filled in and sections 2 to 8 marked "(in progress)".

On September 9 the device recheck (H1) stopped at the weekly limit, and the orchestrator finished it by reading the raw evidence itself. On September 10 the string inventory (X1) was committed at 01:45 as an 8-line skeleton and came back at 04:34 with 1,046 lines. Its new header said the previous agent had stopped at the session limit without leaving any measurements, so everything had been measured again.

The 33-line brief lists no per-agent tasks

The brief has four parts: a one-line goal, verified facts about the environment, six hard rules, and a report format. Each agent's topic came separately; those prompts are not in the repository. The environment part names the Flutter version and which binary to run, the two Android emulators, and "no physical device, no Xcode or macOS". The six rules, paraphrased:

  1. Install no system packages and add no new packages. If one is needed, write "approval needed" in the report.
  2. Upload nothing anywhere. Outputs stay as files in the repository.
  3. During analysis, do not edit code under lib/, android/ or ios/. Write scripts and documents only.
  4. No blanket sed replacements. Move files to a scratch folder instead of rm -rf.
  5. When checking an outside policy, give the URL and the date you checked it. Mark guesses as guesses.
  6. Write the report in Korean, at the assigned path, create it early and update it as you go, "so that partial results survive if the session is cut off".

The report format has five sections: summary, what was checked, findings, fixes that can be applied now, and remaining unknowns. The findings table has six columns: ID, severity (Blocker, High, Medium or Low), description, evidence (file:line or URL), proposed fix, and how to verify it. IDs carry a prefix per topic, such as AND-, IOS-, SEC- or LAB-.

The prohibitions were used. At e450c09, 13 analysis reports contain "approval needed". The store readiness analysis listed an icon generator package as "approval needed (rule 1)", and the iOS project analysis noted that using it would mean adding a dev dependency that needs approval. The fix stage skipped the package and generated the icons with a script on the Python imaging library that was already installed. The release workflows were written but not run. The brief left running them to the main session, and the first successful iOS compile run is recorded in commit 9f03e7a at 00:27 the next day. Eight UI findings were left as 11 deliberately failing tests rather than code changes. Keeping the prohibitions in one file the agent reads every time is the same idea as A permission table for a scheduled AI agent.

The format held too. All 17 reports have the six-column table and the unknowns section, and the 16 that had a body listed 233 findings, 15 of them Blockers. The fix reports took their work by those IDs; the iOS platform fix report alone cites 38 of them. The severity scale did not hold. The iOS project analysis used Info, which the brief never defined, four times, and the dependency and lab analyses invented "Low (confirmed false positive)" and "Low~Medium".

Rule 6 left empty report bodies

The brief assumed that a report created early would hold partial results if the agent was cut off. In the four cases where a committed copy exists (the lab analysis, the after-fix test, the docs consolidation and the string inventory), every body section read "(in progress)", except the environment section of the after-fix test.

The after-fix test report came closest to the rule. Its header told readers that blank cells meant "not measured" if the session ended. When the session did end, every result table was blank. The raw and screens folders in the same commit held two logcat files (103,813 and 89,023 lines), the signalling server log, 43 screenshots and the raw timings of 11 messages. The template script, anchored on the wrong log line, paired only one of them and reported n=1, 11 ms.

Rule 6 asked agents to create the report and to update it, but never said how often, and the findings were never written to a file. As far as the record shows, they lived only in the agent's conversation context. None of the agents cut off in this round got to tidy up its report before it stopped. What was left on disk were the files that running commands and editing docs had produced along the way.

The next agent read git diff and the raw folder

Four of the five handovers continued on files the earlier session had left; the second lab analysis agent, too, started from the first one's device scripts and two install screenshots. The docs agent stopped with its edits uncommitted, because the fix-stage brief let only the main session commit. The main session committed that state as dca6cf9. The finished report, in af912bf at 00:06 on September 9, shows the next agent starting with git diff 7f52466..dca6cf9 to see what had been done. CLAUDE.md had every requested change, the security notes had 7 of 8, and nine other docs plus the store drafts were untouched. The new agent left the finished parts alone and completed 19 files.

The after-fix test was picked up by another lab agent at 23:15 on September 8, by its report, and finished 50 minutes later. It kept the raw files for build, install, connection and messaging, and ran only the remaining tests (lifecycle, blocking, data reset and so on). It did not measure the round trip again; it recalculated it from the burst of 10 messages the earlier session had already sent, using the correct log anchor (p50 61 ms, p95 74 ms). The report grew from 41 lines to 338. The device recheck had stopped after its evidence was essentially collected, so 85 screenshots and 8 kinds of logs on disk were enough for the orchestrator to write the verdict.

The string inventory was reading and judging, and the record shows no files left behind. Starting from the 8-line skeleton, the next agent parsed all 2,864 string literals in 93 files under lib/ again and judged the 464 that can appear on screen. The brief for that round still carried the update-as-you-go rule. The contrast checker recount from the same commit, 8dacf19, is in Our contrast checker skipped 40% of the text.

Put the path and timing for raw evidence in a subagent brief before you ask for a report.

The verify column corrected a backup prediction

The platform security analysis read the code and predicted that an app restored from Android auto backup would lose its Keystore key and become permanently unusable (SEC-2). The lab agent did what the row's verify column said: backed up, uninstalled, reinstalled and restored with bmgr. The app did not get stuck. After a key unwrap error it went back to the setup screen and created a new profile, and the old keys and chat history disappeared without a word (LAB-7). The proposed fix, turning backup off (allowBackup=false), was still needed after the test.

The fix-stage brief said to verify each proposed diff before applying it. The UI fix agent reported that three of diffs A to H were wrong or incomplete and applied corrected versions: what Theme.of returns inside a bottom sheet, how button labels shrink, and the fact that useSafeArea: true does not handle the bottom inset. The instructions were wrong once too. The port assignment in the after-fix test instructions did not match the direction of the adb forward chain, so each app would have dialled itself; the agent swapped them and noted the swap in its environment table.

Letting subagents commit, or always starting over

One way to protect against interruptions is to let each subagent commit its own work. This round ruled that out. Several agents were editing files in the same working tree at once, and a single git stash, or a git checkout that restores files, could wipe someone else's changes. The cost was that interrupted work sat uncommitted until the main session committed it. How sessions collided in one working tree is covered in Claude Code sessions in one repo: file owner table.

The taking-over agent can also always start from scratch. With files left, the device recheck only needed a new verdict from 85 screenshots and 8 kinds of logs, and the after-fix test was finished in 50 minutes by its report. With nothing left, the string inventory re-parsed all 2,864 literals. Writing the report once at the end is what rule 6 was meant to prevent, and for X1 the outcome was the same as if it had.

We found no sign in the record that separate briefs per agent were considered. In practice the three later briefs (fixes, fixes for review findings, and the full inventory) each point back to the shared brief ("applies unchanged", "follow") and add what changed at that stage. Besides rules such as "edit only the files you own", "do not commit" and "write tests that fail when the guard is removed", the review-fix brief added an identity-binding API contract and the inventory brief added a table of expected outputs.

Read-only tasks and severity values outside the scale

Handing over from files on disk only worked where the work produced files anyway. A task that only reads code and judges it, like the string inventory or a code review, leaves nothing behind.

This round's brief listed the four allowed severity values and defined each, and Info and Low~Medium still appeared. If a tool will count or sort by severity, do not stop at listing the values; check the reports when they arrive.

The environment section is machine-specific. This round had no physical device and no Mac, so running on iOS and on real hardware all went to the unknowns. You can reuse the brief's structure, but check that section again on your own machine. We cannot say how many defects these rules prevented, because there is no comparable round without them.

A brief template and the commands for a handover

This template merges the rules of the shared brief and the fix-stage brief, and adds a path for raw output and a unit of update.

# <round> shared brief (<date>)
Goal: <one line>

## Environment (verified only)
- Tool paths and versions: <...>
- Devices available: <...> / not available: <...>

## Do not
1. Install or add packages. If one is needed, write "approval needed"
2. Upload anything. Outputs are files in the repository only
3. Edit files you do not own. Put requests in "requests to other owners"
4. commit, stash or checkout (the main session commits)
5. Guess without saying so. Outside docs get a URL and a check date

## Output paths
- Report: <dir>/<NN>_<topic>.md
  Create it first; the first line is exactly "Status: in progress"
- Raw: <dir>/raw/<NN>_*
  Save command output, logs and screenshots as soon as you get them
- Add a table row each time one finding or one measurement is done

## Report format
Summary / What was checked / Findings / Remaining unknowns
| ID | Severity | Description | Evidence (file:line / URL) | Proposed fix | How to verify |
Severity is exactly one of Blocker, High, Medium, Low

When taking over, read git and the raw folder before the report.

  1. Find unfinished reports by the status line or by the placeholder line that opens an empty section. In this round each report wrote its status differently, so the search found the placeholder lines, which used the Korean words for "writing" and "in progress". At dca6cf9, over the two folders (analysis and fix reports, device tests), this finds three: the docs consolidation, review and after-fix test reports.
    git grep -lE "^(Status: in progress|\((<writing>|<in progress>))" <commit> -- <report dirs>
  2. See what the previous session changed.
    git diff --stat <start commit>..<partial commit> -- <owned files>
  3. List the raw folder. If a measurement has a suspiciously small n, check the calculation script before measuring again.
  4. Set the report's status to done and add one line on who took over what.

Per-judgment rows are not measured yet

We have not measured how many rows survive an interruption when a read-only task like the string inventory writes one row per judgment.

FAQ

Does a subagent's work survive when it hits a session limit?

On this app, only the files it had already written to disk survived. Of the five agents cut off, all four with a committed report had empty bodies apart from one environment section; four of the five handovers ran on logs, screenshots and edited files, and the fifth had nothing and started over.

What should a subagent prompt state first?

What not to do, where outputs go, and the report format. The shared brief here spent its 33 lines on those three and on environment facts, and each agent's topic was given separately.

Does letting subagents commit solve the interruption problem?

We did not try it. Several agents edited the same working tree at once, so only the main session committed; when an agent was cut off, the main session committed its partial work and said so in the commit message.
