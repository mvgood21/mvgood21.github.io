Play Store title keywords: two weeks, no verdict

With about one real user a day, changing a Play Store title could not be judged from search ranks alone; the measurement design had to be fixed before the title was.

By Stephen · Play Store and monetization · 9 min read · Last updated November 15, 2026

We rewrote the Google Play title of our Korean document viewer around search keywords, then tracked its search rank for two weeks. On the main keyword, 한글뷰어 ("HWP viewer", also the app's launcher name), it slipped from 13th to 16th, while two other keywords rose. The note we wrote on day 14 says "no clear gain".

The app had about one real user a day, the search page returned a different number of apps each day, and two of the planned measurement days were skipped. Before you change a title, measure a baseline twice with the same script and put the measurement days on a schedule.

Two weeks of ranks

Each run fetched the logged-out Google Play web search page (Korean language, Korea region) with a script and counted where our app sat among the apps on the page. We call the day of the title change, October 18, D0, and count days from there (D+5, D+14). HWP is a Korean word-processor file format, so most of the seven keywords are Korean phrases about opening those files. The new title was "한글뷰어 슈가독: HWP 한글 파일 열기·PDF 저장" in Korean and "SugarDoc HWP Viewer & PDF Save" in English.

Look at the grey bars before the blue dots. The logged-out page returned a different number of apps for the same keyword on different days. For "hwp viewer" it was 22, then 50, then 15. On the day the list grew to 50 our app showed up for the first time, and when the list shrank it was gone again. The October 28 rank file itself put that rank down to the page getting longer.

So the day-14 run on November 1 only compared keywords whose result count (the number of apps the page returned) stayed within one of the previous run.

KeywordOct 28 (D+10)Nov 1 (D+14)Results
한글뷰어 (HWP viewer)14th16th29 → 28
hwp28th20th30 → 29
한글 문서 (HWP document)22nd11th28 → 28
hwp 뷰어 (hwp viewer)25thnot listed50 → 15, not comparable

Two keywords did rise. But the keyword that matches the app's name slipped across both weeks, and 한글 파일 열기 ("open an HWP file"), which went into the title word for word, still did not make an 11-app list. The November 1 rank file calls this "no clear gain" and adds on the next line: "Signal is weak: 1 real user a day".

Four things that blocked a verdict

First, rank was the only thing we could measure. In those two weeks GA4 (Google Analytics 4) counted 0 to 4 real users a day, after filtering out test devices, emulators and Play's pre-launch robots. A rank can move a few places with no way to see whether installs followed. The ASO (app store optimization) plan written the day before the change said there were too few installs for an experiment to mean anything, and that experiments should wait until weekly installs pass 100. The same section also planned rank runs after the title change, and the only conditions attached to the change were shipping and checking the PDF save feature (SAF PDF save: cancelling without empty files).

Second, the list length kept changing, as shown above. Keeping only keywords with a steady result count where our app appeared left the HWP viewer keyword alone on October 28, and three keywords (HWP viewer, hwp, HWP document) on November 1.

Third, the baseline and the later runs did not come from the same script. The "21st before the change" was counted on October 17 from the same logged-out page, fetched with curl for a competitor survey, and inside that same survey the lead agent had counted 20th. The script's first value came five days after the change, at 13th, and the agent that committed it wrote that one run cannot separate the title effect from day-to-day noise.

Fourth, the description, app versions and a help article changed along with the title. The two-week test plan the agent wrote on the day of the change already listed "three things that changed": the store text, the 1.2.0 release with direct PDF save, and a help article on our site. After that the full description changed once more and four more app versions shipped. Play Console's store listing experiments cannot test titles, so there was no control group either.

There was no rank run on October 25, day 7. That morning the operator reported that a landscape slide PDF would not scroll, and that day's five runs went to the daily check, the fix and the 1.3.2 release, and a lock change in the Play upload script. The only measurement days left in the repository are sentences in a rank file note and a commit message. We could not check whether the scheduled runs' instructions included a rank run.

The "keywords in the title get you into the top 10" idea was not confirmed

An agent wrote both the competitor survey and the ASO plan. Its working hypothesis was that a title containing the search words verbatim gets even a small app into the top 5 to 10, based on another app with installs in the hundreds and no ratings that ranked near the top on all seven keywords. The counterexample was already in the same survey: our title contained 한글뷰어 exactly, and we were 21st. Two weeks later, a title containing 한글 파일 열기 verbatim still did not appear for that keyword.

Before the plan was committed, it went through an adversarial check, where a second agent tries to refute each claim. The survey agent had stated "3 real installs" as fact; the check changed that to "public install band 1+, 2 to 3 daily users in the console" and marked the cause of the low rank as a guess.

On October 8 the operator read a trademark search and chose to use 한글뷰어 in the title. On the day the new title was uploaded to Play at 15:45 Korea time, the agent listed a two-week Google Ads test as the next step. When the operator asked whether a 14-day spend was really needed, the agent withdrew the advice, saying that with ads running at the same time a rise in installs could not be traced to the title or the ads. The operator then decided not to spend money, to publish search articles instead, and to plan ads after the two-week test. No record shows a person changing the measurement design.

Five days of checking a stale copy

The desk that prepares these notes missed the result too. The day-14 file was already on the remote main on November 1, but our harness, the scheduled script that runs agents to check story ideas, only looked at the local copy and postponed this post on November 2 and 6 as "not measured yet". The November 6 morning check even missed the October 23 and 28 files that were already in that copy. The copy was behind the remote; the run early on November 7 read the remote directly with git show origin/main:<path>, found the file, and added the same rule to the desk's procedure.

Users rose after day 14

After the verdict, daily real users went up: 5 on November 3, 11 on November 9.

We cannot tie this to the title. In the same weeks, short video posts started, tablet screenshots went up on the store listing, and the site moved to a new address. The backlog said "next rank check November 8", and that run never happened.

If your app has single-digit daily users, do not judge a store title change by search rank. Until weekly installs pass 100, log it and stop there.

This comes from one app, seven keywords and four runs. We never measured twice on the same day to see how many places the rank wobbles on its own, and we did not record whether competing apps changed their titles in those two weeks. Measurements from the viewer engine side of the same app are in Building an Android HWP viewer with rhwp: measured. The plan to alternate the title with a spaced spelling, 한글 뷰어, has not started.

These are the measurements we did not use this time.

MethodWhy not this timeWhen it fits
Search installs in Play Console's store listing acquisition reportThe ASO plan left it to the operator, and nobody opened it this timeOnce installs pile up enough to count search traffic on its own
Rank on a real, logged-in phonePlanned as "once on the same day", but no record existsWhen you need to know how far the logged-out web order is from what users see
A Console experiment on the short descriptionTitles cannot be tested, and the plan judged installs too few to mean anythingAfter weekly installs pass 100

What to pin down before the next title change

  1. Measure the baseline at least twice with the same script you will use afterwards. Fetch https://play.google.com/store/search?q=<keyword>&c=apps&hl=ko&gl=KR, list the distinct app ids in the order they appear on the page, and use your app's position in that list as its rank.

  2. Record the result count (the number of distinct app ids) next to every rank, and compare only keywords whose count stays within one. Keep the rest as "not comparable". One line per keyword and day is enough.

    date | keyword | rank | results | changed that day
2026-11-01 | 한글뷰어 | 16 | 28 | nothing

  3. Put the measurement days on a schedule, including a run on the day of the change (D0).

  4. Change the title and nothing else. If a description, app version, help article or screenshot changes in the window, write it in the last column.

  5. Write the verdict rule into the repository first. Following the logic of the November 1 verdict, call it a gain only if the main keyword rose on a like-for-like basis at both D+7 and D+14.

  6. Read measurement files from the remote with git show origin/main:<path>. Our local copy was more than two weeks behind.

Checked 2026-11-13. The app repository's three rank files (1cc0044, 68215b5, 9043d19), weekly_rank.py, the competitor survey and ASO plan (8475f45), store text changes (c4f1dd3, 1b7c328), GA4 real-user values in the daily ops reports (Oct 27 to Nov 11), the run log, Claude Code session transcripts from Oct 17 and 18, and this desk's check records (Nov 2 to 7; the local copy was 28 changes behind).
