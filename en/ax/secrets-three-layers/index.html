Keeping secrets away from an AI coding agent: one rule for chat, logs and token permissions

Give the agent commands that check without printing values, keep log masking in one function guarded by a test that fails on copies, and give deploy tokens only the permissions the code needs.

By SugarMount · Testing and release · 11 min read · Last updated November 13, 2026

Giving an agent rules and limits 5/5

An AI coding agent reads files, writes code and designs deployments, and each of those opens a path for a secret to leak. Whatever it reads lands in the session log, the logging code it writes can print tokens, and the deployments it plans can ask for broader tokens than the code needs. All three paths opened for real in three SugarMount app repositories; this note shows how each was closed. The rule behind all three fits in a sentence: never copy a secret's value anywhere, only say where it is and what kind it is.

Chat: the first secrets rule was written 47 seconds after a key reached the session log

On the morning of October 2, 2026, the operator asked the agent to fill in the shared instructions every session reads. To learn the setup, it printed the last 150 lines of the shell history, and one of them exported an AI API key. Tool output is saved verbatim in the session log, so the key was now part of the transcript.

Forty-seven seconds later the agent wrote the first secrets rule into the instructions: one line saying secrets stay out of any output. It said what not to do and nothing about how to check, and for an agent, reading a file and printing it are the same action. The agent then told the operator that an AI API key sat in plain text in the shell history, giving the location and kind but not the value.

Eight minutes on, the operator asked for a rule that keeps passwords and personal data out of every session's chat, and the agent replaced the one line with a rule that also says how to check. Files are checked with commands that show key names and line counts (grep -c, cut -d= -f1), and commands take environment variables or file references instead of values. It covers commits, docs and memory files as well as chat, and a value someone pastes in is not quoted back; the agent recommends rotating it. The scope also widened to personal data.

The agent deleted the four history lines that held the key and counted again: zero. It listed what it left alone, the running session's log file, which could break if edited mid-session, and the terminal window where the key had been typed, and said that deleting doesn't undo the exposure; rotating the key is the only sure fix.

To see whether the rule changed habits, we recounted the session logs on October 25. What grew was the names-only check; counting lines was already a habit before the rule.

Lines matching three known key shapes (the newer AI API key format, GitHub tokens, sk- keys) came to exactly one across all 2,567 logs including subagents: that October 2 output.

# .env: line count and key names, no values
grep -c '=' .env
cut -d= -f1 .env

# shell history: how many lines mention that key name
grep -c 'API_KEY' ~/.bash_history

# commands reference values instead of containing them
curl -H "Authorization: Bearer $API_TOKEN" https://api.example.com/v1/ping

Logs: four copies of a masking regex, and two exceptions that never masked

The chat app (Flutter) passes a shared token as ?token= in the signaling server URL. On September 7 the agent reviewing it before release rated this High: the discovery logs went through debugPrint, which prints in release builds too, and four connect-log lines wrote the whole URL.

The reviewing agent proposed Uri.parse(url).replace(query: null), which keeps the query: in Dart's Uri.replace, a null argument means "keep the existing component". The agent assigned to fix it caught that and switched to a one-line regex.

The copies came from how the work was split. Several fix agents each owned a set of files that day. The mobile owner's scope was "one masking line" in its two files, and the two web files went to another owner, where a separate _maskToken wrapped the same regex. The next day's docs said "regex duplicated in 4 files; extracting a shared helper is still open", while the defect list already said Fixed.

On September 13, writing the shared function meant looking at every place each file turned the URL into a string. Two HttpException sites in the mobile HTTP client had no masking at all: a failed connection or POST put the token into the exception message or its uri field. The mobile owner's first fix had covered the success log line only.

String maskSignalingUrl(String url) =>
    url.replaceAllMapped(_signalingToken, (m) => '${m[1]}***');

final RegExp _signalingToken = RegExp(
  r'([?&](?:token|secret)=)[^&#\s]*',
  caseSensitive: false,
);

The new pattern ignores case, also covers secret=, and stops at # or whitespace. We ran the old pattern ([?&]token=)[^&]* and the new one through Python's re on placeholder values to see the difference:

InputOld regexNew regex
ws://h/ws?TOKEN=XXXXunchanged?TOKEN=***
ws://h/ws?secret=XXXXunchanged?secret=***
ws://h/ws?token=XXXX#frag?token=*** (fragment eaten)?token=***#frag
http://h/api/token/listunchangedunchanged

Three kinds of tests went in with it: 7 rule tests, 1 source guard, and 1 real failure path. The failure-path test starts an HTTP server on the loopback address that answers 401 and checks that the client's exception text contains token=*** and not the value. The source guard, shortened:

test('no copy of the masking regex comes back in discovery', () {
  final offenders = <String>[];
  for (final f in Directory('lib/core/discovery').listSync()) {
    if (f is! File || !f.path.endsWith('.dart')) continue;
    if (f.path.endsWith('discovery_log.dart')) continue; // the definition
    final src = f.readAsStringSync();
    if (src.contains('token=)') || src.contains('_maskToken')) {
      offenders.add(f.path);
    }
  }
  expect(offenders, isEmpty);
});

It fails if the regex fragment token=) or the old helper's name shows up in any file other than the definition. The duplication stayed for five days after it was written down on September 8, so copies are now blocked by a test rather than left to review. Keep one masking function, and commit a test that fails when a copy appears.

Release logcat also carried what users typed

On October 17, QA on the SugarSpeller spell checker found the same class of bug in its release logcat, the Android device log. Up to version 1.6.030, release builds logged the check request URL (which contains the user's text), the start of the raw response, a session key for the external checking service and the push notification token. In the app's logging wrapper, log.e prints whether or not the build is a debug build.

Diagnostic lines moved to log.d, and keys and text are logged only as a length or a present/absent flag. A new test scans all main sources for log calls that print in release and looks only at interpolations and arguments outside string literals. Its first test feeds in the 7 old leaking lines and requires all 7 to be caught (the same yardstick as in 3,066 green tests hid a line that breaks opening the database: checking tests by deleting the guard). A release build of the next version went onto a Galaxy S20, and logcat showed zero such lines.

Permissions: the Worker was redesigned instead of adding permissions to the token

The family app keeps photos in Cloudflare R2 object storage, with a media Worker handling uploads and reads. The deploy notes of October 10 listed three jobs for a person: add Workers KV edit and billing read to the deploy token, create a separate token for the usage analytics API, and issue an R2 S3 key pair so Firebase functions could delete objects. The reason was a free-tier guard that read Cloudflare's analytics API every hour.

That night the operator told the agent to do the work itself instead of handing it over, and around midnight the agent committed a Worker that runs without any extra token. The first design, one new credential per feature, had been the agent's own; this time it rebuilt the same features on the R2 binding, the Durable Object and the shared key it already had. By design the token needs 2 permissions: Workers Scripts Edit and R2 Edit.

  • A Durable Object (a stateful object that runs next to the Worker) now counts the day's requests and R2 reads and writes itself. When the total passes a set share of the free allowance, uploads and reads close for the day and reopen at the next midnight, Korea time.
  • Functions delete R2 objects through a signed DELETE request to the Worker instead of S3 credentials. The signing key is derived from an HMAC key the functions and the Worker already shared; timestamps must be within 60 seconds, a nonce works once, and only paths under the requesting family's folder are deleted.
  • Worker secrets went from 3 to 1, and billing read was never added.

The cost is written down in the ops notes. Because the delete-signing key comes from the shared HMAC key, all 4 function service accounts that can read that key could in theory sign a delete. Narrowing it again means a separate delete key, which is one more Worker secret.

A read-only ops check the next day found the real token had 3 permissions, one more than the design: Account Settings Read. With no billing read, the plan API answered with an auth error, which also confirms this token cannot change the plan or billing.

A copy written another way passes the source guard, and masking does not protect the token

The source guard looks for two strings in one folder. A regex written another way, or a copy in another folder, passes. The spell checker's log scan works line by line, so a log call split across lines gets through.

Masking does not protect the secret itself. The chat app's token is a constant in the app binary and can be extracted, which is why the app treats it only as spam control. The review found the web client cannot send the token in a header, so the fix closed the path from URL to log instead. The chat rule works only while the agent follows it, and the count only finds key shapes we know.

The same night the Worker was reworked to need no extra token, the agent's own tool permissions grew. Its permission checker blocked the IAM grant commands, and approval in chat did not lift the block; an allow rule in the settings was required. The agent asked for lines allowing all gcloud, npx firebase-tools and curl commands, and the operator added them. How we scope what an agent may do on its own is in A permission table for a scheduled AI agent: what it does alone, and which clicks a person makes.

Checks to add to agent instructions, masking code and token scopes

  1. Put checking commands next to the prohibition in your agent instructions: grep -c, cut -d= -f1, and $NAME references in commands (on the file itself: How to write AGENTS.md: only the rules an AI coding agent gets wrong).
  2. Don't let the agent read the shell history or .env whole. Have it count the lines that mention a key name; delete any key it finds there and rotate it. Pass new values through a prompt or a file, not a command argument.
  3. For each kind of string that carries a secret (a URL, say), keep one masking function and call it everywhere that string is built: logs, exception messages, exception uri fields, diagnostics maps.
  4. Write three tests: the rules (case, other key names, fragments, the same word in a path), a source guard (regex fragments outside the definition file), and a real failure path (a 4xx from a local server).
  5. Feed a log checker the old leaking lines first and confirm it catches them.
  6. Install a release build on a real device and search logcat by key name or marker. Grepping for the value puts the value back into your shell history.
  7. For tokens, write down the permissions each feature needs, and before adding a credential check whether an existing binding or key can do the job. Confirm the real scope with read-only calls.
  8. Where something got wider, write one line: what widened, and what it would take to narrow it.
# release logcat: count token= lines that are not masked
adb logcat -d | grep 'token=' | grep -vc 'token=\*\*\*'

What is left: one stale doc line, one transcript line, one undeployed Worker

The chat app's security doc still says "regex duplicated in 4 files"; the code changed and that line did not. The key-shaped line in the October 2 session log has not been deleted, and the logs don't show whether that key was rotated. For the family app, once the Worker is deployed, we need to confirm uploads and deletes work with the 2 designed permissions and whether the extra Account Settings Read is needed at all.

FAQ

Is it safe to let an AI coding agent read my .env file?

Not in a way that prints values. Agent tool output is stored in the session log as is. With cut -d= -f1 .env for key names and grep -c for counts, the agent can still tell whether a setting is missing.

Why is a masking regex copied into several files a problem?

What one copy handles doesn't carry over to the others. In this chat app the web copies masked failure messages too, while two failure exceptions in the mobile file sent the token unmasked. One function plus a source-guard test that fails on copies prevents it.

How do I cut down the cloud token permissions an agent uses?

List the permissions each feature needs, and before creating a credential, check whether an existing binding or shared key can do the same job.
