GA4 custom dimension (not set) for numeric params

Arrow Knots had a GA4 custom dimension registered for the level and still read (not set) for five weeks. Sending the same level number once more as a string made it readable in all 41 events from the new build.

By Stephen · Android development · 9 min read · Last updated November 22, 2026

Our Android puzzle game Arrow Knots had a level custom dimension registered in GA4, yet for more than five weeks after analytics went in on October 8 we couldn't see which level players quit on. The level column in every report read (not set). The registration was fine; the app was sending the level number as a number. Claude Code wrote that analytics code, and the record from that time shows no report ever split by the value.

The build we shipped on November 15 sends the same level number a second time, as a string. In the events it has sent since, the numeric slot is still empty and the string slot has a value every time.

41 events, the numeric level empty in every one

Arrow Knots 1.2.6 puts the level number into its level_up event, sent the first time a campaign level is cleared, twice: once in the original numeric parameter level, once in a new string parameter lv. On November 21 we pulled the counts through the GA4 Data API (the official API for reading report data). Of the 41 level_up events from 1.2.6, all 41 had a value for lv and none had one for level. The numeric stars parameter, which holds the star rating, was empty in all of them too.

What split the two slots is the type the value had going into Firebase. Firebase ships event values in a container called a Bundle, and the app's shared Analytics.log helper puts a Kotlin Int or Long in with the numeric putLong, a Double with putDouble, and everything else with the string putString. In this call, 1.2.6 changed the line like this:

// up to 1.2.5: the level as a number only
log(FirebaseAnalytics.Event.LEVEL_UP, FirebaseAnalytics.Param.LEVEL to level1, "stars" to stars)
// 1.2.6: the same number again as the string lv
log(FirebaseAnalytics.Event.LEVEL_UP, FirebaseAnalytics.Param.LEVEL to level1, "lv" to level1.toString(), "stars" to stars)

level1 is the level number counted from 1, and FirebaseAnalytics.Param.LEVEL is just the string "level". From October 17, when the dimensions were registered, through November 20, numeric level and stars were readable in none of Arrow Knots' 3,319 level_up events. Test phones and emulators were excluded with the filter from GA4 installs: 11 of 19 were test devices.

Our block puzzle, Block Turn, shows the same pattern. Its 972 level_up events also carry a string pid, the board ID (for example R001). pid was readable in 943 of them; numeric level and stars in none. level is a parameter name Firebase defines, but stars is one the app made up, and it was empty too, so what decided it was the type rather than the name.

October 27: looking for the last level before uninstall

We found this while chasing a different question. Of six new Arrow Knots players who came in from ads on October 26, five uninstalled the same day. The next day's check, run by an agent, wrote down the task "collect the last level that uninstalling players reached" and queried GA4. In that query, level was (not set) for the whole history.

The first hypothesis was ten days older. During a deeper GA4 review on October 17 we registered event-scoped custom dimensions (scoped to values attached to a single event): 9 for Arrow Knots, 13 for Block Turn. The note said "data only accumulates from 10-17". Custom dimensions don't backfill, so the expectation was that values would show up from the day of registration. Nobody split a report by that dimension for ten days, and the first query on October 27 showed the expectation was wrong. The bars from October 17 to 26 in the chart are grey as well.

The agent's note on October 27 read: "Both apps' Analytics.log sends Int with putLong, so the numeric parameters appear not to be picked up by these dimensions." The same document had the fix: also send the level as a string, such as lv = "25", register a dimension under that name, and get the operator's approval before shipping. The same (not set) and the same fix are listed in the open items of Puzzle game time limits: 3-star par by simulation.

The dimensions were registered; the type split the values

The GA4 Admin API lists the custom dimensions on the Arrow Knots property (GA4's container for one app's data). Today there are 10, all event-scoped, level and stars among them. The numeric world dimension never showed a value either, while string values on the ad impression event did.

We haven't confirmed why GA4 leaves numeric values out of these dimensions, and we never tried registering the value as a custom metric instead.

The AI's mistakes were the October 8 commit 5396a0c (co-authored by Claude Code), which sent Int values as numbers, and the October 17 assumption that registering would make values appear from that day, which cost ten days of waiting.

The fix kept numeric level, added the string lv on the same event, and registered lv as a dimension. It is one line, and existing level data and milestone events stay as they were. Putting the number in the event name was already in use: tutorial steps fire tut_N_done, each with its own event name, so they need no dimension. That only works when there are few steps. The campaign has hundreds of levels and only four milestone events, which left levels 25 to 50 blank.

The milestone events exist so Google Ads can import conversions by event name, and those names stayed untouched. Removing numeric level, or keeping the name and switching it to a string, were also possible; the record shows we added a new name, lv, instead.

The 1.2.5 release the next day had no lv

On October 28, the day after the fix was written down, Arrow Knots 1.2.5 was submitted to production (commit c1f5811). It changed the big button on the daily puzzle result screen and did not include lv. That day's write-up of the release only said that the numeric (not set) and the rewarded-interstitial events were still open. From October 30 the harness (agent runs that start on a schedule with no one at the keyboard) did only marketing work, such as ad budgets, videos and posting, and changed no app code.

The same October 28 document said nobody could tell why new Block Turn players didn't return the next day, because the last board they played wasn't visible. When we queried on November 21 for this note, Block Turn was sending the board ID pid as a string. pid was readable in 943 level_up events, so the last board a player solved could have been seen through it. "Not visible" had been judged by the numeric level.

The weekly check on November 15 raised it again. It noted all 1,306 level_up events from November 1 to 14, as counted then, read (not set), so there was no telling where between levels 25 and 50 players stopped.

That night the operator said, in effect, "if something is confirmed, ship a new version," and 1.2.6 went out as commit 64e4df1. Pre-release tests (unit, on-device end-to-end, monkey on the release build) all passed. The end-to-end log shows only that the app sends lv from the device. Whether GA4 shows the value could only be checked after release, and that check is the 41 events above.

Split one report before release

  1. Don't ship an instrumented build until a GA4 report split by the new parameter shows values. Use an Explore report or the Data API, not the device log.2. Check the type that goes into the Firebase Bundle. For any value sent with putLong or putDouble that you want to split reports by, also send a putString copy.
  2. Custom dimensions don't fill in data from before registration, so query once the day after you register. Don't wait ten days.
  3. Put the numeric and string versions on the same event, and a single build tells you which one GA4 shows.

A request of this shape (test-device filter omitted), with the property number left as a placeholder. The customEvent: prefix is how the API names a custom dimension.

POST https://analyticsdata.googleapis.com/v1beta/properties/<property>:runReport
{
  "dateRanges": [{"startDate": "2026-11-15", "endDate": "2026-11-20"}],
  "dimensions": [{"name": "customEvent:lv"}, {"name": "appVersion"}],
  "metrics": [{"name": "eventCount"}],
  "dimensionFilter": {"filter": {"fieldName": "eventName",
                                 "stringFilter": {"value": "level_up"}}}
}

Run it again with customEvent:level in place of customEvent:lv to see both slots for the same events and dates. Keeping appVersion in the dimensions shows which build the values start in. Counting test devices too, every version up to 1.2.5 had level as (not set), and all 44 events from 1.2.6 had a value in lv.

Before the level verdict

A string dimension lets you group by level number as a category. Averages or sums of the level would need something else. The level numbers in the 3,278 events sent by builds other than 1.2.6 between October 17 and November 20 (including 1.2.5 events that kept arriving after November 15) will never be readable in GA4.

The sample is small. The 41 events fall on four days between November 15 and 19 (none on the 16th), and the levels in them sit in a few stretches: the first twenty, then a handful past level 100. That is not enough to say anything about drop-off per level.

After November 22, with more than a week of lv from 1.2.6, we look at where between levels 25 and 50 players stop. That is the check the November 15 review scheduled for one week after release.

Block Turn still sends the level number only as numeric level. Since the last board a player solved is already visible through pid, what remains is deciding whether it needs a string copy of the level number or whether pid is enough.

FAQ

Why does my GA4 custom dimension show (not set)?

In this app it showed (not set) only for parameters the app sent as numbers (putLong). The dimensions were registered with event scope, and string parameters on the same events had values.

Can I send a numeric parameter as a string?

Yes, if you use it as a category to split reports by. Arrow Knots kept numeric level and sent the same value again as string lv, and all 41 events from that build showed it.
