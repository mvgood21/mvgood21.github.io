13 parallel AI agent branches passed review and CI; a review of the merged code still confirmed 12 defects

Every branch had its own agent review and green CI. A separate review of the merged code still confirmed 12 defects the existing tests had not caught; by our count, 10 sat between two packages.

By SugarMount · Working with agents · 12 min read · Last updated November 1, 2026

Six review agents that read only the merged code reported 2 blockers and 10 majors, and the agents assigned to refute them could not knock down a single one. Before that, each of the 13 feature branches had been reviewed by three adversarial agents and had green CI. This happened in the early hours of October 10, 2026 (Korea time), while merging the first parallel wave (Wave 1) of AXFamily, our family calendar app. None of the 12 were caught by the existing tests or showed up as a git conflict. By our classification, 10 of the 12 were broken agreements between code written by two different packages.

Sources: git history (merges 58920b9 to ff0c975, a0351cf, 941d79e, c153fae, 74d3685, 5d51b5b, cee9d0f), the descriptions of the integration PR and the billing package PR, the fix report, and the integration workflow script with its run log (each agent's findings and refutation verdict). Times are KST. Rechecked on 2026-10-31.

From the 01:51 merges to the 05:34 PR merge

Wave 1 ran one workflow that put every package through the same steps: one agent implemented it, three agents reviewed the branch through security, cost and correctness lenses, and a fix agent addressed their findings and got the PR to green CI. The two-minute merge of all 13 branches starting at 01:51, and the minimal fixes for 6 package pairs in a0351cf at 02:09, are covered in Claude Code sessions in one repo: file owner table.

Three wiring commits followed to apply the lead session's cross-package decisions, in the order contract, server, app (941d79e at 02:53, c153fae at 03:42, 74d3685 at 04:23). The code the review read included those wiring commits.

The six reviewers started together at 04:29 and finished within 6 to 9 minutes, making 30 to 95 tool calls each. At 04:38 each of the 12 blocker and major findings went to its own refuting agent, and within a minute all 12 came back as real. The fix agent pushed 5d51b5b at 05:28 (115 files, 2,088 lines added). Once all 11 CI jobs passed, the integration PR was merged into develop at 05:34.

The first assumption: green tests meant the integration was done

The plan described Wave 1 as "parallel feature work (separate files only)", and its conflict rules were written per shared file. The integration step was told to resolve conflicts keeping both sides' intent, run every test suite, and fix integration breakage minimally.

The integration agent finished by that standard. Its PR description said it had fixed only what the integration broke, and listed the numbers: 977 Flutter tests, 274 function unit tests and 291 emulator tests, 441 Rules tests (5 skipped) and 132 media Worker tests, all passing. None of the 12 defects found later changed any of those numbers. The lead session had put a review step at the end of the workflow, and that step is where the defects appeared.

32 findings from six lenses; 12 survived refutation

The six lenses were Rules and contract, function security, cost, app security and privacy, app UX, and flow tracing, which followed the core user flow in code from sign-in to account deletion. They reported 32 findings: 20 minor and 12 blocker or major. The cost lens reported only 3 minor findings. One finding from Rules and contract and one from function security were the same defect, found from both sides, so there were 11 distinct defects.

The refutation prompt told each agent to read the code and refute the finding, defaulting to "not real" unless the defect could be shown. Each refuter made 3 to 6 tool calls and returned a verdict in 16 to 25 seconds. The verdicts cited files and line numbers; the one on the missing index pointed out that comments and assets, queried the same way, already had their composite indexes.

Only two stayed inside one package: the share inbox files and the bottom button. In the other 10 (9 distinct defects), each side was correct on its own. In the PDF case, the app sent a first-page thumbnail exactly as its own code comment said, and the server counted pages from PDF bytes exactly as the contract said at the time.

Each branch review read only its own diff

The branch review prompt had each reviewer read git diff origin/develop...origin/<branch>. The index file already existed on develop, and the Rules package was changing it on its own branch, but it never appeared in the diff read by the agent reviewing the records screen's sorted query. The same held for app capture: the server check that accepts only application/pdf for PDF sources was already on develop, but not in that reviewer's diff.

The billing package's review had already found one of these defects. In that branch review, the correctness lens had been told to grep for production callers of every new API, the same rule the operator now keeps in the global instructions for all projects. That review did find that nothing called the billing entry widget, but rated it minor; the billing re-review just before integration raised it to major. The call belonged in the family screen file, which the file owner rules kept the billing fix agent from touching, so the agent put the item in the PR description's "to align with other packages" section, marked as required at integration. The integration workflow's wiring task list was already written into the script when it launched at 01:28, before the billing re-review finished. The item came back as a blocker in the integration review that started at 04:29.

Tests ran per package against that package's own fakes and the Firestore emulator. As the comment at the top of the index test file already said, the Firestore emulator does not enforce composite indexes. The contract's query table listed sources among the list queries, but the required composite index list in the same section left sources out. CI passed, and only the production Firestore would have answered with FAILED_PRECONDITION. (The review caught it before any production deploy, so it never actually happened.)

Agent-written code and tests also hid mismatches. A comment in the today/calendar code said the active-household key was "written by A1's household switcher" (A1 being the family screen package), but git grep found no code anywhere that wrote that key. The bottom button test was named "the FAB is on every tab"; it locked in the placement and label the spec had ruled out.

After merging parallel branches, run a review that reads only the merged code, however many branch reviews came before.

The check we kept: a sorted-query-to-index table

According to the fix report, 5d51b5b added for each defect a test written to fail on the code before the fix; the Rules, index and consent fixes were actually reverted to watch the tests fail. (The revert technique is in Finding fake tests by deleting their guards.) Two of the fixes were turned into checks for the next mismatch of the same kind.

For indexes, the Rules test suite gained a table of app queries that use orderBy. Each row names the app file, the query and the index it needs, and the test looks for that index in the index file. A final test counts how often orderBy: ' appears in each listed file and compares that with the number of table rows, then compares the list of app files containing the string with the table's files. Anyone adding a sorted query has to add a row first.

const count = (rel) => (readFileSync(resolve(appRoot, rel), 'utf8').match(/orderBy:\s*'/g) ?? []).length;
// …
expect(actual).toEqual(expected);
// fail if a file outside the table uses orderBy: '<field>'
const all = execSync(`grep -rlE "^\\s*orderBy: '" lib || true`, { cwd: appRoot, encoding: 'utf8' })
  .split('\n').filter(Boolean).map((f) => f.trim());
expect(all.sort()).toEqual(files.sort());

By October 13, three more app files with sorted queries had been added to the table. The history does not show whether the table check failed first and forced those rows. For household selection, the fix made the app session's current household the single source of truth; with two or more households and no valid selection, the picker returns null instead of falling back to the first one. Three tests pin that rule.

Other routes: a staging project, shared test vectors

A real Firestore project would have exposed the missing index at once. The plan had postponed a staging project until after launch, citing low benefit for the risk and one more place that could incur charges. The device end-to-end runs that same morning used an emulator backend to keep costs at zero, so they would not have shown it either.

One method had already worked. The billing package's tests were written to read a shared vector file (expected results for whether a subscription counts as active) that the billing server package would add, and skipped themselves with "runs automatically once merged" while the file was missing from develop. Right after the merge, that test ran and caught the app and server disagreeing on the entitlement check, which a0351cf fixed. Contracts without a vector file, like consent eligibility or household selection, could not be caught by that test.

What a read-only review missed: three device E2E rounds

Three rounds of device E2E, run after the E2E harness commit at 07:37 the same day, found more runtime defects. One of them, d3fde30, fixed Firestore triggers that crashed without a default Admin app, and the 5d51b5b fix report itself says the Android side got Kotlin unit tests only. Why device checks run separately even after a review converges on zero is covered in Agent code review: fix what survives refutation.

Each finding got one refuter for 16 to 25 seconds, so 12 out of 12 surviving is not evidence that refutation can be dropped. The app UX lens was told to compare screens against the written UI spec, and the button and banner findings cited spec clauses. In a project without a written spec, that lens has nothing to compare against.

How to run integration review as its own step

  1. Collect every branch PR's "to align with other packages" list into the integration task list. Finalize the wiring list only after every branch review is done.
  2. Once everything is merged and all suites are green, hand the integration diff to one read-only agent per area, asking for concrete defects with evidence only and for each one to be refuted by the reviewer before it is reported. AXFamily's six lenses were Rules and contract, function security, cost, app security and privacy, app UX (screens vs. the UI spec), and flow tracing (sign-in to account deletion).
    git diff --stat origin/develop...origin/<integration-branch>
  3. Count production callers for every new widget, function and parameter, excluding the file that defines it. Zero is a finding by itself.
    git grep -n "BillingPlanRow(" -- apps/app/lib ':!apps/app/lib/features/billing/plan_row.dart'
  4. Send each blocker and major to a different agent to refute, and drop anything it cannot be shown (the procedure is in Agent code review: fix what survives refutation).
  5. For each confirmed defect, add a test that fails on the old code, and revert the fix once to watch it fail.
  6. Turn each defect type into a check: a table check when both sides can be counted, like queries and indexes; a shared vector file read by both sides' tests when it is a decision rule.

Next to check: server queries and gaps in the table

The sorted-query table counts only the orderBy: ' string in app code. Server function queries were still added to the required index list by hand on October 13, and the shape of each where clause depends on whoever writes the row. Whether server queries can be counted the same way is the next thing to try.

FAQ

If every branch had an AI review, do I still need an integration review?

You still need one. In AXFamily every branch was reviewed by three agents, and the merged code still had 12 blocker or major defects, 10 of them spanning two packages by our count. A branch review reads only that branch's diff, so it misses the other side of a contract whenever that side is not in the diff.

Will Firestore emulator tests catch a missing composite index?

The emulator does not enforce composite indexes, so tests pass with the index missing. Add a static check that matches the app's sorted queries against the index file, or run the queries against a real project.

How long did the integration review take?

Review took 6 to 9 minutes and refutation under a minute; the fix took about 49 minutes to its commit and about 55 minutes to the PR merge after CI. Counting the merges and wiring before it, the whole run from the 01:51 merges to the 05:34 PR merge took 3 hours 43 minutes.
