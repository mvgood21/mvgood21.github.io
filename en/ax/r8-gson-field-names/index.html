203 unit tests missed a release-only blank result: R8 and Gson field names

A Gson field without @SerializedName stays at its default, with no exception, once R8 renames it, so the defect only shows up when you open the release artifacts.

By SugarMount · Android development · 10 min read · Last updated November 7, 2026

On a release build, the second spell-check path (the one Chat mode falls back to when the first path fails) in our Korean spelling app SugarSpeller would have returned blank corrected text and zero errors, with no exception thrown. All 203 unit tests were passing when we found this on September 14, 2026. R8 had renamed the Gson fields output and etype to a and b; commit 3791c2c added @SerializedName and an invariant test.

Sources: git history and CHANGELOG of the SugarMount app repository (sugarspeller), session logs from that week, the 1.6.026 release APK and mapping.txt built on 2026-10-09, and a reproduction run on 2026-11-04 with R8 9.4.14. The spell-check servers are not named here.

Gson does not complain about a field it can't match

Without @SerializedName, Gson uses the Java field name as the JSON key. In the release build, R8 had done this to the Result response model:

# release mapping.txt just before 3791c2c, 2026-09-14
output -> a
etype  -> b

The server still sends "output" and "etype". The object now has only a and b, so Gson skips both keys and the fields keep their initial "". Parsing succeeds, and the screen shows whitespace and zero errors.

Unit tests run against classes R8 never touched, so none of them ever saw a renamed field. The 203 is our recount of @Test annotations at the commit before 3791c2c (the CHANGELOG says "200 or so"), and it includes tests that parse recorded server responses. The two fields had carried no annotation since the path was added on 2024-06-14. That path then stopped receiving responses at all, until commit 0b74357 revived it on 2026-09-13. Both commits shipped together in 1.6.017. We could not tell from the records whether users saw blank results while the path was alive earlier.

mapping.txt flagged 14 fields; two were defects

Finding it took 28 minutes. At 20:50 KST on September 14 the operator asked for a cross-check. The agent replayed the app's exact requests against the live servers (13 of 13 passed), then read the proguard rules and grew suspicious of model fields with no annotation. A script over the mapping.txt of a clean release build checked 19 model fields and listed 14 as renamed.

Renamed fieldCountVerdict
Already has @SerializedName5Safe, maps by annotation value
Filled by code, not JSON7Gson never touches it
output, etype2Defect

The same table explains half of why the first spell-check path kept working in release: the keys holding its values were annotated. Why its unannotated message and result survived comes later. The fix at 21:18 annotated seven fields across both paths. No usable device was available that night, so "blank screen" was a verdict from mapping.txt and the dex files. We only saw the empty values at runtime later, in the reproduction below.

The agent's claim about debug builds lasted two days

Later that night the agent added an instrumented test (4d29ca4) and wrote in the commit message that because minify is on for debug too, the test runs in the same obfuscated state as the shipping build.

It was wrong, and that came out at 08:31 on September 16. The operator had opened KVM access so an Android 14 emulator could boot, and just before rerunning the test the agent checked whether the models were really obfuscated. Release said output -> a; debug kept the original name. The mapping.txt from October 9 shows the same. We did not establish why: the debug configuration.txt has no -dontobfuscate, though running the reproduction below with R8 --debug kept the names.

The agent then signed the release APK with the debug key, installed it, and blocked the first path's host in the emulator's hosts file to force the fallback. At 08:45 the second path's corrections appeared on the obfuscated build, and commit 5c4e3d7 fixed the docs at 08:47. The v16017 tag had already gone on at 07:47.

"lateinit got lucky" was really a keep rule

3791c2c has a wrong explanation of its own. Five unannotated lateinit fields kept their names, and the commit and the agent's memory file say R8 was keeping the names "by accident." While drafting this note in November we ran javap: Kotlin's lateinit var compiles to a public field, while var output = "" is a private field with a getter. The build at the time still had a rule meant for a Kakao SDK the app never used, -keepclassmembers class * { public static <fields>; public *; }, and that rule pinned every public field name. Commit e05f8e3 removed it on September 25, as told in Play Console said our DEX was 39% optimized. The 1.6.026 mapping.txt has message -> a.

This is a reproduction, not the real app: a Java model of the same field visibility, shrunk with R8 9.4.14, Gson 2.14.0 and the proguard files from 3791c2c, then parsed on the JVM.

AnnotatedConfigurationResult
NoneNo R8 (what unit tests see)Correct
NoneKakao rule + -dontobfuscate (stand-in for debug)Correct
NoneKakao rule (the September 14 release)output=[] etype=[], no exception
output, etype onlyKakao ruleCorrect
output, etype onlyKakao rule removedJsonIOException
All 5 fieldsKakao rule removedCorrect, message -> a

Row three reproduces the incident. Rows four and five show that annotating only output and etype would have passed on September 14, then broken eleven days later when the Kakao rule went away and message was renamed. Here the model is never constructed in code, so it ended in JsonIOException. When the code called the constructors and let the objects escape, both the September 14 configuration and the optimized one in use from September 20 ended in a NullPointerException. We did not build the real app, so we can't say which exception it would have thrown. 3791c2c annotated the lateinit fields for the wrong reason and still got it right. Annotate every field that takes a value from JSON, lateinit or not.

Finding etype in the dex proves little

Before the fix, grep -a etype already hit classes2.dex and classes3.dex. classes4.dex, which held the model, did not have it, and that file gained it after the fix. The before-and-after in 3791c2c was valid because it looked at that one file. But the AAB check that night and the pre-release check on September 16 looped over every dex and passed if etype appeared anywhere, and the report cited that as evidence. That loop would have passed the broken APK too.

Narrowing to one file no longer works either, since the 1.6.026 APK has a single classes.dex. We read all 43,818 strings in 1.6.026: 3 contain etype (a sentence with mimetype, closetype, and etype itself), 43 contain output, 97 contain message, 104 contain result.

dexdump -a from build-tools prints annotations with their values:

unzip -o app-release.apk 'classes*.dex' -d dex
dexdump -a dex/classes.dex | grep -c 'value="etype"'   # 1

The line reads VISIBILITY_RUNTIME Lkt1; value="etype". R8 renamed the annotation class to kt1 as well, so searching by class name finds nothing. Counted this way the release holds 11 spell-check keys in 13 annotations.

An invariant test that fails when one annotation goes

ResponseModelSerializedNameTest uses reflection to require an annotation on every field of the 8 response-model classes. This is the core, shortened:

private val models = listOf(Response::class.java, Response.Result::class.java)
private val codePopulated = setOf("com.example.Response#requestId")

@Test fun `every JSON field has SerializedName`() {
    val missing = models.flatMap { type ->
        type.declaredFields
            .filterNot { Modifier.isStatic(it.modifiers) || it.isSynthetic }
            .map { it to type.name + "#" + it.name }
            .filter { (_, key) -> key !in codePopulated }
            .filter { (f, _) -> f.getAnnotation(SerializedName::class.java) == null }
            .map { it.second }
    }
    assertTrue(missing.joinToString("\n"), missing.isEmpty())
}

The real file has three tests, adding a check of annotation values against JSON keys and a check that the exemption list codePopulated (10 entries today) holds no dead names. Before committing, the agent deleted the annotation on etype, watched this test and the key test end in FAILED, and restored it.

No package keep, and a debug device test can't see this

The broadest alternative is -keep on the whole model package. 3791c2c did not add one, and the session has no record of weighing it. Judged now, the empty values would go away but safety would hang on one rule, and losing that rule would bring the incident back.

The instrumented test stayed, but on a debug build it can't see this defect. We have not tried setting testBuildType to release. A launch check doesn't help either: the R8 incident in What to check before shipping an AI-built Android app was a crash at startup, and this one crashes nothing, so a cold start passes. The method behind our reproduction, shrinking the model with R8 --classfile under the app's proguard files and parsing on the JVM, showed the empty values with no device, but it is not in the repository.

Running the release APK through the whole path is the strongest evidence. On September 16 that session ran from 08:23 to 08:46, including other checks, and needed KVM access and a hosts-file block. So the invariant test runs with every test pass, and running the release APK stays a manual step in the docs for when a regression is suspected.

Auditing your own Gson models, from fromJson to the release APK

  1. rg 'fromJson|TypeToken|GsonConverterFactory' app/src/main lists what Gson fills. With Retrofit, follow the interface return types too.
  2. In the release mapping.txt, put each renamed field in one of the three rows above.
  3. Add the invariant test, delete one annotation and confirm the failure.
  4. For each key, count value="key" in dexdump -a across all dex files and compare with the number of annotations in source. In 1.6.026 message appears twice, once per model, so accepting "at least one" would miss a lost annotation.
  5. Sign the release APK with the debug key, install it, and reach a screen that goes through that parser. A path behind a fallback only runs if you block the path in front of it.

What the test misses: new models and removed keep rules

models is a handwritten list, so a new response class is unchecked until someone adds it. The test only sees annotations on the source model; it passes if the keep rule protecting the annotation disappears or a class turns abstract. Step 5, running the release APK, is where those two show up. The two existing models stayed on Gson, while the explanation feature from The first LLM feature in a spell-check app takes its response as a Map and avoids this problem. We have not used a code-generating serializer.

Stale test comments and a dex check still done by hand

  • The test's header comment and the agent's memory still say that minified debug builds rename fields, and the memory also says lateinit survives by accident. Both need correcting.
  • The dex check in the docs is still a manual grep. It should become a dexdump -a value count in the release build script, with its key list taken from the test's expected values.
  • The only device on record that ran this path on an obfuscated build is the emulator. The next release should go through the fallback on real hardware.

FAQ

Do I still need keep rules if I use @SerializedName?

It depends on your Gson version. Gson 2.14.0, which this app uses, ships META-INF/proguard/gson.pro with rules that protect annotated fields, and our proguard-common.pro has a similar rule. In our local cache the 2.11.0 jar contains that file and the 2.10.1 jar does not, so open your own jar first.

Is "Abstract classes can't be instantiated" the same bug?

It comes from R8 too, but the symptom is different. In our reproduction, a top-level model with no annotated fields came out of R8 as an abstract class, and Gson threw JsonIOException. gson.pro protects <init>() on classes with @SerializedName fields, and annotating that class's fields made the error go away.
