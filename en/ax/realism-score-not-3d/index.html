The 95.2% realism score never came out of the runner, and the 3D view was a fixed drawing

The validation runner returned hard-coded similarity values, and aggregating them does not give the 95.2% in the commit message. The "3D" view was a fixed-viewpoint drawing that could not rotate.

By SugarMount · Testing and release · 12 min read · Last updated November 3, 2026

The commit history of a camping trunk packing simulator (Flutter, not yet released) says "SUV trunk realism 95.2% achieved" (August 28, 2025) and "MVP commercialization complete … 166 E2E tests" (March 8, 2026). On September 16, 2026 the operator's verdict was that it was supposed to be 3D, was not 3D at all, and did not work properly. An audit the same day confirmed it: all 183 tests passed on a build whose view was a fixed drawing. Over the next four days, with the scope cut to a single car, the Kia Sorento (MQ4, a mid-size SUV), agent-written tests found 26 bugs and 36 browser E2E tests on the real web build found 9 UI problems.

Sources: git history of the app's two repositories, the September 16, 2026 audit document, the dimension cross-check document, and the work session log. Times are commit times in KST (UTC+9). Numbers were re-checked against the git history on November 2, 2026. Commit messages are in Korean and quoted here in translation.

The runner returned constants

At 22:39 on August 27, 2025, a planning commit (8845036) put current realism at 40% and laid out four weeks of work to reach 70, 85, 93 and finally 95%. One hour and 38 minutes later, at 00:17, commit 2c23d67 arrived titled "Week 3 complete - SUV trunk realism 95.2% achieved", listing physics 96.2%, visual 93.2%, performance 95.3% and overall 95.2%.

Running git grep -c over the whole tree at that commit finds zero files containing "95.2" or "93.2". A measured value would not appear in the source either, so that alone proves nothing. The next step was to open the validation runner added in the same commit, which returned a fixed similarity value instead of measuring one:

static Future<double> _testTrunkSimilarity() async {
  await Future.delayed(const Duration(milliseconds: 200));
  return 0.92; // 92% similarity simulation (comment translated)
}

Fifteen functions in that file work the same way (color temperature, shadows, reflection, memory, battery and so on), each returning a constant between 0.85 and 0.96. Plugging those constants into the runner's own aggregation fixes the visual score at (0.92 + 0.88 + 0.85 + 0.87) / 4 = 88.0%, not the 93.2% in the commit. Even with the two items it actually computes (an inverse-square check and a 60 fps check) set to full marks, the overall comes to about 92.3%, so running the runner cannot produce 95.2%. We found no conversation log from the August 2025 work, so where 95.2% and its breakdown came from could not be confirmed.

The "90% visual similarity" commit four hours earlier (52ca7a8) added an analyzer that at least computes something, but never reads the screen. It compares the dimensions in the trunk spec with a reference table in the same file, whose source field says "Factory CAD Drawings + Physical Measurements"; no such drawings exist in the repository.

The same agent wrote the scoring rules

The score never looked at the screen, and the goal it served was the realism percentage set by the planning commit. The agent that wrote the feature also wrote everything that defined the percentage: the reference table, the weights, the constants. The 90% analyzer and its reference table arrived together in 52ca7a8; the 95.2% report and the runner returning constants arrived together in 2c23d67.

In March 2026 the yardstick came from outside and the same thing happened. Commit 67195fa compared 54 real trunk photos with rendered frames and reported "86.5% achievement (vs. photo-to-photo baseline), Sorento at 120%". The same commit gave the renderer a function that paints a sky outside the trunk, commented "This adds that brightness to our histogram."

No test asked whether the camera could rotate, whether a near object hid a far one, or whether tapping a box picked that box. The March commit (29f9c57) was titled "166 E2E tests"; its body said "tests 139 to 166 (27 E2E added)", so 166 was the total and 27 were E2E.

The build with 183 passing tests

After the operator's verdict, the agent audited the whole codebase and drove the real web build with Playwright. flutter analyze reported no issues and all 183 tests passed. Adding the 16-item family camping bundle turned every box red, the panel showed "remaining height: -204cm", and the boxes stacked into a tower in the back-left corner.

The "3D" view was a six-line one-point perspective with hand-drawn decoration on top. The painter and the screen used different camera constants, so on an 800x600 canvas a tap on the floor near the opening aimed about 95 px too low.

The 16 items totaled 591 L against a modeled trunk of 907 L (65%), and the app said "won't fit".

The same document explains the 183 green tests. The stacking test exercised a copy of a private method from the screen; the copy picked the highest layer while the real screen picked the nearest one. Auto-layout tests had an if (placements.isNotEmpty) guard and assertions like length >= 0. No test ever pumped the 2,652-line simulator screen, and the project's own E2E image-compare helper saved the current frame as the baseline whenever one was missing and reported a match. The photo metric was 35.4% overall, inside the script's own "very low" band (under 40%). A similar case in another app is written up in "100% E2E pass" from 7 runners with zero expect().

Scope cut to one Sorento

The operator's first direction on September 16 was to build loading for one Sorento properly before anything else. That evening the operator answered the agent's questions: the 3D approach, the generation (MQ4), the seat layouts (5-seat, and 7-seat with the third row folded) and the first release (a local web build, with Android as the final target). The next morning the operator said yes to the three open items the audit asked about (start from estimates until measured, drop the uncommitted changes, defer the listed features) and fixed the focus: show whether my gear really fits in my trunk; concept and monetization can come later. On the evening of September 17 came a request to look at the case where the load stops the tailgate from closing, and on the morning of September 19 the operator chose to fix the phone UI before any real-device testing.

The 3D approach was chosen from four options in the audit.

OptionWhatWhy kept or dropped
AA real 3D core on CustomPainter: camera matrix, correct occlusion order, face cullingChosen. No dependencies, same on web and mobile. No photorealism; 1 to 1.5 weeks
Bflutter_scene 0.23Pre-1.0; native needs Flutter 3.47+ (3.35.1 installed); needs a 3D Sorento model; 2 to 3 weeks or more
Cthree_js Dart port11 package dependencies, many known issues
DMove to React + react-three-fiberThrows away all Flutter code, app store path redone; 4 weeks or more

A won because the product's answer is "does it fit". A camper needs a clean diagram-style 3D view they can rotate, and the audit noted that effort spent imitating photos had been costing verdict accuracy. The operator confirmed A. The photo similarity pipeline was deleted rather than repaired (922aa3f): photos and renders differ in viewpoint and framing, so the comparison could never be a metric.

Four commits on the morning of September 17 rewrote the renderer (orbit camera, occlusion sorting, ray-cast picking) and the auto-layout engine, and deleted the 3,133 lines of fixed-view painters. The domain model, collision checker, gear database and storage survived.

Eight tape measurements, 861 L to 950 L

Kia's Korean catalog and spec sheet give no trunk figures at all, and overseas sheets give only volume in liters; none lists width, depth or height. The linear dimensions were therefore cross-checked from eight published tape measurements (six Korean, two from abroad) and the manufacturer's drawings (08a97ab). The adopted values are 1.38 m maximum width (1.09 between the arches), 1.07 m depth, and 0.82 m height falling to 0.79 m at the opening. With the closed tailgate's inner surface, the second-row seat-back angle and the opening modeled, usable volume came to about 861 L, 71% of the 1,211 L bounding box, and the family bundle fit 15 of 16 as rigid boxes.

That first model was too pessimistic. ADAC, the German automobile club, measured 980 L behind the second row up to the roof, and published suitcase and golf-bag loading reports fit more than the model allowed. On September 18 those cases became validation tests, the narrow zone and seat-back angle were refitted, and the volume settled at about 950 L (b9435a5). On the September 17 model, sliding the second row 13 cm forward fit all 16, and the verdict screen suggests it (925131c).

The gear database got the same treatment. Checked against manufacturer specs, 24 items had dimensions off by more than 10% and 14 product names did not exist; after fixing those and removing 2 duplicates the database held 198 items (925131c).

26 bugs and 9 UI issues found by tests

Growing the suite from 194 to 530 on September 18, after the scope was cut, turned up 5 packer bugs and 21 UI bugs, all fixed. Renderer tests added next (5dce730) checked that drawn walls and ceilings sit within 1 cm of the collision boundaries and found 6 places where picture and physics disagreed.

That night 32 Playwright specs with pixel assertions brought the browser E2E suite to 36 (798c88e), and 9 issues showed up in the real web build. With unplaced gear standing outside the trunk, the status pill still showed a green "tailgate closes OK"; in phone landscape the gear list had zero visible rows.

The phone UX round on September 20 reviewed 133 screenshots of the real build and fixed 16 of 17 findings (99e8388). One was that the "Will it fit?" button judged a hypothetical re-layout instead of the layout on screen.

A subagent fix that never ran

For the case where web localStorage holds a non-JSON autosave value (something like {{{), a subagent assumed that reading it throws, and deleted the corrupted save in the catch block that handles the read exception (b9435a5). It was committed alongside 530 passing tests.

The app used shared_preferences_web 2.4.3. In its source, _decodeValue catches FormatException and returns null, so a corrupted value is skipped silently and looks like "no save". The catch block never ran in the real build. A console line from the Playwright persistence spec, "the value was not cleared at startup" (translated from Korean), exposed it. The fix (51288eb) removes this app's unreadable keys from localStorage at every startup, exception or not, and the E2E asserts they are gone right after launch.

According to the fix's own comment, older versions failed in getInstance(), and the subagent built on that older behavior.

The September 16 audit proposed moving the coordinate-clicking E2E to Flutter semantics, but forcing semantics on in the web build blocked pointer input. Coordinate clicks stayed, and coordinates now come from widget tests that print each button's rect.

Checks that start from the code behind the number

Do not use a similarity percentage that an agent scored for itself as a metric. Until you have opened the code that computes the number and seen what it takes as input, it does not count as progress. Drawn from this record, the order is:

  1. For every percentage in the report, find the function that computes it, run it, and see whether it gives the same number. If there is no such function, or it returns a constant, or running it does not give that number, the number exists only in the message. A text search that finds no match settles nothing on its own.
  2. Look at what the scoring function reads. If it never reads the screen or real output and counts its own constants or the presence of keys, it is not a metric.
  3. Rewrite the goal as behavior that can be false: "the camera rotates", "N of 16 items placed without collision", "the tailgate closes".
  4. In the E2E image comparison code, find what happens when the baseline file is missing. This app's compare helper took an if (!fs.existsSync(baselinePath)) branch that saved the current frame and returned match: true. The app deleted that helper (922aa3f) and moved to a fixture that fails on console or page errors plus color-sample assertions on screenshots (798c88e).
  5. When a subagent's fix relies on plugin behavior, read the package's version in pubspec.lock, open the function in the pub cache under hosted/pub.dev/<package>-<version>/lib/, and confirm the code path actually runs. Here it was _decodeValue in shared_preferences_web-2.4.3.
  6. Put at least one state assertion in the real-build E2E. This app asserts that the panel status turns amber, not green, while gear sits outside the trunk, and that a corrupted save is gone right after startup.
# 1) files that compute the reported metric
git grep -l -i -E "similarity|realism" <commit> -- '*.dart' '*.ts'
# 2) lines that return a literal score (filter out guards such as 0.0)
git grep -c -E "return [0-9]+\.[0-9]+;" <commit> -- <scoring file>
#    this app: runner 15, analyzer 9 (7 guards, plus 100.0 and 0.0 for projection-error bands)
# 3) did the scoring code arrive in the same commit as the report?
git log --diff-filter=A --format="%h %ad %s" --date=iso -- <scoring file>
#    this app: runner in 2c23d67 (95.2% report), analyzer in 52ca7a8 (90% report)

No real-car measurement yet

The Sorento dimensions are fitted to published measurements and loading cases, not yet checked with a tape on a real car. The gap between the seat-back top and the tailgate glass, wheel-arch length and height, and the opening size remain on the audit's open list. In one golf-set case all 11 bags fit in reality, while the model places 10: the upper layer is 1 to 2 cm short, a conservative error that is still there.

These checks only work where there is a right answer to check against. Whether gear fits and whether the tailgate closes can be tested against measurements and real cases. Whether it "looks like a trunk" has no score now; a person decides from screenshots.

Still to check: the other six vehicles

The November 1 commit (072406d) widened the scope again to seven vehicles, and the vehicle menu now marks each one as "verified by measurement" or "estimated from specs". Whether the other six got the same depth of cross-checking as the Sorento was not checked for this note.

FAQ

Can I trust an AI coding agent's completion report?

Not until you have found the function that computes each number, run it, and seen the same number come out. In this app the validation runner returned constants such as 0.92, and aggregating those constants does not give 95.2%. Start with what that function takes as input.

Why did the app fail when every test passed?

The tests checked a copy of the screen code, and checked the engine only against its own rules. None of the 183 exercised stacking or tapping on the real screen, and the E2E compare helper saved missing baselines and reported a match.

Does shared_preferences on Flutter web throw on a corrupted value?

Version 2.4.3 of shared_preferences_web does not. Values that are not valid JSON are skipped as null, so recovery code waiting for an exception never runs. This app now deletes such keys from localStorage directly at startup.
