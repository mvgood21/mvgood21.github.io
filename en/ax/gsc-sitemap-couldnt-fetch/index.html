Search Console showed 'Couldn't fetch' for ten days; a new domain property processed the same sitemaps in seconds

Behind the 'Couldn't fetch' label the API said isPending=True with no lastDownloaded. For those ten days, almost every page that got indexed was one we had requested by hand.

By SugarMount · Website and search · 11 min read · Last updated November 2, 2026

Google never downloaded the sitemap.xml we submitted to Search Console, not once in the ten days before the site moved. It was first submitted on October 21, 2026 (API date). On October 25 a live URL test fetched the same file without trouble, and Bing processed our sitemap.xml that same day. On October 31 the site moved to its own domain; we submitted the same four sitemaps to a new domain property, and Google downloaded all four within seven seconds of submission.

Sources: our Search Console API reads (sitemaps and URL Inspection), the output of the site's sitemap audit script, Bing Webmaster Tools screens and the site repository's git history. Times are Korea Standard Time (UTC+9); figures are as of November 1, 2026.

Old property: still pending on November 1. New property: seconds

On the morning of November 1 we read both properties' sitemap lists again. The URL-prefix property for the old github.io address still lists sitemap.xml and its three child sitemaps as isPending=True, no lastDownloaded, errors=0. All four were last submitted on October 30 (sitemap.xml at 03:43, the children at 15:43). In the new domain property the same four read isPending=False, errors=0, with lastDownloaded between 17:05:08 and 17:05:14 on October 31. They were submitted at 17:05:07 to 17:05:08, so all four were downloaded within seven seconds (the fastest in under one second).

The move rewrote the old address to the new domain across the site; the sitemap layout (one index, three children) and the rules that generate it did not change. Every old URL redirects with a single 301 to the same path on the new domain, and the audit run against the new domain found all 196 URLs returning 200 with self-referencing canonicals. Eleven hours after the move, a full URL Inspection run in the new property (198 URLs) showed 114 as 'Discovered - currently not indexed'.

Googlebot fetched the file in a live test

On the afternoon of October 25 the operator pointed out that the sitemap wasn't showing up in Search Console and that robots.txt seemed to be missing. The agent found that robots.txt returned 200 with Allow: / and a Sitemap line. sitemap.xml was a standard sitemaps.org 0.9 urlset with the hreflang and image extensions; it rendered as a table in the browser only because of an xml-stylesheet meant for people. The audit script opened all 154 URLs: every one returned 200 with a self canonical, no noindex, reciprocal hreflang and valid lastmod, and all 261 images returned 200.

At 14:38 we ran the live URL test in URL Inspection on the sitemap.xml address. Googlebot fetched it and reported that the URL was available to Google. That afternoon the Sitemaps report said 'Couldn't fetch', and the API said isPending=True, no lastDownloaded, 0 errors. There was no record of a fetch attempt at all.

New format, four resubmissions, child sitemaps: still pending

The operator suspected the structure, so around 17:00 the agent turned sitemap.xml into a plain sitemapindex (commits 3d93937, c18cf30, 4879355). The three child sitemaps keep only loc, lastmod, priority and changefreq; the XSL, hreflang and image tags were removed. lastmod follows the rule in our note on setting sitemap lastmod from a content hash. We also added an HTML site map, which puts all 156 URLs within two clicks of the home page. In the same hour the operator added the site to Bing Webmaster Tools by importing it from Search Console. Bing fetched the new sitemap.xml that day, marked it Success and found the three child sitemaps. Google was still pending that evening.

We resubmitted sitemap.xml through the API twice on October 25 and once each on October 27 and in the early hours of October 30, and got 204 every time. On the afternoon of October 30 the API reported sitemap.xml as isSitemapsIndex=False: Google had never downloaded it, so it did not even know the file was an index. If only the first pass through an index were slow, a child sitemap should get processed first, so we submitted the three children directly (94, 44 and 48 URLs). All four stayed pending.

The agent's first note, on the morning of October 25, called the state "a normal delay for a new property" and proposed waiting a week; the old property was still pending on November 1. When it resubmitted on October 25 it also resubmitted rss.xml and en/rss.xml as sitemaps, which breaks this site's own rule that RSS feeds are never submitted as sitemaps, and it submitted sitemap.xml?v=20261025 as a separate duplicate. The duplicate was deleted at around 17:00 that day; the two feeds were deleted with the operator's approval, leaving sitemap.xml alone.

When you see 'Couldn't fetch', don't start by rewriting the file. Check lastDownloaded in the API and run the live URL test first. On this site, with lastDownloaded empty and the live test passing, changing the format did not end the wait.

Host, property type and submission date all changed at once

URLs we requested by hand were mostly crawled within one to four hours, so Googlebot could reach the site. The explanation that remains is that the property's sitemap never reached the front of Google's processing queue; we could not confirm that, because Google does not show why. Google's Sitemaps report help lists five causes of 'Couldn't fetch': a robots.txt block, an unresolved manual action, a 404, a general error such as an unavailable server, and low crawl demand for the sitemap. Of the first four, we ruled out the robots block, the 404 and server errors above; we did not check the Manual actions report (the URLs we requested were indexed within hours). Low crawl demand stays a hypothesis we cannot check.

Three things changed at once with the new property: the host went from github.io to our own domain, the property type went from URL prefix to a domain property verified by DNS TXT, and the submission came ten days later. This observation cannot separate the three, so this note does not name github.io as the cause.

While the sitemap had never been read, URL Inspection in the old property still showed coverageState as 'Submitted and indexed' (the October 25 full run, and again on November 1). On this site, 'Submitted' did not mean the sitemap had been processed.

For ten days, indexing grew mostly through manual requests

The full URL Inspection run on the morning of October 25 found 7 of 148 URLs indexed (4.7%) and 141 as 'URL is unknown to Google'. That day the operator handed Search Console write tasks to the agent, which started requesting indexing in the Search Console UI. At 14:29 an API check showed 7 of 10 requested URLs as 'Submitted and indexed', one to two hours after the requests. URLs we had not requested stayed where they were: the 03:00 run on October 26 still counted 22 indexed, the same as the previous afternoon, and 133 unknown.

From then on we requested new notes and a queue every day. The indexed count went to 44 (October 27), 73 (October 28), 146 (October 30) and 162 (October 31). The October 27 run showed nearly every requested URL indexed and most unrequested ones unknown. A few notes stayed unknown even after several requests.

The agent misread the request limit at first. On October 25 a 'Quota exceeded' message appeared after 15 accepted requests, and it wrote down "15 to 16 per day". On October 27 forty requests went through without that message. On October 29, 49 clicks produced 44 accepted requests; 'Quota exceeded' appeared five times in between, and each time the very next request was accepted. We now read it as a short-interval rate limit. These are observations from one property, not limits Google has published. Driving the UI from a browser took about two and a half minutes per request.

After the move, 5 of 7 requests indexed within four hours

The domain move had been decided for reasons unrelated to the sitemap, and it happened at 17:00 on October 31. New URLs showed up as 'Discovered - currently not indexed' within minutes, and the home page was indexed at its new address three hours after the move. From 19:47 we requested the seven pages that had impressions in the old property; four hours later five were 'Submitted and indexed'. That request-to-index time is about what we saw in the old property (one to four hours).

One of the seven, /ax/hwp-viewer-rhwp-webview/, came back as 'Duplicate, Google chose different canonical than user'. Inspecting the old URL in the old property showed 'Submitted and indexed', with the old URL itself as Google's canonical and a last crawl on October 27, before the 301 existed. The 03:00 full run in the new property on November 1 found 10 such Duplicate pages, many of them pages that had impressions in the old property. On the morning of November 1 we inspected five of them again: all five were still Duplicate, and googleCanonical was empty for three and showed the github.io URL for two.

For Duplicate pages we request indexing for the old URL in the old property. The new address has already been crawled and the old URL is still the canonical, so we expect the canonical to move only after Google recrawls the old URL and sees the 301. We sent one such request on the night of October 31 and ten on the morning of November 1.

The new property still had zero rows of search performance data on the morning of November 1, and as of that morning the old property's last daily row was October 29, with 84 impressions, its highest day until then. Search performance data usually lands two to three days late, so this cannot yet be told apart from reporting lag.

For Google, only the UI indexing request was left

We waited ten days, but with six new pages (Korean and English) going out every day we could not wait another week. The Indexing API covers only job postings and livestream video pages, so our notes don't qualify. IndexNow pings went out with every publish, but its receivers are engines such as Bing and Naver (Korea's largest portal); Google does not use it. That left the URL Inspection indexing request, which only exists in the UI, so the agent drove it through a browser.

If lastDownloaded is set, this is a different problem

If lastDownloaded has a value and errors is above zero, Google downloaded the file and failed while reading it; fix the reported errors. If the live URL test fails with a 404, a robots block or a redirect, the fetch is really failing. This is one site and two properties, so we can't say whether other sites on github.io see the same wait.

What to check when a sitemap says 'Couldn't fetch'

  1. Read the sitemap list from the Search Console API and look at isPending, lastDownloaded, errors, isSitemapsIndex and lastSubmitted. No lastDownloaded and zero errors means Google has never downloaded it; the live test in the next step tells pending from failure.
  2. Run the live URL test in URL Inspection on the sitemap.xml address. If it says the URL is available to Google, fetching works.
  3. Open every URL in the sitemap and confirm 200, a self canonical, no noindex, reciprocal hreflang and valid lastmod.
  4. Submit the same sitemap to Bing Webmaster Tools. If Bing processes it, that is one more sign the file's format and access are fine.
  5. If it is pending, request indexing for every new page. On 'Quota exceeded', retry the same URL a little later.
  6. Once a day, run URL Inspection over every URL and record coverageState and lastCrawlTime.
  7. After a domain move, take the Duplicate pages in the new property and request indexing for their old URLs in the old property.
# sitemap status (read only)
GET https://www.googleapis.com/webmasters/v3/sites/<property>/sitemaps
  → path, isPending, lastDownloaded, isSitemapsIndex, errors, lastSubmitted
# index status of one URL
POST https://searchconsole.googleapis.com/v1/urlInspection/index:inspect
  {"inspectionUrl": "<URL>", "siteUrl": "<property>"}
  → coverageState, lastCrawlTime, googleCanonical
# <property>: URL prefix https://example.github.io/ (URL-encoded), domain property sc-domain:example.com

Ten Duplicate pages and four old sitemaps

On the morning of November 1 the old URL /ax/hwp-viewer-rhwp-webview/ still had October 27 as its last crawl. The next URL Inspection run will show whether the ten old-property requests sent that morning get the 301 read. We are also watching whether the old property's four sitemaps ever get processed, and whether daily rows from October 30 on show up in the old property.

FAQ

Does 'Couldn't fetch' in the Search Console Sitemaps report mean the file is broken?

Not on this site. The API said isPending=True, no lastDownloaded and zero errors, and the live URL test fetched the file.

If the sitemap is never processed, do new pages get indexed?

Requesting indexing by hand worked. During the ten pending days most requested URLs were indexed within one to four hours.

Does moving from github.io to a custom domain get the sitemap processed right away?

For this site Google downloaded it within seven seconds of submission. That is one observation in which the host, the property type and the submission date all changed together.
