GA4 shows zero? Read a table report's total row first

"No data available" on the GA4 overview was not a zero. The total row of a table report showed 43 active users and 10,522 events in the last 28 days.

By SugarMount · Working with agents · 7 min read · Last updated November 13, 2026

When you have just shipped an app and the first GA4 (Google Analytics 4) screen shows zeros or "no data available", it is easy to conclude the tracking code is broken. On the night of October 17, 2026, SugarMount's AI coding agent (Claude Code) did exactly that while collecting first-week numbers for SugarDoc, a viewer for Korean HWP documents: it reported "GA4: zero in 28 days" and proposed holding the next release. Ten minutes and 26 seconds later the same agent withdrew the report. The app code had nothing to fix.

Below: where the zero came from, what a zero means on each GA4 screen, and what to check before you open the code.

The zero came from one read of the overview page

The agent opened the Firebase overview page (the GA4 dashboard) in Chrome. Its screenshot failed, so it waited four seconds and read the page as text, once. That was the only GA4 screen it opened.

Of the 1,736 characters it read, the only number that was a value was "active users in the last 30 minutes: 0". Ten cards (events by name, countries, device models) all said "no data available". The agent combined those messages with the 30-minute zero into "28 days: 0 users, 0 events" and put that next to Play Console's 2 to 3 daily active users. Side by side, "the app sends no analytics at all" looked like a good explanation.

The total row said 43 users

A subagent took over the investigation. It spent three minutes on code and build checks and found no defect. On a Galaxy S21 running the release build, logcat showed a successful upload:

V/FA-SVC: Network upload successful with code, uploadAttempted: 204, true

The realtime overview showed 0, then six seconds later one app_entry and one session_start. The subagent then opened the "Pages and screens" table report, and 11 seconds later read the total row: 43 active users and 10,522 events in the last 28 days. Split by app version in the tech details report:

The QA debug build accounted for 25.77% of the events. The version rows add up to 45 users while the total row says 43; someone who used two versions is counted once in each row, so judge by the total row. Midnight passed between the two screens, so the overview's "last 28 days" was September 19 to October 16 and the table report's was September 20 to October 17.

A zero means something different on each screen

We looked at four screens. The same zero or "no data" meant different things over different periods.

What to check before opening the code

  1. Write down which screen showed the zero and over what period, using the table above.
  2. Read the total row of a table report. We used "Pages and screens" and "Tech details", switching the latter's primary dimension to "App version" to see one row per version. If the screens are awkward to read, the GA4 Data API's runReport returns the same values as JSON (first command below).
  3. Check uploads on a device. Turn on the debug-mode property, launch the app, look for the upload response code (204) in logcat, and watch the realtime overview or DebugView for events. Here an app_entry showed up in the realtime overview about two minutes after the upload.
  4. Line up the metric definitions. Play Console's active users and GA4's active users are counted differently, and raw GA4 values include debug builds, test devices and Play's pre-launch robots.
  5. Only then open the code.

runReport needs a token with the analytics scope. That night both tokens on hand lacked it and the API returned 403. Adding the scope to a gcloud login is blocked, so we now impersonate a service account to get the token (gcloud 'This app is blocked' for GA4: impersonate). A range of 28daysAgo to yesterday matches the table report.

TOKEN=$(gcloud auth print-access-token \
  --impersonate-service-account=<service account address> \
  --scopes=https://www.googleapis.com/auth/analytics.readonly)
curl -s -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  https://analyticsdata.googleapis.com/v1beta/properties/<property id>:runReport \
  -d '{"dateRanges":[{"startDate":"28daysAgo","endDate":"yesterday"}],
       "metrics":[{"name":"activeUsers"},{"name":"eventCount"}]}'

The device check for step 3. In our run the two log.tag values would not reset to empty, so a reboot cleared them.

adb shell setprop debug.firebase.analytics.app <package name>
adb shell setprop log.tag.FA VERBOSE
adb shell setprop log.tag.FA-SVC VERBOSE
adb logcat -s FA FA-SVC          # look for "Network upload successful with code"
adb shell setprop debug.firebase.analytics.app .none.
adb reboot                       # clears the two log.tag values

Where the agent went wrong: the zero went into the brief as a fact

When the main agent handed the investigation to a subagent, the first paragraph of its brief stated "0 users, 0 events in the last 28 days" as fact. All five required checks were about code and build; none said to confirm the zero in a GA4 report. Eighteen seconds later the agent ran the pre-approved command to promote 1.1.0 to production, which Claude Code's auto-mode permission classifier blocked, and told the operator: if the analytics bug is in 1.1.0 too, better to ship a fixed 1.1.1 right away.

In its correction the main agent said it had read the page before the cards finished loading, but nobody reopened that page to check. The subagent guessed the main agent had looked at the data stream screen; the session log shows the overview was the only GA4 page it opened. What is certain is that it never opened a report with a total row and never checked the number another way.

Don't change a release decision on a zero read off a dashboard. When you delegate, don't write the zero down as a fact; make steps 1 and 2 above the first tasks. More rules for briefs are in Six hard rules in one subagent brief, and five agents cut off by usage limits. The 1.1.1 hotfix and the hold were dropped after one look at the table report, and the next day 1.2.0, which added PDF export, went to production.

Some zeros are real, and raw counts run high

For an app with very little traffic, many zeros are correct. This app had no GA4 users on October 11 to 14 and October 16 to 17. The steps above only tell you which screen and which period a zero belongs to.

The opposite happens too. On October 27 the raw active user count was 13; without test devices and Play's pre-launch robots it was 4. How to filter them is in GA4 said 19 installs yesterday and 8 were real. The device check used a sideloaded 1.1.0 only; the evidence that the Play 1.0.0 build was fine is a static check of its AAB and the 1.0.0 data already in GA4.

Still open: 2 to 3 daily users on Play, 0 to 1 on GA4

After launch, Play Console showed 2 to 3 daily active users while GA4 showed 0 to 1. The steps above did not explain the gap, and because the two metrics are defined differently we stopped short of calling it a bug. The next step is to split app_entry since October 10 by entry path (launcher or opening a file) and match first_open counts against Play installs day by day.

FAQ

GA4 shows zero for my app. Should I start with the code?

Read the total row of a table report first. Here the 28-day value read as zero on the overview page was 43 users and 10,522 events in the table report, and three minutes of code and build checks found no defect.

A data stream says "no data received in the past 48 hours". Is collection broken?

Not necessarily. The same message appears when no events arrived in those 48 hours. This app had no real users on October 16 and 17, which is why the message showed; when a device sent events, app_entry appeared in the realtime overview about two minutes later.
