An AI agent reported "GA4: zero in 28 days"; the table report had 43 users

The zero came from reading the Firebase overview page as text, once. A table report for the last 28 days showed 43 active users and 10,522 events, and the app code had nothing to fix.

By SugarMount · Working with agents · 11 min read · Last updated November 8, 2026

An AI agent told the operator that GA4 had recorded nothing for 28 days and that measurement was broken; 10 minutes and 26 seconds later the same agent took it back. It was 23:57 Korea time on Saturday, October 17, 2026, one week after our HWP document viewer SugarDoc went public on Google Play, in a Claude Code session that was collecting the app's numbers through Chrome. The subagent sent to investigate read 43 active users and 10,522 events for the last 28 days from a GA4 table report, 34 users and 7,728 events of them on the Play release build.

Sources: the Claude Code session logs (the main session and the investigating subagent, both jsonl), docs and commits in the sugar-utils and game repositories, and the GA4 page text captured in those logs. The logs store UTC; times here are converted to Korea time (UTC+9). GA4 property numbers and other account or app identifiers are left out. Checked again on 2026-11-03.

One read of the overview page after a 4-second wait

At 23:50 the operator tried, in the same session, to re-authenticate gcloud Application Default Credentials (ADC) with an analytics scope. The command failed because the shell it ran in had no gcloud. The operator then told the agent to go through Chrome if the login didn't work, and at 23:52:56 the main agent opened the Firebase overview dashboard in GA4. The screenshot taken right after failed with "Can't interact with browser-internal or unparseable URLs", so it waited 4 seconds and pulled the page text once, at 23:53:06. That was its only look at GA4. Its next calls went to Play Console statistics and Android vitals.

The text it got was 1,736 characters long. It contained exactly one number that was a value, "active users in the last 30 minutes: 0"; the other digits were chart axis ticks. Ten places said "no data available", including the cards for event count by event name, users by country and users by device model. The first card, user activity over time, had no value in its text, only the date tick "17 Oct". In the 23:57 report this became a table row: "last 28 days: users 0, events 0, no records even from QA devices."

The agent went wrong when it turned wording into a number. It combined "no data available" with a 30-minute zero into a 28-day total of zero, then set that next to Play Console's 2 to 3 daily active users. Side by side, "the app is not sending analytics at all" looked like a reasonable story.

The zero went into the subagent brief as a fact

At 23:56:38 the main agent handed the root-cause hunt to a subagent. The brief opened by stating that the GA4 property showed zero users and zero events for the last 28 days, not even from QA devices. The five required checks (whether the google-services plugin was applied, the Firebase resources in the built bundle, FirebaseApp initialization, the consent default, the event call sites) were all code or build; a logcat check on a connected phone was listed as optional. Nothing asked it to confirm the zero in a GA4 report, and it was told to fix any bug it found in a separate git worktree.

Eighteen seconds later the main agent ran the production promotion for version 1.1.0 (versionCode 4), which the operator had approved earlier. Claude Code's auto-mode permission classifier blocked it as "[Production Deploy]". The 23:57 report, four minutes after the page-text read, passed the command to the operator with a caveat: if the analytics bug was also in 1.1.0, it would be better to ship a fixed 1.1.1 straight away. A worktree and branch for the fix were listed as work in progress.

No person corrected anything in those ten minutes. The permission classifier blocked the production promotion for its own reasons, unrelated to the zero; the hotfix and the hold that came from the zero were withdrawn after the investigating subagent's report. Do not change a release decision on the strength of a zero read off a dashboard. This zero reached the report and the brief without the name of the page or the date range it came from. More rules for writing subagent briefs are in Six hard rules in one subagent brief, and five agents cut off by usage limits.

The investigator checked code, then a phone, then the report

The subagent followed the brief's order and started with code and build. For about three minutes from 23:56 it checked the condition that applies the google-services plugin, the Firebase resources in the 1.1.0 release APK (key names only), the initialization provider, and the path that switches the consent default on. It found no defect. The static check of the 1.0.0 and 1.1.0 app bundles came later, at 00:04, after the phone test. At 23:59 the Firebase Management API showed both apps, release and debug, linked to two GA4 data streams.

Around midnight it moved to a Galaxy S21 with the 1.1.0 release build already installed. With Firebase debug mode switched on for the package, logcat showed initialization succeeding, collection enabled and analytics_storage=granted, and at 00:00:52 this line:

V/FA-SVC: Network upload successful with code, uploadAttempted: 204, true

At 00:01 it tried to pull the numbers through the GA4 Data API. Both tokens it had, the ADC token and the gcloud user token, lacked an analytics scope, so both calls returned 403. That left the GA4 pages in Chrome. The data streams page said "no data received in the past 48 hours" for both streams. The realtime overview showed 0 at 00:02:44 and, six seconds later on the same page, one app_entry and one session_start event. At 00:05:38 the subagent opened the "Pages and screens" table report; the text it read 11 seconds later had a total row with 43 active users and 10,522 events for the last 28 days.

34 of the 43 users were on the Play release

At 00:06 it split the tech details table by app version: 1.0.0 (the Play release) 34 users and 7,728 events, 1.0.0-debug 6 users and 2,712 events, 1.1.0 (internal test track) 5 users and 82 events. The debug build alone accounted for 25.77% of events. The user counts per version add up to 45, while the total row said 43.

According to the subagent's report, GA4 had 5 users after the public launch on October 10 (3 on 1.0.0, 2 on 1.1.0): about 4 on the 10th and 0 or 1 a day after that. So 3 of the 34 users on 1.0.0 came after launch; who the rest, seen before launch, were was not broken down in that session. Midnight also passed between the two reads: the overview's "last 28 days" was September 19 to October 16, and the table's "last 28 days" was September 20 to October 17.

The loading guess was never checked; the streams guess contradicts the log

In its 00:07:49 correction the main agent wrote that the zero came from reading the overview text before the cards had finished loading. That may be true, but nobody checked it. There is no record of the same overview page being opened again to see whether the cards filled in.

The subagent offered a different guess: the main agent had probably looked at the data streams page with its "no data in 48 hours" line, at the realtime zero, or at the wrong property or a filter. The session log rules that out. The only GA4 page the main agent opened was the Firebase overview. The streams message itself was accurate: the app really had zero users on October 16 and 17.

The main agent never opened a report with a total row and never checked the number by a second route. The Data API was blocked, so the browser was the only route, but in that same browser the subagent went from opening a table report to reading its total in 11 seconds.

Data API, code review, a screenshot, a hotfix

The Data API's runReport call returns activeUsers and eventCount as JSON, so it does not depend on whether a card has rendered. That night both tokens lacked the analytics scope and got 403, and the operator's re-login attempt at 23:50 had failed. The growth plan committed the next day (8475f45) still said Claude could not see GA4 numbers directly and left every cost-per-install and conversion figure as an estimate. The GA4 report tool in the game repository read GA4 with a service-account token; commit 7a61407 on October 22 made it mint that token from ADC alone, with no gcloud user login. Ten days after the incident the daily ops check (68215b5, covering October 27) was reading per-app GA4 Data API numbers through that tool's filter.

The brief sent the investigator to the code first, and that review only showed there was no defect; the 28-day total appeared once a table report was opened. The growth plan named an operator's GA4 screenshot as a fallback, which puts the decision on hold until a person opens the page. The 1.1.1 hotfix and the held promotion were dropped once the table report was on screen. Version 1.1.0 (4) never went to production; the next day 1.2.0 (5), which added direct PDF saving, did (6687cd0, c676b49).

Some zeros are real, and raw counts run high

For an app with almost no traffic, many pages are right to show zero. According to the subagent's report, SugarDoc had zero GA4 users on October 11 to 14 and October 16 to 17. The steps below only tell you which page and which date range a zero belongs to.

Raw counts can also run high: in the October 27 daily check, SugarDoc's raw active users were 13; with test devices and Play pre-launch robots removed, there were 4. That was the day the robots tested the newly uploaded 1.3.3 (versionCode 9). How we filter raw counts is in GA4 said 19 installs yesterday and 8 were real.

The on-device check used only the sideloaded 1.1.0 build. Neither connected phone had 1.0.0 installed from Play, so the evidence that 1.0.0 collected data is a static check of its app bundle and the 1.0.0 rows in GA4.

Overview card, total row, logcat 204, metric definitions

We looked at four pages this time, and a zero or "no data" meant something different on each.

  1. Find the page your zero came from in the table above and write down its range.
  2. Read the total row of a report with a table. This time the subagent opened the "Pages and screens" report and the Tech details report (r=user-technology-detail in the URL), and in Tech details switched the primary dimension to "App version" to get the version rows. With the range set to 28daysAgo through yesterday, runReport returns the same range.
  3. Watch an upload from a device. Turn on debug mode for the package, launch the app, find the upload response code in logcat, then look for the events in DebugView or the realtime report. This time the realtime report was used instead of DebugView; one app_entry appeared about two minutes after the upload.
  4. Line up metric definitions. Play Console's active users and GA4's active users are counted differently. Inside GA4, the version rows summed to 45 against a total of 43, and debug builds, test devices and pre-launch robots sit in the raw numbers.
  5. Only then open the code. When handing this to a subagent, do not state the zero as a fact; make steps 1 and 2 its first tasks.

The runReport call for step 2 is the request that stopped at 403 that night, with identifiers removed; only endDate was changed to yesterday so the range matches the reports. The scopes are the ones in the re-login command the subagent left in its report.

gcloud auth application-default login \
  --scopes=https://www.googleapis.com/auth/analytics.readonly,https://www.googleapis.com/auth/cloud-platform

curl -s -X POST \
  -H "Authorization: Bearer $(gcloud auth application-default print-access-token)" \
  -H "x-goog-user-project: <cloud-project-id>" \
  -H "Content-Type: application/json" \
  https://analyticsdata.googleapis.com/v1beta/properties/<property-id>:runReport \
  -d '{"dateRanges":[{"startDate":"28daysAgo","endDate":"yesterday"}],
       "metrics":[{"name":"activeUsers"},{"name":"eventCount"}]}'

The device check for step 3 runs as below. According to the subagent's report, the two log.tag properties could not be set back to empty and stayed at VERBOSE; it noted they clear on reboot.

adb shell setprop debug.firebase.analytics.app <package-name>
adb shell setprop log.tag.FA VERBOSE
adb shell setprop log.tag.FA-SVC VERBOSE
adb logcat -s FA FA-SVC          # look for "Network upload successful with code"
adb shell setprop debug.firebase.analytics.app .none.
adb reboot                       # clears the two log.tag values (an empty setprop did not work in this session)

Play's 2 to 3 daily users against GA4's 0 to 1

The gap between Play Console's 2 to 3 daily active users and GA4's 0 or 1 a day after launch was not settled by these steps; the session stopped once it found the two metrics are defined differently, without deciding whether it was a bug. The subagent's suggested next step was to split app_entry since October 10 by entry path (launcher or file open) and compare first_open with Play installs. That was not done in the session, and on November 3 we found no table in the sugar-utils docs that lines the two up by date.

FAQ

GA4 shows zero for my app. Should I start with the code?

Read the total row of a table report first. Here, a 28-day value read as zero on the overview page was 43 users and 10,522 events in a table report, and three minutes of code and build review found no defect.

A data stream says "no data received in the past 48 hours". Is collection broken?

It can simply mean no events arrived in those 48 hours. SugarDoc had zero real users on October 16 and 17, which is why the message appeared; after the phone uploaded its events, app_entry showed up in the realtime report about two minutes later.
