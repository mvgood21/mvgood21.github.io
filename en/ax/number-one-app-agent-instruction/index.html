Claude Code agents told to build a No. 1 app

One vague Claude Code instruction set 11 agents running and put two versions into production within 23 hours; two weeks later the app had moved from 20th to 16th for its main keyword.

By Stephen · Working with agents · 10 min read · Last updated November 18, 2026

"Make it the No. 1 app in the Android store" came with no number attached. A week after the Korean document viewer SugarDoc went public, the operator, in rough language, told the agent to launch a huge number of agents and keep working for three days. Before planning anything, the Claude Code agent measured where the app stood: 1+ installs and 0 reviews.

Over the next 23 hours two versions were submitted to the production track, the stage where a release goes to every user. The operator typed the 1.2.0 promotion and the store-listing commands himself, and also vetoed a ₩140,000 ad test. Two weeks later the verdict written in the repository was "no clear gain".

20th for the main keyword, unlisted for the other four

The instruction arrived at 21:22 on October 17 (Korea time). Within five minutes the agent had read the repository docs, the Play release tracks and the public store page, and pulled Play search results for five keywords. For 한글뷰어 ("Hangul viewer", the main Korean query) SugarDoc was 20th of 29 apps. For the other four, including hwp and hwpx (the Korean word processor's file formats), it was not listed at all. A research agent counting the same page that day got 21st.

The operator had named three dashboards: GA4, AdMob and Google Ads. AdMob had nothing to show because the app carries no ads, and Google Ads only came up as a plan for a new campaign. GA4 could not be read at first: the machine's Google login lacked the analytics scope. The operator tried the login command himself and it failed, then said to use the browser extension and that everything was approved. The agent opened GA4 and the Play Console through Claude in Chrome, an extension that reads and clicks in the user's own Chrome tabs.

The 23:50 status report, after saying seven agents were running, went on: "I can't create ten million agents running for three days, and I can't promise the No. 1 spot. Instead I'm starting with what actually blocks the ranking."

Seven agents in three stages

The agent wrote a workflow script, a file that sets which agents run in which order and which run in parallel, and the run started at 23:50. The stages were research, build and review, and each stage's written results became the next stage's input.

StageWhat the agent didTime
Research14 competitor apps and 231 of their reviews10 min
ResearchWhat the app really does, read from the code5 min
BuildNew store title and description (ko/en)11 min
Build"Save as PDF" without the print screen76 min
BuildAds and search acquisition plan, help article draft8 min
ReviewAdversarial review of the new code (a review that only hunts for defects; 3 fixed)18 min
ReviewCheck of the store copy's claims (the plan file had not been written)8 min

Every agent's shared instructions said not to commit, push, upload to Play or publish.

The workflow took 104 minutes. Run back to back, the seven agents add up to 137, so parallelism saved about 33 minutes. One development agent, with 193 tool calls over 76 minutes, set the length of the whole run. How many agents could run at once on this machine is covered in Claude Code parallel agents: 10 tasks, 3 at a time.

Counting four agents outside the workflow, 11 agents ran in this session (purple in the timeline above).

Both of the lead agent's premises were wrong

The lead agent, the main session that talked with the operator and launched the others, suspected two things. Most top competitors put "PDF save" or "PDF convert" in their titles and SugarDoc lacked it, and GA4 showed zero for 28 days, so measurement looked broken.

The research agent that read the code corrected the first. PDF save had shipped in 1.0.0 through the system print screen; what was missing was a direct save that skips that screen, and store copy that said so. How 1.2.0's save was tested is in SAF PDF save: cancelling without empty files.

The second came from reading a dashboard before it finished loading, and the agent withdrew it ten minutes later, once the GA4 diagnosis agent reported back. That story is in GA4 shows zero? Read the total row first.

With both premises gone, the remaining problem was traffic. The research agent widened the check to seven keywords, and places 1 to 4 rotated among the same five apps, each with 100,000 or more installs. Yet a small app with 100+ installs and no ratings sat 3rd to 7th on all seven keywords, with the search words written into its title exactly as people type them.

At that point the research agent rewrote the goal in its document: "No. 1 is not realistic in the short term," while the top 10 for three keywords, the main one included, had evidence behind it. Its estimated condition was a first 20 to 50 reviews.

Telling the agent to do it all did not get production promotion past the permission checker

On the morning of October 18 the agent committed 1.2.0. Its upload to the internal test track was denied once and went through when it was run again after the operator told the agent to do it all itself; the log does not say why it passed.

Promotion to production was blocked once the night before for 1.1.0 and twice that morning for 1.2.0. The blocker was Claude Code's auto-mode permission checker, which classifies a command's risk before it runs, and each time the reason was "Production Deploy".

The agent did not work around it. It told the operator that permission given in chat does not lift this checker, and offered two ways out: the operator could run the command himself, or add it to the allow list under Claude Code's /permissions. At 12:08 the operator ran the promotion command, and in the afternoon he ran the store-listing upload too.

Denial reasonCountWhat it blocked
Production Deploy63 promotions, 1 internal-track upload, 1 store listing, launching 1 site-fix agent
Permission Grant1Clicking "Enable" on the Play reporting API
Modify Shared Resources1A commit plus merge to main (the commit alone went in on retry)
No verdict1312 document writes by subagents, 1 status-file edit by the lead

"No verdict" means the checker made no call at all. Four subagents could not write to the repository, and the lead copied or applied their results itself.

Version 1.3.0 turned on editing, so it was still open whether an edited file would open and re-save in the Hancom app (the Korean word processor's mobile suite). That evening the agent advised holding the release until that check. The operator answered that he approved publishing to production. After that approval the agent promoted the build itself, and no denial was logged for that command. The log does not say why the checker let it through, so we don't recommend this as a way past the checker. The Hancom check passed 38 minutes after release.

Two weeks with a new title instead of ₩140,000 in ads

At 15:46, reporting the 1.2.0 submission, the agent listed a Google Ads test at ₩10,000 a day for 14 days as the next step. About six minutes later the operator asked whether a ₩140,000 experiment was really needed, and 17 seconds after that the answer was "Don't do it now." It gave two reasons: the ad money could not be earned back, and with the store title changed that same day, more installs could not be traced to either cause. The second reason was already true at 15:46. The agent reversed its own advice only once the operator questioned the amount.

The operator asked about ₩1,000 to ₩2,000 a day instead, and the agent advised against it because ad learning (the early period in which the ad platform works out whom to show the ad) would never finish on that budget. Thirty seconds after that answer the operator decided: spend as little as possible, publish the help article, watch for two weeks, then plan paid marketing properly. The agent saved the decision to a memory file, notes that later agent sessions also read, as a rule not to propose ad spend before November 1.

At 16:19 the operator pointed out that the site's robots.txt needed attention too. The agent found the old file allowed everything and listed only the sitemap, so build tools and data folders were open to crawlers, and pushed a fix within a minute (3f504be).

The title changed on October 18 to one that spells out "open HWP Hangul files" and "PDF save". On a search where apps with 100,000 or more installs rotate through places 1 to 4, the November 1 record says no clear gain. The main keyword stood at 16th, four places above the 20th it started from, but within the two weeks it went 13th, 14th, 16th. "한글 파일 열기" (open Hangul file), which is in the title, still did not list the app.

For "hwp" and "한글 문서" (Hangul document) the app rose from 28th and 22nd on October 28 to 20th and 11th on November 1; before that, those result pages listed only 10 or 11 apps. The same record notes about one real user a day, too few to tie such rank moves to installs.

Nor was this a one-change test: in the same two weeks, updates 1.3.1 to 1.3.3, a site search-visibility pass and one short video on October 31 also went out. The day-7 check planned for October 25 was never run.

How to split a vague instruction

When an agent gets a vague goal, make it measure a baseline before it plans. Here, 20th place and zero reviews were measured first, and the 23:50 report said plainly that No. 1 could not be promised. Both wrong premises came out when separate agents re-checked the code and the reports.

  1. Measure search rank per keyword, installs, reviews and release-track state. Count the same value a second way (here it came out 20th and 21st).

  2. Rewrite the goal from the baseline and competitor data. Split what cannot be promised from what has evidence, and say so in the first report.

  3. Split the work into research, build and review, and get each agent's result as text or a file. Put "no commit, upload or publish" in the shared instructions.

  4. Have a separate agent that reads the code check the lead's premises, such as "this feature is missing" or "this metric is zero".

  5. List what a person must do (production deploys, enabling APIs, ad spend) in the first report. Under auto mode, add those commands to the /permissions allow list beforehand or have a person run them.

  6. Change one thing at a time, and write the re-measurement date and who will run it into a file.

There is no ad plan yet. The operator wanted it written properly after two weeks, but as of November 17 the growth plan document is the October 18 version. Reviews are the next number to watch.
