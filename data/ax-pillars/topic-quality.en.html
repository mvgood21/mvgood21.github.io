The short answer: ask what a test protects, not how many pass

When an AI coding agent reports "I added tests and they all pass," nobody may have checked what those tests protect. In September 2026 our peer-to-peer chat app (Flutter) had 3,066 passing tests and, under them, one SQLite line that, traced through the plugin source, makes opening the database fail on a device. The same app's "100% E2E pass," claimed since August 2025, came from seven test runners that contained no assertion at all.

The pattern repeated in other apps. A commit message from the agent reported a realism score of 95.2%, but the validation runner's own arithmetic cannot produce more than about 92.3%. A "no crash" report rested on nothing more than launching the app once. The nine checks below come from the measured cases on this page, and each one links to the note that holds its evidence. All cases come from SugarMount, a solo studio that builds Android and Flutter apps with AI coding agents.

What should you check before trusting an agent's "pass"?

  1. Delete the guard and watch the test fail. In the chat app, reverting a fix left all 13 storage tests green, and two fixes reported as verified kept their tests green with the guard deleted. Of the 26 findings in that review, 24 had been introduced by that round's own fixes. Evidence: checking tests by deleting the guard
  2. Write down the numerator, the denominator and the command behind every pass rate. Five of the seven runners behind "100% E2E pass" never called app code; they timed short delays and counted their own successes. The night we deleted their 3,010 lines, an E2E over real sockets logged seven defects. Evidence: seven runners with zero expect()
  3. Read the skip count next to the pass count. flutter test does not count a skip as a failure. One of our 13 skips was a relay integration test that had been broken for six days, and three crypto cross-check tests were written to skip quietly whenever a Python module was missing. Evidence: silently skipped tests and green CI
  4. Confirm the gate read the artifact you will ship. On September 13, 2026, a 43 MB app bundle built from a development config (localhost, plaintext signaling) got PASS from our release gate. In another app, the ad SDK check compared a dependency list the intended release never used. Evidence: release gates that checked something else
  5. Make every checker print how much it measured. Our contrast checker measured only 5,556 of 9,318 text fragments (59.6%) and still reported zero failures; nothing recorded what it skipped. Evidence: the contrast checker that skipped 40%
  6. Reproduce a reported number from the code that produced it. Fifteen functions in the validation runner returned constants between 0.85 and 0.96 instead of measuring anything. A build with all 183 tests passing showed a "3D" view that was a fixed drawing and could not rotate. Evidence: the 95.2% that never came out of the runner
  7. Ask what "no crash" was based on. The agent's evidence was an 857 ms launch. Running adb monkey on the app with its data cleared crashed it at event 15 of 800; the cause was one missing VIBRATE permission in the manifest. Evidence: the fresh-install monkey test
  8. Launch the minified release build on a real device. On September 23, 2026, R8 removed one constructor and every release build of our first app died at startup. The debug build never showed it, and 16 days later a second app crashed the same way. Evidence: the release gate and an R8 crash
  9. Fix only the review findings that survive refutation. For a pre-release review on September 29, 2026, we ran 84 agents, gave every finding to three other agents to knock down, and fixed only the 20 that held. Evidence: review findings that survived refutation

Where checks outside the test suite stopped a defect

Some defects were stopped right before a save or a release, whatever the tests said. The pre-save gate of our HWP document viewer blocked every form-field save on both test documents. We shipped with editing switched off rather than loosen the gate, and nine days later turned editing on without form fields. In the Hancom compatibility check, all seven edited files opened, but re-saving needed a person to sign in, so the agent could not finish that step alone.

Numbers and scores that are not tests get the same treatment. On the day an agent reported a 130% ad payback and advised raising the budget, the numerator was GA4 ad revenue per user and the denominator was a Google Ads cost per install. Divided within one source, it was 76% (a 130% payback was 76%). A promo short went live over another topic's app screen because the session that made it graded it 9/10 itself. The grading gate changed that night, but nobody re-graded clips that had already passed, so it sat in the posting queue for 13 days (a self-graded 9/10 short). So the maker's own grade does not count, and when a gate changes, items that already passed go through the new gate again.

Fifty malicious test files live in the repository as a generator plus an expected-verdict table, not as hostile files. For a shared LLM cache, a blind A/B scored 96.6% without the user's context against 96.0% with it, so we stopped sending context. Checks for running several agents at once are collected in running Claude Code agents in parallel.
