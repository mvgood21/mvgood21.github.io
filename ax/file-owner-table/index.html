Claude 세션 여러 개가 한 저장소를 고칠 때: 머지 13개로 확인한 파일 주인 표

커밋 하나가 다른 세션이 만들던 파일 50개를 담아 간 뒤, 공유 파일마다 주인을 한 명씩 적는 표를 만들어 병렬 작업을 나눴습니다.

작성 SugarMount · 에이전트와 일하는 법 · 읽는 시간 13분 · 최종 업데이트 2026년 10월 29일

출시 1.0.3의 크래시를 고친 커밋 32fca47에는 파일 74개가 바뀌어 있었고, 그중 50개는 같은 작업 트리에서 다른 Claude Code 세션이 만들던 다음 앱의 파일이었습니다. 2026년 9월 23일, 유틸리티 앱 저장소(sugar-utils)의 일입니다. 16일 뒤 가족 일정 앱 AXFamily는 공유 파일 주인 표를 담은 계획서를 쓰고, 다음 날 기능 브랜치 13개를 2분 11초 만에 머지했습니다. 손으로 합친 머지는 7개였습니다. 기능별로 나눈 번역 조각 파일에서는 한 번도 나오지 않았고, 커밋해 둔 합본 번역 파일(머지 4개), stub 목록에 없던 이름과 오류 코드(M1), 다른 주인 칸의 색인 파일(A1·A2), 테스트 파일(F2)에서 나왔습니다.

근거는 두 저장소의 git 기록(32fca47, ca1ade4, 머지 3e9d0cb~e5f9798, 58920b9~ff0c975, a0351cf, 5d51b5b), AXFamily의 2026-10-09 출시 계획서, 당시 세션들이 남긴 메모리 노트, 이 사이트의 AGENTS.md입니다. 손 머지 수는 2026-10-28에 git show --cc로 다시 세었습니다.

출시 수정 커밋에 다른 세션이 만들던 파일 50개가 들어갔습니다

9월 23일 저녁 sugar-utils 작업 트리에서는 세션 두 개가 돌고 있었습니다. 하나는 사진 용량 줄이기 앱(U01)의 1.0.3 출시를 마무리했고, 다른 하나는 다음 앱인 사진 반전·회전(U02)을 만들고 있었습니다. 22시 24분에 U01 세션이 커밋한 32fca47의 메시지는 R8이 지운 생성자를 살린 수정, 출시 점검 스크립트, 분석 기본값 변경과 백로그 메모를 적었을 뿐 U02 이야기는 없었습니다. 실제 변경은 74파일, 3,946줄 추가였고 apps/sugarflip/과 docs/store/sugarflip/ 아래 50파일(3,313줄)과 이미지 엔진 core/images 5파일(428줄)은 U02 세션이 아직 만드는 중이던 코드였습니다. U02 세션의 메모리 노트는 이것을 "git add -A 식으로 쓸어 담았다"고 적었습니다. U02의 엔진과 화면은 다음 날 13시 29분 7821dbd에서야 제대로 된 설명과 함께 커밋됐습니다.

같은 커밋이 새로 넣은 scripts/qa/release_launch.sh 13행에는 ./gradlew --stop이 있었습니다. Gradle 문서에 따르면 --stop은 명령을 낸 Gradle과 같은 버전으로 뜬 데몬을 모두 끝냅니다. 같은 PC에서 한글 띄어쓰기 앱을 빌드하던 세션도 Gradle 9.6.0을 썼고, 그 세션의 메모리 노트에는 이날 clean 빌드 두 번이 Gradle build daemon has been stopped: stop command received로 끊겼다고 남아 있습니다.

세션들은 서로 이웃을 의심했습니다. U02 세션은 데몬을 멈춘 쪽을 한글 띄어쓰기 앱 빌드로 적었고, 한글 띄어쓰기 세션은 sugar-utils를 지목했습니다. 두 저장소의 전체 이력에서 --stop이 들어간 곳은 32fca47의 출시 스크립트 하나뿐입니다(누가 몇 시에 그 줄을 실행했는지는 기록이 없습니다). 그 줄은 15일 동안 스크립트에 남아 있다가 10월 8일 ca1ade4에서 --no-daemon으로 교체됐습니다.

같은 작업 트리에서는 git이 내 변경과 남의 변경을 가르지 못합니다

같은 작업 트리에서는 git이 알릴 충돌이 생기지 않습니다. 두 세션의 변경이 한 인덱스에 섞이고, 먼저 커밋한 세션이 그 순간 작업 트리에 있던 모든 파일의 주인이 됩니다. 파일마다 주인이 정해져 있지 않으면 에이전트는 "이 파일은 내가 고친 것"인지 판단할 근거가 없습니다. Gradle 데몬도 같은 구조였습니다. 데몬은 파일이 아닌데도 같은 PC의 세션들이 함께 쓰는 공유물이었고, 주인 없이 아무 세션이나 끌 수 있었습니다.

U02 세션은 그날 메모리 노트에 규칙을 남겼습니다. 공유 파일(AGENTS.md, 백로그, CHANGELOG, 템플릿)은 고치기 직전에 다시 읽고 Write 대신 부분 Edit을 쓴다. commit, stash, reset, gradlew --stop은 하지 않는다. 빌드가 다른 세션 때문에 끊길 수 있으니 종료 코드를 믿지 말고 테스트 결과 XML의 시각을 보고 다시 돌린다. 같은 규칙은 지금 운영자의 전역 지침(모든 프로젝트에 적용)에도 들어 있고, 거기에는 긴 Gradle 빌드를 --no-daemon으로 돌린다는 줄이 함께 있습니다.

worktree로 나눠도 AppContainer.kt는 머지 4번 중 3번을 손으로 합쳤습니다

작업 트리를 나누는 방법은 그보다 먼저 써 봤습니다. 9월 20일 23시 10분에 저장소를 만들고, 기반 작업 4개(파일 처리, 이미지 엔진, 광고·결제, 분석)를 서브에이전트마다 git worktree 하나씩 맡겼습니다. 23시 28분부터 40분까지 12분 동안 브랜치 4개가 머지됐고, 다음 날 0시 26분까지 두 개가 더 들어가 모두 6개였습니다. git show --cc로 보면 기반 작업 머지 4개 중 3개에서 AppContainer.kt를 손으로 합쳤습니다. 이 저장소는 DI 프레임워크 없이 앱마다 이 파일 하나에서 의존성을 직접 엮기로 정해 두었고(ADR 0001), 그래서 모든 기반 작업이 이 파일에 자기 줄을 보태야 했습니다.

worktree는 작업 중인 파일이 섞이는 것을 막아 줍니다. 여러 작업이 한 줄씩 보태야 하는 연결 파일의 충돌은 머지할 때 그대로 나옵니다. 게임 저장소에서는 '에이전트 수백 개 써도 돼'의 실제: 워크스트림 10개, 하루 59커밋, 동시 실행은 3개에 쓴 대로 워크스트림마다 "독점 소유" 파일 열을 두었습니다. AXFamily는 거기서 빠져 있던 공유 연결 파일 쪽을 표로 따로 적었습니다.

AXFamily 계획서는 공유 파일 행마다 주인과 다른 패키지가 쓸 길을 적었습니다

10월 9일 AXFamily의 출시 계획서는 결론 1번에 "Wave 0 한 명이 공유 파일을 먼저 전부 깐다. … 이 공유 파일을 Wave 1 이후에는 아무도 고치지 않는다"를 두었습니다. 2장 "병렬 작업 충돌 규칙"의 표는 열이 세 개입니다. 아래는 그 표를 줄인 것입니다.

공유 파일주인다른 패키지가 하는 방법
계약 스키마와 생성물W0 계약 레인손대지 않는다. 필요한 계약은 W0의 후속 PR 큐에 올린다
firestore.rules, 색인 파일R1테스트용 JSON만 rules-tests/fixtures/<pkg>/에 둔다
함수 index.ts, errors.ts 등W0W0가 예정된 export를 모두 stub(NOT_IMPLEMENTED)로 등록하고, 각 패키지는 자기 handler 파일만 채운다
앱 기본 틀(pubspec, 라우터, 서비스 등록, 매니페스트, Gradle 파일)W0라우트·광고 정책·채널은 기능 폴더의 파일로 내고 W0의 레지스트리가 모은다

CI 워크플로W0검사 파일 하나를 추가하면 자동 발견된다
Gradle 빌드·기기없음워크트리와 관계없이 동시에 하나만, --no-daemon

W0 한 에이전트가 이 파일들을 직렬로 깔았고(10월 9일 19시 54분 머지), 그 뒤 Wave 1 표의 패키지 12개가 "주요 파일(배타)" 열에 적힌 폴더 안에서 병렬로 일했습니다. 세션끼리 말로 맞추는 방식은 32fca47에서 파일 50개가 섞였고, worktree만 나누는 방식은 AppContainer.kt를 머지 4번 중 3번 손으로 합쳤습니다. 세션 하나로 전부 직렬 처리하면 충돌은 없지만 패키지 12개를 하나씩 해야 했습니다. 직렬로 했을 때 걸렸을 시간은 재지 않았습니다.

머지 13개 중 7개를 손으로 합쳤고, 번역 조각 파일은 0번이었습니다

10월 10일 1시 51분 06초부터 53분 17초까지 통합 브랜치에 기능 브랜치 13개가 들어갔습니다. 계획서 표의 12개에 표에 없던 디자인 시스템 브랜치(UX0)가 더해진 수입니다. git show --cc로 머지마다 양쪽을 섞어 합친 구간(결합 hunk)이 남은 파일을 뽑으면 7개 머지에 그런 구간이 있습니다.

  • 앱 화면 패키지 4개(A2~A5)의 머지: 합본 app_ko.arb·app_en.arb와 거기서 생성한 Dart 파일 3개. CI 검사가 "합본이 조각과 다르면 병합 도구를 돌리고 커밋하라"고 요구해서, 브랜치마다 합본을 다시 만들어 커밋했습니다. 조각 파일 parts/는 13개 머지 어디에도 나오지 않았습니다.
  • 미디어 패키지(M1) 머지: 함수 index.ts와 errors.ts. M1은 W0의 예정 export 16개에 없던 confirmAssetUpload를 추가했고, 오류 코드 목록 한 줄을 계정 패키지(F1)와 M1이 각자 고쳤습니다.
  • A1·A2 머지: R1이 주인인 firestore.indexes.json.

나머지는 테스트 파일이었습니다. 머지 기준점과 각 브랜치를 git diff --name-only로 비교해 표와 맞춰 보면, 13개 중 8개 브랜치가 다른 칸의 파일을 고쳤습니다. 합본 번역 파일과 계획서가 각 패키지에 맡긴 fixture 파일은 뺀 수이고, B1의 공유 벡터 파일까지 넣으면 9개입니다. 계획서의 "Wave 1 이후 아무도 고치지 않는다"는 지켜지지 않았습니다. 의존성 파일에 두 줄, Gradle 파일에 두 줄, 매니페스트에 네 줄 같은 수정은 git이 조용히 합쳤고, 손 머지로 드러난 것은 같은 줄을 두 브랜치가 고친 경우뿐입니다. 8개 가운데 일부(M1, F1)는 stub 목록에 없던 엔드포인트(confirmAssetUpload)와 W0가 errors.ts에 미리 넣지 않은 오류 코드 때문이었습니다.

git이 조용했던 6쌍과 통합 리뷰의 12건은 파일 주인 표 밖의 문제였습니다

머지 16분 뒤인 2시 9분, a0351cf "Wave 1 통합 깨짐 최소 수정"이 패키지 쌍 6개를 고쳤습니다. 앱의 유료 이용권 판정(A4)이 결제 서버(B1)의 구독 상태 규칙과 달랐고, 광고 동의 타입을 A4와 설정 패키지(A5)가 따로 선언했고, 오류 문구가 미디어 쪽 새 오류 코드를 몰랐습니다. 여섯 쌍 모두 서로 다른 파일이라 git 충돌은 없었습니다. 5시 28분의 5d51b5b는 통합 리뷰가 확정한 결함 12건과 minor 수정, 계약 문서 재고정을 함께 담은 커밋으로, 115파일에 2,088줄을 더했습니다. 보호자 판정을 함수 하나(isGuardianOf)로 모았고, 지금 보고 있는 가족이 누구인지는 화면 패키지 세 곳(A2·A3·A4)이 모두 AppSession.currentHouseholdId 한 값을 쓰게 했습니다. 빠진 색인 2개를 넣으면서 "앱의 orderBy 쿼리와 색인 표"를 대조하는 검사도 추가했습니다.

표에는 파일의 주인은 있었지만 "보호자"나 "현재 가족" 같은 개념의 주인은 없었습니다. 같은 개념을 두 번 정의한 것은 5d51b5b의 통합 리뷰에서야 보였습니다. 파일 주인 표는 텍스트 충돌을 줄이는 도구로 쓰고, 계약 어긋남은 통합 리뷰와 그 결과로 만든 검사에 맡기십시오. 한 기능을 여러 폴더에 걸쳐 바꾸는 리팩터링처럼 칸을 나눌 수 없는 작업에는 이 표를 써 보지 않았습니다.

나누기 전에 적는 표 한 장과 머지 뒤에 돌리는 명령 두 개

에이전트 수를 정하기 전에 공유 파일 목록과 주인부터 적으십시오. 같은 작업 트리를 쓰는 세션에는 커밋 권한을 주지 않습니다.

  1. 여러 작업이 한 줄씩 보태야 하는 파일을 찾습니다. DI 컨테이너, 라우터, 엔드포인트 목록, 의존성 파일, 번역 합본, CI 설정, DB 색인이 후보입니다.
  2. 파일마다 주인을 한 명 정하고, 같은 행에 다른 작업이 대신 쓸 길(조각 파일, 레지스트리에 등록되는 자기 파일)을 적습니다. 빌드와 기기처럼 파일이 아닌 공유물에도 행을 하나 만듭니다.
  3. 주인 한 명이 연결 파일을 먼저 깝니다. 예정된 이름은 전부 stub로 등록합니다.
  4. 합본처럼 도구가 만드는 파일은 머지 뒤에 통합 담당이 다시 만듭니다. 이 사이트의 AGENTS.md도 같은 원칙입니다. 글 작성자는 <main>과 제목·설명만 고치고 tools/build.py를 돌리지 않으며, 생성 파일과 <main> 밖은 통합 빌드를 하는 빌드 주인 한 명이 맡습니다. 이 노트의 초안을 쓰는 에이전트들도 2026년 10월 26일 사이트 사본 하나를 함께 써서 서로의 글이 섞이고 지워진 뒤로 작성자마다 사본을 따로 받습니다.
  5. 같은 작업 트리를 쓸 수밖에 없다면: 편집 직전에 다시 읽기, 부분 Edit, commit·stash·reset·--stop 금지, Gradle은 --no-daemon, 성공 여부는 테스트 결과 XML의 시각으로 확인.
  6. 머지 뒤에 표가 샌 곳을 셉니다.
    # 머지에서 양쪽을 섞어 합친 구간이 남은 파일
git show --cc --format= <merge> | grep '^diff --cc'
# 브랜치가 고친 파일을 표와 대조
git diff --name-only $(git merge-base <base> <branch>) <branch>
    AXFamily에서는 첫 명령이 손 머지가 있는 머지 7개를 찾았고, 둘째 명령의 결과를 표와 대조하니 다른 칸을 고친 브랜치 8개가 나왔습니다.

지침 파일에 이런 규칙을 어떻게 적는지는 AGENTS.md 작성법: AI 코딩 에이전트가 틀리기 쉬운 규칙만 적는다에 따로 정리했습니다.

아직 커밋되고 있는 합본 번역 파일과 개념 주인 칸

AXFamily의 develop 브랜치에는 지금도 합본 app_ko.arb와 생성된 Dart 파일 3개가 git에 들어 있고, CI가 그 최신 여부를 검사합니다. 이 파일들을 머지 뒤 통합 담당만 다시 만들게 바꾸는 일은 아직 하지 않았습니다. 주인 표에 "개념" 행(보호자 판정, 현재 가족)을 더하면 5d51b5b 같은 통합 결함이 줄어드는지는 아직 시험하지 않았습니다.

자주 묻는 질문

Claude Code 세션 두 개를 같은 작업 트리에서 돌려도 되나요?

돌릴 수는 있지만, 운영자가 요청하지 않으면 어느 세션도 커밋하지 않게 하십시오. sugar-utils에서는 한 세션의 커밋 32fca47이 다른 세션이 만들던 파일 50개를 함께 담았습니다. 그 뒤로 같은 트리의 세션은 commit, stash, reset, gradlew --stop을 하지 않습니다.

git worktree를 쓰면 병렬 에이전트 충돌이 없어지나요?

작업 중 파일이 섞이는 문제는 없어지지만, 여러 작업이 함께 고치는 연결 파일의 충돌은 머지 때 그대로 나옵니다. 9월 20일 머지 4개 중 3개에서 AppContainer.kt를 손으로 합쳤습니다.

gradlew --stop이 다른 프로젝트 빌드까지 멈추나요?

같은 Gradle 버전으로 뜬 데몬이면 함께 끝납니다. Gradle 문서가 그렇게 적고 있고, 같은 PC에서 Gradle 9.6.0을 쓰던 다른 저장소의 clean 빌드 두 번이 "stop command received"로 끊겼습니다. 긴 빌드는 --no-daemon으로 돌리십시오.
