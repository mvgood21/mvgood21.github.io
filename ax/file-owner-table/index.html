에이전트 여럿을 한 저장소에서 3/6

출시 수정 커밋에 다른 세션의 파일 50개가 들어갔습니다

9월 23일 저녁, 유틸리티 앱 저장소의 한 작업 트리에서 세션 두 개가 돌고 있었습니다. 하나는 사진 용량 줄이기 앱의 1.0.3 출시를 마무리했고, 다른 하나는 다음 앱인 사진 반전·회전을 만들고 있었습니다. 밤 10시 24분 출시 세션의 커밋 메시지는 출시 빌드 크래시 수정, 출시 점검 스크립트, 분석 기본값 변경을 적었을 뿐 반전·회전 앱 이야기는 없었습니다. 실제로는 74개 파일이 바뀌었고 그중 반전·회전 앱 폴더의 50개와 이미지 엔진 5개는 옆 세션이 아직 만들던 코드였습니다. 옆 세션의 메모리 노트는 이것을 "git add -A 식으로 쓸어 담았다"고 적었습니다.

같은 커밋이 넣은 출시 점검 스크립트에는 ./gradlew --stop이 있었습니다. Gradle 문서에 따르면 이 명령은 같은 버전으로 뜬 데몬을 모두 끝냅니다. 같은 PC에서 한글 띄어쓰기 앱을 빌드하던 세션도 같은 Gradle 버전을 썼고, 그날 clean 빌드 두 번이 "stop command received"로 끊겼습니다. 두 세션은 서로 상대를 의심했지만, 두 저장소 이력에서 --stop이 들어간 곳은 그 스크립트 하나뿐입니다. 이 줄은 15일 뒤 --no-daemon으로 바뀌었습니다.

같은 작업 트리에서는 git이 내 변경과 남의 변경을 가르지 못합니다

같은 작업 트리에서는 git이 알릴 충돌이 생기지 않습니다. 두 세션의 변경이 한 인덱스에 섞이고, 먼저 커밋한 세션이 그 순간 작업 트리에 있던 모든 파일의 주인이 됩니다. 파일마다 주인이 정해져 있지 않으면 에이전트는 "이 파일은 내가 고친 것"인지 판단할 근거가 없습니다. Gradle 데몬도 같은 구조였습니다. 파일이 아닌데도 같은 PC의 세션들이 함께 쓰는 공유물이었고, 아무 세션이나 끌 수 있었습니다.

옆 세션은 그날 규칙을 남겼습니다. 공유 파일은 고치기 직전에 다시 읽고 파일 전체 대신 부분만 고친다. commit, stash, reset, gradlew --stop은 하지 않는다. 다른 세션 때문에 빌드가 끊길 수 있으니 종료 코드 대신 테스트 결과 파일의 시각을 본다. 이 규칙은 지금 모든 프로젝트의 에이전트 지침에 들어 있고, 긴 Gradle 빌드는 --no-daemon으로 돌린다는 줄이 함께 있습니다.

worktree로 나눠도 연결 파일은 손으로 합쳤습니다

git worktree는 같은 저장소를 폴더 하나 더 꺼내 각자 다른 브랜치에서 일하게 하는 기능입니다. 9월 20일 이 저장소를 만들 때 기반 작업 4개(파일 처리, 이미지 엔진, 광고·결제, 분석)를 서브에이전트마다 worktree 하나씩 맡겼고, 12분 동안 브랜치 4개가 머지됐습니다. 그중 3개에서 의존성을 엮는 파일 AppContainer.kt를 손으로 합쳤습니다. 이 저장소는 DI 프레임워크 없이 앱마다 이 파일 하나에서 의존성을 직접 엮기로 했기 때문에, 모든 기반 작업이 이 파일에 자기 줄을 보태야 했습니다.

worktree는 작업 중인 파일이 섞이는 것을 막아 줍니다. 여러 작업이 한 줄씩 보태야 하는 연결 파일의 충돌은 머지할 때 그대로 나옵니다. 게임 저장소에서는 AI 코딩 에이전트를 동시에 몇 개 돌릴 수 있는지 정할 때 워크스트림마다 "독점 소유" 파일 열을 두었고, AXFamily는 거기서 빠져 있던 공유 연결 파일을 표로 따로 적었습니다.

AXFamily 계획서는 공유 파일마다 주인과 대신 쓸 길을 적었습니다

10월 9일 AXFamily의 출시 계획서는 결론 1번에 "기반 담당 한 명이 공유 파일을 먼저 전부 깐다. 그 뒤로는 아무도 이 파일들을 고치지 않는다"를 두었습니다. 충돌 규칙 표를 줄이면 이렇습니다.

공유 파일주인다른 패키지가 하는 방법
API 계약 스키마와 생성물기반 담당손대지 않고, 필요한 계약은 기반 담당의 후속 작업 목록에 올린다
DB 보안 규칙, 색인 파일보안 규칙 패키지테스트용 데이터만 자기 폴더에 둔다
서버 함수 목록, 오류 코드기반 담당예정된 함수를 모두 빈 껍데기(stub)로 미리 등록하고, 각 패키지는 자기 함수 파일만 채운다
앱 기본 틀(의존성, 라우터, 매니페스트, Gradle)기반 담당라우트·광고 설정은 기능 폴더의 파일로 내고 레지스트리가 모은다
합본 번역 파일병합 도구각 기능은 자기 번역 조각 파일에만 쓰고 도구가 합친다
CI 워크플로기반 담당검사 파일 하나를 추가하면 자동으로 발견된다
Gradle 빌드·기기없음워크트리와 관계없이 동시에 하나만, --no-daemon

기반 담당 에이전트가 이 파일들을 직렬로 깐 뒤, 패키지 12개가 각자 배타 폴더 안에서 병렬로 일했습니다. 세션끼리 말로 맞추는 방식은 파일 50개가 섞였고, worktree만 나누는 방식은 연결 파일을 머지 4번 중 3번 손으로 합쳤습니다. 세션 하나로 전부 직렬 처리하면 충돌은 없지만 패키지 12개를 하나씩 해야 하고, 그 시간은 재지 않았습니다.

머지 13개 중 7개를 손으로 합쳤고, 번역 조각 파일은 0번

10월 10일 새벽 2분 11초 동안 통합 브랜치에 기능 브랜치 13개가 들어갔습니다. 계획서의 12개에 디자인 시스템 브랜치가 더해진 수입니다. git show --cc로 머지마다 양쪽을 섞어 합친 구간이 남은 파일을 뽑으면 7개 머지에 그런 구간이 있었습니다.

  • 앱 화면 패키지 4개: 합본 번역 파일과 거기서 생성한 Dart 파일 3개. CI가 "합본이 조각과 다르면 병합 도구를 돌리고 커밋하라"고 요구해서 브랜치마다 합본을 다시 만들어 커밋했습니다. 조각 파일은 13개 머지 어디에도 나오지 않았습니다.
  • 미디어 패키지: 서버 함수 목록과 오류 코드 파일. 미리 등록한 함수 16개에 없던 함수를 하나 추가했고, 오류 코드 한 줄을 계정 패키지와 각자 고쳤습니다.
  • 앱 패키지 두 곳: 보안 규칙 패키지가 주인인 색인 파일.
  • 나머지는 테스트 파일이었습니다.

브랜치마다 고친 파일을 표와 맞춰 보면, 13개 중 8개 브랜치가 다른 주인의 파일을 고쳤습니다. "그 뒤로는 아무도 고치지 않는다"는 지켜지지 않았습니다. 의존성 파일 두 줄, 매니페스트 네 줄 같은 수정은 git이 조용히 합쳤고, 손 머지로 드러난 것은 두 브랜치가 같은 줄을 고친 경우뿐이었습니다.

git이 조용했던 곳에서 계약이 어긋났습니다

머지 16분 뒤의 최소 수정이 패키지 쌍 6개를 고쳤습니다. 앱의 유료 이용권 판정이 결제 서버 규칙과 달랐고, 광고 동의 타입은 두 패키지가 따로 선언했습니다. 모두 서로 다른 파일이라 git 충돌은 없었고, 그 뒤 통합 리뷰가 확정 결함 12건을 더 찾았습니다. 표에는 파일의 주인은 있었지만 "보호자"나 "현재 가족" 같은 개념의 주인은 없었습니다. 그 12건은 병렬 브랜치 13개를 합친 뒤 통합 리뷰가 찾은 결함 12건에 정리했습니다. 파일 주인 표는 텍스트 충돌을 줄이는 도구로 쓰고, 계약 어긋남은 통합 리뷰에 맡기십시오.

나누기 전에 적는 표 한 장과 머지 뒤에 돌리는 명령 두 개

에이전트 수를 정하기 전에 공유 파일 목록과 주인부터 적으십시오. 같은 작업 트리를 쓰는 세션에는 커밋 권한을 주지 않습니다.

  1. 여러 작업이 한 줄씩 보태야 하는 파일을 찾습니다. DI 컨테이너, 라우터, 엔드포인트 목록, 의존성 파일, 번역 합본, CI 설정, DB 색인이 후보입니다.
  2. 파일마다 주인을 한 명 정하고, 같은 행에 다른 작업이 대신 쓸 길(조각 파일, 레지스트리에 등록되는 자기 파일)을 적습니다. 빌드와 기기처럼 파일이 아닌 공유물에도 행을 하나 만듭니다.
  3. 주인 한 명이 연결 파일을 먼저 깔고, 예정된 이름은 전부 빈 껍데기로 등록합니다.
  4. 합본처럼 도구가 만드는 파일은 머지 뒤에 통합 담당이 다시 만듭니다. 이 사이트도 같은 원칙입니다(여러 에이전트 세션이 고치는 정적 사이트의 --check 게이트).
  5. 같은 작업 트리를 쓸 수밖에 없다면: 편집 직전에 다시 읽기, 부분 편집, commit·stash·reset·--stop 금지, Gradle은 --no-daemon, 성공 여부는 테스트 결과 파일의 시각으로 확인.
  6. 머지 뒤에 표가 샌 곳을 셉니다.
    # 머지에서 양쪽을 섞어 합친 구간이 남은 파일
git show --cc --format= <merge> | grep '^diff --cc'
# 브랜치가 고친 파일을 표와 대조
git diff --name-only $(git merge-base <base> <branch>) <branch>

AXFamily에서는 첫 명령이 손 머지가 있는 머지 7개를, 둘째 명령이 다른 주인의 파일을 고친 브랜치 8개를 찾았습니다. 지침 파일에 이런 규칙을 적는 법은 AGENTS.md 작성법에 따로 정리했습니다.

아직 커밋되고 있는 합본 번역 파일과 개념 주인 칸

AXFamily의 개발 브랜치에는 지금도 합본 번역 파일과 생성된 Dart 파일 3개가 들어 있고, CI가 그 최신 여부를 검사합니다. 이 파일들을 통합 담당만 다시 만들게 바꾸는 일은 아직 하지 않았습니다. 주인 표에 "개념" 행(보호자 판정, 현재 가족)을 더하면 통합 결함이 줄어드는지도 아직 시험하지 않았습니다.

자주 묻는 질문

Claude Code 세션 두 개를 같은 작업 트리에서 돌려도 되나요?

돌릴 수는 있지만, 요청받지 않은 세션은 커밋하지 않게 하십시오. 한 세션의 커밋이 다른 세션이 만들던 파일 50개를 함께 담아 간 뒤로, 같은 트리의 세션은 commit, stash, reset, gradlew --stop을 하지 않습니다.

git worktree를 쓰면 병렬 에이전트 충돌이 없어지나요?

작업 중 파일이 섞이는 문제는 없어지지만, 여러 작업이 함께 고치는 연결 파일의 충돌은 머지 때 그대로 나옵니다. 9월 20일 머지 4개 중 3개에서 의존성 연결 파일을 손으로 합쳤습니다.

gradlew --stop이 다른 프로젝트 빌드까지 멈추나요?

같은 Gradle 버전으로 뜬 데몬이면 함께 끝납니다. Gradle 문서가 그렇게 적고 있고, 같은 PC의 다른 저장소에서 clean 빌드 두 번이 "stop command received"로 끊겼습니다. 긴 빌드는 --no-daemon으로 돌리십시오.

근거는 두 앱 저장소의 git 기록, AXFamily의 출시 계획서(2026-10-09), 당시 세션들의 메모리 노트입니다. 손 머지 수는 2026년 10월 28일에 git show --cc로 다시 셌고, 11월 13일에 9월 20일 머지를 다시 확인했습니다.
