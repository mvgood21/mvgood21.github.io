클로드 코드 실기기 테스트: E2E 세 번 돌린 기록

클로드 코드 실기기 테스트를 세 번 돌리는 동안 단위 테스트는 통과였지만 결함이 나왔고, SDK가 여는 외부 요청은 따로 막아야 했습니다.

작성 Stephen · 검증과 출시 · 읽는 시간 11분 · 최종 업데이트 2026년 11월 17일

단위 테스트가 모두 통과한 Flutter 앱을 휴대폰과 PC 에뮬레이터에서 사람 순서대로 써 보니, 첫 화면의 [시작하기] 버튼부터 눌리지 않았습니다. 클로드 코드(Claude Code)가 같은 날 아침 만든 비용 0 테스트 환경에서 세 번 돌리는 동안 결함 31건을 고쳤습니다.

테스트가 초록이면 에이전트는 끝났다고 보고합니다. 운영 서버를 건드리지 않게 막은 장치도 처음에는 틀려서, 실제 클라우드 없이 돈다던 테스트 빌드가 10월 13일까지 실행할 때마다 Google 서버로 요청을 보냈습니다.

07시 53분, 두 기기 모두 첫 버튼이 안 눌렸습니다

2026년 10월 10일 아침 7시 37분, 클로드 코드가 가족 일정 앱 AXFamily의 테스트 환경을 커밋하고 곧바로 기기 E2E(End-to-End, 사용자 순서대로 앱 전체를 끝까지 써 보는 테스트) 에이전트를 돌렸습니다. 기기 A는 운영자의 Galaxy S21, B는 PC의 Android 에뮬레이터였습니다.

[시작하기]가 넘어가지 않자 에이전트는 화면 구조를 덤프하고 라우터를 읽은 뒤, 고치기 전에 실패하는 테스트부터 작성했습니다. 라우터의 화면 이동 규칙은 온보딩 중인 사용자를 나이 확인 화면으로 보내야 했는데, 그 단계가 환영 화면을 허용 경로로 두어서 아무 데도 보내지 않았습니다.

가입도 두 기기에서 실패했습니다. 앱은 PC의 로컬 Firebase에 127.0.0.1로 붙게 만들었는데, Flutter용 Firebase 플러그인(FlutterFire)이 기본값으로 이 주소를 10.0.2.2로 변환했습니다. 테스트 빌드는 127.0.0.1과 localhost에만 평문 HTTP를 허락했기 때문에 두 기기 모두 'Cleartext HTTP traffic to 10.0.2.2 not permitted'로 막혔습니다. 게다가 10.0.2.2는 에뮬레이터 안에서만 PC를 가리키는 주소라, 허용했더라도 S21에서는 PC에 닿지 않습니다.

가족 만들기에서는 가짜 API 키 형식이 틀려 모든 서버 함수 호출이 실패했습니다. 고칠 때마다 R8(출시 빌드의 코드 축소 도구)로 줄인 릴리스 APK를 다시 빌드했습니다. 첫 빌드는 5분 30초쯤, 그 뒤 다시 빌드는 대개 1~3분 걸렸습니다.

App Check는 Firebase의 디버그 공급자를 쓰는 길도 있었지만, 그 공급자는 Google 서버와 토큰을 교환해야 해서 demo- 프로젝트에서는 쓸 수 없었습니다.

출시 게이트는 운영 AAB를 열어 컴파일된 코드(dex)와 Flutter 코드 파일(libapp.so)에서 테스트 표식 문자열을 찾고, 하나라도 있으면 빌드를 막습니다.

CI의 격리 검사는 조건 문장들이 그대로 있는지 보고, 조건을 하나씩 지운 사본에서는 검사가 실패하는지도 확인합니다. 하네스 커밋의 '가드 제거' 사례는 14개였습니다. 출시물을 여는 게이트는 출시 게이트가 출시물이 아닌 것을 검사하고 있었다: 평문 AAB와 dart-define 하나에 있습니다.

회차마다 무작위 입력 도구 monkey 3,000번에 크래시와 ANR(앱 응답 없음)이 없었습니다. 지시문은 R8이 지운 클래스를 못 찾는 오류를 로그에서 찾으라고 했지만 0건이었습니다(R8이 출시 빌드를 죽인 사례는 바이브코딩 앱 출시 전 점검: 안드로이드 릴리스 빌드와 R8 크래시).

R8 대신 나온 것은 흐름과 상태의 결함이었습니다. B가 가족에 들어온 뒤에도 A가 앱을 다시 켜기 전까지 할 일 담당자 목록에 B가 없었고(두 계정이 번갈아 써야 보이는 결함), AI 제안을 승인해도 서버가 쓴 변경을 앱이 몰라 오늘 화면이 첫 설정 카드에 그대로 있었습니다. 1회차와 3회차 커밋 메시지는 고친 18건마다 수정 없이는 실패하는 테스트를 함께 넣었다고 적었습니다. 하네스를 만들 때 Flutter 테스트 1,118개는 1회차 결함들이 코드에 남은 채로 모두 통과했습니다.

3회차에 고친 결함에서는 기기 B에서 AI 정리가 재시도 가능한 오류로 끝났는데도 기록 화면 맨 위 띠가 "AI 결과가 기다리고 있다"고 말했습니다. 2회차부터 열려 있던 항목입니다.

기록상 실기기에서만 난 결함은 없습니다. 수정 기록 어디에도 "S21에서만 재현"이라는 말이 없습니다. 에뮬레이터는 시간대가 GMT였고 S21은 가족과 같은 서울 시간이어서, 날짜 선택기의 '오늘'이 기기 시간대를 따르는 결함은 에뮬레이터 화면에만 나타났습니다.

'실제 클라우드 없이'는 10월 13일까지 사실이 아니었습니다

하네스 README 첫 줄은 실제 클라우드 없이 기기 두 대로 핵심 흐름을 끝까지 돌린다고 적었지만, 1회차 보고부터 Google 로깅 주소는 정상 응답(HTTP 200)을, Firebase Installations(설치마다 ID를 발급하는 서비스)는 거절 응답(HTTP 400)을 돌려주고 있었으니 요청이 실제로 밖에 나간 것입니다. 400은 가짜 API 키를 형식에 맞게 고친 뒤부터 생겼다고 에이전트가 보고에 스스로 적었습니다.

3회차가 끝났을 때도 앱 프로세스마다 Installations 경고가 24줄씩 남았습니다. 같은 날 오후 커밋 753cc37은 테스트 빌드에서 Firebase 자동 수집 설정을 끄고 README에 "Installations·FCM 등록 요청 없음"이라고 적었습니다. 35분 뒤 리뷰를 반영한 c2aeb59는 실제로 달라진 설정이 키 하나뿐이라고 고치고, '네트워크 0'을 기기 확인 전까지 미확인 항목으로 낮췄습니다.

다음 날 운영자의 다른 폰 Galaxy S20으로 한 실기기 QA 보고는 Installations 400을 다시 찍고 그 미확인 항목을 '아니다'로 확정했습니다. 원인으로 적힌 것은 푸시 토큰 요청이었습니다.

하네스는 앱이 직접 부르는 서버 주소만 로컬로 돌렸고, SDK가 스스로 여는 요청은 대상 밖이었습니다. 격리 게이트는 소스 문장과 산출물 속 문자열을 읽을 뿐이어서, 하네스 커밋의 격리 테스트 21개는 평문 허용 호스트 같은 설정은 봤지만 실행 중인 앱의 외부 연결을 막거나 세는 사례가 하나도 없었습니다.

10월 13일 d90e21a는 설정을 더 끄는 대신 전송 단계에서 막았습니다.

  • 앱 시작 때 Firebase보다 먼저 만들어지는 빈 ContentProvider(Android 구성 요소)가 Java의 https 처리기를 '항상 거부'하는 처리기로 교체합니다.
  • 테스트 빌드의 네트워크 보안 설정(NSC)에서 신뢰 인증서를 0개로 두어 다른 TLS 연결도 핸드셰이크에서 끝납니다.
  • Dart의 HttpClient는 로컬 평문 http만 엽니다.

같은 날 기기 판정 스크립트가 앱 UID(Android가 앱마다 붙이는 사용자 번호)의 외부 네트워크 바이트를 세었고, S21과 S20 모두 0이었습니다. 리뷰에서 0만으로는 늘 0을 내는 고장 난 집계와 구분할 수 없다는 지적이 나와, 같은 방법으로 센 시스템 UID 바이트가 0보다 커야 PASS라는 대조 조건이 붙었습니다.

에뮬레이터를 쓰지 않기로 한 날

10월 11일 오후 2시 32분, 운영자가 왜 자꾸 PC 에뮬레이터를 켜느냐고, S20으로 테스트하라고 하지 않았느냐고 물었습니다. 에이전트는 바로 에뮬레이터를 종료했고, 스토어 스크린샷 작업 에이전트에게 에뮬레이터를 쓰라고 지시한 것이 자기라고 답했습니다. 그날 오후 커밋 9fcff82가 찾은 근본 원인은 계획서의 옛 결정 한 줄과 표 속 문장 두 개였습니다. 옛 결정은 "두 번째 테스트 기기: Play 이미지 에뮬레이터. S20은 쓰지 않는다."였습니다.

계획서에는 S21을 기기 A, S20을 기기 B로 정한 새 결정을 넣었습니다. 설치 스크립트는 기기 일련번호(serial)가 emulator-로 시작하거나 에뮬레이터 시스템 속성이 보이면 우회 스위치 없이 끝나고, 지침 검사 테스트는 옛 문장 세 줄을 다시 넣으면 실패합니다. 그 대신 시간대 결함을 잡았던 GMT 기기도 함께 빠졌습니다.

같은 하네스를 만드는 순서

에이전트가 낸 '완료' 보고는 릴리스 빌드를 기기 두 대에서 시나리오 끝까지 돌린 회차 기록이 붙었을 때만 받으십시오.

  1. 테스트 빌드는 운영과 같은 릴리스·R8 설정을 쓰고, 빌드 상수 하나(dart-define)가 있을 때만 테스트 코드를 넣습니다. 패키지 접미어, 디버그 키 서명, Play 업로드용 번들(AAB) 금지를 같이 겁니다.

  2. 가짜 백엔드와 모델은 에뮬레이터이면서 demo- 프로젝트일 때만 고르고, 하나만 참이면 호출을 거부합니다.

  3. FlutterFire의 주소 자동 변환을 끄고, adb reverse(PC 포트를 기기 쪽 127.0.0.1로 넘기는 명령)로 연결합니다. 평문은 127.0.0.1과 localhost에만 허용합니다.

    firestore.useFirestoreEmulator('127.0.0.1', 8180, automaticHostMapping: false);
adb -s <기기> reverse tcp:8180 tcp:8180

  4. 운영 AAB에서 테스트 표식을 찾는 게이트를 두고, 가드 제거 사례 테스트로 고정합니다.

  5. 기기 두 대의 언어와 시간대를 다르게 맞추고, 가입·초대·AI 제안·사진·계정 삭제까지 12단계 시나리오를 돌립니다. 결함마다 실패 테스트, 수정, 다시 빌드, 기기 재확인 순서로 갑니다.

  6. 외부 네트워크는 기기의 dumpsys netstats detail에서 앱 UID의 바이트로 계산합니다. 증가가 0이고, 차단 장치 설치 로그가 있고, 같은 방법으로 센 시스템 UID는 0보다 커야 PASS입니다. 다른 앱 정보가 섞인 출력이라 기기 안에서 걸러 값만 가져옵니다.

결제·푸시·Play Integrity는 런북으로 넘겼습니다

Play 결제 완료, 실제 푸시, 사진 파일 삭제, Play Integrity(Play에서 받은 앱인지 확인하는 서비스)로 받는 App Check 토큰은 이 하네스로 확인하지 못합니다. 실제 AI와 운영 서버를 쓰는 기기 테스트는 10월 13일 따로 만든 실행 절차서(런북)를 따릅니다. 같은 날 운영자는 S20과 S21에서 이 E2E를 분명히 통과해야 완료라고 못박았습니다.

Firebase 로컬 에뮬레이터도 오류를 냈습니다. 가족 삭제가 CANCELLED로 몇 번 실패했고, 에이전트는 원인을 에뮬레이터 쪽으로 보면서도 재시도 코드를 넣었습니다. 실제 Firestore에서도 그런지는 이 하네스로 알 수 없습니다.

개인 폰을 기기 A로 쓰면 공유 시트와 사진 선택기를 열지 않아야 합니다(연락처와 개인 사진이 화면에 나옵니다). 그래서 사진 단계는 기기 B에서 했습니다.

실기기 한 대의 시간대를 가족과 다르게 두는 단계를 넣어야 날짜 선택기 같은 결함을 다시 잡을 수 있는데, 이 프로젝트의 체크리스트에는 아직 그 줄이 없습니다.
