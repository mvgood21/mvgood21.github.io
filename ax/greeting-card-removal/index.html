AI로 붙인 기능을 AI로 걷어냈다: 인사카드 10,001줄과 형제 앱

인사카드 제거와 R8 최적화를 함께 낸 1.6.020에서 APK가 25.66MB에서 13.15MB가 됐고, 감소분 중 약 11MB가 인사카드 에셋이었습니다.

작성 SugarMount · 회고와 숫자 · 읽는 시간 11분 · 최종 업데이트 2026년 11월 6일

143개 파일과 10,001줄을 지운 커밋 하나(f6ef50e)로 맞춤법 검사 앱 '한글 띄어쓰기'의 인사카드 기능이 끝났습니다. 2026년 9월 20일 밤, 운영자가 이 기능을 억지로 붙였다고 말한 지 35분 만에 들어간 커밋입니다. 기능 자체는 2025년 8월 31일부터 12월 10일까지 커밋 41개로 붙었고, 그중 38개에 Claude 표기가 있습니다. 2026년 1월에 형제 앱 생생카드가 이 코드를 가져가 따로 섰는데도, 원래 앱에는 8개월 더 남아 있었습니다.

출처: 맞춤법 앱 저장소와 생생카드 저장소의 git 기록, 맞춤법 앱 CHANGELOG 1.6.020 항목, 배포 뒤 관측 문서(GA4 집계), 2026년 9월 20~22일 작업 세션 기록. 숫자는 2026년 11월 4일에 git 기록에서 다시 세었습니다.

지운 파일 13.70MB 중 앱 Kotlin 소스는 0.22MB

f6ef50e는 파일 124개를 지우고 18개를 고치고 1개를 새로 만들었습니다. 지운 것은 인사카드 화면 세 개(ActivityMainGreeting, 카드 에디터, 카드 Fragment), 인사카드용 Room 데이터베이스, 눈 내리는 MP4 인코더와 오디오 먹서, 카드 이미지, 캐럴 7곡, 감자꽃 폰트, 그리고 단위 테스트 13개와 계측 테스트 1개입니다. 지운 10,001줄 중 7,857줄이 Kotlin, 2,124줄이 XML이었습니다.

지운 파일의 원래 크기를 git으로 더하면 13.70MB인데, 앱 Kotlin 소스 15개는 그중 0.22MB였습니다. 카드 이미지 폴더의 파일 69개가 6.68MB, 배경 그림 retro.png 한 장이 3.91MB, 감자꽃 폰트가 1.07MB, 캐럴 7곡이 1.02MB, 눈 애니메이션 lottie 파일이 0.34MB였습니다(커밋 메시지는 앞의 셋을 6.5MB, 3.8MB, 1.1MB로 적었습니다).

APK 크기는 CHANGELOG에 실린 측정값입니다. 수정 전 HEAD(1.6.019)를 같은 환경에서 다시 빌드해 기준선으로 삼았습니다.

1.6.019 기준선1.6.020
APK(서명 전)25.66MB13.15MB(−48.7%)
AAB29.95MB18.33MB(−38.8%)
DEX(압축 전)16.31MB14.84MB(−9.0%)

이 표의 감소분을 모두 인사카드 몫으로 읽으면 틀립니다. 같은 날 같은 릴리스에 R8 최적화를 막던 -dontoptimize 한 줄을 지운 커밋(a597223)이 함께 들어갔습니다. CHANGELOG는 감소분의 대부분인 약 11MB를 인사카드 에셋으로, 최적화 몫을 DEX 1.5MB 안으로 나눠 적었습니다. 최적화 쪽 경과는 Play Console 'DEX 최적화 39%'의 범인: 쓰지도 않는 Kakao SDK keep 규칙에서 따로 다룹니다.

커버리지 95%라던 커밋들, 저장소엔 측정 도구가 없었습니다

첫 커밋 0a0f404(2025-08-31)는 파일 21개에 2,495줄을 더하며 인사카드 목록과 Room 모듈을 만들었고, 본문에 "95% 커버리지 달성 (30+ 테스트 케이스)"라고 적었습니다. 같은 날 들어간 커밋 두 개(fb1c8b4, 979c6d4)는 Material 3 테마가 기존 앱 테마와 맞지 않아 생긴 오류를 고친 것입니다. 9월 3일 "Y2K 글리치 네온 인사카드 에디터 완전 구현"(be41ccb)은 파일 60개를 바꾸고 "메모리 누수 및 크래시 0건"을 적었습니다. 9월 10일에는 인사카드가 채팅형·클래식형에 이어 세 번째 화면 모드(UIMode.GREETING)가 됐습니다. 11월 말에 이벤트별 카테고리가, 12월 7~8일에 10초짜리 눈 내리는 MP4 공유와 캐럴 7곡이 붙었습니다.

41개 커밋 중 24개가 2025년 9월에 들어갔고, 추가 줄을 더하면 18,087줄, 삭제는 9,188줄입니다(문서 포함, 102일).

41개 중 다섯 개가(같은 시기 문서 커밋 db2ee27까지 치면 여섯 개) 95% 또는 99% 커버리지를 적었지만, 이 저장소의 전체 기록에서 git log --all -S jacoco와 -S kover는 한 줄도 나오지 않아, 커버리지 도구는 들어온 적이 없습니다. 제목에 '완성'이 붙는 버릇은 커밋 701개로 본 AI 코딩 1년에서 세어 두었습니다. 첫 커밋이 "완전한 greeting 모듈"이라고 부른 Room 데이터베이스는 지우기 직전에 그 모듈 파일 4개 밖의 앱 코드(main)에서 부르는 곳이 0곳이었습니다. 9월 11일 c05d669는 저장된 값이 없을 때의 기본 화면을 인사카드로 두고 디버그 빌드에서는 인사카드 모드를 강제로 저장하게 했는데, 약 24시간 뒤 0c5ceab가 기본값을 채팅으로 되돌렸습니다. 다음 배포 태그가 11월 28일이라 이 기본값으로 나간 버전은 없습니다.

세 번째 메인 화면이 된 인사카드, 8개월 동안의 사본

인사카드는 채팅형·클래식형과 나란히 서는 메인 화면 하나로 들어왔고, 별도 모듈로 나뉘지 않았습니다. 그래서 카드 그림과 캐럴이 맞춤법만 쓰는 사용자의 APK에도 그대로 실렸고, 메인 화면에 들어가는 공통 수정은 화면 세 개에 따로 들어가야 했습니다.

형제 앱이 생긴 뒤에도 이 구조는 그대로였습니다. 2026년 1월 15일 생생카드 저장소의 첫 커밋 c623dd8은 파일 297개, 17,030줄로 시작했고 메시지에 "Greeting card functionality migrated from sugarspeller"라고 적혀 있습니다. 원래 앱에서 지우는 일은 그때 하지 않았습니다. 그 뒤 9월 13일까지 맞춤법 앱에서 ActivityMainGreeting을 고친 커밋이 5개 있고, 다섯 모두 광고나 뒤로 가기처럼 채팅 화면과 함께 고친 공통 수정입니다. 9월 13일의 '한 번 더 누르면 종료' 회귀 수정(289ed55)은 세 화면을 각각 26줄, 23줄, 22줄 고쳤습니다. 왜 1월에 바로 지우지 않았는지는 기록을 찾지 못했습니다.

다른 앱으로 옮긴 기능은 옮긴 그 릴리스에서 원래 앱에서도 지우십시오. 이 앱에서는 그 8개월 동안 공통 수정 5개가 이미 생생카드로 옮긴 세 번째 화면까지 고쳐야 했습니다.

메뉴 두 곳은 링크로, 저장된 값은 채팅으로

9월 20일 운영자는 인사카드를 이 앱에서 전부 빼되 서랍과 상단 모드 메뉴 두 곳의 버튼은 남겨 생생카드로 보내고, 한글 맞춤법에 집중하자고 했습니다. 운영자는 용량도 많이 줄 거라고 봤습니다. 6분 뒤 Play의 코드 최적화 요구(기한 2027년 2월)도 같이 처리하자고 했고, 그것이 a597223입니다.

남긴 메뉴는 새로 만든 SugarCardLauncher로 연결됐습니다. 생생카드가 설치돼 있으면 앱을 열고, 없으면 market://, 그것도 안 되면 https 스토어 주소를 엽니다. Android 11(API 30)부터는 다른 앱의 설치 여부를 보려면 매니페스트에 <queries> 선언이 있어야 해서 생생카드 패키지 하나를 넣었습니다. 메뉴를 누를 때마다 GA4에 sugarcard_open(installed)가 남습니다.

업데이트 전에 인사카드 모드를 골라 둔 사용자는 설정에 "greeting" 문자열이 저장돼 있습니다. 화면 모드를 읽는 코드는 f6ef50e 이전부터 아래 모양이라, 모르는 값은 채팅 모드로 갑니다.

fun fromString(value: String?): UIMode {
    return values().find { it.value == value } ?: CHAT
}

그래서 따로 옮기는 코드는 넣지 않았고, UIModeTest에 "greeting"이 CHAT으로 떨어지는지 보는 테스트를 하나 더했습니다. 테스트 주석에 적힌 이유는 이 사용자가 스플래시 화면 뒤에서 멈추면 안 된다는 것입니다.

AI 추정은 10MB·테스트 9개, 기기 확인은 사람 몫

코드를 고치기 전 에이전트가 내놓은 계획은 지울 화면과 모듈은 짚었지만 숫자는 작았습니다. 카드 이미지 6.5MB, retro.png 3.8MB, 눈 애니메이션 0.3MB를 더해 대략 10MB가 빠진다고 했고, 지울 단위 테스트를 9개로 잡았습니다. 실제 커밋은 감자꽃 폰트와 캐럴 7곡을 더 지웠고 단위 테스트는 13개였습니다.

에이전트는 작업 환경에 연결된 기기가 없어 실기기 확인을 하지 못했다고 보고하고, 디버그 키로 서명한 릴리스 APK를 남긴 뒤 네이버·다음 검사, 히스토리, 구독, 카카오 공유, 인사카드 메뉴를 눌러 봐 달라고 운영자에게 넘겼습니다. 운영자는 다음 날 잘 동작한다고 답했고, 1.6.020은 9월 22일에 배포됐습니다.

런처에는 틀린 가정이 하나 남았습니다. market://을 열다 예외가 나면 브라우저로 넘어가는데, 그 분기 주석은 "Play 스토어 앱이 없는 기기"였습니다. 10월 9일 같은 방식을 게임 메뉴에 붙인 뒤(efc0acf) Galaxy S21 실기기에서는 스토어 앱 세 개가 링크를 받아 예외 없이 선택 창이 나왔습니다. 게임 메뉴 커밋 59분 뒤 8bbe179가 게임과 생생카드 링크 모두 Play 패키지를 먼저 지정하도록 고쳤습니다. 경과와 기기별 결과는 SKT 판매 삼성 폰에서 market://을 열면 스토어 선택 창이 뜬다에서 다룹니다.

메뉴는 남겨 앱부터 열고, 릴리스는 합쳤습니다

메뉴까지 지우는 안은 운영자가 처음 요청에서 막았습니다. 라벨은 '인사 카드로 전환'에서 '인사 카드'로만 줄였습니다. 이제 모드 전환이 아니기 때문입니다.

무조건 스토어로 보내는 안은 에이전트가 계획에서 먼저 물었습니다. 운영자는 앱 우선 순서를 그대로 받았고, 그 대가로 매니페스트에 <queries>가 하나 늘었습니다. 런처 주석대로 이 선언이 빠지면 설치 여부를 알 수 없어 모든 탭이 스토어로 갑니다.

인사카드 제거와 R8 최적화를 다른 릴리스로 나누면 크기 변화가 어디서 왔는지 깨끗하게 보입니다. 운영자는 같이 내기로 했고, 그래서 크기 절의 기준선을 따로 빌드했습니다.

저장한 사용자 데이터가 있으면 순서가 달라집니다

이 제거에 데이터 이전이 필요 없었던 것은 앞에서 본 Room 데이터베이스를 부르는 화면이 제거 시점에 없었기 때문입니다. 사용자가 만든 카드를 저장하는 DB였다면 내보내기나 형제 앱으로 넘기는 길을 먼저 만들어야 합니다.

모드 파서가 모르는 값에 예외를 던지는 구조였다면 테스트 하나로 끝나지 않았을 겁니다. 업데이트한 사용자가 시작 화면에서 멈출 수 있으니, 그때는 저장된 값을 바꾸는 마이그레이션 코드가 먼저입니다.

제거 전에 인사카드 화면이 얼마나 쓰였는지 확인한 기록은 찾지 못했고, 남은 숫자는 제거 뒤의 메뉴 탭뿐입니다. 많이 쓰이는 기능이라면 지우기 전에 화면 사용량부터 봐야 합니다.

기능을 형제 앱으로 넘길 때 따르는 순서

  1. 지울 파일 목록과 크기를 git으로 셉니다. git diff --raw로 삭제된 파일의 blob을 얻고 git cat-file -s로 크기를 더하면, 줄 수와 바이트 중 어느 쪽이 큰지 먼저 보입니다.
  2. 지울 모듈의 호출자를 git grep -l로 셉니다. 모듈 밖에서 부르는 곳이 0곳이면 데이터 이전 없이 지워도 됩니다.
  3. 저장된 설정값이 사라진 값을 만났을 때 어디로 떨어지는지 코드로 읽고, 그 경로를 단위 테스트 하나로 고정합니다.
  4. 메뉴를 남긴다면 형제 앱 런처를 만듭니다. 설치 확인용 <queries>를 넣고, 스토어는 Play 패키지를 지정한 market://, 일반 market://, https 주소 순서로 엽니다.
  5. 크기는 수정 전 HEAD를 같은 환경에서 빌드한 기준선과 비교합니다. 같은 릴리스에 다른 변경이 있으면 몫을 나눠 적습니다.
  6. 릴리스 APK를 실기기에 설치하고, 남긴 메뉴를 설치된 경우와 안 된 경우로 각각 눌러 봅니다.
  7. 메뉴 탭 이벤트에 설치 여부를 함께 남겨 수요를 봅니다.

탭 54건이 설치로 이어졌는지는 아직 모릅니다

배포 뒤 2주(9월 22일~10월 5일) 동안 sugarcard_open은 54건, 약 39명이었고, 누른 순간 생생카드가 설치돼 있던 경우는 0건이라 모두 스토어로 갔습니다(GA4, 관측 문서 기준). 10월 9일부터 22일까지 생생카드 탭이 61건 더 쌓였습니다. installed는 누른 순간에 이미 깔려 있었는지만 알려 줍니다. 1.6.027부터 이 이벤트는 sibling_app_open(target=sugarcard)으로 이름이 바뀌었으니, 다음에는 이 이벤트와 생생카드 쪽 설치 경로를 맞대어 볼 차례입니다.

자주 묻는 질문

앱에서 기능을 지우면 그 모드를 저장해 둔 사용자는 어떻게 되나요?

저장값을 읽는 코드가 모르는 값을 어디로 보내느냐에 달려 있습니다. 이 앱은 모르는 값을 채팅 모드로 돌리는 fromString이 이미 있어서, 남아 있던 "greeting"도 채팅 화면으로 열립니다. 그 경로는 단위 테스트로 고정했습니다.

기능을 지웠는데 APK가 생각보다 덜 줄었습니다. 무엇을 봐야 하나요?

지운 파일의 바이트부터 보십시오. 이 앱은 10,001줄을 지웠지만 앱 Kotlin 소스는 0.22MB였고, 크기는 카드 이미지·배경 그림·폰트·캐럴 같은 에셋에서 줄었습니다.

다른 앱 설치 여부를 확인하는 코드가 늘 '없음'을 돌려줍니다.

Android 11(API 30)부터는 매니페스트 <queries>에 상대 패키지를 선언해야 getLaunchIntentForPackage가 그 앱을 찾습니다. f6ef50e에서는 생생카드 패키지 하나를 선언했고, 이후 게임 메뉴를 붙이며 늘었습니다.
