서브에이전트 브리프의 절대 규칙 6개와 한도로 끊긴 에이전트 5건

커밋에 남은 보고서 4개는 환경 절 하나 말고는 본문이 비어 있었습니다. 이어받은 에이전트는 앞 에이전트가 디스크에 쓴 로그와 고친 파일에서 다시 시작했습니다.

작성 SugarMount · 에이전트와 일하는 법 · 읽는 시간 13분 · 최종 업데이트 2026년 11월 2일

Flutter로 만든 P2P 채팅 앱의 스토어 출시 준비를 나눠 맡은 서브에이전트 5건이 일을 끝내지 못하고 끊겼습니다. 2026년 9월 7일부터 10일까지 세션 한도가 3건, 주간 사용 한도가 1건이었고, 나머지 1건은 사유 미기록입니다. 공통 브리프의 여섯째 규칙은 보고서를 먼저 만들고 진행하면서 채우라는 것이었는데, 커밋에 남은 보고서를 볼 수 있는 4건은 수정 후 E2E의 환경 절 하나 말고는 본문 절이 모두 비어 있었습니다. 이어받은 에이전트는 git diff, logcat, 스크린샷을 읽었고, 기록상 남은 파일이 없던 문자열 전수 검증은 처음부터 다시 측정했습니다.

근거는 이 앱 저장소의 git 기록(e450c09, d464dc4, 7f52466, 9f03e7a, dca6cf9, af912bf, e9d882f, 67edc8d, 8dacf19), 공통 브리프와 그 뒤 브리프 3개, 분석 보고서 17개와 수정 보고서 42개입니다. 시각은 커밋 시각(한국 시간)이고, 이어받은 작업의 시작·종료 시각은 보고서에 적힌 값입니다. 보고서 줄 수와 발견 수는 2026-11-01에 git 기록에서 다시 집계했습니다.

9월 7~10일, 끊긴 에이전트 5건

분석 라운드는 9월 7일 23시 10분 커밋 e450c09로 들어왔습니다. 공통 브리프 한 장(33줄)과 분석 보고서 17개가 함께 커밋됐는데, 그중 에뮬레이터 랩 보고서(14번)는 19줄짜리 뼈대였습니다. 머리말은 "작성 중 (에이전트 진행 중, 부분 결과)"이고 모든 절이 "(작성 중)"이었습니다. 47분 뒤 d464dc4에서 71줄로 채워진 그 보고서의 머리말에는 첫 에이전트가 기기 스크립트와 설치 스크린샷 2장까지 남기고 중단했고, 두 번째 에이전트가 이어서 했다고 적혀 있습니다.

9월 8일 9시 8분 커밋 dca6cf9의 메시지는 "agent interrupted by session limit; to be continued"입니다. 문서 통합을 맡은 에이전트가 세션 한도로 멈췄고, 그 보고서는 19줄 뼈대였습니다. 에이전트가 고친 문서 4개(CLAUDE.md, 릴리스 계획, 보안 문서, 위협 모델)는 같은 커밋에 부분 작업으로 들어갔습니다. 같은 커밋에는 보고서 기록상 그날 0시 24분에 수정 후 E2E를 시작한 랩 에이전트의 결과 폴더도 들어 있었습니다. 이 에이전트 역시 세션 한도로 끊겼고, 보고서는 1절 환경 표만 채운 채 2~8절이 "(진행 중)"이었습니다.

9월 9일 기기 재확인(H1)은 실행 에이전트가 주간 사용 한도로 중단돼 오케스트레이터가 원본 증거를 읽고 판정을 마쳤습니다. 9월 10일 문자열 전수 검증(X1)은 1시 45분에 8줄 뼈대로 커밋됐다가 4시 34분에 1,046줄로 다시 들어왔습니다. 새 머리말은 "앞선 에이전트가 세션 한도로 중단되어 측정 결과가 남지 않았으므로 전부 처음부터 다시 측정했다"입니다.

공통 브리프 33줄에는 에이전트별 할 일이 없습니다

브리프는 목표 한 줄, 검증된 환경 사실, 절대 규칙 6개, 보고서 형식으로 되어 있습니다. 에이전트마다 맡은 주제는 이 파일에 없고 따로 주어졌습니다(그 프롬프트는 저장소에 남아 있지 않습니다). 환경 사실에는 Flutter 버전과 실행 경로, 에뮬레이터 2대, "물리 기기 없음, Xcode/macOS 없음"이 들어 있습니다. 절대 규칙은 요지만 옮기면 이렇습니다.

  1. 시스템 패키지 설치와 새 패키지 추가 금지. 필요하면 보고서에 "승인 필요"로 적는다.
  2. 외부 업로드 금지. 산출물은 저장소 안 파일로만 남긴다.
  3. 분석 단계에서는 lib/, android/, ios/ 코드를 고치지 않는다. 스크립트와 문서만 쓴다.
  4. 블랭킷 sed 치환 금지. rm -rf 대신 임시 폴더로 옮긴다.
  5. 외부 정책을 확인하면 URL과 확인 날짜를 적고, 추측은 "추정"으로 표시한다.
  6. 보고서는 한국어로, 정해진 경로에 초반에 먼저 만들고 진행하면서 갱신한다. 괄호 안 이유는 "세션이 끊겨도 부분 결과가 남도록"이다.

보고서 형식은 요약, 검증한 것, 발견 사항, 즉시 적용할 수정, 남은 unknown 다섯 절입니다. 발견 사항 표는 ID, 심각도(Blocker/High/Medium/Low), 내용, 근거(file:line 또는 URL), 수정 제안, 검증 방법의 여섯 칸이고, ID에는 주제별 접두사(AND-, IOS-, SEC-, LAB- 등)를 붙입니다.

금지 규칙은 실제로 쓰였습니다. e450c09 시점 분석 보고서 13개에 "승인 필요"가 나옵니다. 스토어 준비 분석은 아이콘 생성 패키지 추가를 "승인 필요(규칙 1)"로 적었고, iOS 프로젝트 분석도 그 패키지를 쓰려면 dev_dependency 추가라 승인이 필요하다고 적었습니다. 수정 단계는 그 패키지 대신 이미 깔려 있던 Python 이미지 라이브러리로 스크립트를 써서 아이콘을 만들었습니다. 릴리스 워크플로는 작성만 하고 실행하지 않았습니다. 브리프가 실행 여부를 메인 세션에 맡겼고, iOS 컴파일 워크플로의 첫 성공은 다음 날 0시 27분 커밋 9f03e7a에 기록됐습니다. UI 발견 8건은 코드 수정 대신 일부러 실패하는 테스트 11개로 남았습니다. 금지 목록을 파일 한 장에 두고 매번 읽히는 방식은 AI 에이전트 권한 표: 돈·계정·정책은 사람이 누른다와 같습니다.

보고서 형식은 17개 모두 여섯 칸 표와 남은 unknown 절을 갖췄고, 본문이 있던 16개의 발견 행은 233개(Blocker 15)였습니다. 수정 보고서는 이 ID로 일을 받았습니다. iOS 플랫폼 수정 보고서 하나가 인용한 분석 ID만 38개입니다. 등급은 정의대로 가지 않았습니다. iOS 프로젝트 분석은 정의에 없는 Info를 4건 썼고, 의존성 분석과 랩 분석은 "Low(오탐 확인)"와 "Low~Medium"을 만들어 썼습니다.

규칙 6대로 먼저 만든 보고서 4개는 본문이 비어 있었습니다

브리프는 보고서를 먼저 만들면 끊겨도 부분 결과가 남는다고 가정했습니다. 커밋에 남은 보고서를 볼 수 있는 4건(랩 분석, 수정 후 E2E, 문서 통합, 문자열 전수)은 본문 절이 모두 "(작성 중)"이나 "(진행 중)"뿐이었고, 수정 후 E2E만 환경 절을 채웠습니다.

규칙에 가장 가까웠던 것은 수정 후 E2E 보고서입니다. 머리말에 세션이 끊기면 표의 빈 칸은 미측정으로 보라고 적어 두었습니다. 그런데 끊긴 시점의 결과 표는 통째로 빈 칸이었습니다. 같은 커밋의 raw·screens 폴더에는 logcat 두 개(103,813줄과 89,023줄), 서버 로그, 스크린샷 43장, 메시지 11건의 왕복 지연 원본이 있었습니다. 템플릿 스크립트는 로그 앵커가 틀려 그중 1건만 짝지어 n=1, 11 ms라고 냈습니다.

규칙 6은 만들기와 갱신하기를 요구했지만 갱신 단위를 정하지 않았고, 판정은 파일에 쓰이지 않았습니다. 기록으로 보면 판정은 에이전트의 대화 맥락 안에만 있었던 것으로 보입니다. 이 라운드에서 끊긴 에이전트 중 끊기기 전에 보고서를 정리한 경우는 없었습니다. 끊긴 뒤 디스크에는 명령을 돌리고 문서를 고치는 과정에서 저절로 생긴 파일이 남았습니다.

이어받은 쪽은 git diff와 raw 폴더부터 읽었습니다

다섯 건 중 네 건은 앞 세션이 남긴 파일 위에서 이어 갔고, 랩 분석 14번도 첫 에이전트의 기기 스크립트와 설치 스크린샷 2장에서 출발했습니다. 문서 통합 에이전트는 고친 문서를 작업 트리에 둔 채 멈췄습니다. 수정 단계 브리프가 커밋을 메인 세션에만 맡겼기 때문이고, 메인 세션이 그 상태를 dca6cf9로 부분 커밋했습니다. 9월 9일 0시 6분 af912bf에서 완성된 보고서를 보면, 이어받은 에이전트는 git diff 7f52466..dca6cf9로 앞 세션이 고친 범위부터 확인했습니다. CLAUDE.md는 지시 항목이 모두, 보안 문서(SECURITY.md)는 8개 중 7개가 반영돼 있었고, 나머지 문서 9개와 스토어 초안은 손대지 않은 상태였습니다. 이어받은 쪽은 반영된 부분을 다시 쓰지 않고 19개 파일을 마쳤습니다.

수정 후 E2E는 보고서 기록상 9월 8일 23시 15분부터 다른 랩 에이전트가 이어받아 50분 만에 끝냈습니다. 빌드, 설치, 연결, 메시지 전송까지는 남은 raw를 그대로 쓰고 라이프사이클, 차단, 데이터 삭제 같은 나머지 시험만 새로 했습니다. 왕복 지연은 다시 재지 않고, 앞 세션이 이미 보낸 버스트 10건을 로그 앵커를 바로잡아 다시 계산해 p50 61 ms, p95 74 ms를 얻었고, 보고서는 41줄에서 338줄로 늘었습니다. 기기 재확인(H1)은 증거 수집이 사실상 끝난 뒤에 끊겨서, 디스크의 스크린샷 85장과 로그 8종으로 판정만 하면 됐습니다.

문자열 전수 검증은 코드를 읽고 판정하는 일이었고, 기록상 남은 파일이 없었습니다. 다음 에이전트는 8줄 뼈대에서 시작해 lib/ 93개 파일의 문자열 리터럴 2,864개를 처음부터 다시 파싱하고 화면에 나올 수 있는 464개를 판정했습니다. 그 라운드 브리프의 5번 규칙도 진행하면서 갱신하라는 문장 그대로입니다. 같은 커밋 8dacf19에서 대비 검사기를 다시 센 일은 대비 검사기는 글자 40%를 재지 못했다에 적었습니다.

서브에이전트 브리프에는 보고서를 먼저 만들라는 말보다, 원본 증거를 어느 경로에 언제 쓰라는 말을 먼저 적으십시오.

검증 방법 칸이 고친 백업 복원 예측

플랫폼 보안 분석은 코드를 읽고, Android 자동 백업으로 복원된 앱이 Keystore 키를 잃어 영구히 쓸 수 없게 된다고 예측했습니다(SEC-2). 랩 에이전트가 그 행의 검증 방법 칸대로 bmgr로 백업, 삭제, 재설치, 복원을 실제로 돌리자 앱은 멈추지 않았습니다. 키 풀기 오류 뒤 설정 화면으로 돌아가 새 프로필을 만들었고, 이전 키와 대화 기록은 조용히 사라졌습니다(LAB-7). 백업을 끄라는 수정 제안(allowBackup=false)은 실측 뒤에도 그대로 필요했습니다.

수정 단계 브리프는 분석 보고서의 diff를 검증한 뒤 적용하라고 했습니다. UI 수정 에이전트는 diff A~H 가운데 3개가 틀리거나 모자라 고쳐서 적용했다고 보고했습니다. 바텀시트 안에서 Theme.of가 앱 테마를 돌려준다는 점, 버튼 글자 처리, useSafeArea: true가 아래쪽 여백을 처리하지 않는다는 점입니다. 지시문이 틀린 적도 있습니다. 수정 후 E2E 지시문의 포트 배정은 adb forward 방향과 맞지 않아 그대로 하면 앱이 자기 자신에게 접속하게 돼 있었고, 에이전트가 뒤집어 적용한 뒤 그 사실을 환경 표에 적었습니다.

에이전트 직접 커밋과 처음부터 다시 하기

끊김에 대비하는 다른 방법은 서브에이전트가 직접 커밋하게 하는 것입니다. 이 라운드는 그것을 막았습니다. 같은 파일을 여러 에이전트가 동시에 고치고, git stash나 파일을 되돌리는 git checkout 한 번이 남의 변경을 지울 수 있어서입니다. 그 대가로 끊긴 작업은 미커밋 상태로 남았고, 메인 세션이 대신 커밋해야 했습니다. 같은 작업 트리에서 세션끼리 충돌한 일은 Claude Code 여러 세션 충돌과 파일 주인 표에 따로 적었습니다.

이어받는 쪽이 늘 처음부터 다시 하는 방법도 있습니다. 남은 파일이 있던 기기 재확인은 스크린샷 85장과 로그 8종으로 판정만 새로 했고, 수정 후 E2E는 보고서 기록상 50분 만에 끝났습니다. 남은 것이 없던 문자열 전수 검증은 리터럴 2,864개를 다시 파싱했습니다. 보고서를 끝에 한 번만 쓰게 하는 방식은 브리프가 규칙 6으로 피하려던 것인데, X1의 결과는 끝에 한 번 쓴 것과 같았습니다.

에이전트마다 브리프를 따로 쓰는 방법은 이 기록에서 검토한 흔적이 없습니다. 실제로는 공통 브리프 한 장을 뒤에 나온 브리프 3개(수정, 리뷰 지적 수정, 전수 검증)가 "그대로 적용", "따른다"로 다시 불렀고, 각 브리프는 그 단계에서 달라진 것을 더했습니다. 소유 파일만 고칠 것, 커밋하지 말 것, 가드를 지우면 실패하는 테스트를 쓸 것 같은 규칙에 더해, 리뷰 지적 수정 브리프는 신원 바인딩 API 계약을, 전수 검증 브리프는 산출물 표를 붙였습니다.

읽기만 하는 작업과 정의 밖 심각도 값

디스크에 남은 파일로 이어받는 방식은 일하면서 파일이 생기는 작업에서만 통했습니다. 코드를 읽고 판정만 하는 작업(문자열 전수, 코드 리뷰)은 부산물이 없습니다.

이 라운드의 브리프는 심각도 허용 값 4개와 그 정의를 적었는데도 Info와 Low~Medium이 나왔습니다. 심각도로 세거나 정렬하는 도구를 붙일 거라면 허용 값을 적는 데서 멈추지 말고, 받은 보고서를 따로 검사해야 합니다.

환경 사실 절은 기계마다 다릅니다. 이 라운드는 물리 기기와 macOS가 없어서 iOS 실행과 실기기 확인이 모두 남은 unknown으로 갔습니다. 브리프 틀은 가져가도 그 절은 자기 환경에서 다시 확인해 써야 합니다. 이 규칙들이 결함을 얼마나 줄였는지는 비교할 라운드가 없어 말할 수 없습니다.

그대로 쓰는 브리프 틀과 이어받기 명령

공통 브리프와 수정 단계 브리프의 규칙을 합치고, 원본 경로와 갱신 단위를 더한 틀입니다.

# <라운드 이름> 공통 브리프 (<날짜>)
목표: <한 줄>

## 환경 사실 (확인한 것만)
- 도구 경로와 버전: <...>
- 쓸 수 있는 기기: <...> / 없는 것: <...>

## 하지 말 것
1. 패키지 설치·추가 금지. 필요하면 보고서에 "승인 필요"
2. 외부 업로드 금지. 산출물은 저장소 안 파일로만
3. 담당 밖 파일 수정 금지. 필요하면 "다른 소유자에게 요청" 절에
4. commit, stash, checkout 금지 (커밋은 메인 세션)
5. 추측은 "추정", 외부 문서는 URL과 확인 날짜

## 산출물 경로
- 보고서: <dir>/<NN>_<topic>.md
  시작하자마자 만들고 첫 줄은 정확히 "상태: 진행 중"
- 원본: <dir>/raw/<NN>_*
  명령 출력, 로그, 스크린샷은 얻는 즉시 파일로
- 발견 하나, 측정 하나가 끝날 때마다 표에 한 줄 추가

## 보고서 형식
요약 / 검증한 것 / 발견 사항 / 남은 unknown
| ID | 심각도 | 내용 | 근거(file:line / URL) | 수정 제안 | 검증 방법 |
심각도는 Blocker, High, Medium, Low 중 하나만

이어받을 때는 보고서보다 git과 raw 폴더를 먼저 봅니다.

  1. 미완료 보고서를 찾습니다. 이 라운드는 상태 표기가 보고서마다 달라서, 검색에 걸린 것은 빈 절에 들어 있던 "(작성 중)", "(진행 중)" 자리표시 줄이었습니다. 아래 명령을 dca6cf9의 두 폴더(분석·수정 보고서 폴더와 기기 시험 폴더)에 돌리면 문서 통합, 리뷰, 수정 후 E2E 보고서 3개가 나옵니다.
    git grep -lE "^(상태: 진행 중|\((작성|진행) 중)" <커밋> -- <보고서 폴더들>
  2. 앞 세션이 고친 범위를 확인합니다.
    git diff --stat <시작 커밋>..<부분 커밋> -- <담당 파일>
  3. raw 폴더의 파일 목록을 보고, n이 이상하게 작은 측정이 있으면 다시 재기 전에 계산 스크립트부터 확인합니다.
  4. 보고서 머리의 상태를 완료로 바꾸고, 누가 무엇을 이어받았는지 한 줄 적습니다.

판정마다 한 줄 쓰기는 아직 재 보지 않았습니다

문자열 전수 검증처럼 부산물이 없는 작업에 판정마다 한 줄씩 쓰게 했을 때 끊긴 뒤 몇 줄이 남는지는 아직 재 보지 않았습니다.
