9월 7~10일, 끊긴 에이전트 5건

끊긴 이유는 세션 한도 3건, 주간 사용 한도 1건, 기록 없음 1건입니다. 다섯 건 모두 이어받은 쪽이 일을 마쳤습니다.

작업끊긴 이유끊긴 때 보고서이어받은 뒤
에뮬레이터 랩 분석기록 없음19줄, 모든 절 "(작성 중)"47분 뒤 71줄. 기기 스크립트와 스크린샷 2장에서 출발

공통 브리프 33줄: 금지 규칙 6개와 보고서 형식

브리프는 목표 한 줄, 검증된 환경 사실, 절대 규칙 6개, 보고서 형식으로 되어 있었습니다. 에이전트마다 맡은 주제는 따로 줬습니다. 환경 사실에는 Flutter 버전, 에뮬레이터 2대, "물리 기기 없음, macOS 없음"이 들어 있었습니다. 절대 규칙의 요지는 이렇습니다.

  1. 시스템 패키지 설치와 새 패키지 추가 금지. 필요하면 보고서에 "승인 필요"로 적는다.
  2. 외부 업로드 금지. 산출물은 저장소 안 파일로만 남긴다.
  3. 분석 단계에서는 앱 코드를 고치지 않는다. 스크립트와 문서만 쓴다.
  4. 일괄 치환 금지. rm -rf 대신 임시 폴더로 옮긴다.
  5. 외부 정책은 URL과 확인 날짜를 적고, 추측은 "추정"으로 표시한다.
  6. 보고서는 정해진 경로에 초반에 먼저 만들고 진행하면서 갱신한다. "세션이 끊겨도 부분 결과가 남도록."

보고서의 발견 사항 표는 ID, 심각도(Blocker/High/Medium/Low), 내용, 근거(파일과 줄 또는 URL), 수정 제안, 검증 방법의 여섯 칸이었습니다. 보고서 17개가 모두 이 형식을 지켰고, 본문이 있던 16개에서 발견 233건(Blocker 15건)이 나왔습니다. 수정 단계는 이 ID로 일을 받았습니다.

금지 규칙은 실제로 쓰였습니다. 분석 보고서 13개에 "승인 필요"가 나오고, 아이콘 생성 패키지를 추가하자는 제안은 승인을 기다리는 대신 이미 깔려 있던 Python 이미지 라이브러리 스크립트로 바뀌었습니다. 금지 목록을 파일 한 장에 두고 매번 읽히는 방식은 AI 에이전트 권한 표와 같습니다. 반면 심각도 허용 값은 지켜지지 않아, 정의에 없는 Info와 "Low~Medium"이 나왔습니다.

먼저 만든 보고서가 비어 있던 이유

규칙 6은 보고서를 만들고 갱신하라고 했지만 언제 갱신하는지는 정하지 않았습니다. 기록으로 보면 판정은 파일이 아니라 에이전트의 대화 맥락 안에만 있었고, 끊기기 전에 보고서를 정리한 에이전트는 없었습니다.

수정 후 E2E 보고서가 가장 규칙에 가까웠습니다. 머리말에 "세션이 끊기면 빈 칸은 미측정으로 보라"고 적었지만, 끊긴 시점의 결과 표는 통째로 비어 있었습니다. 같은 폴더에는 logcat 두 개(약 10만 줄과 9만 줄), 서버 로그, 스크린샷 43장, 메시지 11건의 왕복 지연 원본이 있었습니다. 계산 스크립트는 로그 기준점을 잘못 잡아 그중 1건만 짝지었고, n=1, 11 ms라는 숫자를 냈습니다.

이어받은 쪽은 git diff와 원본 폴더부터 읽었습니다

문서 통합 에이전트는 고친 문서를 작업 트리에 둔 채 멈췄습니다. 커밋은 메인 세션만 하게 돼 있어서, 메인 세션이 그 상태를 부분 커밋했습니다. 이어받은 에이전트는 git diff로 앞 세션이 고친 범위부터 확인했습니다. 에이전트 지침 파일은 모든 항목이, 보안 문서는 8개 중 7개가 반영돼 있었고 나머지 문서 9개는 그대로였습니다. 반영된 부분은 다시 쓰지 않고 19개 파일을 마쳤습니다.

수정 후 E2E를 이어받은 에이전트는 빌드, 설치, 연결, 메시지 전송까지 남은 원본을 그대로 쓰고 나머지 시험만 새로 했습니다. 왕복 지연도 다시 재지 않고, 앞 세션이 보낸 10건을 기준점을 바로잡아 다시 계산해 p50 61 ms, p95 74 ms를 얻었습니다.

문자열 전수 검증은 코드를 읽고 판정하는 일이라 남은 파일이 없었습니다. 다음 에이전트는 93개 파일의 문자열 리터럴 2,864개를 처음부터 다시 파싱하고, 화면에 나올 수 있는 464개를 판정했습니다. 같은 날 대비 검사기를 다시 센 일은 대비 검사기는 글자 40%를 재지 못했다에 적었습니다.

서브에이전트 브리프에는 보고서를 먼저 만들라는 말보다, 원본 증거를 어느 경로에 언제 쓰라는 말을 먼저 적으십시오.

검증 방법 칸이 고친 예측

보안 분석 에이전트는 코드를 읽고, Android 자동 백업으로 복원된 앱이 암호 키를 잃어 영구히 쓸 수 없게 된다고 예측했습니다. 랩 에이전트가 그 행의 검증 방법 칸대로 백업, 삭제, 재설치, 복원을 실제로 돌리자 앱은 멈추지 않았습니다. 키 풀기 오류 뒤 설정 화면으로 돌아가 새 프로필을 만들었고, 이전 키와 대화 기록은 조용히 사라졌습니다. 결론은 달라졌지만 백업을 끄라는 수정 제안은 그대로 필요했습니다.

지시문이 틀린 적도 있습니다. UI 수정 에이전트는 분석 단계의 수정안 8개 가운데 3개가 틀리거나 모자라 고쳐서 적용했다고 보고했고, 수정 후 E2E 지시문의 포트 배정은 방향이 반대라 그대로 하면 앱이 자기 자신에게 접속하게 돼 있었습니다. 에이전트는 뒤집어 적용하고 그 사실을 환경 표에 적었습니다.

서브에이전트가 직접 커밋하게 하면 어땠을까

끊김에 대비하는 다른 방법은 서브에이전트가 직접 커밋하게 하는 것입니다. 이 라운드는 그것을 막았습니다. 여러 에이전트가 같은 작업 트리에서 동시에 파일을 고치고 있어서, git stash나 git checkout 한 번이 남의 변경을 지울 수 있었기 때문입니다. 그 대가로 끊긴 작업은 미커밋으로 남았고 메인 세션이 대신 커밋했습니다. 같은 작업 트리에서 세션끼리 부딪힌 일은 Claude Code 여러 세션 충돌과 파일 주인 표에 따로 적었습니다.

에이전트마다 브리프를 따로 쓰지도 않았습니다. 뒤에 나온 브리프 3개(수정, 리뷰 지적 수정, 전수 검증)가 공통 브리프를 "그대로 적용"한다고 부르고, 그 단계에서 달라진 것만 더했습니다. 소유 파일만 고칠 것, 커밋하지 말 것, 가드를 지우면 실패하는 테스트를 쓸 것 같은 규칙입니다.

읽기만 하는 작업에는 남는 파일이 없습니다

디스크에 남은 파일로 이어받는 방식은 일하면서 파일이 생기는 작업에서만 통했습니다. 코드를 읽고 판정만 하는 작업(문자열 전수, 코드 리뷰)은 남는 것이 없습니다. 환경 사실 절은 기계마다 다르니, 틀은 가져가도 그 절은 자기 환경에서 다시 확인해 써야 합니다. 이 규칙들이 결함을 얼마나 줄였는지는 비교할 라운드가 없어 말할 수 없습니다.

그대로 쓰는 브리프 틀과 이어받기 명령

공통 브리프와 수정 단계 브리프의 규칙을 합치고, 원본 경로와 갱신 단위를 더한 틀입니다.

# <라운드 이름> 공통 브리프 (<날짜>)
목표: <한 줄>

## 환경 사실 (확인한 것만)
- 도구 경로와 버전: <...>
- 쓸 수 있는 기기: <...> / 없는 것: <...>

## 하지 말 것
1. 패키지 설치·추가 금지. 필요하면 보고서에 "승인 필요"
2. 외부 업로드 금지. 산출물은 저장소 안 파일로만
3. 담당 밖 파일 수정 금지. 필요하면 "다른 소유자에게 요청" 절에
4. commit, stash, checkout 금지 (커밋은 메인 세션)
5. 추측은 "추정", 외부 문서는 URL과 확인 날짜

## 산출물 경로
- 보고서: <dir>/<NN>_<topic>.md
  시작하자마자 만들고 첫 줄은 정확히 "상태: 진행 중"
- 원본: <dir>/raw/<NN>_*
  명령 출력, 로그, 스크린샷은 얻는 즉시 파일로
- 발견 하나, 측정 하나가 끝날 때마다 표에 한 줄 추가

## 보고서 형식
요약 / 검증한 것 / 발견 사항 / 남은 unknown
| ID | 심각도 | 내용 | 근거(file:line / URL) | 수정 제안 | 검증 방법 |
심각도는 Blocker, High, Medium, Low 중 하나만

이어받을 때는 보고서보다 git과 원본 폴더를 먼저 봅니다.

  1. 미완료 보고서를 찾습니다. 상태 줄이나 빈 절의 자리표시 줄로 찾습니다.
    git grep -lE "^(상태: 진행 중|\((작성|진행) 중)" <커밋> -- <보고서 폴더들>
  2. 앞 세션이 고친 범위를 확인합니다.
    git diff --stat <시작 커밋>..<부분 커밋> -- <담당 파일>
  3. 원본 폴더의 파일 목록을 보고, n이 이상하게 작은 측정이 있으면 다시 재기 전에 계산 스크립트부터 확인합니다.
  4. 보고서 머리의 상태를 완료로 바꾸고, 누가 무엇을 이어받았는지 한 줄 적습니다.

판정마다 한 줄 쓰기는 아직 재 보지 않았습니다

자주 묻는 질문

서브에이전트가 세션 한도로 끊기면 하던 작업이 남나요?

디스크에 쓴 파일만 남습니다. 끊긴 5건의 보고서는 빈 절뿐이었고, 이어받기는 작업 중에 생긴 로그, 스크린샷, 고친 파일에서 했습니다.

서브에이전트 프롬프트에는 무엇을 먼저 넣어야 하나요?

하지 말 것, 산출물과 원본의 경로, 보고서 형식입니다. 이 라운드의 공통 브리프는 이 세 가지와 환경 사실로 33줄이었고, 맡을 주제는 에이전트마다 따로 줬습니다.

서브에이전트에게 커밋을 맡기면 끊김 문제가 풀리나요?

이 라운드에서는 맡기지 않았습니다. 여러 에이전트가 같은 작업 트리를 쓰고 있어 커밋은 메인 세션만 했고, 끊긴 작업은 메인 세션이 부분 커밋한 뒤 메시지에 이어서 할 일이라고 적었습니다.

근거는 채팅 앱 저장소의 git 기록, 공통 브리프와 뒤 브리프 3개, 분석 보고서 17개와 수정 보고서입니다. 시각은 한국 시간, 보고서 줄 수는 2026년 11월 13일에 git 기록에서 다시 셌습니다.
