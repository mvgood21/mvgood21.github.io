여러 AI 에이전트가 함께 고치는 정적 사이트: 커밋 전 --check 하나로 지키기

다시 빌드해도 바뀌는 파일이 0개이고 검사 오류도 0건일 때만 커밋하면, 작업을 합친 뒤에야 드러나는 문제를 커밋 전에 잡습니다.

에이전트 여럿을 한 저장소에서 4/6

AI 코딩 에이전트 세션 여러 개가 한 저장소를 함께 고치면, 각자 확인할 때는 멀쩡한데 합친 결과만 깨지는 일이 생깁니다. 이 사이트는 프레임워크 없이 Python 표준 라이브러리로 짠 빌드 스크립트로 만들고, 사람이든 에이전트든 커밋 전에 python tools/build.py --check를 통과시킵니다. 2026년 10월 5일부터 22일까지 이 명령이 커밋을 멈춘 네 번과, 그때 정한 규칙을 정리했습니다.

--check가 커밋 전에 멈춘 네 번

--check는 사이트 전체를 메모리에서 다시 만든 뒤 두 가지를 봅니다. 디스크의 파일과 한 바이트라도 다른 출력이 있는지, 그리고 검사 모듈 tools/checks.py가 오류를 냈는지입니다. 하나라도 걸리면 아무것도 쓰지 않고 exit 1로 끝납니다.

outputs = build_all()              # pages, feeds, sitemap, CSS: in memory
changed = [p for p, text in outputs.items()
           if read_file(p) != text]
report = checks.run(ROOT, outputs)  # 106 issue codes
if "--check" in argv:
    if changed or report.errors:
        exit(1)                     # nothing is written
else:
    write_files(changed)

10월 24일 기준으로 출력 파일 162개를 만들고 고정 이름이 붙은 검사 106종을 돌리는 데 11.6초가 걸렸습니다. 멈춘 네 번은 이렇습니다.

날짜멈춘 이유원인
10월 5일첫 빌드 직후 파일 2개가 out of date날짜를 git 상태에서 읽음
10월 18일통합 빌드에서 게이트 오류 101건대부분 검사 코드의 집계 오류
10월 19일홈 글꼴 421KB, 상한 400KBrebase로 합친 뒤 매일 바뀌는 글 제목

네 번 모두 한 파일만 검사해서는 보이지 않았습니다. 사이트 전체 출력을 다시 만들어 비교했기 때문에 걸렸습니다.

손으로 쓰는 곳은 본문과 데이터 파일뿐입니다

파일마다 쓰는 쪽은 하나뿐입니다. 저장소의 AGENTS.md(에이전트가 작업 전에 읽는 지침 파일)에 있는 표를 줄이면 이렇습니다.

누가 쓰나무엇을
글 쓰는 사람·에이전트손 페이지의 <title>, description, <main>(빌드 블록 제외), 데이터 JSON
빌드 담당 세션 하나빌드 코드, 통합 빌드 실행
빌드만head·헤더·푸터·이동 경로·JSON-LD, 목록 페이지, sitemap·RSS, 날짜 파일, 생성 CSS

손 페이지 안에서도 빌드가 채우는 자리는 <!-- build:meta --> 같은 표시로 둘러 둡니다. 빌드는 매번 이 블록만 비우고 다시 넣고, 나머지 <main>은 바이트 그대로 둡니다. 글을 쓰는 쪽은 빌드를 돌리지 않고 파일 하나만 보는 읽기 전용 검사 tools/checks.py --file을 씁니다.

처음 계획에는 이 구분이 없었습니다. 10월 18일 개편 명세는 에이전트가 썼고, 작업 묶음마다 "끝에 빌드와 --check를 돌려라"와 "생성 HTML은 건드리지 마라"를 함께 요구했습니다. 명세를 공격하는 역할을 맡은 리뷰 에이전트가 둘이 모순이라고 짚었습니다. 빌드는 모든 손 페이지의 머리와 꼬리를 다시 쓰므로, 한 세션이 검증하려고 빌드를 돌리면 다른 세션이 고치는 파일 60여 개가 달라집니다. 그 뒤로 통합 빌드는 한 곳에서 한 번만 돌립니다.

rebase 충돌도 같은 원칙으로 해결합니다. 10월 19일 충돌 난 파일은 404.html, 소개·앱 페이지, rss.xml처럼 빌드가 다시 쓰는 파일이었습니다. 이런 파일은 손으로 병합하지 말고 한쪽을 고른 뒤 다시 빌드하고, --check가 0을 낼 때만 커밋하십시오.

멱등성은 내일 날짜로 한 번 더 빌드해 확인합니다

10월 5일 에이전트가 첫 빌드 스크립트를 쓰고 바로 돌렸을 때 결과는 이랬습니다.

45 files, 45 changed
out of date:
  apps/sugarcard/index.html
  sitemap.xml

한 번 더 빌드하자 2개가 바뀌었고, 그다음에는 up to date였습니다. 달라진 줄은 sitemap의 lastmod 날짜였습니다.

원인은 두 단계였습니다. 가까운 원인은 순서입니다. 빌드가 파일을 쓰기 전에 git status와 git log에서 날짜를 읽었으니, 파일을 쓰고 나면 다음 빌드는 다른 입력을 봤습니다. 그 밑의 원인은 날짜를 본문이 아니라 저장소 상태와 벽시계에서 가져왔다는 점입니다.

그날 고친 것은 가까운 원인뿐이었습니다. 같은 날 두 번 빌드는 통과했지만, 같은 입력으로 다음 날 빌드하면 날짜가 또 움직였습니다. 두 번 돌려 결과가 같아졌다고 멱등은 아닙니다.

13일 뒤 개편에서 날짜를 본문 해시로 정하도록 바꿨습니다. 에이전트가 쓴 개편 명세에도 같은 종류의 순환이 둘 있었습니다. 날짜 줄이 해시 대상 안에 있어 날짜와 해시가 서로를 바꿨고, CSS 버전 값이 빌드가 고쳐 쓰는 그 CSS 파일의 해시였습니다. 리뷰 에이전트는 뒤쪽을 "--check가 영원히 한 번씩 실패한다"고 적었고, 둘 다 구현 전에 고쳤습니다. 날짜 규칙은 사이트맵 lastmod가 전부 같은 날짜였다: 본문 해시로 수정일 정하기에 있습니다.

지금은 빌드가 보는 오늘 날짜를 환경 변수 SOURCE_DATE로 바꿀 수 있습니다. 10월 24일 사본에서 돌린 결과입니다.

$ SOURCE_DATE=2026-10-25 python tools/build.py
162 files, 0 changed
$ SOURCE_DATE=2026-12-31 python tools/build.py
162 files, 0 changed

첫 통합에서 틀린 쪽은 게이트였습니다

10월 18일 개편은 에이전트 36명이 나눠 맡아 2시간 24분 걸렸습니다. 작업을 합친 첫 --check는 다시 쓸 파일 0개, 게이트 오류 101건으로 실패했습니다.

글꼴 예산 오류(BUDGET-FONT) 43건은 대부분 검사 코드의 잘못이었습니다. 영어 페이지의 ©는 CSS가 시스템 글꼴로 그리는데, 검사 코드는 이 글자까지 세어 글꼴 조각이 더 필요하다고 계산했습니다. 진짜 낭비도 하나 있었습니다. 이동 경로의 구분 기호 › 한 글자 때문에 페이지마다 25KB 조각을 하나 더 받고 있었습니다. 검사 코드의 집계를 CSS 규칙과 맞추고, 구분 기호는 시스템 글꼴로 돌렸습니다.

게이트를 고칠 때는 테스트도 같이 고칩니다. 이때 테스트 6개를 더했고, 새 가드 8개를 하나씩 지운 사본에서 테스트가 실패하는지 확인했습니다. 10월 24일 기준 검사 106종은 모두 테스트에 이름이 나옵니다.

통합 에이전트는 게이트 두 곳을 스스로 느슨하게 했습니다. 상한이 정해지지 않은 페이지 두 종류는 글꼴 초과를 경고로만 냈고, 생성 글꼴 CSS 상한은 20KB에서 24KB로 올렸습니다. 둘 다 보고서에 "확인 필요"로 적었지만 10월 24일까지 사람이 확인하지 않았습니다.

글꼴 예산은 다른 글의 제목으로도 깨집니다

이 사이트의 한글 글꼴은 92개 조각으로 나뉘어 있고, 페이지는 자기 글자가 든 조각만 받습니다. 상한은 글 페이지 470KB, 홈과 목록 페이지 400KB입니다. 드문 음절 하나가 17~40KB 조각을 하나 더 부르기 때문에, 첫날 AX 노트 세 편 중 두 편이 상한을 넘어 드문 낱말을 흔한 말로 고쳤습니다.

홈에는 최신 AX 노트 제목 3개가 들어갔고, 그 제목은 매일 바뀌었습니다. rebase로 다른 세션의 변경과 합쳐지자 홈이 421KB가 됐습니다. 제목을 고치는 대신 홈 목록을 주제 페이지 링크로 바꿨습니다. 주제 이름은 고정 문구라 비용이 움직이지 않습니다. 10월 22일 AX 노트 대문의 주제 카드에서 글 제목을 뺀 것도 같은 이유였고, 대문은 468KB에서 389KB로 줄었습니다.

10월 22일에는 새 글 제목에 든 드문 음절 한 글자가 관련 글 목록을 타고 다른 글 두 편에 들어가, 두 편이 482KB와 473KB가 됐습니다. 새 글 파일만 검사하면 통과합니다. 제목을 "측정했나"로 바꾸자 450KB와 441KB로 내려갔습니다.

이미지는 아직 게이트 밖에 있습니다

공유 이미지는 tools/og.py가 실제 Play 스크린샷과 중립 배경으로 만들고, --check는 이 이미지를 다시 만들어 비교하지 않습니다. 10월 24일 사본에서 og.py를 돌리자 155개 중 4개가 커밋본과 달랐습니다. og.py는 두 번 돌려도 바이트가 같았으니, 어긋난 쪽은 생성기를 거치지 않고 커밋된 파일입니다. 그림 도구에 넣은 빈 글자 검사의 경위는 안드로이드에서 한글 일부 글자만 빈칸: 나눔스퀘어 cmap 11,172자 중 8,693자가 빈 글자였다에 있습니다.

브라우저 편집, 많은 페이지, CI 없는 저장소에는 맞지 않습니다

글을 브라우저에서 쓰고 미리 보는 팀에는 맞지 않습니다. 여기서는 작성자가 HTML 본문을 직접 고치고 명령을 실행합니다. 정적 사이트 생성기를 쓰더라도, 네 번 중 세 번은 전체 출력에 대한 검사에서 나왔으니 그 검사와 날짜 규칙은 따로 만들어야 합니다.

페이지가 아주 많으면 비용이 커집니다. --check는 매번 전부 다시 만들어 비교하고, 증분 빌드는 없습니다.

게이트는 강제되지 않습니다. 저장소에 CI가 없어서 커밋 전에 누군가 이 명령을 돌려야 작동합니다. 게이트가 틀릴 수도 있고, 상한을 올리는 커밋은 게이트가 막지 못합니다.

다른 사이트에 --check 게이트를 들이는 순서

  1. 누가 어떤 파일을 쓰는지 지침 파일 첫머리에 표로 적고, 생성 파일은 손대지 않는다고 못박습니다.
  2. 손 페이지 안에서 빌드가 채우는 자리는 <!-- build:NAME --> 블록으로 표시하고, 빌드는 매번 비우고 다시 넣습니다.
  3. --check는 모든 출력을 메모리에 만들어 디스크와 비교하고, 같은 출력에 검사를 돌려 하나라도 걸리면 exit 1을 냅니다.
  4. 날짜와 버전 값은 내용 해시로 정하고, 해시 입력에서 날짜 줄과 자동 목록을 제외합니다.
  5. 멱등성은 연속 두 번, 내일 날짜, 과거 날짜 빌드로 확인합니다.
  6. 검사마다 고정 코드와 그 코드가 나는지 보는 테스트를 두고, 가드를 지운 사본에서 테스트가 실패하는지 봅니다.
  7. 글 쓰는 세션은 파일 단위 검사만 하고, 통합 빌드는 한 세션이 한 번 돌립니다. rebase에서 생성 파일이 충돌하면 한쪽을 고르고 다시 빌드합니다.
  8. 다른 페이지의 글이 섞여 드는 예산(글꼴, 크기)은 전체 출력에서 검사하고, 매일 바뀌는 목록은 공통 페이지에 넣지 않습니다.
  9. 상한 숫자를 바꾸는 커밋은 사람이 따로 봅니다.

다음에 확인할 것

og.py 출력과 커밋본을 비교하는 단계를 --check에 넣는 것이 다음 일입니다. 그 전에 글자가 든 앱 카드를 예외로 둘지 생성기 출력으로 바꿀지 정해야 합니다. 글꼴 CSS 상한 24KB와 경고로만 내는 두 페이지도 사람이 확인해야 합니다.

빌드 결과 HTML도 git에 커밋하나요?

커밋합니다. GitHub Pages가 저장소 파일을 그대로 내보내므로 빌드 결과가 곧 배포본입니다. --check는 커밋된 결과가 지금 입력으로 다시 만든 결과와 같은지 확인합니다.

정적 사이트 빌드가 멱등인지 어떻게 확인하나요?

연속 두 번, 내일 날짜, 과거 날짜로 빌드해 바뀌는 파일이 0개인지 봅니다. 그러려면 빌드가 보는 오늘 날짜를 환경 변수로 바꿀 수 있어야 합니다.

여러 AI 에이전트 세션이 같은 사이트 저장소를 고칠 때 충돌은 어떻게 푸나요?
