AI 코딩 에이전트는 몇 개까지 동시에 돌릴 수 있나: 상한은 메모리와 테스트폰이 정했다

코드를 고치는 에이전트는 한 번에 3개까지만 돌았습니다. 상한을 정한 것은 에이전트 수가 아니라 여유 메모리 4GB와 공용 테스트폰 2대였습니다.

작성 SugarMount · 에이전트와 일하는 법 · 읽는 시간 7분 · 최종 업데이트 2026년 11월 13일

에이전트 여럿을 한 저장소에서 1/6

Claude Code는 메인 세션이 서브에이전트를 여러 개 띄워 일을 나눠 맡길 수 있습니다. 2026년 10월 3일, 퍼즐 게임 화살표 매듭풀기를 300판에서 1,000판으로 늘리면서 운영자는 "에이전트 수백 개 써도 된다"고 했습니다. 그날 커밋은 59개였지만, 코드를 쓰는 에이전트가 동시에 돈 것은 최대 3개였습니다. 에이전트를 몇 개 띄울지 고민한다면 에이전트 수보다 빌드 한 번에 드는 메모리와 쓸 수 있는 기기 수를 먼저 세는 편이 맞습니다.

요청은 '수백 개', 코드를 쓴 에이전트는 동시에 3개

요청 1분 뒤 에이전트는 설계용 Workflow를 띄웠습니다. Workflow는 Claude Code에서 서브에이전트 여러 개를 스크립트 하나로 묶어 돌리는 도구입니다. 난이도 곡선, 게임 경제, 디자인, 스토어 문구, 다국어를 주제별로 나눈 에이전트 24개가 52분 동안 일했고, 코드를 건드리지 않는 일이라 11개가 동시에 돌았습니다.

그 결과를 합친 사양서가 커밋되고 3분 뒤 구현 Workflow가 시작됐습니다. 에이전트 41개가 구현, 적대적 리뷰, 수정, 머지를 나눠 맡아 5시간 6분을 돌았는데, 동시에 실행된 수는 첫 단계의 엔진 규칙, 레벨 생성기, 문자열과 빌드 설정 3개가 최대였습니다. 뒤 단계는 2개씩이거나 혼자 돌았습니다.

3이라는 숫자는 에이전트가 스스로 골랐습니다. 구현 직전에 남긴 판단은 16코어에 메모리 13GB, 그중 여유 4GB라 Android 빌드를 한 번에 2~3개로 묶겠다는 것이었고, 작업 중 한 에이전트가 찍은 메모리 상태도 같았습니다.

$ free -g
               total        used        free      shared  buff/cache   available
Mem:              13           8           2           0           2           4

10월 3~4일의 커밋, 머지, 에이전트 수

이틀 동안 이 저장소에서는 세션 3개가 움직였습니다. Agent·Workflow 칸은 세 세션이 직접 부른 횟수이고, 마지막 칸은 Workflow 안에서 뜬 에이전트 수와 동시 최대입니다.

날짜커밋머지Agent 호출WorkflowWorkflow 안 에이전트 (동시 최대)
10-035911112설계 24 (11), 구현 41 (3)
10-04526143E2E 수정 10 (3), 출시 준비 조사 150 (14)

출시 준비 조사의 150은 기록 파일 수라 재시도분이 섞여 있습니다. 이 저장소의 세션 6개(9월 30일~10월 17일)에서 운영자는 에이전트를 많이 띄우라고 5번 말했지만, 메인 세션의 Agent 호출은 모두 53번, Workflow 실행은 10번이었습니다.

병렬도를 정한 것은 메모리, 기기 2대, 파일 주인 표

먼저 막힌 곳은 빌드 메모리였습니다. 구현 메모에는 Gradle 작업자를 4개로 묶고(--max-workers=4) 작업 공간 하나에서 Gradle 빌드는 한 번에 하나만 돌리라고 적혀 있습니다. 워크스트림마다 커밋 전에 단위 테스트와 디버그 빌드를 통과해야 했으니, 동시 워크스트림 수가 곧 동시 빌드 수였습니다. 빌드를 하지 않는 조사·설계 Workflow는 6번 돌면서 동시 11~14개까지 올라갔습니다.

테스트폰은 Galaxy S21과 S20 두 대였고, 이 두 대를 다른 앱 저장소 세션까지 모두 5개 세션이 나눠 썼습니다. 그래서 구현 메모에는 "어떤 워크스트림도 기기를 만지지 않는다, E2E는 나중에 S21에서만"이라고 적었습니다. 이틀 동안 이 저장소 세션들이 받은 세션 간 메시지 148건 가운데 114건이 두 기기를 언급했고, 상당수가 "10분만 쓰겠다" 같은 순서 조율이었습니다.

파일에도 주인을 정했습니다. 사양서의 워크스트림 표에는 "독점 소유" 열이 있어서, 카메라 담당은 카메라 관련 파일 3개만 고쳤습니다. 각 워크스트림은 자기 git worktree(같은 저장소를 폴더 하나 더 꺼내 쓰는 git 기능)에서 커밋만 하고, 통합 브랜치에 머지하는 것은 통합 에이전트 하나뿐이었습니다. 표에서 빠진 공유 파일이 어디서 부딪혔는지는 AI 에이전트 여러 개가 한 저장소를 고칠 때의 파일 주인 표에 따로 적었습니다.

'실패 0'으로 끝난 앱이 첫 실행에서 죽었습니다

밤 10시 27분, 구현 Workflow는 "41개 모두 완료, 실패 없음"으로 끝났습니다. 마지막 머지 에이전트가 전체 JVM 테스트와 디버그 빌드까지 통과시킨 상태였습니다. 1분 뒤 S21에 설치하자 앱이 실행 직후 죽었습니다. Android 빌드 도구가 에셋 이름 끝의 .gz를 떼어 내는 바람에, 코드가 찾는 레벨 파일이 APK 안에 없었습니다. 10시 31분에 올라온 수정은 레벨 파일을 압축하지 않은 채로 넣고, 에셋 이름이 .gz로 끝나면 실패하는 회귀 테스트를 붙였습니다.

33개 항목짜리 세부 E2E는 자정 넘어 S21 한 대로 65분이 걸렸습니다. 31개가 통과하고 1개(큰 판 화면 이동 끊김)가 실패했으며 1개는 디버그 빌드로는 확인할 수 없었습니다. 버그와 디자인 문제 10건을 고친 Workflow도 동시 3개였습니다.

에이전트가 틀린 것은 '완료'의 정의였습니다. 기기를 못 쓰게 한 규칙은 맞았지만, 그 대가로 41개의 '완료'는 JVM 테스트와 컴파일 통과만 뜻했고 기기에서만 보이는 결함은 모두 맨 끝으로 밀렸습니다. 이걸 잡은 것은 운영자가 첫 요청에 넣은 "S21에 설치해서 E2E 테스트까지"라는 한 구절이었습니다. 새벽에 운영자가 S20도 내주자, 출시 빌드 무작위 입력 3,000회 x 3 검사가 수정 작업과 나란히 돌았습니다(크래시 0건).

에이전트를 몇 개 띄울지 정하기 전에, 동시에 돌릴 수 있는 빌드 수와 기기 수부터 세십시오.

병렬 에이전트 수를 정하는 순서

  1. 여유 메모리를 보고 동시에 돌릴 빌드 수를 정합니다. 이번에는 13GB 중 여유 4GB에서 3개였습니다. 코드를 고치는 에이전트 수의 상한이 이 숫자입니다.
  2. 빌드를 하지 않는 조사·설계는 따로 셉니다. 이 일은 동시 11~14개도 돌았습니다.
  3. 실기기는 워크스트림에서 빼고, 누가 언제 쓰는지 순서를 정합니다.
  4. 워크스트림마다 고칠 파일을 표로 나누고, 머지는 통합 에이전트 하나만 합니다.
  5. '완료'는 릴리스 빌드를 실기기에서 실행해 본 뒤로 정합니다. 테스트 통과만으로는 이번 크래시를 잡지 못했습니다.

다음 실험

  • 동시 4개가 들어가는지. 이번에는 여유 메모리를 몇 번 찍어 본 것이 전부라, 다음에는 1분마다 기록해 3이 안전 여유였는지 낭비였는지 보겠습니다.
  • 메시지 대신 기기 잠금. 기기 언급 메시지 114건을 잠금 파일 하나(누가, 언제까지)로 바꾸면 기다리는 시간이 얼마나 줄어드는지 측정합니다.
  • 14의 정체. 조사용 Workflow 5번 모두 동시 14개에서 더 오르지 않았습니다. 도구 설정의 상한인지는 아직 확인하지 않았습니다.

자주 묻는 질문

Claude Code 서브에이전트는 몇 개까지 병렬로 돌릴 수 있나요?

이 기록에서는 빌드를 하지 않는 조사용 Workflow가 동시 14개까지 돌았습니다. Gradle 빌드를 하는 구현 에이전트는 여유 메모리 4GB에 맞춰 3개로 묶었습니다.

에이전트마다 git worktree를 따로 주면 충돌이 사라지나요?

git 충돌은 줄지만 기기와 메모리를 두고 벌어지는 다툼은 남습니다. 이번에는 독점 파일 표와 통합 에이전트 한 명만 머지하는 규칙으로 git 쪽을 막았고, 기기 두 대는 세션 간 메시지로 순서를 맞췄습니다.

워크스트림 10개를 하루에 어떻게 합쳤나요?

의존 순서대로 단계를 나누고, 단계가 끝날 때마다 통합 에이전트가 브랜치를 차례로 머지한 뒤 단위 테스트와 디버그 빌드를 돌렸습니다. 10월 3일 저녁 3시간 37분 동안 머지 커밋 11개가 이렇게 생겼습니다.

숫자는 게임 저장소의 git 기록, 사양서와 구현 메모, Claude Code 세션 기록을 스크립트로 센 값입니다. 시각은 한국 시간, 기준일은 2026년 10월 21일입니다.

이 글은 SugarMount가 직접 측정한 값으로 쓰고, 초안 작성에 AI 코딩 에이전트를 썼습니다.
