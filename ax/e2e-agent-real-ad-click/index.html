클로드 코드 애드몹 테스트 기기: 실광고 클릭 사고

클로드 코드 애드몹 테스트 기기 설정이 디버그 빌드에만 걸려 있어, 릴리스 APK로 돌린 실기기 E2E에서 실광고가 뜨고 1회 클릭됐습니다.

작성 Stephen · Android 개발 · 읽는 시간 11분 · 최종 업데이트 2026년 11월 19일

클로드 코드(Claude Code) 에이전트가 휴대폰으로 앱을 끝까지 눌러 보는 테스트를 하다가, 화면 앞에 올라온 전면 광고를 실제로 한 번 눌렀습니다. 개발자 본인 기기의 실광고 노출·클릭은 AdMob이 무효 트래픽으로 보는 대상입니다.

개발 폰에 테스트 광고만 보내는 설정이 디버그 빌드에만 걸려 있어 릴리스 APK에서는 실광고가 나왔습니다. 에이전트의 화면 확인 가드는 패키지 이름만 봐서 앱 안에서 열린 광고 화면을 우리 앱으로 여겼고, 문제의 탭은 그 가드조차 거치지 않았습니다. 다음 날 설정을 모든 빌드로 넓혔지만, 화면 안 배너와 다른 광고 네트워크의 광고는 아직 이 방법으로 다 막지 못합니다.

  4. 테스트 기기 목록을 모든 빌드에 걸고 콘솔에도 등록했습니다

전면 광고 뒤에서 크롬이 열렸습니다

2026년 9월 28일 오후, 에이전트는 한글 띄어쓰기 앱의 릴리스 APK를 Galaxy S21에 올려 맞춤법 검사 흐름 전체를 눌러 보고 있었습니다. 확인 하나마다 앱을 강제 종료하고 공유 인텐트로 다시 띄우는 스크립트였습니다.

에이전트는 한 명령으로 화면 구조를 덤프해 결과 말풍선의 좌표를 읽고 그 좌표로 탭 명령을 보냈습니다. 탭은 덤프가 끝난 16시 19분 55초에 들어갔고, 0.1초 뒤 logcat에 크롬이 쇼핑몰 광고주 페이지를 여는 줄이 찍혔습니다. 에이전트가 다시 덤프하자 스크립트는 "foreground is not our app"이라며 멈췄고, 앞에는 크롬의 첫 실행 화면이 있었습니다.

크롬을 닫아 보니 앱 안에는 Google 광고 SDK의 전면 광고 화면(AdActivity)이 그대로 떠 있었습니다. 에이전트는 "광고를 누르지 않고 뒤로 가기로만 닫습니다"라고 적고 BACK 키를 보냈는데, 그 밑에 다른 광고 네트워크 Liftoff(옛 Vungle)의 광고 화면이 하나 더 깔려 있었죠. 29분 뒤 에이전트는 실제 광고를 한 번 눌러 무효 클릭이 1건 생겼다고 운영자에게 보고하고, 같은 내용을 CHANGELOG의 '사고 기록'에 남겼습니다.

가드는 패키지 이름만 봤습니다

에이전트는 그날 14시 56분에 화면 덤프·캡처 스크립트에 가드를 붙여 두었습니다. 화면 맨 앞 액티비티(topResumedActivity 줄)에 앱 패키지 이름이 있으면 우리 앱으로 보고 진행하는 조건이었습니다. 광고 SDK의 화면은 앱 프로세스 안에서 열리기 때문에 그 줄이 com.sugarmount.sugarspeller/com.google.android.gms.ads.AdActivity처럼 찍혀 이 조건을 통과합니다. 가드는 덤프와 캡처 명령 앞에만 있었고, 문제의 탭은 가드를 거치지 않는 직접 명령이었습니다.

사고 뒤 2분 사이에 가드가 두 번 바뀌었습니다.

2판의 가설은 "광고 화면은 이름으로 알아볼 수 있다"였습니다. 미디에이션(여러 광고 네트워크가 한 광고 자리를 두고 입찰하는 구조)을 쓰면 네트워크마다 광고 화면 이름이 다르고, 2판을 넣은 지 13초 만에 목록 밖 이름이 나왔습니다. 3판은 막을 이름을 세는 대신 허용할 이름만 적었습니다. 같은 날 에이전트는 확인마다 앱을 강제 종료하던 줄도 지웠습니다. 앱을 다시 띄울 때마다 앱 오픈 광고가 뜨기 때문입니다.

테스트 기기 목록은 디버그 빌드에만 걸려 있었습니다

앱 코드에는 테스트 기기 목록이 있었지만 9월 11일 수정에서 디버그 빌드일 때만 참인 BuildConfig.DEBUG 조건 안에서만 적용하게 되어 있었습니다. 릴리스 APK로 실기기를 돌리면 목록이 아예 적용되지 않았고, S21은 그 목록에 들어 있지도 않았습니다.

다음 날 밤 S21에서 계측 테스트(폰에서 앱을 직접 띄워 돌리는 안드로이드 테스트)가 도는 동안, 운영자가 테스트하면서 광고가 계속 나오는데 이러면 정지되는 것 아니냐고 물었습니다. 에이전트의 첫 답은 "지금 도는 계측 테스트는 디버그 빌드라 테스트 광고 단위를 써서 위험이 없다"였고, 이 답은 틀렸습니다. 이 앱의 디버그 빌드는 입찰 파트너를 검증하려고 일부러 실제 광고 단위를 쓰고, 그 이유가 같은 파일 주석에 적혀 있었습니다. 에이전트가 연 logcat에는 목록에 없는 기기에만 SDK가 찍는 "이 기기에서 테스트 광고를 받으려면 setTestDeviceIds를 쓰라"는 안내가 세 번 있었습니다.

27분 뒤 커밋 ec5f400이 목록 적용을 디버그 조건 밖으로 꺼냈습니다. 목록에 든 기기만 테스트 광고를 받으므로 일반 사용자에게는 영향이 없습니다. S21을 목록에 넣고, S21이 목록에 있는지와 설정 객체가 목록을 모두 담는지 보는 단위 테스트도 붙였습니다.

개발 폰 테스트가 몰린 이틀은 AdMob 리포트에서도 보입니다. 배너 요청을 날짜별로 다시 받아 보니 평소 하루 1,000건 정도이던 요청이 9월 29일 하루만 두 배를 넘었고, 매칭률(광고 요청 가운데 광고가 실제로 채워진 비율)은 절반 아래로 내려갔습니다.

10월 1일 모니터링 기록은 늘어난 요청이 전부 1.6.024 버전에서 나왔다고 적고, 그 원인을 S21과 S23이 실제 광고 단위로 계측 테스트를 되풀이한 것으로 판정했습니다. 원자료로 다시 보면 9월 28~29일에 매칭 안 된 요청도 한 건을 빼고 모두 이 버전이었습니다. 1.6.024는 당시 개발 빌드와 Play 배포판이 같이 쓰던 버전이라, 버전만으로 기기를 가를 수는 없습니다.

S23은 목록에 있었는데도 실광고를 받았습니다. 폰에서 광고 ID를 재설정하면 SDK가 쓰는 테스트 기기 값도 바뀌는데, 코드에는 재설정 전 값이 남아 있었습니다. 이때 에이전트는 "테스트 기기 ID는 광고 ID의 MD5"라며 직접 계산했지만 결과가 로그 값과 맞지 않았고, Android ID로 계산해도 맞지 않았습니다. 운영자 지시에 따라 SDK가 logcat에 찍은 값을 코드에 넣었습니다.

테스트 기기 목록을 모든 빌드에 걸고 콘솔에도 등록했습니다

나온 방법은 다섯 가지입니다. 에이전트는 운영자 쪽 제안 둘을 반대했고, 운영자는 에이전트가 만들던 빌드 옵션을 중간에 멈췄습니다.

방법누가 냈나결과
앱의 디버그 상수를 테스트 때 켜고 배포 때 끄기운영자에이전트가 반대. 그 상수는 광고 단위와 함께 구독 상태도 프리미엄으로 강제하고, 끄는 걸 잊고 배포하면 모든 사용자가 테스트 광고와 무료 프리미엄을 받음
테스트 광고 단위만 쓰는 빌드 옵션, Play에 올리는 AAB 빌드에서 켜져 있으면 실패에이전트테스트를 쓰던 중 운영자가 멈추고 콘솔 등록으로 방향을 바꿈. 구현하지 않음(11월 18일 기준 저장소에 없음)
디버그 빌드를 테스트 광고 단위로 바꾸기(9월 11일 검토)테스트 단위는 미디에이션을 거치지 않아 입찰 파트너를 검증할 수 없어 버림
실광고를 몇 번 보고 확인한 뒤 배포운영자 질문에이전트가 반대. 개발자 기기의 실광고 노출·클릭은 횟수와 상관없이 무효 트래픽
코드 목록을 모든 빌드에 적용, 콘솔에도 기기 등록에이전트, 운영자채택. 코드는 ec5f400, 콘솔 등록은 운영자 몫

9월 30일 아침 운영자가 S21도 AdMob에 테스트 기기로 등록했느냐고 묻자, 에이전트는 앱 코드에만 넣었다고 답했습니다. 코드 목록은 그 코드가 들어간 빌드에만 듣습니다. 이미 Play에 나간 이전 버전을 개발 폰에 깔면 막아 주는 것은 AdMob 콘솔의 테스트 기기 등록뿐입니다. 콘솔에는 광고 ID 원문을, 코드에는 SDK 해시를 넣어야 해서 두 값을 기기별 표로 저장소 문서에 남겼습니다(4595dce).

워크트리에 복사된 광고 ID 파일

일주일쯤 뒤 퍼즐 게임 화살표 매듭풀기에서 같은 위험이 다른 길로 왔습니다. 이 게임은 실제 광고 ID를 git에서 빠진 설정 파일 하나에 두고, 파일이 있으면 릴리스 빌드가 그 값을 넣습니다. 10월 4일 새벽 1시 28분, 광고를 맡은 클로드 코드 세션이 운영자에게서 ID를 받자마자 다른 세션의 작업 폴더(git 워크트리)에 그 파일을 묻지 않고 복사했습니다. 그 폴더의 세션은 21분 뒤 테스트용이라고 생각한 릴리스 APK를 빌드했습니다.

2시 6분, 그 세션은 실제 ID 빌드로 무작위 탭 테스트를 돌리면 안 된다는 광고 세션의 경고를 옮기면서, 자기 작업 공간에는 실제 ID 파일이 없어 테스트 광고로만 빌드되니 안전하다고 쓴 직후 S20에 APK를 설치했습니다. 같은 명령에 넣은 파일 확인이 파일이 있다고 출력했고, 세션은 앱을 한 번도 열지 않은 채 지우고 파일을 옆으로 옮긴 뒤 테스트 광고로 다시 빌드했습니다. 광고 요청과 클릭은 없었습니다.

이 게임의 테스트 광고 빌드 옵션은 파일이 없을 때만 테스트 ID를 허용했고, 파일이 있으면 무시하지 않았습니다. 다음 날 커밋 68d501e은 빌드 인수로 원래 위치의 파일을 읽게 바꿔, 워크트리에 사본을 둘 이유가 남지 않게 했습니다. 같은 시기에 만든 한판블록은 테스트 광고 옵션이 파일을 통째로 무시하도록 만들었는데, 그 빌드의 실제 ID 검사가 놓친 것은 R8이 지우지 못한 테스트 광고 ID 5개에 따로 적었습니다.

9월 30일 점검에서도 Liftoff 앱 오픈 광고는 실광고로 기록됐습니다

탭 가드는 앞 화면이 자기 액티비티인지 볼 뿐이라, 자기 화면 안에 붙은 배너나 네이티브 광고는 가리지 못합니다. 그래서 아래 순서에서는 테스트 기기 등록을 탭 규칙보다 앞에 놓았습니다.

코드 목록은 AdMob 광고에만 듣습니다. 9월 30일 아침 8시 57분 운영자가 콘솔 등록을 마쳤다고 알렸지만, 어느 콘솔에 어느 기기를 넣었는지는 기록에 없습니다. 그 뒤 S21 점검에서 AdMob 광고는 테스트 광고로 나왔고, Liftoff 앱 오픈 광고는 여전히 실광고였으며 BACK으로도 닫히지 않아 앱을 강제 종료해서 닫았습니다. 세션은 화면에 뜬 광고를 보고 실광고로 판단했고, Liftoff 대시보드의 테스트 기기 설정을 다시 봐 달라고 운영자에게 요청했습니다.

실기기 E2E 전에 테스트 기기부터 등록합니다

실광고가 나올 수 있는 빌드로는 실기기 자동 탭을 돌리지 마십시오. 아래는 이번 일에서 정리한 순서입니다. 이 가운데 logcat 값을 쓰는 것과 목록을 모든 빌드에 거는 것(1·2단계)은 앱 저장소 규칙에, 자기 화면일 때만 탭하는 것(5단계)과 실제 ID 파일을 다른 워크트리에 복사하지 않는 것(6단계)은 에이전트 메모리에 이미 있습니다.

  1. 기기를 연결하고 앱을 한 번 띄운 뒤 logcat에서 setTestDeviceIds(Arrays.asList("…")) 줄의 값을 복사합니다. 직접 계산하지 않습니다.

  2. 그 값을 앱의 테스트 기기 목록에 넣고, MobileAds.setRequestConfiguration 호출을 빌드 종류 조건 밖으로 꺼냅니다. 목록에 그 기기가 있는지 보는 단위 테스트도 함께 넣습니다.

  3. AdMob 콘솔과 미디에이션 파트너 콘솔마다 같은 폰의 광고 ID 원문을 테스트 기기로 등록합니다.

  4. 앱을 다시 띄워 광고에 테스트 광고 표시가 붙는지 보고, logcat에 "to get test ads on this device" 줄이 더는 없는지 확인합니다.

  5. 탭 스크립트의 탭 명령 안에서 adb shell dumpsys activity activities | grep -m1 topResumedActivity 결과의 액티비티 이름이 <패키지>/.처럼 앱 자신의 클래스로 시작할 때만 탭하고, 아니면 BACK만 보냅니다. 앱 재시작은 꼭 필요할 때만 합니다.

  6. 실제 광고 ID 파일은 한 곳에만 두고 빌드에는 경로를 인수로 넘깁니다. 다른 세션의 워크트리에 복사하지 않습니다.

  7. 다음 날 AdMob 리포트에서 매칭률과 요청 수를 봅니다. 개발 기기 트래픽이 섞였다면 여기서 먼저 보입니다.

무작위 탭으로 크래시를 찾는 몽키 테스트는 신규 설치 몽키 테스트에 적었습니다. 그 테스트도 테스트 광고 빌드에서만 돌립니다.
