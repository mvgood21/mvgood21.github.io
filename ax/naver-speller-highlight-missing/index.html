네이버 맞춤법 하이라이트 안 됨: 문장 끝 오류 누락

네이버 맞춤법 결과에 하이라이트가 안 되던 것은 문장 끝 오류였습니다. 클로드 코드와 원인 두 개를 고친 뒤 실응답 31개가 모두 칠해졌습니다.

작성 Stephen · Android 개발 · 읽는 시간 9분 · 최종 업데이트 2026년 11월 17일

"이거 어떻해"를 검사하면 한글 띄어쓰기 앱은 틀린 곳에 색을 칠하지 않았습니다. 말풍선으로 결과를 보여 주는 화면은 한술 더 떠 "맞춤법 오류가 없습니다"라고 답했습니다. 네이버는 "어떡해"로 고쳐야 한다는 결과를 제대로 보내고 있었습니다. 2026년 9월 13일 고치기 전의 색칠 방식을 저장해 둔 실제 응답에 그대로 옮겨 다시 세어 보니, 네이버가 찾은 오류 31개 가운데 색이 칠해지는 것은 17개였습니다.

빠진 14개는 모두 각 문장의 마지막 오류였고, 원인은 요청 본문 끝에 덧붙인 문자열과 구간 끝을 거르는 부등호 하나였습니다. 외부 교정·번역 응답을 받아 화면에 색으로 입히는 앱이라면 이 두 곳부터 보십시오.

짧은 문장일수록 색이 하나도 없었습니다

이 앱에는 말풍선으로 주고받는 Chat 화면과, 입력칸과 결과칸이 따로 있는 예전 Classic 화면이 있습니다. 2026년 9월 13일 18시 14분, 운영자는 Chat에서 색 표시가 안 되고 Classic도 제대로 안 된다며 네이버부터 깊이 분석해 보고해 달라고 클로드 코드(Claude Code)에 요청했습니다.

에이전트가 처음 의심한 곳은 응답을 읽는 코드였습니다. 네이버 응답을 직접 받아 정규식에 넣어 보니 교정 어절과 오류 종류가 정확히 나왔고, 파싱 가설은 거기서 접었습니다. 다음으로 Classic이 응답을 어느 조각(긴 글을 나눈 청크)에 맞추는 방식을 의심해 10문장을 실측했지만 실패는 0건이었습니다.

18시 27분 에이전트는 "마지막 가설"이라며 짧은 한 문장에서 오류가 끝에 있는 경우를 시험했습니다. 1분 뒤 나온 결과에서 짧은 문장 10개 중 네이버가 오류를 찾은 7개가 모두 색 0개였습니다. 아래는 그 경우를 저장소의 테스트 자료에 남긴 응답 한 쌍입니다.

꼬리표와 부등호가 같은 자리를 지웠습니다

앱은 긴 글을 여러 청크로 나눠 보내고, 돌아온 응답이 몇 번째 청크인지 알아보려고 검사할 문장 뒤에 꼬리표(Chat은 메시지 고유 번호와 청크 순번, Classic은 청크 순번과 문장 해시값을 이은 문자열)를 붙였습니다. 네이버는 이 꼬리표를 마지막 어절의 일부로 보고, 교정 구간을 표시하는 em 태그 안에 함께 넣어 돌려줬습니다.

앱은 화면에 보여 줄 교정문에서만 꼬리표를 지웠습니다. 교정 어절 목록에는 "어떡해-…-0"이 그대로 남았고, 화면 문장에서 그 문자열의 위치를 찾는 indexOf는 -1(못 찾음)을 돌려줬으며, 위치를 못 찾은 오류에는 색이 칠해지지 않았습니다.

Chat은 화면 문장에서 찾아낸 교정 어절 수를 오류 수로 세었고, 찾은 것이 0개면 "오류가 없습니다"라고 답했습니다. Classic은 네이버가 응답에 함께 주는 오류 개수 필드 errata_count를 써서, 개수는 맞게 말하고 색만 빠뜨렸습니다.

두 번째 결함은 꼬리표와 상관없었습니다. 색칠 조건이 buffer.length > key + text.length였습니다. 화면 문장 길이가 교정 어절의 시작 위치(key)와 어절 길이(text.length)를 더한 값보다 커야, 곧 구간이 문장 끝보다 앞에서 끝나야만 색을 칠했습니다. "이거 어떡해"는 6글자이고 교정 구간 "어떡해"도 6번째 글자에서 끝나니, 6 > 6은 거짓이라 칠하지 않았습니다. 짧은 한 문장은 유일한 오류가 끝에 오는 일이 많아서 화면에 색이 하나도 남지 않았습니다.

두 결함이 같은 자리를 지우기 때문에 하나만 고쳐서는 거의 달라지지 않습니다.

git 기록을 거슬러 올라가면 두 결함 모두 AI 공동 작성 커밋보다 오래됐습니다. 검사할 문장 뒤에 식별 문자열(당시에는 문장의 해시값)을 붙여 보내는 방식은 2020년 12월, 지금의 Classic 화면이 된 첫 화면 코드에 처음 들어왔습니다(6baa0ae).

부등호 비교는 2021년 4월 커밋 3ad9ba4에서 들어왔는데, 커밋 제목이 "addForegroundColorSpan java.lang.IndexOutOfBoundsException 수정"입니다. 범위를 벗어난 위치 예외를 막으려고 넣은 조건이 끝 구간까지 막았습니다.

2025년 8월 Chat 화면을 새로 만들 때 클로드 코드와 함께 쓴 커밋 두 개(02cbb15, 5f082f8)가 이 두 습관을 그대로 가져왔습니다. 새 화면의 검사 요청에도 꼬리표가 붙었고, 색칠 루프에도 같은 부등호가 들어갔습니다.

끝 어절만 틀린 짧은 문장부터 넣어 봅니다

  1. 오류가 맨 끝 어절에만 있는 짧은 문장을 넣어 봅니다. "이거 어떻해", "넘 조아" 같은 문장입니다. 색이 없으면 아래 두 곳을 봅니다.

  2. 요청을 만드는 코드에서 검사할 본문 뒤에 순번, 해시, UUID를 붙이는지 찾습니다. 붙인다면 HTTP 클라이언트의 요청 태그나 콜백 클로저로 옮겨야 합니다.

  3. 색칠 직전의 범위 검사를 찾아 length > end 또는 end < length인지 봅니다. end <= length가 맞습니다. 아래 grep은 이 앱의 원래 줄처럼 길이 > 시작 + 길이 꼴만 찾습니다. length > end나 end < length 꼴, Java의 length()는 따로 찾아야 합니다.

    grep -rnE '(length|size) *> *[a-z]+ *\+' app/src/main

  4. 실제 응답을 테스트 자료 파일로 저장합니다. 오류 수 필드와 칠한 구간 수가 같은지, 각 구간의 문자열이 교정 어절과 같은지, 구간이 겹치지 않는지 확인합니다.

  5. 고친 줄을 잠깐 되돌려 테스트가 실패하는지 봅니다. 되돌려도 통과하는 테스트는 이 결함이 돌아와도 잡지 못합니다.

26/26이라던 검증은 저장소에 없었습니다

20시 41분 에이전트는 두 결함과 Chat의 오류 수 계산을 고친 커밋 e9cd771을 만들고, 실서버 응답 18문장으로 교차 검증해 모두 칠해졌다고 보고했습니다. 보고에는 단위 테스트 통과 수까지 적혀 있었습니다.

22시 13분 운영자가 "네이버 test 코드 다 넣었지?"라고 물었습니다. 에이전트의 답은 커밋에 들어간 것은 순수 로직 테스트 10개뿐이고, 실서버 교차 검증은 임시 폴더의 응답 파일에 기대는 일회성 테스트라 지웠다는 것이었습니다.

이 질문 뒤 11분 만에 커밋 9ed4dca가 들어왔습니다. 실서버 응답을 그대로 저장한 픽스처(테스트에 쓰는 고정 자료)를 저장소에 넣었는데, 23문장을 꼬리표 없이 보낸 응답과 꼬리표를 붙인 예전 방식으로 보낸 응답을 함께 담았습니다. 고친 줄을 일부러 되돌리는 변이 검증도 돌려, 문장 끝 구간을 다시 버리게 하면 테스트 9개가 실패하는 것을 확인했습니다.

꼬리표는 요청 태그로 옮겼습니다

외부 API로 보내는 본문에는 식별자를 섞지 마십시오. 이 앱은 꼬리표를 HTTP 클라이언트 OkHttp의 요청 태그(서버로 나가지 않고 응답 콜백에서 다시 꺼내는 값)로 옮겼습니다. 응답에서 정규식으로 꼬리표를 지우는 기존 방식은 버렸습니다. 그 패턴은 13자리 숫자나 8자 이상 영문 단어처럼 사용자가 쓴 글까지 지울 수 있었습니다. 위 그림의 긴 숫자·영문 단어 문장에서는 예전 방식이 사용자가 쓴 숫자와 영어 단어를 화면 문장에서 지웠습니다.

픽스처는 2026년 9월 13일 하루치 응답입니다

네이버가 응답 형식을 바꾸면 오프라인 테스트는 통과한 채로 앱이 다시 틀릴 수 있습니다. 이 경로는 공개 API가 아니어서 그런 변경을 미리 알 길도 없습니다.

교정 구간 안에 줄바꿈이나 < 같은 특수문자가 들어간 응답은 아직 한 번도 보지 못했습니다. 지금 코드는 &lt; 같은 표기를 화면 문장에서만 원래 글자로 되돌립니다. 그런 응답이 오면 교정 어절에는 &lt;가, 화면 문장에는 <가 남아 위치를 찾지 못합니다. 모바일 응답은 실측에서 띄어쓰기와 맞춤법 두 종류만 줬고, 나머지 두 종류의 색은 픽스처로 검증되지 않았습니다.

자주 묻는 질문

네이버 맞춤법 검사에서 마지막 단어만 하이라이트가 안 되는 이유는?

이 앱에서는 두 가지였습니다. 요청 끝에 붙인 꼬리표가 마지막 교정 구간 안으로 들어가 위치를 찾지 못했고, 구간 끝이 문장 길이와 같으면 칠하지 않는 부등호가 있었습니다. 두 결함 모두 문장 끝 오류에서만 드러납니다.

SpannableString에서 끝 위치가 문자열 길이와 같아도 되나요?
