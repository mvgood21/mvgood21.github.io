모바일 게임 손맛 개선: 하트가 충돌보다 109ms 먼저 줄던 순서를 코드와 녹화 프레임으로 찾았다

애니메이션을 고치라고만 시키지 마십시오. 코드와 녹화 프레임을 함께 주고 이벤트마다 원인과 결과의 순서를 표로 내게 하십시오. 시각 측정은 증명용입니다.

작성 SugarMount · 게임 개발 · 읽는 시간 11분 · 최종 업데이트 2026년 11월 7일

막힌 화살표를 누르면 하트가 먼저 변하고, 109ms 뒤에야 화살표가 막는 화살표에 닿았습니다. 2026년 10월 1일 밤 Galaxy S21에서 녹화한 출시 전 퍼즐 게임 화살표 매듭풀기 영상에 남은 순서입니다. 운영자가 애니메이션이 엉성하다고 평하자 에이전트는 10분 47초 뒤 719줄을 커밋했지만 이 순서는 그대로였고, 이벤트별 타이밍을 묻는 코드·프레임 리뷰를 돌린 뒤에야 고쳐졌습니다. 수정 뒤 녹화에서 하트는 접촉보다 16ms 늦게 움직입니다.

출처: 게임 저장소의 커밋 da0e624, 3eb21df, 65dcf41과 리뷰 문서, 그날의 에이전트 세션 기록입니다. 109ms와 16ms는 2026년 11월 4일에 당시 녹화 원본에서 다시 측정한 값입니다. 시각은 한국 시간입니다.

녹화를 다시 측정하니 하트가 109ms 앞섰습니다

수정 전 영상과 수정 뒤 영상에는 막힌 탭이 한 번씩 들어 있습니다. 두 영상을 프레임별로 풀어 연속 프레임의 밝기 차이가 25를 넘는 픽셀을 헤더와 판 영역으로 따로 세고, 프레임 시트를 눈으로 대조했습니다. 프레임 간격은 중앙값 약 8ms라 그 단위로 측정할 수 있었습니다. 60Hz 화면이면 약 17ms가 한계입니다.

사건수정 전 (레벨 151)수정 뒤 (레벨 52)
화살표가 움직이기 시작3,807ms3,851ms
하트가 변하기 시작3,815ms3,984ms
접촉 (수정 전은 판 흔들림, 수정 뒤는 접촉 링)3,924ms3,968ms
접촉 기준 하트의 위치109ms 앞16ms 뒤

수정 전에는 화살표가 출발하고 8ms 만에 하트가 부풀기 시작했고, 접촉 직전에는 이미 절반쯤 흐려져 있었습니다. 리뷰 문서는 이 장면을 "결과가 원인보다 먼저 나옵니다"라고 적었습니다. 그날 리뷰는 60fps 프레임 차이를 시각과 함께 찍어 하트 쪽 변화(3.817초)가 판 변화(3.933초)보다 앞서는 출력을 얻었지만, 문서에 측정값을 남기지는 않았습니다. 109ms는 고친 뒤 한 달이 지나 원본 프레임에서 다시 측정한 값입니다.

수정 뒤 코드에서는 접촉 콜백이 링보다 먼저 호출됩니다. 영상의 16ms는 약 2프레임으로, 화면에 나타나기까지의 차이입니다.

719줄 재작성으로도 순서는 그대로였습니다

22:05, 운영자는 애니메이션이 엉성해서 이런 게임을 누가 하겠느냐는 취지로 평했습니다. 에이전트의 처음 가설은 연출이 모자란다는 것이었습니다. 뱀처럼 휘어 나가는 이동, 직접 합성한 효과음 5종, 진동, 색종이, 별 카드를 넣었고 22:16에 da0e624를 커밋했습니다.

에이전트는 S21에서 화면을 녹화해 프레임을 뽑아 보기도 했습니다. 5fps로 89장, 10fps로 162장과 149장을 잘랐습니다. 그때 기록에는 막힌 탭의 충돌과 하트 애니메이션이 문제없다고 남아 있습니다. 순서를 측정한 기록은 없습니다. 고친 것도 결과 화면 배경의 농도, 색종이 크기·개수, 맞닿은 화살표의 색 배정이었습니다. 보고에는 "프레임 단위로 확인했다"고 적혔지만, 재작성한 코드 안에서 하트는 여전히 탭 순간에 줄었습니다.

약 15분 뒤 운영자가 더 깊이 분석해서 다시 하라고 지시했습니다. 에이전트는 분석을 세 갈래로 돌렸고, 그중 손맛 리뷰 에이전트가 4분 51초 만에 보고서를 냈습니다. 영상에서 찾은 문제 6건, 권고 14건이었습니다.

하트 코드가 애니메이션 시작 다음 줄에 있었습니다

순서가 뒤집힌 직접 원인은 호출 순서입니다. bump는 코루틴으로 애니메이션을 띄우고 바로 돌아오기 때문에, 그다음 두 줄이 탭을 처리하는 그 프레임에 실행됩니다.

is TapResult.Blocked -> {
    fx.bump(id, distance, r.blockers)  // 애니메이션을 띄우고 바로 반환
    lives = state.lives                // 탭 순간에 하트 감소
    feedback.blocked(view)             // 탭 순간에 소리와 진동
}

한 단계 아래에서는 state.tap()이 결과를 그 자리에서 확정하고 화면 코드가 그 자리에 붙어 있어, 판정 시각과 표시 시각이 나뉘지 않았습니다.

막힌 화살표가 막는 화살표까지 나가는 찌르기 시간은 거리에 따라 달랐습니다. 식은 (90 + 45 * distance).toInt().coerceAtMost(260)입니다. 리뷰 문서는 접촉이 탭 90~260ms 뒤라고 적었는데, 이 값은 이 식의 양 끝입니다. 거리 값은 k + 0.55라서 실제로 막힌 탭은 약 114ms가 가장 짧고, 녹화에서 측정한 찌르기는 117ms였습니다. 이 탭은 식의 가장 짧은 경우에 가깝고, 먼 곳에서 막혔다면 식으로는 뒤집힘이 260ms 가까이 벌어집니다.

프레임 수보다 리뷰에 던진 질문이 달랐습니다

첫 확인이 통과시킨 막힌 탭 동작이 리뷰에서는 문제로 올라왔습니다. 리뷰 에이전트도 같은 영상을 10fps로 잘라 149장을 봤습니다. 지시문에는 이벤트별 모션 타이밍과 이징, 이벤트별 피드백 층(시각·소리·진동), 프레임에서 보이는 끊김을 평가하라고 적혀 있었습니다.

10fps는 프레임 간격이 100ms라서 109ms 차이는 고작 한 칸입니다. 리뷰 에이전트는 코드를 먼저 읽고 149장을 본 뒤, 막힌 탭 구간만 30fps와 60fps로 다시 잘랐습니다.

순서 뒤집힘은 리뷰 문서에서 코드 행으로 짚였고, 프레임 번호가 붙은 근거는 없습니다. 날아가는 화살표가 하트와 상태바 위를 지나가는 장면(f58, f62, f89), 시작 팝인이 스플래시 페이드에 가려지는 장면(f21), 주황 화살표에서 빨간 경고 틴트가 거의 안 보이는 장면은 프레임에서 나왔습니다. 호출 순서와 소리·진동 시점은 코드로, 화면에 보이는지와 실제 시각은 프레임으로 확인하십시오.

판정은 두고 표시만 접촉 시점으로 옮겼습니다

판정까지 접촉 시점으로 늦추는 방법도 있었지만 리뷰는 판정을 즉시 유지하라고 적었고, 구현도 그렇게 했습니다. 문서에 그 이유는 적혀 있지 않습니다. bump에 onContact 콜백을 넣어 하트, 소리, 진동만 그 안으로 옮겼습니다(3eb21df).

fx.bump(id, dist, r.blockers) {        // 찌르기가 끝나면 호출
    feedback.contact(view, costsLife = !tutorial)
    if (!tutorial) lives = state.lives
}

거리에 비례하던 찌르기는 110ms로 고정해 접촉 시점이 거리에 따라 달라지지 않습니다. 이번 두 탭의 찌르기는 수정 전후 모두 117ms였고, 달라진 것은 하트의 위치입니다. 판을 흔드는 양은 0.12칸에서 4dp로 줄였고, 빨간색은 접촉 링에만 남겼습니다. 막힌 화살표는 진한 색으로 변하고, 막는 화살표에는 흰 윤곽선이 생깁니다.

콜백 안의 lives = state.lives는 연타가 들어오면 최종값으로 건너뛰었고, 다음 날 아침 6133e9e에서 접촉 하나에 하트 하나씩 줄도록 고쳤습니다. 그 사고는 막힌 화살표 연타와 잠금 없는 실패 카드에 따로 적었습니다.

8색을 지키는 대신 6색으로 줄였습니다

리뷰는 색도 측정했습니다. Machado 2009 시뮬레이션 행렬에 색차 공식 CIEDE2000을 적용했고, 문서는 색차 10 미만을 구분이 어려운 값으로 잡았습니다. 2026년 11월 4일에 이 공식을 따로 구현해 다시 계산했더니 값이 모두 일치했습니다.

조건옛 8색 최소 색차새 6색 최소 색차
정상 시각12.822.5
적색약5.517.0
녹색약7.416.7
청색약2.718.5

종이색 배경 대비는 amber가 2.43:1, green이 2.9:1로 WCAG 1.4.11 기준 3:1에 못 미쳤습니다. 경고색 빨강과 주황 화살표의 색차는 정상 시각에서 11.1이지만 청색약에서는 2.0까지 떨어졌습니다. 그래서 막힘 상태는 모양과 움직임으로 보여 주기로 했습니다. 리뷰는 8색 전부를 색각 이상에서 안전하게 만들기는 사실상 어렵다고 봤고, 이웃 그래프가 평면 그래프라 6색이면 충분하다고 적었습니다.

여기서 리뷰가 틀렸습니다. 대비를 맞추려고 amber를 B87A00으로 낮추라고 권했는데, 이 색을 쓰면 녹색약에서 주황과의 색차가 7.4에서 2.4로 나빠집니다. 리뷰 에이전트는 이 값을 22:35 실행 출력에서 봤는데도 권고를 그대로 남겼습니다. 구현을 맡은 에이전트는 한 색만 고치지 않고 6색 조합을 탐색해 팔레트를 통째로 새로 골랐습니다. 리뷰가 제시한 색차 20 이상은 채우지 못했고 16.7을 하한으로 받아들였습니다.

리뷰대로 만들자 첫 탭에서 앱이 죽었습니다

권고 14번은 삼성 기기에서 약한 진동을 VibrationEffect.Composition으로 교체하라는 내용이었고, 필요한 권한은 적혀 있지 않았습니다. 3eb21df는 이 권고를 넣으면서 VIBRATE 권한을 선언하지 않았습니다. 첫 화살표가 나가는 순간 SecurityException이 났습니다.

에이전트는 22:46에 튜토리얼 확인 스크립트가 크래시 없이 끝났다고 봤고, S24에는 설치와 실행만 확인한 상태였습니다. 운영자가 테스트가 끝난 거냐고 되묻자 그제야 아니라고 답했습니다. 약 4분 뒤 운영자가 S24에서 직접 눌러 튜토리얼 오류를 찾았습니다. 처음 설치 상태의 S21에서 monkey를 돌리자 800 이벤트 중 15번째에 죽었습니다. 22:47에는 레벨 확인 스크립트가 같은 코드로 화살표를 16개 제거하고도 죽지 않았습니다. 두 스크립트가 왜 이 크래시를 못 봤는지는 기록만으로 확정하지 못했습니다.

65dcf41이 권한을 선언하고 진동 실패를 기본 진동으로 넘겼고, S21에서 3개 시드로 800 이벤트씩 돌려 치명 오류 0건을 확인했습니다. 바로 뒤 f7beb3d는 처음 설치 상태의 monkey 검사를 스크립트로 고정했습니다.

막힌 탭을 녹화해 표를 만들고, 고친 뒤 다시 만듭니다

  1. 실기기에서 이벤트가 모두 나오는 판을 녹화합니다. 막힘, 제거, 클리어가 한 번씩은 들어가게 합니다.
  2. 전체를 10fps로 잘라 시트로 묶고, 프레임 번호를 찍어 에이전트에게 보입니다.
  3. 에이전트에게 코드를 함께 읽히고 "이벤트별로 원인 프레임, 결과 프레임, 소리·진동 호출 위치를 표로 내라. 결과가 원인보다 앞서는 곳을 찾아라. 각 수치가 코드 식인지 영상 실측인지 표시하라"고 시킵니다. 지시문에 "더 좋게"는 쓰지 않습니다.
  4. 의심 구간만 60fps로 다시 잘라 눈으로 보고, 시각은 원본 프레임의 타임스탬프에서 읽습니다.
  5. 고친 뒤 같은 장면을 녹화해 같은 표를 채우고, 처음 설치 상태에서 monkey까지 돌립니다. 방법은 신규 설치 몽키 테스트 글에 있습니다.
adb shell screenrecord --time-limit 25 --bit-rate 8000000 /sdcard/run.mp4
adb pull /sdcard/run.mp4
ffmpeg -i run.mp4 -vf fps=10,scale=360:-1 f_%04d.png
ffmpeg -ss 3.6 -t 0.9 -i run.mp4 -vf fps=60,scale=360:-1 g_%03d.png

-ss 3.6 -t 0.9는 자기 영상의 막힌 탭 시각으로 교체합니다. 아래 코드는 프레임마다 시각과, 밝기 차이가 25를 넘는 픽셀 수를 헤더·판 영역별로 찍습니다. 영역 비율은 게임마다 다릅니다.

import cv2
c = cv2.VideoCapture("run.mp4")
H = int(c.get(cv2.CAP_PROP_FRAME_HEIGHT)); prev = None
while True:
    ok, f = c.read()
    if not ok: break
    t = c.get(cv2.CAP_PROP_POS_MSEC)
    g = cv2.cvtColor(f, cv2.COLOR_BGR2GRAY)
    if prev is not None:
        d = cv2.absdiff(g, prev) > 25
        print(round(t), d[int(H*.04):int(H*.1)].sum(), d[int(H*.12):int(H*.8)].sum())
    prev = g

이 글의 표는 OpenCV로 두 영상의 원본 프레임(수정 전 1,276장, 수정 뒤 1,840장)을 그대로 읽어 얻었습니다. 화면이 멈춘 동안은 프레임이 나오지 않습니다. 두 녹화의 간격은 중앙값 8ms, 최대 3초였으니 프레임 번호를 시각으로 환산하지 마십시오.

소리, 진동, 손가락, 긴 플레이는 영상 밖입니다

소리는 화면 녹화에 담기지 않았고 진동 세기도 영상으로 알 수 없습니다. 자동 탭은 칸 정중앙만 누르므로 실제 손가락의 정확도도 알려 주지 않습니다. 긴 플레이에서만 나오는 결함도 마찬가지입니다. 이 게임의 스프링 복귀 크래시는 다음 날 300판 스트레스 실행에서 28번 나왔습니다.

판이 쉬웠던 문제는 재작성 보고에 이미 적혀 있었고, 같은 밤 별도의 레벨 분석이 수치로 잡아 생성기를 고쳤습니다. 레벨 생성 쪽 기록은 화살표 퍼즐 1,100판을 만든 역구성 생성기와 G2 게이트에 있습니다.

먼 거리 막힘과 리텐션은 재지 않았습니다

먼 곳에서 막힌 화살표는 측정하지 않았습니다. 손맛이 나아졌는지를 리텐션 같은 플레이어 지표로 비교한 값도 없습니다.

자주 묻는 질문

게임 피드백 애니메이션 타이밍은 몇 ms로 맞춰야 하나요?

이 게임은 찌르기를 110ms로 고정하고 하트, 소리, 진동을 접촉 콜백에 넣었습니다. 다른 게임에 그대로 옮길 값으로 검증한 것은 아닙니다.

녹화 영상은 몇 fps로 잘라야 하나요?

전체를 볼 때는 10fps, 구간을 볼 때는 60fps를 쓰고, 시각은 원본 프레임에서 읽으십시오. 이 녹화는 평균 85.58fps로 잡혔습니다.

디버그 빌드로 재도 되나요?

순서를 찾는 데는 충분했습니다. 이 글의 두 영상은 디버그 빌드입니다. 릴리스 빌드에서 같은 측정은 하지 않았으므로, 프레임 지연까지 비교하려면 릴리스 빌드로 다시 측정하십시오.
