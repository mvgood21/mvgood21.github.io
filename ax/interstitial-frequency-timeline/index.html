전면 광고 빈도를 기기 타임라인으로 정했다: 안내 퍼즐은 세지 않는다

안내 퍼즐 3판을 광고 카운터에서 빼자 퍼즐 모드의 첫 전면이 실전 3판 뒤로 갔습니다. 무엇을 셀지는 신규 설치 기기의 광고 로그를 시간순으로 보고 정했습니다.

작성 SugarMount · 스토어와 수익화 · 읽는 시간 13분 · 최종 업데이트 2026년 11월 2일

실전 퍼즐을 한 판도 풀지 않은 신규 설치 상태에서 실행 91초 만에 첫 전면 광고가 나왔습니다. 2026년 10월 4일 Galaxy S21에 한판블록을 새로 깔고 안내 퍼즐 3개를 푼 뒤 [다음]을 누른 순간이었습니다. 테스트 광고 릴리스 빌드를 사람 속도로 플레이하는 하네스가 남긴 기기 로그입니다. 같은 날 운영자는 안내 퍼즐을 광고 카운터에서 빼기로 했고, 커밋 메시지 기준으로 에뮬레이터의 첫 전면은 181초에서 314초로 늦어졌습니다. 같은 측정에서 클래식 모드의 전체 화면 광고가 10분당 1.4회로 3수 역전 퍼즐(3.3회)의 절반 아래로 나와, 클래식 게임 오버 한 번은 전면 조건에서 두 판으로 세게 바꾸었습니다.

근거는 게임 저장소(sugar-game)의 광고 계획 문서와 출시 리허설 문서, PRD v2.1의 11.2절, git 기록 2a4b820·df52a51·575aaa1·73a12ad·e430133·85e3685, 하네스 block_session_sim.py와 시뮬레이터 block_revenue_sim.py입니다. 기준일은 2026년 11월 1일입니다.

신규 설치 첫 전면은 실전 0판에서 나왔습니다

한판블록의 전면 광고는 판을 마치고 [다음]·[다시 하기]·[홈]을 누를 때만 나옵니다. 숫자는 코드 한 곳(Money.RULES)에 모여 있었습니다. 판 종료 3번 이상, 직전 전면 뒤 2판, 세션 시작 뒤 90초, 앞선 전체 화면 광고 뒤 120초, 세션 5회와 하루 20회 상한이고, 미리 불러 둔 광고가 있을 때만 보여 줍니다. 이 글에서 전체 화면 광고는 전면, 보상형, 앱 오프닝 광고를 모두 가리킵니다. PRD v2.1의 11.2절은 전면을 "첫 3판 종료와 세션 시작 90초 이내에는 띄우지 않는다"고 적었고, 배너는 "안내 퍼즐과 첫 3판에는 숨긴다"고 적었습니다.

10월 4일 측정은 모두 앱 데이터를 지운 신규 설치 상태에서 시작했습니다. 하네스(block_session_sim.py)는 모드와 플레이 속도를 정해 둔 실행, 곧 페르소나를 돌리고 광고 노출은 SDK 로그에서 읽습니다. S21에서는 안내 퍼즐 R001~R003을 풀고 R003의 [다음]에서 91초에 첫 전면이 나왔습니다. 에뮬레이터는 안내 퍼즐을 64초에 끝냈고, 첫 전면은 R004를 푼 뒤 181초에 나왔습니다. 에뮬레이터에서 돌린 혼합 페르소나와 복귀 페르소나의 첫 전면은 158초, 134초였습니다.

안내 3판이 '3판 조건'을 이미 채웠습니다

판 종료를 세는 함수가 안내 퍼즐을 구분하지 않았습니다. 에이전트와 함께 쓴 첫 코드(cd62087)의 Money.onRunEnded()는 안내 퍼즐 풀이도 실전 판과 똑같이 배너용 판 수와 전면용 승수에 더했습니다. 안내 3판이 끝나는 순간 '판 종료 3번'은 이미 채워져 있었습니다.

3판 조건과 90초 유예는 둘 다 새 이용자를 보호하려고 둔 숫자입니다. 그런데 안내 퍼즐 3개를 푸는 시간이 64~90초라 두 조건이 거의 같은 시점에 풀렸습니다. 보호가 더해지지 않고 겹쳤고, 첫 전면 시각은 안내 퍼즐을 얼마나 빨리 푸느냐에 따라 정해졌습니다. 에뮬레이터는 3판 조건을 64초에 채우고도 90초 유예에 걸려 다음 판인 R004 뒤에야 전면을 받았고, S21은 R003을 마친 시점에 유예도 거의 끝나 있어 안내 직후에 받았습니다.

숫자는 문서에서 왔습니다. 같은 저장소의 다른 게임(Arrow Knots) 수익화 설계 문서는 첫 전면을 세션 시작 뒤로 미루라는 업계 자료를 인용해 90초 유예를 정했고, 한판블록도 PRD v2.1에 같은 90초를 적고 공용 모듈(Pacer)에 넘겼습니다. 하네스는 10월 4일 출시 준비 커밋 575aaa1에서 처음 들어왔습니다. 그 전까지 첫 몇 분을 시간축으로 본 기록은 저장소에 없습니다.

에이전트와 함께 쓴 검사도 이 동작을 굳히고 있었습니다. 같은 날 오전 커밋 4fa0dfa의 기기 E2E는 S1 시나리오에서 'R004부터 배너가 보인다'를 통과 조건으로 검사했습니다. PRD대로라면 R004는 실전 첫 판이라 배너가 없어야 합니다. 출시 계획 워크플로의 초안은 이 문제를 시뮬레이션 결과로만 주장했고, 교차검증에서는 반박이 나왔습니다. 기기 로그가 나오자 계획 문서는 이 항목을 실측으로 확정했습니다.

판 길이가 모드별 빈도를 갈랐습니다

3수 역전 퍼즐 페르소나를 에뮬레이터에서 12분 돌렸을 때 전면은 181, 322, 465, 611초에 4번 나왔습니다. 간격은 141~146초, 10분당 3.3회입니다. 퍼즐 한 판이 1분 전후라 '2판마다' 조건은 매번 먼저 채워졌고, 빈도를 묶은 쪽은 120초 간격이었습니다.

클래식은 반대였습니다. S21에서 안내 3판을 포함한 14분 세션 동안 클래식 2판(150수)을 두었고, 계획 문서는 한 판을 약 5분으로 적었습니다. 전면은 안내 직후 한 번뿐이어서, 하네스가 받은 부활 보상형 한 번을 더해도 전체 화면 광고는 10분당 1.4회였습니다. 다음 전면 자격은 2판을 끝내야 생기고 2판이면 약 10분이니, 클래식에서 빈도를 먼저 묶은 쪽은 120초 간격보다 '2판마다' 조건입니다.

출시 계획의 시뮬레이터(block_revenue_sim.py)는 클래식 한 판을 90초로 가정했습니다. 같은 줄 주석에는 클래식 공급 실험 문서의 사람 목표가 4~10분이라고 적혀 있었습니다. 시뮬레이터는 전면이 화면에 머무는 시간도 15초로 잡았지만, 하네스는 사람처럼 5~8초 보고 닫았습니다. 퍼즐 페르소나를 시뮬레이터로 재현하면 12분에 전면 4.09회로 횟수는 실측 4회와 맞았고, 간격 중앙값은 162초로 실측 141~146초보다 길었습니다. 11월 1일 같은 명령(persona)을 다시 돌린 결과도 4.09회, 162초입니다.

안내 퍼즐 제외, 클래식 두 판, 6판 조건은 버림

10월 4일 저녁 커밋 e430133에 운영자의 광고 빈도 결정 세 가지가 들어갔습니다(같은 목록의 네 번째는 아래 배너 자리 규칙입니다). 커밋 메시지가 붙인 이름은 '기기 측정에서 나온 사용자 결정'입니다. 스토어 설명의 광고 안내도 같은 커밋에서 "안내 퍼즐과 처음 세 판에는 배너도, 판 사이 광고도 나오지 않아요"로 맞췄습니다.

  • 안내 퍼즐은 배너와 전면 카운트에 넣지 않습니다. 퍼즐 모드에서는 실전 3판을 끝내기 전에는 배너도 전면도 보지 않습니다.
  • 클래식 게임 오버는 전면 조건에서 두 판으로 셉니다. 코드는 승수를 두 번 더하므로 클래식에서는 새 이용자가 두 번째 게임 오버부터, 그 뒤로는 게임 오버마다 전면 자격을 얻고, 배너는 그대로 세 판부터입니다. 120초 간격과 세션·하루 상한도 그대로이고, 계획 문서는 클래식 이용자가 10분당 1.4회에서 약 2회가 될 것으로 추정했습니다.
  • 판이 진행 중일 때(클래식에서 한 수 이상 둔 뒤, 퍼즐에서 조각을 놓은 뒤) 앱으로 돌아오면 앱 오프닝 광고를 띄우지 않습니다.
fun onRunEnded(tutorial: Boolean = false, classic: Boolean = false) {
    if (tutorial) return
    runsEnded++
    prefs.edit().putInt(K_RUNS, runsEnded).apply()
    if (!enabled) return
    ads.onWin()
    if (classic) ads.onWin()
}

첫 전면 조건을 3판에서 6판으로 올리면 상수 하나만 바꾸면 됩니다. 계획 문서는 안내 퍼즐을 생략한 이용자나 버린 판이 섞이면 유예 길이가 들쭉날쭉해진다는 이유로 안내 풀이만 빼는 쪽을 권했습니다. 모든 판마다 전면을 띄우는 안은 120초 간격이 이미 빈도를 묶고 있어서 하지 않기로 했고, 판이 긴 클래식만 게임 오버마다로 바꾸었습니다. 클래식 결과 화면의 [홈]에서 전면을 빼는 안도 검토했지만, 계획 문서가 점수 화면 뒤를 허용 위치로 보고 유지를 권했고, 코드는 그대로입니다. 클래식을 바꾼 데는 Block Blast 같은 장르 게임이 게임 오버마다 전면을 띄우는 관행도 참고가 됐습니다.

새 이용자를 보호하는 숫자를 정할 때 안내 퍼즐은 광고 카운터에 넣지 마십시오. 정한 뒤에는 신규 설치 기기에서 첫 광고가 몇 초, 몇 번째 판에 뜨는지 로그로 확인하십시오.

출시 때는 Firebase가 없어 D1·D7을 재지 못했습니다

기기 타임라인은 광고가 언제, 몇 번 뜨는지를 보여 줄 뿐 이용자가 남는지는 보여 주지 않습니다. Analytics는 10월 11일 vc4 커밋 ae9cd16에서야 들어왔고, 원격 설정은 11월 1일에도 없습니다. 그 뒤 GA4로 D1을 보기 시작했지만, 전면 규칙 변경과 묶어 비교한 기록은 아직 없습니다. 계획 문서도 안내 퍼즐 제외의 근거를 PRD 준수와 첫인상으로 적고, 리텐션 개선 폭은 정량 근거가 없다고 밝혔습니다.

원격 설정과 분석 도구가 있고 이용자가 충분한 앱이라면 빈도 한 축만 바꾼 50/50 A/B가 더 나은 근거입니다. PRD 11.3절은 신규 5% 전면 홀드백을 계획했지만, 계획 문서는 D7 12%와 10%를 가르려면 1:19 배분에서 약 4.2만 설치가 필요하다는 이유로 이 방식을 쓰지 않기로 하고, 규모가 생기면 50/50 단일 축 A/B를 돌리기로 했습니다. 원격 설정이 없는 한판블록에서는 빈도를 바꿀 때마다 앱 업데이트와 심사를 거쳐야 합니다.

페르소나는 정해진 속도 범위로 한 번씩 돌린 실행입니다. 실제 이용자의 속도 분포가 아니고, 같은 규칙에서도 첫 전면이 91초와 181초로 갈렸습니다. 테스트 광고 빌드라 실제 광고의 로드율과도 다를 수 있습니다. 코드는 미리 불러 둔 전면이 있을 때만 띄우므로, 실제 노출은 측정값과 같거나 적습니다. 실제 이용자의 첫 장 행동은 퍼즐 게임 첫날 이탈 분석: 첫 장에 숨은 벽 4판에 따로 적었습니다.

pm clear 뒤 12~15분 로그를 뽑고 S11을 먼저 돌립니다

  1. 테스트 광고 ID만 든 빌드를 준비합니다. 릴리스 빌드라면 난독화(minify)를 켜 둔 채 광고와 판 종료 로그 줄만 남깁니다. 실제 ID가 섞이지 않았는지는 R8이 남긴 테스트 광고 ID 5개와 dex 건수 검사처럼 dex에서 셉니다. 실제 광고 ID 빌드는 자동 탭으로 돌리지 않습니다(무효 클릭).
  2. 앱이 전체 화면 광고를 띄우는 순간마다 한 줄(ads: show interstitial 같은 형식)을, 판이 끝날 때마다 한 줄을 찍게 합니다.
  3. 앱 데이터를 지워 신규 설치 상태로 만들고, 로그를 비운 뒤 기기 시계로 시작 시각을 적습니다.
  4. 사람 속도로 12~15분 플레이합니다. 우리 하네스는 퍼즐 한 판에 20~60초 생각, 클래식 한 수에 1.5~3.5초, 전면은 5~8초 보고 닫기, 부활 제안은 절반만 수락으로 두었습니다. 모드마다 따로 돌립니다.
  5. 첫 전체 화면 광고 시각, 전면 간격, 전체 화면 광고 10분당 횟수(횟수 / 분 x 10)를 셉니다.
  6. 판 도중 복귀 규칙은 순서로 확인합니다. 한 수 둔 뒤 홈으로 나가 기준(4분)보다 긴 250초를 기다렸다 돌아오면 앱 오프닝이 없어야 하고(S11), 이어서 홈 화면에서 같은 복귀를 하면 떠야 합니다(S10). S11을 먼저 돌리면 그날의 앱 오프닝 상한(하루 2회)이 아직 비어 있어서, 광고가 안 뜬 이유가 판 도중 규칙 하나로 좁혀집니다.
  7. 규칙을 바꾼 뒤 같은 페르소나로 다시 돌려 전후를 비교합니다.
adb shell pm clear <패키지>
adb logcat -c
adb shell date +%s.%N        # 시작 시각(기기 시계)
adb logcat -v epoch -s ads:D GAME:D > session.log

# python timeline.py session.log <시작 시각> <플레이 분>
import re, sys
log, t0, minutes = sys.argv[1], float(sys.argv[2]), float(sys.argv[3])
rx = re.compile(r"\s*([\d.]+)\s+\d+\s+\d+\s+\w\s+ads\s*:\s+show (\w+)")
shows = [(round(float(m[1]) - t0), m[2]) for m in map(rx.match, open(log, errors="ignore")) if m]
inter = [t for t, kind in shows if kind.lower() == "interstitial"]
print("first", shows[:1], "gaps", [b - a for a, b in zip(inter, inter[1:])],
      "per10min", round(len(shows) / (minutes / 10), 2))

변경 뒤 S21과 클래식은 다시 재지 않았습니다

11월 1일 기준 저장소에는 안내 퍼즐을 제외한 뒤의 S21 첫 전면 시각과, 클래식을 두 판으로 센 뒤의 10분당 횟수를 기기에서 다시 측정한 기록이 없습니다. 314초도 커밋 메시지에만 있고 원 로그는 저장소에 남지 않았습니다. 어떤 페르소나와 빌드로 측정했는지도 적혀 있지 않습니다. 커밋 주석은 처음 세 판에는 판 사이 광고가 없다고 적고 있지만, 코드로는 클래식만 하는 이용자에게 두 번째 게임 오버부터 전면 자격이 생깁니다. 운영자는 11월 1일 코드를 그대로 두고 스토어 안내에서 이 문장을 빼기로 했습니다. 실제 광고 ID 빌드에서 첫 전면 시점을 손으로 확인하는 항목은 출시 리허설 문서에 운영자가 할 일로 남아 있습니다.

퍼즐 게임의 첫 전면 광고는 언제 띄우나요?

한판블록 퍼즐 모드에서는 안내 퍼즐을 빼고 실전 3판을 끝낸 뒤, 세션 시작 90초가 지났을 때부터 내보냅니다. 클래식은 게임 오버를 두 판으로 세므로 두 번째 게임 오버부터입니다. 2026년 10월 4일 에뮬레이터에서는 314초였습니다(커밋 메시지 기준).

전면 광고 간격과 'N판마다' 중 어느 쪽이 빈도를 정하나요?

판 길이로 갈립니다. 2판에 걸리는 시간이 120초 간격보다 길면 '2판마다'가, 그렇지 않으면 간격이 빈도를 정합니다. 한 판이 1분 전후인 3수 역전 퍼즐은 120초 간격이, 한 판이 약 5분인 클래식은 '2판마다' 조건이 빈도를 정했고, 한판블록은 그래서 클래식 게임 오버를 두 판으로 셉니다.

오프라인에서 배너 빈 공간이 남지 않게 하려면?

로드 실패 콜백에서 자리를 접고, 한동안 자리와 요청을 두지 않습니다. 한판블록은 실패 뒤 1분에서 최대 10분까지 기다립니다. 채워지기 전 높이를 0으로 두는 방식은 늦은 채움이 보드를 밀어서 쓰지 않았습니다.
