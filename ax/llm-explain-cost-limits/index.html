59건 평가: flash-lite 78%, 3.8-flash 100%

'왜 틀렸나요?'는 교정된 어절을 누르면 이유 한 줄과 근거 규정 이름을 돌려주는 버튼입니다. 모델은 앱 테스트 픽스처에 저장된 검사기 응답에서 뽑은 교정 59건(네이버 38건, 다음 21건)으로 골랐습니다. 합격선은 설계 문서에 미리 적은 정확 90% 이상, p95 2.5초 이하였고, 호출은 모두 Vertex AI global 엔드포인트로 했습니다.

flash-lite는 73%였고, 띄어쓰기 판단 순서와 자주 나오는 교정의 근거표를 넣은 v2 프롬프트로도 78%에 그쳤습니다. 틀린 답에는 '명사+하다' 붙여쓰기를 어미로 본 설명과 "해여" 같은 깨진 글자가 있었습니다. 3.8-flash는 오타가 없었고 틀린 것은 규정 인용 5건이었습니다. 1,000건당 비용이 $0.42에서 $0.93으로 올라가도 정확도 기준을 넘은 모델은 이것 하나라 기본 모델이 됐습니다.

3.8-flash의 첫 실행은 59건이 모두 빈 응답이었습니다. 출력 상한 160토큰을 모델의 '생각' 토큰이 다 써 버렸기 때문이고, thinkingBudget: 0으로 생각을 끄자 정상으로 돌아왔습니다. 지연 목표 2.5초는 못 지켰습니다. 이 모델은 global 엔드포인트에만 있어서 서울과 도쿄 리전에서는 404가 났고, 호출 한 번에 2.1~2.8초가 걸렸습니다. 설계 문서는 앱 시한(당시 8초) 안이고 버튼 자리에 진행 표시가 있다는 이유로 목표를 p95 5초로 고쳤습니다.

AI Studio 키는 $300 크레딧과 묶이지 않았습니다

402의 원인은 결제 경로였습니다. 오류 원문은 Your prepayment credits are depleted였고, 키 인증은 통과했습니다. 이 프로젝트의 AI Studio 결제는 선불 전용이라, Firebase를 종량제(Blaze)로 바꿀 때 받은 90일 $300 무료 체험 크레딧(Cloud Billing 쪽)과 연결되지 않았습니다.

에이전트는 그날 12시 01분에 "$300 크레딧이면 Gemini API 유료 티어 비용도 같은 프로젝트에 청구"된다고 했고, 10분 뒤에도 크레딧이 둘 모두에 먼저 차감된다는 표를 냈습니다. 스펙은 12시 18분 키 없는 Vertex AI로 바뀌었다가, 12시 21분 운영자가 만들어 둔 AI Studio 키를 보고 "같은 결제 계정"이라는 이유로 키 방식으로 돌아갔습니다(220b267, 740b9d5).

낮에 만든 함수, 한도, 캐시는 전부 가짜 프로바이더로 테스트해서, 진짜 Gemini는 밤 10시 무렵 평가에서 처음 불렸습니다. 22시 04분 402를 보고하며 에이전트가 처음 권한 것도 AI Studio 선불 크레딧 구매(최소 $5)였습니다. 22시 06분 운영자가 $300 무료 크레딧이 Blaze 요금에 포함돼 결제되는 것 아니었냐고 되묻자 에이전트는 설명이 틀렸다고 인정했습니다. 에이전트는 예전에는 AI Studio 키에 결제를 붙이면 Cloud 결제 계정으로 후불 청구됐다고 설명했고, 이 프로젝트는 그렇지 않았습니다.

22시 10분 커밋 de79cfd가 Gemini 인증을 Vertex AI와 ADC(Application Default Credentials, 실행 환경의 서비스 계정 자격)로 옮겼습니다. Vertex는 Cloud Billing으로 청구돼 설계 문서상 크레딧이 적용되는 경로이고, 관리할 API 키도 없습니다. 49분 뒤 배포에서 문제가 하나 더 나왔습니다. 쓰지 않는 Secret을 함수에 선언만 해 놓아도 배포 때 Secret Manager를 조회하다 403으로 실패해서, 키 모드일 때만 선언하게 고쳤습니다(e67a4f7).

LLM 기능을 만들 때는 결제 경로부터 실제 호출 한 건으로 확인하십시오. 다만 200 응답은 어느 잔액에서 빠졌는지 알려 주지 않습니다. 이 앱도 Vertex로 옮긴 뒤의 비용은 함수가 쌓은 토큰 수에 단가를 곱해 계산했고, 결제 보고서에서 크레딧 차감을 대조한 기록은 저장소에 없습니다.

하루 3,000회에서 함수가 LLM 호출을 끊습니다

함수 explainCorrection은 Firebase Functions 2세대의 호출형(callable) 함수 하나입니다. 앱은 프로세스가 첫 화면을 띄울 때 익명 로그인을 걸고, SDK가 요청마다 인증 토큰을 붙여 보냅니다. 함수 안의 순서는 입력 검증, 캐시 조회, 한도 차감, LLM 호출, 캐시 저장입니다. 캐시가 한도보다 앞이라 이미 만든 설명은 무료 횟수를 쓰지 않습니다.

하루의 경계는 한국 시간 자정이고, 일자 키는 서버 시간대에 기대지 않고 UTC 밀리초에 9시간을 더해 만듭니다. 전체 상한이 세는 단위는 LLM 시도입니다. 재시도와 겹쳐 보낸 요청도 하나씩 들어가고, 네트워크 오류처럼 과금 전에 실패한 시도만 돌려받습니다. 시한 초과는 프로바이더가 이미 과금했을 수 있어서 돌려받지 않고 그대로 셉니다.

예산 알림은 결제를 막지 않아, 설계 문서는 이 3,000회 차단을 "실제 안전장치"로 적었습니다. 평가 때 단가($0.93)로 3,000회를 다 채우면 하루 약 $2.8이고, 9월 28일 근거표를 늘린 v3 프롬프트(1,000건당 약 $1.1) 기준으로는 약 $3.3입니다(계산값). 횟수 상한이 금액 상한이 되는 것은 호출 한 번의 토큰이 묶여 있어서입니다. 입력 어절은 원문과 교정이 각각 60자(코드 포인트)까지, 출력은 160토큰까지입니다. 오전에 에이전트가 낸 추정(건당 0.1원 미만, 월 1,000원 미만)은 flash-lite 단가였고, 고른 모델의 1,000건당 비용은 flash-lite v1의 3.4배입니다. 이 상한은 출시된 앱의 호출을 막는 것이고, 개발 중 테스트 호출의 비용 상한은 Vertex AI 테스트 비용 하드캡에 따로 적었습니다.

구독 여부는 첫 출시 단계에서 앱이 보낸 값을 믿습니다. 위조해도 얻는 것은 하루 95회 더, 비용으로 10원 미만이라 영수증 검증은 다음 출시 단계로 넘겼습니다. 하루 합계 문서를 사용자 한도와 같은 트랜잭션에 넣었더니 동시 요청이 락 타임아웃으로 죽어서, 9월 28일에 합계를 트랜잭션 밖으로 뺐습니다(73085eb). 그래서 전체 상한은 동시 진행 요청 수만큼 넘을 수 있습니다.

Remote Config는 런처 화면에서만 갱신돼서, 다른 앱에서 글자를 선택해 여는 미니창만 쓰는 사용자는 런처를 거치지 않아 explain_enabled를 꺼도 버튼이 남을 수 있었습니다. 9월 29일 릴리스 리뷰에서 나왔고, 미니창이 시트를 띄울 때 설정을 새로 받게 고쳤습니다(4c99287).

콜드 스타트 7.9초를 보고 앱 시한을 15초로

9월 27일 밤 운영 배포 뒤 스모크 검사에서 첫 호출은 7.9초, 이어진 호출은 1.6~3.0초였습니다. 최소 인스턴스는 0, 앱의 시한은 8초였습니다. 식은 서버의 첫 호출이 시한과 0.1초 차이였습니다. 커밋 df8f740이 앱 시한을 15초로 늘렸습니다. 최소 인스턴스를 1로 두는 안(월 약 $3~4)은 콜드 스타트가 문제가 될 때 쓸 대안으로 함수 문서에만 남겼습니다. 10월 26~27일 이틀 LLM 비용이 $0.020(약 28원)이었으니, 그 고정비가 설명 비용보다 몇 배 많습니다.

다음 날에는 반복 평가에서 한 번 44.5초까지 늘어진 호출 때문에 서버 쪽 시한을 시도당 6초, 전체 12초로 정했습니다. 10월 25일부터는 4초 동안 답이 없으면 같은 요청을 하나 더 보내고, 10월 24일 25건 중 16건이던 실패가 10월 26~27일 16건 중 0건이 됐습니다.

검사 사용자의 3.7%, 시트를 연 사람의 41%

출시 전 WATCH.md에 적은 규칙은, 14일 뒤 검사 사용자 중 버튼을 누른 비율이 8% 이상이면 유지하고 3% 미만이면 버튼 위치와 문구를 실험하는 것이었습니다. 10월 17일 판정(10월 2~16일, 1.6.025 이상) 결과는 검사 사용자 1,527명 중 56명, 3.7%였고 요청은 77건이었습니다. 두 경계 사이입니다.

같은 기간 교정 어절을 눌러 시트를 연 사람은 138명(9.0%)이었고, 그중 56명이 버튼을 눌렀습니다. 시트까지 온 사람의 41%가 이유를 궁금해했으니 버튼보다 시트가 발견되지 않는 쪽이 병목이었습니다. 다음 버전 1.6.031(10월 18일 단계적 출시)에 색칠한 구간을 누를 수 있다고 알리는 1회 안내를 넣었습니다.

하루 요청이 8건 수준이라 캐시 적중률은 14일 동안 11%로 목표 40%에 한참 못 미쳤습니다. 공유 캐시 설계는 LLM 공유 캐시와 문맥을 보내지 않기로 한 블라인드 A/B에 따로 적었습니다.

자기 앱에 붙이는 순서

  1. Cloud Billing으로 청구되는 경로(이 앱은 Vertex AI)로 실제 모델을 한 건 부르고, 402나 403이면 다른 작업을 멈추고 결제 경로부터 정합니다. 200이 오면 결제 보고서에서 크레딧 차감을 확인합니다.
  2. 테스트 데이터 50건 정도로 후보 모델마다 정확도, p95, 1,000건당 비용을 한 표로 냅니다. 합격선은 먼저 적고, 생각 기능이 있는 모델은 생각 예산을 0으로 정합니다.
  3. 호출형 함수 하나에 익명 인증을 요구하고, 사용자별 무료, 구독자, 함수 전체 한도를 서비스 시간대의 일자 키로 셉니다. 상한 값은 배포 없이 바뀌는 문서에 두고 0을 '닫힘'으로 정합니다.
  4. 입력 길이와 출력 토큰에 상한을 둡니다.
  5. 앱에 버튼을 숨기는 원격 스위치를 두고, 모든 진입 화면이 그 값을 갱신하는지 확인합니다.
  6. 운영 배포 뒤 식은 상태의 첫 호출 시간을 재고 앱 시한을 그보다 길게 잡습니다. 출시 전에 판정 행(사용률 문턱 둘, 캐시 적중률, 실패율, 하루 비용)을 적습니다.
