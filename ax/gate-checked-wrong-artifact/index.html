평문 시그널링 AAB가 출시 게이트를 통과했고, 다른 앱의 광고 SDK 판정은 출시하려던 빌드가 쓰지 않는 의존성 목록(클래스패스)을 봤습니다.

통과 표시를 의심하기 5/6

개발용 설정으로 빌드해 "제출용은 아니다"라고 문서에 적어 둔 Android 앱 번들(AAB)이 출시 게이트에서 PASS를 받았습니다. 2026년 9월 13일 Flutter P2P 채팅 앱의 일입니다. 서버 주소는 localhost였고, 연결을 맺는 시그널링도 암호화하지 않은 평문이었습니다. 한 달 뒤 가족 일정 앱 AXFamily에서는 게이트의 광고 SDK 판정이 출시하려던 빌드와 다른 의존성 목록을 보고 있었습니다.

두 게이트 모두 AI 코딩 에이전트와 같이 만들었고, 둘 다 출시물 옆에서 따로 만든 입력을 판정했습니다. 게이트가 초록이면 출시물도 검증됐다고 믿고 있다면, 그 PASS가 무엇을 읽었는지부터 봐야 합니다.

평문 시그널링 AAB가 PASS를 받았습니다

채팅 앱의 릴리스 워크플로는 빌드 전에 dart-define 파일(Flutter가 빌드 때 앱에 넣는 키=값 설정)을 이 한 줄로 검사했습니다.

grep -Eq 'example\.invalid|CHANGE_ME' "$f"   # 있으면 실패

운영 설정 파일은 자리표시용 호스트 때문에 걸렸습니다. 개발 설정 파일은 호스트가 localhost이고 TLS가 꺼져 있었지만, 두 문자열이 없으니 통과했습니다. 9월 13일 CI가 업로드 키로 서명한 43MB 검증 AAB가 바로 이 개발 설정으로 빌드됐고, 번들 검증 스크립트도 PASS를 냈습니다.

같은 날 쓴 배포 문서는 이 AAB를 "파이프라인 검증본이라 제출용은 아니다"라고 적으면서도 첫머리에 "코드 쪽 차단 요소는 없다"고 요약했습니다. 저장소 지침대로면 평문 ws:// 시그널링은 앱 설정 말고는 막는 곳이 없어서, 같은 워크플로로 서명된 제출용 AAB가 평문 시그널링을 들고 나갈 수 있었습니다.

이틀 뒤의 교차 검증 문서는 계기를 이렇게 적고 시작합니다. "배포 가능 여부를 내가 쓴 문서로 판단하면 교차 검증이 아니라 자기 확인이다." 그래서 배포 문서의 주장을 근거로 쓰지 않고 저장소 상태를 다시 측정했고, 판정은 "아직 배포하면 안 된다"였습니다(막는 것은 운영 결정 3개였고, 그 전에 결함 3건이 나왔습니다).

그날 밤 커밋 184e5ee는 워크플로와 검증 스크립트 양쪽에 같은 규칙을 넣었습니다. TLS가 켜져 있어야 하고, 호스트가 비었거나 localhost이거나 사설·루프백·링크로컬 IP면 실패입니다. 파이프라인 예행연습은 기본값 false인 플래그 allow_insecure_signaling을 켜야만 경고를 찍고 지나갑니다. 규칙을 넣은 뒤 픽스처(일부러 만든 시험 입력) 6개를 손으로 돌려 결과를 문서에 남겼고, 다시 돌린 출력은 뒤에 있습니다.

같은 커밋은 서명 확인도 고쳤습니다. 서명 확인 도구 keytool이 오류를 표준 출력으로 내보내는 바람에 '서명 못 읽음' 분기가 한 번도 돌지 않았고, 스크립트는 이유 없이 끝나 뒤의 검사들을 건너뛰었습니다. 나쁜 빌드가 통과하지는 않았습니다. 지금은 출력에 인증서 소유자 줄(Owner:)이 있는지로 판정합니다. 같은 밤 CI의 암호 대조 테스트 skip은 조용히 skip되는 테스트가 CI를 초록으로 만든다에 따로 썼습니다.

AXFamily 게이트는 다른 광고 SDK를 봤습니다

AXFamily가 광고에 쓰는 google_mobile_ads 9.1.0 플러그인은 빌드 때 받은 dart-define을 보고 Android 광고 SDK를 고릅니다. build.gradle은 Gradle 속성 dart-defines(base64로 바꾼 KEY=VALUE를 콤마로 이은 값)를 풀어 이렇게 정합니다.

def useNextGenSdk = dartEnvironmentVariables.USE_NEXT_GEN_SDK ? dartEnvironmentVariables.USE_NEXT_GEN_SDK : false

값이 있으면 Next-Gen SDK(ads-mobile-sdk), 없으면 Legacy SDK(play-services-ads)가 붙습니다. flutter build는 dart-define을 이 속성으로 Gradle에 넘기지만, Gradle을 따로 부르면 속성이 없으니 언제나 Legacy입니다.

10월 9일 커밋 5427191이 들인 게이트는 네 단계였습니다. 빌드 폴더를 지우고, AAB를 새로 빌드하고, Gradle로 릴리스 의존성 목록을 뽑고, 판정합니다. 세 번째 단계에는 dart-define이 없었습니다. AAB를 어떤 값으로 빌드했든 판정 대상은 Legacy 목록이었고, 저장소에 커밋해 둔 기준 의존성 목록(스냅샷)도 같은 명령에서 나왔으니 비교는 일치할 수밖에 없었습니다.

dart-define 판정은 반대쪽으로 어긋나 있었습니다. 게이트는 허용 목록에 있는 키만 받았는데, 그 목록에 USE_NEXT_GEN_SDK가 없었습니다.

같은 날 Galaxy S21에서 무작위 입력 2,000번을 견딘 것은 Next-Gen 릴리스 빌드였습니다. 그런데 이 게이트를 통과할 수 있는 빌드는 그 검증이 다루지 않은 Legacy 빌드뿐이었고, 검증한 설정은 모르는 키라는 이유로 막히게 되어 있었습니다.

10월 10일 커밋 c38703b가 세 번째 단계에 AAB와 같은 값을 넘기게 했습니다. flutter build가 Gradle에 넘기는 것과 같은 형식으로 -Pdart-defines를 만들고, 값은 화면에 찍지 않습니다. 판정은 USE_NEXT_GEN_SDK를 받되 값이 정확히 'true'여야 합니다. 플러그인의 조건식은 build.gradle의 언어인 Groovy 규칙대로 비어 있지 않은 문자열을 모두 참으로 보기 때문에, 'false'를 줘도 Next-Gen이 붙습니다.

다시 뽑은 스냅샷은 아래처럼 바뀌었고, 테스트에는 실패해야 하는 경우 셋('false', 빈 문자열, 키 없음)이 들어갔습니다.

스냅샷도 같은 명령으로 만들었습니다

AXFamily 쪽 원인은 세 겹입니다. 게이트는 의존성 목록을 출시물과 다른 명령으로 뽑았고, 플러그인이 dart-define으로 의존성을 고르니 결과가 달라졌습니다. 게이트를 만든 커밋에는 두 명령이 같은 입력을 받는지 대조한 흔적이 없습니다. 마지막 겹은 비교 기준인 스냅샷과 테스트 픽스처까지 같은 명령에서 나왔다는 점입니다. 수정 전 게이트를 끝까지 돌린 기록은 남아 있지 않습니다.

채팅 앱에서도 저장소에 이미 있던 개발 설정은 게이트를 거쳤지만, 고치기 전까지는 막혀야 할 입력으로 다뤄진 적이 없었습니다.

c38703b보다 여섯 시간 반 앞서 커밋 1fcc1e1이 AAB 안의 dex(컴파일된 앱 코드)와 libapp.so(Flutter의 Dart 코드가 컴파일돼 들어가는 파일)를 직접 열어 E2E 테스트 모드가 섞였는지 보는 단계를 넣었습니다. 출시물을 읽는 장치가 있었는데도 SDK 목록은 Gradle 보고서로 판정했습니다.

빠진 검사는 결정 기록에 있었습니다

AXFamily의 10월 5일 결정 기록에 이미 이 조건이 있었습니다. Next-Gen은 opt-in이라 CI에 USE_NEXT_GEN_SDK=true를 고정하고, 릴리스 APK에 ads-mobile-sdk가 들어 있는지 검사한다는 내용입니다. 항목 상태는 '권고(가결 추정)', 곧 운영자가 반대하지 않은 권고입니다. 백로그 완료 기준도 같은 dart-define을 요구했습니다. 10월 9일 게이트에는 둘 다 없었고, 대신 Legacy 목록을 스냅샷으로 커밋했습니다.

두 게이트와 두 수정, 그리고 틀렸던 배포 문서 요약까지 모두 Claude 공동 작성 커밋에서 나왔습니다. 요약을 바로잡은 것은 사람이 아니라 교차 검증 문서였고, 기록에 남은 사람의 일은 결정 기록의 권고에 반대하지 않은 것까지입니다.

금지 문자열 대신 필수 값을 요구했습니다

자리표시 목록에 localhost만 더했다면 픽스처의 192.168.0.10과 172.20.1.5는 TLS를 켜도 통과합니다. 수정은 막을 주소를 늘어놓는 대신 출시물이 가져야 할 값(TLS 켜짐, 공개 호스트)을 요구했고, 예행연습 때문에 예외는 기본값 false 플래그로만 엽니다.

AXFamily에서는 USE_NEXT_GEN_SDK가 비어 있지만 않으면 받아 주는 방법도 있었습니다. 플러그인과 같은 규칙이지만, 'false'를 적은 설정이 Next-Gen 빌드를 만들어도 게이트는 아무 말을 하지 않습니다. 정확히 'true'만 받게 했습니다.

기록 파일을 읽는 검사는 로컬에서 SKIP됩니다

채팅 앱 검증 스크립트의 새 TLS 검사와 기존 dart-define 기록 검사는 AAB를 열지 않습니다. 워크플로가 설정에서 만들어 AAB 옆에 둔 기록 파일 dart_defines.txt를 읽습니다. 그 파일 없이 로컬에서 돌리면 두 검사는 SKIP이고, 다른 검사가 통과하면 결과는 PASS입니다. AAB와 기록 파일이 짝인지도 보지 않습니다.

아래는 11월 11일 새 TLS 검사만 떼어 픽스처 7개로 다시 돌린 출력입니다. 처음 여섯은 9월 15일 결과와 같고, 일곱째 픽스처에는 기록 파일이 없습니다. signal.example.com은 예약 도메인 자리표시자입니다.

AAB를 스스로 새로 만드는 AXFamily 게이트는 같은 입력을 넘기기가 쉬웠습니다. 채팅 앱 워크플로의 호스트 검사는 IP 리터럴만 판정해서, 공개처럼 보이는 이름이 사설 IP로 풀려도 막지 못합니다.

고친 게이트 입력에는 테스트가 없습니다

채팅 앱의 픽스처는 손으로 돌려 결과만 문서에 남겼습니다. 184e5ee가 바꾼 파일은 워크플로와 검증 스크립트 둘뿐이고, 그 뒤로 고친 커밋도 없습니다. AXFamily도 게이트가 Gradle에 -Pdart-defines를 넘기는지는 어떤 테스트도 보지 않습니다.

그 인자가 빠지면 지금은 Next-Gen 스냅샷과 어긋나 막힙니다. 오류가 안내하는 스냅샷 재생성 스크립트의 사용법 주석에도 이 인자가 없어서, 주석대로 다시 만들면 고치기 전 구조로 돌아갑니다. 결정 기록이 요구한 출시물(기록에는 릴리스 APK) 안의 ads-mobile-sdk 확인도 아직 게이트에 없습니다.

게이트마다 통과하면 안 되는 입력 하나

그래서 게이트 자체를 이 순서로 검사합니다. 다른 Android 앱 묶음에서 쓰는 업로드 전 3단계 검사는 AI가 만든 Android 앱, 출시 전에 무엇을 검사하나에 따로 있습니다.

  1. 단계마다 무엇을 읽는지 적습니다. 출시물 자체(AAB의 매니페스트, dex, 서명), 출시물을 만든 입력, 따로 만든 입력 중 하나입니다.
  2. 따로 만든 입력이면 출시물을 만든 명령과 같은 인자인지 대조합니다. Flutter라면 Gradle에도 -Pdart-defines로 같은 값을 넘겨야 합니다. AXFamily 게이트는 android 폴더에서 이렇게 합니다(잠금 처리와 출력 저장은 생략했습니다). $DEFINES는 --dart-define-from-file에 준 JSON 파일입니다. 
    DD="$(node -e 'const d=JSON.parse(require("fs").readFileSync(process.argv[1],"utf8"));process.stdout.write(Object.entries(d).map(([k,v])=>Buffer.from(k+"="+v).toString("base64")).join(","))' "$DEFINES")"
./gradlew --no-daemon -q :app:dependencies --configuration releaseRuntimeClasspath "-Pdart-defines=$DD"
  3. 스냅샷과 비교하는 단계는 스냅샷을 만든 명령도 같은 인자인지 봅니다. 한 번은 출시물 쪽에서 SDK를 직접 확인합니다. 10월 9일 재검증은 R8이 남기는 이름 대응표 mapping.txt에서 Next-Gen 패키지가 111줄 나오는 것으로 확인했습니다. 
    grep -c 'com.google.android.libraries.ads.mobile.sdk' build/app/outputs/mapping/release/mapping.txt
    com.google.android.gms.ads로 찾으면 Next-Gen 안의 호환 클래스(그 기록에서 37줄)도 걸리니 Legacy 판정에 쓰지 않습니다. 위 줄은 그 확인을 옮긴 예시로, 그대로 실행한 기록은 없습니다.
  4. 금지 문자열 목록 대신 출시물이 가져야 할 값(TLS 켜짐, 스위치 값 정확히 'true')을 요구합니다. 예외는 기본값 false인 플래그로만 열고, 켜면 경고가 찍히게 합니다.
  5. 게이트마다 통과하면 안 되는 픽스처를 하나 만듭니다. 저장소에 이미 있는 개발 설정, 스위치가 빠진 dart-define 파일, 서명 안 된 AAB 같은 것입니다. FAIL과 함께 이유가 찍히는지도 봅니다.
  6. 그 픽스처를 테스트로 커밋합니다. 게이트를 고친 커밋에는 그 게이트가 막았어야 할 입력을 함께 넣으십시오.

자주 묻는 질문

flutter build의 --dart-define이 Android 의존성도 바꾸나요?

플러그인에 따라 달라집니다. google_mobile_ads 9.1.0은 Gradle 속성 dart-defines에서 USE_NEXT_GEN_SDK를 읽어 광고 SDK를 고르므로, Gradle을 따로 부를 때는 같은 값을 -Pdart-defines로 넘겨야 같은 의존성이 나옵니다.

USE_NEXT_GEN_SDK=false로 주면 Legacy SDK가 들어가나요?

9.1.0에서는 들어가지 않습니다. 플러그인이 비어 있지 않은 문자열을 참으로 보므로 'false'도 Next-Gen이 되고, Legacy를 쓰려면 키를 빼야 합니다.
