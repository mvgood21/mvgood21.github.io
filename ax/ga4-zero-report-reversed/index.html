GA4에 0이 보일 때 먼저 볼 곳: 표 보고서의 합계 행

GA4 개요 화면의 '사용 가능한 데이터 없음'은 0이 아니었습니다. 표 보고서 합계 행에는 지난 28일 활성 사용자 43명, 이벤트 10,522건이 있었습니다.

작성 SugarMount · 에이전트와 일하는 법 · 읽는 시간 9분 · 최종 업데이트 2026년 11월 13일

앱을 막 출시하고 GA4(Google 애널리틱스 4) 첫 화면에서 0이나 "데이터 없음"을 보면 수집 코드가 깨졌다고 생각하기 쉽습니다. 2026년 10월 17일 밤, SugarMount의 AI 코딩 에이전트(Claude Code)도 한글뷰어 슈가독 출시 1주일 지표를 보다가 "GA4 28일 0건"이라고 보고하고 다음 버전의 출시를 미루자고 했습니다. 10분 26초 뒤 같은 에이전트가 그 보고를 거뒀고, 앱 코드에는 고칠 곳이 없었습니다.

아래는 0이 어디서 나왔는지, 화면마다 0이 무엇을 뜻하는지, 그리고 코드를 열기 전에 확인할 순서입니다.

0은 개요 화면 글자를 한 번 읽고 나왔습니다

에이전트는 Chrome으로 Firebase 개요 화면(GA4 대시보드)을 열었고, 스크린샷이 실패하자 4초를 기다린 뒤 화면 글자를 한 번 읽었습니다. GA4 화면을 연 것은 이 한 번뿐입니다.

그때 읽은 글자 1,736자에서 값으로 된 숫자는 "지난 30분 동안의 활성 사용자 0" 하나였습니다. 이벤트 이름별, 국가별, 기기 모델별 카드 10곳은 모두 "사용 가능한 데이터 없음" 또는 "없습니다"였습니다. 에이전트는 이 문구와 30분짜리 0을 합쳐 "지난 28일 사용자 0, 이벤트 0"을 만들었고, Play Console의 하루 활성 사용자 2~3명 옆에 놓았습니다. 둘을 나란히 두자 "앱이 분석 데이터를 아예 보내지 못한다"는 설명이 그럴듯해졌습니다.

표 보고서 합계 행에는 43명이 있었습니다

원인 조사를 맡은 서브에이전트는 코드와 빌드를 3분 동안 점검했고 결함을 찾지 못했습니다. Galaxy S21에 깔린 출시 빌드로 앱을 띄우자 logcat에 업로드 성공 줄이 찍혔습니다.

V/FA-SVC: Network upload successful with code, uploadAttempted: 204, true

실시간 개요는 처음에 0이었다가 6초 뒤 app_entry 1건, session_start 1건을 보여 줬습니다. 이어서 보고서의 "페이지 및 화면" 표를 열자, 11초 만에 합계 행에서 지난 28일 활성 사용자 43명, 이벤트 10,522건을 읽었습니다. 기술 세부정보 표를 앱 버전으로 나누면 아래와 같습니다.

이벤트의 25.77%는 QA용 debug 빌드 몫이었습니다. 버전 행의 사용자를 더하면 45명인데 합계 행은 43명입니다. 한 사람이 두 버전을 쓰면 버전 행마다 한 번씩 세어지므로, 판단은 합계 행으로 합니다. 두 화면 사이에 자정이 지나서 개요의 "지난 28일"은 9월 19일~10월 16일, 표 보고서는 9월 20일~10월 17일로 하루 밀린 범위였습니다.

GA4 화면마다 0의 뜻이 다릅니다

이번에 본 화면은 넷이었습니다. 같은 0이나 "데이터 없음"이라도 기간과 뜻이 달랐습니다.

화면기간이번에 본 것읽는 법

표 보고서 합계 행지난 28일(어제까지)43명, 10,522건판단 기준

데이터 스트림의 "최근 48시간 동안 수신한 데이터가 없습니다"도 사실이었습니다. 이 앱은 10월 16~17일 실제 사용자가 0명이었습니다.

코드를 열기 전에 확인하는 순서

  1. 0이 나온 화면 이름과 기간을 위 표에서 찾아 적습니다.
  2. 표가 있는 보고서에서 합계 행을 읽습니다. 이번에는 "페이지 및 화면" 표와 "기술 세부정보" 표를 열었고, 기술 세부정보의 기본 측정기준을 "앱 버전"으로 바꿔 버전별 행을 봤습니다. 화면을 읽기 어렵다면 GA4 Data API의 runReport가 같은 값을 JSON으로 돌려줍니다(아래 첫 명령).
  3. 기기에서 업로드를 봅니다. 디버그 모드 속성을 켜고 앱을 띄운 뒤 logcat에서 업로드 응답 코드(204)를 찾고, 실시간 개요나 DebugView에 이벤트가 오는지 봅니다. 이번에는 업로드 약 2분 뒤 실시간 개요에 app_entry 1건이 보였습니다.
  4. 지표 정의를 맞춰 봅니다. Play Console의 활성 사용자와 GA4 활성 사용자는 집계 정의가 다르고, debug 빌드, 테스트 기기, Play 사전 출시 로봇도 원시 값에 들어갑니다.
  5. 여기까지 마친 뒤에 코드를 엽니다.

runReport는 analytics 권한이 붙은 토큰이 있어야 합니다. 그날은 토큰 두 개 모두 그 권한이 없어 403이었습니다. gcloud 로그인에 스코프를 더하는 길은 막혀 있어서, 지금은 서비스 계정을 가장해 토큰을 받습니다(gcloud '차단된 앱', 서비스 계정 가장으로 우회). 기간을 28daysAgo~yesterday로 두면 표 보고서와 같은 범위입니다.

TOKEN=$(gcloud auth print-access-token \
  --impersonate-service-account=<서비스 계정 주소> \
  --scopes=https://www.googleapis.com/auth/analytics.readonly)
curl -s -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  https://analyticsdata.googleapis.com/v1beta/properties/<속성 번호>:runReport \
  -d '{"dateRanges":[{"startDate":"28daysAgo","endDate":"yesterday"}],
       "metrics":[{"name":"activeUsers"},{"name":"eventCount"}]}'

3번의 기기 확인 명령입니다. 이번 기록에서는 log.tag 두 값을 빈 값으로 되돌리지 못해 재부팅으로 지웠습니다.

adb shell setprop debug.firebase.analytics.app <패키지 이름>
adb shell setprop log.tag.FA VERBOSE
adb shell setprop log.tag.FA-SVC VERBOSE
adb logcat -s FA FA-SVC          # "Network upload successful with code" 줄을 찾습니다
adb shell setprop debug.firebase.analytics.app .none.
adb reboot                       # log.tag 두 값 정리

에이전트가 틀린 곳: 0을 사실로 적은 조사 지시

메인 에이전트는 원인 조사를 서브에이전트에 넘기면서, 지시문 첫 문단에 "지난 28일 사용자 0, 이벤트 0"을 사실로 적었습니다. 필수 점검 다섯 항목은 모두 코드와 빌드였고, GA4 보고서에서 0이 맞는지 다시 보라는 항목은 없었습니다. 18초 뒤에는 미리 승인받아 둔 1.1.0의 production 승격 명령을 실행했다가 Claude Code 자동 모드의 권한 분류기에 막혔고, 운영자에게 "분석 수집 버그가 1.1.0에도 있다면 고친 1.1.1을 바로 올리자"고 보고했습니다.

정정 보고에서 메인 에이전트는 카드가 다 그려지기 전에 글자를 읽었다고 설명했지만, 같은 화면을 다시 열어 확인한 기록은 없습니다. 서브에이전트는 데이터 스트림 화면을 봤을 거라고 추정했는데, 세션 기록상 메인 에이전트가 연 GA4 화면은 개요 하나였습니다. 확실한 것은 합계 행이 있는 보고서를 열지 않았고, 숫자를 두 번째 경로로 맞춰 보지 않았다는 점입니다.

화면 글자에서 읽은 0으로 배포 결정을 바꾸지 마십시오. 서브에이전트에게 넘길 때는 0을 사실로 쓰지 말고, 위 순서의 1번과 2번을 첫 작업으로 적습니다. 지시문을 쓰는 다른 규칙은 서브에이전트 브리프의 절대 규칙 6개와 한도로 끊긴 에이전트 5건에 있습니다. 1.1.1 핫픽스와 승격 보류는 표 보고서 한 장을 본 뒤 버렸고, 다음 날 PDF 저장을 넣은 1.2.0이 production에 올라갔습니다.

0이 맞는 날과 부풀려진 원시 값

트래픽이 정말 적은 앱에서는 0이 맞는 화면이 많습니다. 이 앱의 GA4 사용자는 10월 11~14일과 16~17일에 0명이었습니다. 위 순서는 그 0이 어느 화면, 어느 기간의 값인지 가르는 데까지만 돕습니다.

반대로 10월 27일에는 원시 활성 사용자가 13명이었는데, 테스트 기기와 Play 사전 출시 로봇을 빼면 4명이었습니다. 거르는 방법은 GA4의 '어제 설치 19건'은 사실 8건이었다에 적었습니다. 기기 확인은 직접 설치한 1.1.0으로만 했고, Play에서 받은 1.0.0이 정상이라는 근거는 AAB 정적 검사와 GA4에 들어온 1.0.0 데이터입니다.

남은 일: Play 하루 2~3명과 GA4 하루 0~1명

공개 뒤 Play Console의 하루 활성 사용자 2~3명과 GA4의 하루 0~1명 차이는 위 순서로 풀리지 않았고, 두 지표의 정의가 달라 버그인지 단정할 수 없다는 데서 멈췄습니다. 다음에 할 일은 10월 10일 이후 app_entry를 진입 경로(런처, 파일 열기)별로 나누고, first_open 수를 Play 설치 수와 날짜별로 맞춰 보는 것입니다.

자주 묻는 질문

GA4에 데이터가 0으로 나오면 앱 코드부터 봐야 하나요?

코드보다 표가 있는 보고서의 합계 행을 먼저 읽으십시오. 이번에는 개요 화면에서 0으로 읽힌 28일 값이 표 보고서에서 43명, 10,522건이었고, 코드와 빌드를 3분 동안 점검해서 나온 결함은 0건이었습니다.

데이터 스트림에 "최근 48시간 동안 수신한 데이터가 없습니다"가 뜨면 수집이 끊긴 건가요?

끊겼다는 뜻은 아닐 수 있습니다. 그 48시간에 들어온 이벤트가 없어도 같은 문구가 나옵니다. 이 앱은 10월 16~17일 실제 사용자가 0명이라 그 문구가 나왔고, 기기에서 이벤트를 보내자 약 2분 뒤 실시간 개요에 app_entry가 보였습니다.

2026-11-03 확인. Claude Code 세션 기록(메인 세션과 조사 서브에이전트, UTC를 한국 시간으로 바꿈), 앱과 게임 저장소의 문서와 git 기록. GA4 속성 번호와 계정 식별값은 적지 않았습니다.
