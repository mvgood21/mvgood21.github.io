AI 에이전트가 보고한 'GA4 28일 0건', 표 보고서에는 43명이 있었다

GA4 0건은 개요 화면 글자를 한 번 읽고 낸 오판이었고, 표 보고서에는 지난 28일 활성 사용자 43명과 이벤트 10,522건이 있었습니다.

작성 SugarMount · 에이전트와 일하는 법 · 읽는 시간 14분 · 최종 업데이트 2026년 11월 8일

AI 에이전트가 "GA4가 지난 28일 동안 0건"이라며 측정이 깨졌다고 보고했고, 10분 26초 뒤 같은 에이전트가 그 보고를 거둬들였습니다. 2026년 10월 17일 토요일 밤 23시 57분(한국 시간), 한글뷰어 슈가독(SugarDoc)이 Play에 공개된 지 1주일째 되는 날 지표를 Chrome으로 모아 보던 Claude Code 세션이었습니다. 조사를 맡은 서브에이전트가 GA4 표 보고서에서 읽은 값은 지난 28일 활성 사용자 43명, 이벤트 10,522건이었고, 그중 Play 출시본이 34명, 7,728건이었습니다. 앱 코드에는 고칠 곳이 없었습니다.

근거는 Claude Code 세션 기록(메인 세션과 조사 서브에이전트의 jsonl), sugar-utils와 게임 저장소의 문서와 커밋, 세션 기록에 남은 GA4 화면 글자입니다. 세션 기록의 시각은 UTC로 저장돼 있어 한국 시간으로 바꿔 적었습니다. GA4 속성 번호와 계정·앱 식별값은 쓰지 않습니다. 확인 기준일은 2026-11-03입니다.

개요 화면을 4초 기다려 한 번 읽었습니다

23시 50분, 운영자가 같은 세션에서 analytics 스코프로 gcloud 애플리케이션 기본 사용자 인증 정보(ADC)를 다시 받으려 했지만, 명령이 실행된 창에 gcloud가 없어 실패했습니다. 운영자는 로그인이 안 되면 Chrome으로 진행하라고 했고, 메인 에이전트는 23시 52분 56초에 Firebase 개요 화면(GA4 대시보드)을 열었습니다. 바로 이어 찍은 스크린샷은 "Can't interact with browser-internal or unparseable URLs" 오류로 실패했고, 4초를 기다린 뒤 23시 53분 6초에 화면 글자를 한 번 읽었습니다. GA4 화면을 연 것은 이 한 번뿐이고, 곧바로 Play Console 통계와 Android vitals로 넘어갔습니다.

그때 읽은 글자 1,736자 가운데 숫자로 된 값은 "지난 30분 동안의 활성 사용자 0" 하나였고(나머지 0~1은 차트 눈금), "사용 가능한 데이터 없음" 또는 "없습니다"가 10곳에 있었습니다. 이벤트 이름별 이벤트 수, 국가별, 기기 모델별 카드가 모두 이 문구였습니다. 첫 카드 "시간 경과에 따른 사용자 활동"에는 날짜 눈금 "17 10월" 말고 값으로 읽을 숫자가 없었습니다. 23시 57분 보고의 표에는 이것이 "지난 28일 사용자 0, 이벤트 0. QA 기기 기록도 없음"으로 적혔습니다.

에이전트는 "데이터 없음" 문구와 30분짜리 0을 합쳐 28일 합계 0을 만들었고, 그 숫자를 Play Console의 하루 활성 사용자 2~3명 옆에 놓았습니다. 둘을 나란히 두자 "앱이 분석 데이터를 아예 보내지 못한다"는 설명이 그럴듯해졌습니다.

0을 사실로 적은 브리프와 승격 보류 제안

23시 56분 38초, 메인 에이전트는 원인 조사를 서브에이전트에 넘겼습니다. 영어로 쓴 브리프의 첫 문단은 GA4 속성이 지난 28일 동안 사용자 0, 이벤트 0이고 QA 기기 기록조차 없다는 내용이었습니다. 필수 점검 목록 다섯 항목(google-services 플러그인 적용, 빌드 산출물의 Firebase 리소스, FirebaseApp 초기화, 동의 기본값, 이벤트 호출 지점)은 모두 코드와 빌드 항목이었고, 기기 logcat 확인은 선택으로 붙어 있었습니다. GA4 보고서에서 0이 맞는지 다시 보라는 항목은 없었고, 버그를 찾으면 별도 worktree에서 고치라는 지시가 들어 있었습니다.

18초 뒤 메인 에이전트는 미리 승인받아 둔 1.1.0(4)의 production 승격 명령을 실행했고, Claude Code 자동 모드의 권한 분류기가 "[Production Deploy]"로 막았습니다. 글자를 읽은 지 4분 뒤인 23시 57분 보고는 이 명령을 운영자에게 넘기면서 "분석 수집 버그가 1.1.0에도 들어 있다면, 고친 1.1.1을 바로 올리는 편이 낫다"고 덧붙였습니다. 수정용 worktree와 브랜치 이름도 진행 중 작업으로 적혔습니다.

이 10분 동안 사람이 고친 지점은 없었습니다. 권한 분류기는 0과 상관없이 production 승격 명령을 막았을 뿐이고, 0에서 나온 핫픽스·보류 제안은 조사를 맡은 서브에이전트의 보고를 받고 거둬졌습니다. 화면 글자에서 읽은 0으로 배포 결정을 바꾸지 마십시오. 이번 0은 어느 화면의 어느 기간 값인지 적히지 않은 채 보고서와 브리프에 들어갔습니다. 서브에이전트에게 맡길 일을 적는 다른 규칙은 서브에이전트 브리프의 절대 규칙 6개와 한도로 끊긴 에이전트 5건에 있습니다.

조사 에이전트는 코드, 기기, 보고서 순으로 갔습니다

서브에이전트는 브리프 순서대로 코드와 빌드부터 봤습니다. 23시 56분부터 약 3분 동안 google-services 플러그인 조건, 1.1.0 출시 APK의 Firebase 리소스(키 이름만), 초기화 provider, 동의 기본값 경로를 확인했고 결함은 없었습니다. 1.0.0과 1.1.0 AAB 정적 검사는 기기 확인 뒤 00시 4분에 했습니다. 23시 59분에는 Firebase 관리 API로 출시 앱과 debug 앱이 GA4 스트림 두 개에 연결돼 있는 것을 봤습니다.

자정에는 Galaxy S21로 갔습니다. 기기에 깔린 1.1.0(4) 출시 빌드에 Firebase 디버그 모드 속성을 켜고 앱을 띄우자 logcat에 초기화 성공, 수집 켜짐, analytics_storage=granted가 찍혔고, 00시 00분 52초에 이 줄이 나왔습니다.

V/FA-SVC: Network upload successful with code, uploadAttempted: 204, true

00시 1분에는 GA4 Data API로 숫자를 받으려 했지만, ADC 토큰과 gcloud 사용자 토큰 둘 다 analytics 스코프가 없어 403이 났습니다. 남은 길은 Chrome으로 여는 GA4 화면입니다. 데이터 스트림 화면은 두 스트림 모두 "최근 48시간 동안 수신한 데이터가 없습니다"였고, 실시간 개요는 00시 2분 44초에 0이었다가 6초 뒤 같은 화면에서 app_entry 1건, session_start 1건을 보여 줬습니다. 00시 5분 38초에 서브에이전트가 보고서의 "페이지 및 화면" 표를 열었고, 11초 뒤 읽은 글자의 합계 행에 지난 28일 활성 사용자 43명, 이벤트 10,522건이 있었습니다.

43명 중 34명이 출시본, 6명은 QA 빌드

00시 6분에 기술 세부정보 표를 앱 버전으로 나누자 1.0.0(Play 출시본) 34명·7,728건, 1.0.0-debug 6명·2,712건, 1.1.0(내부 테스트) 5명·82건이었습니다. 이벤트의 25.77%가 QA용 debug 빌드 몫입니다. 버전 행의 사용자를 더하면 45명인데 합계 행은 43명이었습니다.

서브에이전트 보고로는 10월 10일 공개 뒤 GA4 사용자가 5명(1.0.0 3명, 1.1.0 2명)이었고, 일별로는 10일에 약 4명, 그 뒤로는 하루 0~1명이었습니다. 28일 동안의 1.0.0 사용자 34명 가운데 공개 뒤 사용자는 3명이고, 공개 전에 잡힌 나머지가 누구인지는 그 세션에서 나누지 않았습니다. 두 화면 사이에 자정이 지나서, 개요 화면의 "지난 28일"은 9월 19일~10월 16일, 표 보고서의 "지난 28일"은 9월 20일~10월 17일로 하루 밀린 범위입니다.

'로딩 전'은 확인 못 했고, '스트림 화면'은 기록과 어긋납니다

00시 7분 49초 정정 보고에서 메인 에이전트는 0건이 Firebase 개요 화면의 카드가 다 로딩되기 전에 글자를 읽어서 생긴 오판이라고 썼습니다. 그럴 수 있지만 확인한 사실은 아닙니다. 같은 개요 화면을 다시 열어 카드가 채워지는지 본 기록이 없습니다.

서브에이전트는 다른 추정을 냈습니다. 메인 에이전트가 데이터 스트림 화면의 "48시간 동안 수신 없음"이나 실시간 개요의 0, 또는 잘못된 속성이나 필터를 봤을 거라는 추정입니다. 세션 기록과는 맞지 않습니다. 메인 에이전트가 연 GA4 화면은 Firebase 개요 하나였습니다. 스트림 문구 자체는 사실이었고, 10월 16~17일에는 실제로 사용자가 0명이었습니다.

메인 에이전트는 합계 행이 있는 보고서를 열지 않았고, 숫자를 두 번째 경로로 맞춰 보지 않았습니다. Data API가 막혀 있어 두 번째 경로가 브라우저뿐이었지만, 같은 브라우저에서 서브에이전트가 표 보고서를 열고 합계를 읽기까지는 11초였습니다.

Data API, 코드 점검, 화면 캡처, 핫픽스

GA4 Data API의 runReport는 화면 글자 대신 activeUsers와 eventCount를 JSON으로 돌려주므로 카드가 그려졌는지와 상관이 없습니다. 그날은 두 토큰 모두 analytics 스코프가 없어 403이었고, 23시 50분 운영자의 다시 로그인 시도도 실패해 그 자리에서 쓰지 못했습니다. 다음 날 커밋된 성장 계획 문서(8475f45)도 "Claude는 지금 GA4 숫자를 직접 볼 수 없다"고 적고 광고 단가와 전환율을 모두 추정으로 남겼습니다. 게임 저장소의 GA4 보고 도구는 서비스 계정 토큰으로 GA4를 읽었고, 10월 22일 커밋(7a61407)에서 gcloud 사용자 로그인 없이 ADC만으로 그 토큰을 만들게 바뀌었습니다. 사고 열흘 뒤 일일 점검 문서(68215b5, 10월 27일분)는 그 도구의 필터를 쓴 앱별 GA4 Data API 값으로 바뀌어 있었습니다.

브리프는 코드부터 보게 했고, 그 점검은 결함이 없다는 것까지만 보여 줬습니다. 28일 합계는 표 보고서를 열고서야 나왔습니다. 성장 계획 문서는 운영자의 GA4 화면 캡처를 대안으로 적었지만, 그 길은 사람이 화면을 열 때까지 판단을 미뤄야 합니다. 1.1.1 핫픽스와 1.1.0 승격 보류는 표 보고서 한 장을 본 뒤 버렸습니다. 1.1.0(4)은 결국 production에 오르지 않았고, 다음 날 PDF 저장을 넣은 1.2.0(5)이 production에 올라갔습니다(6687cd0, c676b49).

0이 맞는 화면과 부풀려진 원시 값

트래픽이 정말 적은 앱에서는 0이 맞는 화면이 많습니다. 서브에이전트 보고로는 이 앱의 GA4 사용자가 10월 11~14일과 16~17일에 0명이었습니다. 아래 순서는 그 0이 어느 화면, 어느 기간의 값인지 가르는 데까지만 돕습니다.

반대로 10월 27일 일일 점검에서는 SugarDoc의 원시 활성 사용자가 13명이었는데, 테스트 기기와 Play 사전 출시 로봇을 빼면 4명이었습니다. 그날 올린 1.3.3(9)을 사전 출시 로봇이 시험했습니다. 원시 값을 거르는 방법은 GA4의 '어제 설치 19건'은 사실 8건이었다에 적었습니다.

기기 확인은 사이드로드한 1.1.0(4)로만 했습니다. 연결된 두 기기 모두 Play에서 받은 1.0.0이 없었고, 1.0.0이 정상이라는 근거는 AAB 정적 검사와 GA4에 들어온 1.0.0 데이터입니다.

데이터 스트림 상태최근 48시간"수신한 데이터가 없습니다"사용자가 적으면 사실일 수 있음
표 보고서 합계 행지난 28일(어제까지)43명, 10,522건판단 기준
  1. 0이 나온 화면 이름과 기간을 위 표에서 찾아 적습니다.
  2. 보고서 원본에서 합계 행을 읽습니다. 이번에는 보고서의 "페이지 및 화면" 표와 "기술 세부정보" 표(주소의 r=user-technology-detail)를 열었고, 기술 세부정보에서 기본 측정기준을 "앱 버전"으로 바꿔 버전별 행을 봤습니다. 기간을 28daysAgo~yesterday로 맞추면 같은 범위를 runReport로 받습니다.
  3. 기기에서 업로드를 봅니다. 디버그 모드 속성을 켜고 앱을 띄운 뒤 logcat에서 업로드 응답 코드를 확인하고, DebugView나 실시간 개요에 이벤트가 오는지 봅니다. 이번에는 DebugView 대신 실시간 개요를 봤고, 업로드 약 2분 뒤 app_entry 1건이 보였습니다.
  4. 지표 정의를 맞춰 봅니다. Play Console의 활성 사용자와 GA4 활성 사용자는 집계 정의가 다릅니다. GA4 안에서도 버전 행의 합(45)과 합계(43)가 달랐고, debug 빌드, 테스트 기기, 사전 출시 로봇이 원시 값에 들어 있습니다.
  5. 여기까지 마친 뒤에 코드를 엽니다. 서브에이전트에게 넘길 때는 0을 사실로 쓰지 말고, 1번과 2번을 첫 작업으로 적습니다.

2번의 runReport 요청은 그날 403에서 멈춘 요청에서 식별값만 지운 형태이고, 화면과 범위를 맞추려고 endDate만 yesterday로 고쳤습니다. 스코프는 서브에이전트가 보고서에 남긴 다시 로그인 명령 그대로입니다.

gcloud auth application-default login \
  --scopes=https://www.googleapis.com/auth/analytics.readonly,https://www.googleapis.com/auth/cloud-platform

curl -s -X POST \
  -H "Authorization: Bearer $(gcloud auth application-default print-access-token)" \
  -H "x-goog-user-project: <Cloud 프로젝트 ID>" \
  -H "Content-Type: application/json" \
  https://analyticsdata.googleapis.com/v1beta/properties/<속성 번호>:runReport \
  -d '{"dateRanges":[{"startDate":"28daysAgo","endDate":"yesterday"}],
       "metrics":[{"name":"activeUsers"},{"name":"eventCount"}]}'

3번의 기기 확인은 아래 순서입니다. 서브에이전트 보고로는 log.tag 두 값이 빈 값으로 되돌려지지 않아 VERBOSE로 남았고, 재부팅하면 사라진다고 적었습니다.

adb shell setprop debug.firebase.analytics.app <패키지 이름>
adb shell setprop log.tag.FA VERBOSE
adb shell setprop log.tag.FA-SVC VERBOSE
adb logcat -s FA FA-SVC          # "Network upload successful with code" 줄을 찾습니다
adb shell setprop debug.firebase.analytics.app .none.
adb reboot                       # log.tag 두 값 정리(서브에이전트 기록상 빈 값 설정이 안 됨)

Play 하루 2~3명과 GA4 하루 0~1명의 차이

Play Console의 하루 활성 사용자 2~3명과 GA4의 공개 뒤 하루 0~1명 차이는 위 순서로 풀리지 않았고, 두 지표의 정의가 달라 버그인지 단정할 수 없다는 데서 멈췄습니다. 서브에이전트가 남긴 다음 할 일은 10월 10일 이후 app_entry를 진입 경로(런처, 파일 열기)별로 나누고 first_open 수를 Play 설치 수와 맞춰 보는 것이었습니다. 그 세션에서는 하지 않았고, 11월 3일에 sugar-utils 문서를 찾아봤을 때도 날짜별로 둘을 맞댄 표는 없었습니다.

GA4에 데이터가 0으로 나오면 앱 코드부터 봐야 하나요?

코드보다 표가 있는 보고서의 합계 행을 먼저 읽으십시오. 이번에는 개요 화면에서 0으로 읽힌 28일 값이 표 보고서에서 43명, 10,522건이었고, 코드와 빌드를 3분 동안 점검해서 나온 결함은 0건이었습니다.

데이터 스트림에 "최근 48시간 동안 수신한 데이터가 없습니다"가 뜨면 수집이 끊긴 건가요?

끊겼다는 뜻은 아닐 수 있습니다. 그 48시간에 들어온 이벤트가 없어도 같은 문구가 나옵니다. 이 앱은 10월 16~17일 실제 사용자가 0명이라 그 문구가 나왔고, 기기에서 이벤트를 보내자 약 2분 뒤 실시간 개요에 app_entry가 보였습니다.
