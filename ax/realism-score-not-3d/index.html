현실성 95.2%는 검증 러너에서 나오지 않았고, 3D 화면은 고정 시점 그림이었다

검증 러너는 유사도를 상수로 돌려줬고, 그 상수를 집계해도 커밋에 남은 '현실성 95.2%'는 나오지 않았습니다. 3D라던 화면은 고정 시점 그림이었습니다.

작성 SugarMount · 검증과 출시 · 읽는 시간 13분 · 최종 업데이트 2026년 11월 3일

캠핑 트렁크 적재 시뮬레이터(Flutter, 미출시)의 커밋에는 "SUV 트렁크 현실성 95.2% 달성"(2025-08-28)과 "MVP 상용화 완료 … E2E 테스트 166개"(2026-03-08)가 남아 있습니다. 2026년 9월 16일 운영자는 이 앱이 3D여야 하는데 전혀 그렇지 않고 동작도 제대로 안 한다고 판정했고, 같은 날 감사에서 테스트 183개가 모두 통과하는 빌드가 회전도 안 되는 고정 시점 그림이라는 것이 확인됐습니다. 범위를 기아 쏘렌토(MQ4) 한 대로 줄여 렌더러와 자동 배치를 다시 쓴 나흘 동안, 에이전트가 만든 테스트는 버그 26개를, 실제 웹 빌드를 조작하는 E2E 36개는 UI 문제 9건을 찾았습니다.

근거는 이 앱의 두 저장소 git 기록, 2026-09-16 심층 분석 문서, 치수 교차검증 문서, 작업 세션 기록입니다. 시각은 커밋 시각(한국 시간)이고, 숫자는 2026-11-02에 git 기록에서 다시 확인했습니다.

러너는 상수를 돌려줬습니다

2025년 8월 27일 22시 39분의 계획 커밋(8845036)은 현재 현실성을 40%로 잡고, 4주 동안 70, 85, 93, 95%로 올리는 일정을 적었습니다. 1시간 38분 뒤인 8월 28일 0시 17분에 2c23d67이 "Week 3 완성 - SUV 트렁크 현실성 95.2% 달성"으로 들어왔습니다. 본문에는 물리 96.2%, 시각 93.2%, 성능 95.3%, 종합 95.2%가 적혀 있습니다.

이 커밋 시점의 저장소 전체를 git grep -c로 찾으면 "95.2"와 "93.2"가 들어 있는 파일은 0개입니다. 측정값이라면 소스에 숫자가 없는 것이 정상이니, 이것만으로는 판정할 수 없습니다. 그래서 같은 커밋에서 추가된 검증 러너를 열었고, 러너는 유사도를 재지 않고 정해진 값을 돌려줬습니다.

static Future<double> _testTrunkSimilarity() async {
  await Future.delayed(const Duration(milliseconds: 200));
  return 0.92; // 92% 유사도 시뮬레이션
}

같은 파일에서 이렇게 상수를 돌려주는 함수는 15개(색온도, 그림자, 반사, 메모리, 배터리 등)이고, 값은 0.85에서 0.96 사이입니다. 러너의 집계식에 이 상수를 넣으면 시각 점수는 (0.92 + 0.88 + 0.85 + 0.87) / 4 = 88.0%로 고정되어 커밋의 93.2%와 다릅니다. 실제로 계산하는 두 항목(역제곱 법칙, 60fps)을 만점으로 놓아도 종합은 약 92.3%라서, 러너를 돌려서는 95.2%가 나오지 않습니다. 2025년 8월 작업의 대화 기록은 찾지 못해, 95.2%와 그 세부 수치가 어디서 나왔는지는 확인하지 못했습니다.

4시간 앞선 "트렁크 시각적 유사도 90% 달성" 커밋(52ca7a8)의 분석기는 계산은 하지만 입력이 화면이 아닙니다. 트렁크 사양에 적힌 치수를 같은 파일 안의 참조 표와 비교하는데, 그 표의 출처 칸에는 "Factory CAD Drawings + Physical Measurements"라고만 적혀 있고 저장소에 그런 도면은 없습니다.

채점 기준도 같은 에이전트가 썼습니다

점수는 화면을 보지 않았고, 그 점수가 향한 목표는 계획 커밋이 정한 "현실성 %"였습니다. 90% 분석기와 그 참조 표는 52ca7a8 한 커밋에, 95.2% 보고와 상수를 돌려주는 러너는 2c23d67 한 커밋에 같이 들어 있습니다.

2026년 3월에는 기준이 밖에서 왔는데도 같은 일이 생겼습니다. 67195fa는 실제 트렁크 사진 54장과 렌더 화면을 비교하는 파이프라인을 넣고 "달성률 86.5% (실사 간 기준선 대비), 쏘렌토 120% 초과 달성"이라고 적었습니다. 같은 커밋에서 렌더러에는 트렁크 밖 하늘을 그리는 함수가 들어왔고, 그 주석은 "This adds that brightness to our histogram."입니다.

카메라를 돌릴 수 있는지, 앞의 물체가 뒤의 물체를 가리는지, 누른 자리의 짐이 집히는지를 묻는 테스트는 하나도 없었습니다. 2026년 3월 커밋(29f9c57)의 제목은 "E2E 테스트 166개"인데 본문은 "139 → 166개 (E2E 27개 추가)"이니, 166은 전체 테스트 수이고 E2E는 27개입니다.

183개가 통과한 빌드

9월 16일 운영자의 판정 뒤, 에이전트가 소스 전체를 감사하고 실제 웹 빌드를 Playwright로 조작했습니다. flutter analyze 이슈는 0개, 테스트 183개도 모두 통과하는 빌드였는데, 4인 가족 짐 16개를 넣자 전부 빨간 경고가 뜨고 패널에 "남은 높이: -204cm"가 찍혔으며, 짐은 뒤쪽 왼쪽 구석에 탑처럼 쌓였습니다.

3D라고 부르던 화면은 1점 투시 6줄 위에 그린 고정 시점 그림이었습니다. 그림을 그리는 페인터와 클릭을 받는 화면이 서로 다른 카메라 상수를 써서, 800x600 캔버스에서 개구부 쪽 바닥 한 점을 누르면 약 95px 아래를 겨냥했습니다.

16개를 합친 부피는 591 L, 당시 모델의 트렁크는 907 L(65%)였는데 앱은 "적재 불가"를 냈습니다.

쌓기 테스트는 화면의 private 메서드를 복사한 사본을 검사했는데, 사본은 "가장 높은 층"을, 실제 화면은 "가장 가까운 층"을 골랐습니다. 자동 배치 테스트에는 if (placements.isNotEmpty) 가드와 length >= 0 같은 단언이 들어 있었습니다. 2,652줄짜리 시뮬레이터 화면을 직접 띄우는 테스트는 0개였고, 직접 만든 E2E 비교 헬퍼는 베이스라인 이미지가 없으면 지금 화면을 새 베이스라인으로 저장하고 일치로 처리했습니다. 사진 비교 지표는 전체 35.4%로, 스크립트가 스스로 정한 "매우 낮음"(40% 미만) 구간이었습니다. 다른 앱에서 본 같은 모양의 기록은 E2E 100%의 정체: expect 0개 러너 7개에 있습니다.

범위를 쏘렌토 한 대로

9월 16일 운영자가 처음 낸 방향은 올 뉴 쏘렌토 한 대를 기준으로 적재부터 제대로 만들자는 것이었습니다. 그날 저녁에는 에이전트가 물은 3D 방식, 세대(MQ4), 좌석 구성, 1차 배포를 골랐습니다. 다음 날 아침에는 문서가 남긴 확인 사항 세 가지에 모두 동의하면서 초점을 하나로 정했습니다. 정말 내 트렁크에 짐이 들어가는지를 보여 주는 것이고, 컨셉과 수익 모델은 그다음입니다. 9월 17일 저녁에는 짐을 실은 뒤 테일게이트가 닫히지 않는 경우를 따로 봐 달라고 했고, 9월 19일 아침에는 실기기 테스트보다 폰 화면 UI를 먼저 맞추자고 정했습니다.

3D 방식은 분석 문서가 놓은 네 갈래 중에서 골랐습니다.

9월 17일 아침 커밋 네 개가 렌더러(오빗 카메라, 가림 정렬, 레이캐스트 조작)와 자동 배치 엔진을 새로 쓰고 고정 시점 페인터 3,133줄을 지웠습니다. 살린 것은 도메인 모델, 충돌 판정기, 장비 DB, 저장소였습니다.

실측 8건, 861 L에서 950 L로

기아 국내 카탈로그와 제원표에는 트렁크 치수가 아예 없고, 해외 자료도 용량(L)만 적습니다. 그래서 선형 치수는 공개된 줄자 실측 8건(국내 6, 해외 2)과 제조사 도면으로 교차검증했습니다(08a97ab). 새로 채택한 값은 최대 폭 1.38 m(휠하우스 사이 1.09), 깊이 1.07 m, 높이 0.82 m에서 개구부 쪽 0.79 m입니다. 닫힌 테일게이트 안쪽 면, 2열 등받이 기울기, 개구부 크기를 모델에 넣자 실사용 부피는 직육면체 1,211 L의 71%인 약 861 L가 됐고, 4인 가족 짐은 강체 기준 16개 중 15개가 들어갔습니다.

이 첫 모델은 실제보다 비관적이었습니다. 독일 자동차 클럽 ADAC는 2열 뒤 천장까지 980 L로 측정했고, 공개된 캐리어와 골프백 적재 사례도 모델보다 많이 실었습니다. 9월 18일 이 사례들을 검증 테스트로 옮기고 좁은 구간과 등받이 기울기를 다시 맞춰 약 950 L로 보정했습니다(b9435a5). 9월 17일 모델 기준으로는 2열을 13cm 앞으로 밀면 16개가 모두 들어갔고, 판정 화면이 그 제안을 냅니다(925131c).

장비 DB를 제조사 스펙과 대조하니 치수가 10% 넘게 틀린 항목이 24개, 존재하지 않는 제품명이 14개였고, 이를 고치고 중복 2개를 지워 DB는 198개가 됐습니다(925131c).

테스트가 찾은 버그 26개와 UI 9건

범위를 좁힌 뒤인 9월 18일 테스트를 194개에서 530개로 늘리는 동안 패커 버그 5건과 UI 버그 21건이 나왔고 모두 고쳤습니다. 이어서 들어간 렌더러 테스트(5dce730)는 그려진 벽과 천장이 충돌 판정의 경계와 1cm 안에서 맞는지를 물었고, 그림과 물리가 어긋난 곳 6건을 찾았습니다.

같은 날 밤 픽셀 단언 기반 Playwright 스펙 32개를 더해 브라우저 E2E가 36개가 됐고(798c88e), 실제 웹 빌드에서 9건이 걸렸습니다. 못 넣은 짐이 트렁크 밖에 세워져 있는데도 상태 표시가 초록색 "테일게이트 닫힘 OK"였고, 폰 가로 화면에서는 짐 목록이 0줄이었습니다.

9월 20일 폰 UX 라운드에서는 실제 빌드 스크린샷 133장을 보고 리뷰 17건 중 16건을 고쳤습니다(99e8388). 그중 하나는 "들어갈까?" 버튼이었습니다. 화면에 놓인 배치를 판정해야 할 버튼이 가상으로 다시 배치한 결과를 판정하고 있었습니다.

실행되지 않은 서브에이전트 수정

웹 localStorage에 JSON이 아닌 자동 저장 값({{{ 같은 것)이 남은 경우를 처리하는 일에서, 서브에이전트는 읽기가 예외를 던진다는 전제로 읽기 예외를 잡는 catch 블록에서 손상된 저장을 지우게 했습니다(b9435a5).

이 앱이 쓰던 shared_preferences_web 2.4.3의 소스를 열면 값을 읽는 _decodeValue가 FormatException을 잡고 null을 돌려줍니다. 깨진 값은 예외 없이 건너뛰어 "저장 없음"으로 보이고, catch 블록은 실제 빌드에서 한 번도 실행되지 않았습니다. 이것을 드러낸 것은 Playwright persistence 스펙의 콘솔 줄 "값은 시작 시 지워지지 않았다"였습니다. 수정본(51288eb)은 예외 여부와 상관없이 시작할 때 이 앱의 키 중 JSON으로 읽히지 않는 값을 localStorage에서 바로 지우고, E2E가 시작 직후 지워졌는지 단언합니다.

수정본의 주석에 따르면 옛 버전은 getInstance() 자체가 실패했고, 서브에이전트는 그 옛 동작을 전제로 삼았습니다.

9월 16일 분석 문서는 좌표 클릭 E2E를 Flutter 시맨틱스 기반으로 바꾸자고 했지만, 웹에서 시맨틱스를 강제로 켜자 포인터 입력이 막혔습니다. 좌표 클릭은 그대로 두고, 좌표는 Flutter 화면 테스트에서 버튼의 rect를 찍어 얻습니다.

숫자를 낸 코드부터 여는 점검

에이전트가 스스로 매긴 유사도 %는 지표로 쓰지 마십시오. 그 숫자를 계산하는 코드와 그 코드의 입력을 열어 보기 전에는 진척으로 세지 않습니다.

  1. 보고의 %마다 그 지표를 계산하는 함수를 찾아 직접 실행하고, 같은 숫자가 나오는지 봅니다. 함수가 없거나, 상수를 돌려주거나, 실행해도 그 숫자가 안 나오면 그 숫자는 메시지에만 있습니다.
  2. 채점 함수가 무엇을 입력으로 받는지 봅니다. 화면이나 실제 출력을 읽지 않고 자기 상수나 키 존재를 세면 지표가 아닙니다.
  3. 목표를 동작 문장으로 다시 적습니다. "카메라를 돌릴 수 있다", "짐 16개 중 몇 개가 충돌 없이 놓인다", "테일게이트가 닫힌다"처럼 틀릴 수 있는 문장이어야 합니다.
  4. E2E의 이미지 비교 코드에서 베이스라인 파일이 없을 때 무엇을 하는지 찾습니다. 이 앱의 비교 헬퍼는 if (!fs.existsSync(baselinePath)) 분기에서 지금 화면을 저장하고 match: true를 돌려줬습니다.
  5. 서브에이전트가 플러그인 동작을 근거로 고친 코드는 pubspec.lock에서 그 패키지의 version을 읽고, pub cache의 hosted/pub.dev/<패키지>-<버전>/lib/에서 해당 함수를 열어 그 경로가 실제로 실행되는지 확인합니다.
  6. 실제 빌드 E2E에 상태 단언을 하나 이상 넣습니다. 이 앱은 짐이 트렁크 밖에 있으면 패널 상태가 초록이 아니라 주황이어야 한다는 것과, 손상된 저장이 시작 직후 지워져 있어야 한다는 것을 단언합니다.
# 1) 보고된 지표 이름으로 계산 코드가 든 파일 찾기
git grep -l -i -E "similarity|realism" <커밋> -- '*.dart' '*.ts'
# 2) 그 파일에서 상수를 그대로 돌려주는 줄 세기
git grep -c -E "return [0-9]+\.[0-9]+;" <커밋> -- <채점 파일>
#    이 앱: 검증 러너 15줄, 분석기 9줄(가드 7줄, 투영 오차 구간 점수 100.0·0.0 2줄)
# 3) 보고와 같은 커밋에서 채점 코드가 함께 들어왔는지
git log --diff-filter=A --format="%h %ad %s" --date=iso -- <채점 파일>
#    이 앱: 러너는 2c23d67(95.2% 보고), 분석기는 52ca7a8(90% 보고)

실차 실측은 아직 없습니다

쏘렌토 치수는 공개된 실측과 적재 사례로 맞춘 값이고, 실차를 직접 줄자로 확인한 값은 아직 없습니다. 골프 세트 사례는 실제로 11개가 모두 실렸는데 모델은 10개만 넣어, 위층 깊이가 1~2cm 모자란 보수적 오차가 남았습니다.

이 점검은 맞혀 볼 정답이 있는 곳에서만 듣습니다. 짐이 들어가는지, 문이 닫히는지는 실측과 사례로 맞춰 볼 수 있지만, "트렁크처럼 보이는가"에는 지금 점수가 없고 사람이 스크린샷을 보고 정합니다.

남은 확인: 6개 차종의 적재 사례 수

11월 1일 커밋(072406d)에서 차종이 7종으로 다시 늘었고, 차종 메뉴에는 "실측 검증"과 "제원 기반 추정"이 따로 표시됩니다. 쏘렌토에 한 교차검증을 나머지 6종에도 같은 깊이로 했는지는 이 글을 쓰면서 확인하지 않았습니다.
