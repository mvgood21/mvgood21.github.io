클로드 코드 예약 실행 멈춤: 회차가 남긴 상태

클로드 코드 예약 실행 하네스에서 exit 0으로 끝난 회차가 남긴 파일 두 개가 다음 회차들을 막았고, 이제 다음 회차는 이를 보존 브랜치로 옮기고 진행합니다.

작성 Stephen · 에이전트와 일하는 법 · 읽는 시간 11분 · 최종 업데이트 2026년 11월 21일

클로드 코드(Claude Code)를 매일 정한 시각에 사람 없이 돌리는 하네스에서, 한 회차가 정상 종료(exit 0)로 끝났는데 같은 앱의 다음 회차들이 시작조차 못 했습니다. 그 회차가 일을 덜 끝낸 채 파일 두 개를 고쳐 둔 상태로 끝났고, 다음 날 저녁부터는 다른 원인이 겹쳐 그 앱은 사흘 동안 돌지 못했습니다. 일주일 뒤에는 하루 사이 소셜 게시 회차 4번이 한 건도 올리지 못했는데, 이때도 종료 코드는 모두 0이었습니다.

두 사건 모두 회차는 정상 종료했고, 다음 회차를 막은 것은 회차가 남긴 상태, 곧 작업 트리와 브라우저 연결이었습니다.

목차 (7)
  1. 커밋하고 10분 뒤 하위 에이전트가 멈췄습니다
  2. 한글 앱만 30시간 먼저 멈췄습니다
  3. 다음 회차의 기록도 틀렸습니다
  4. 소셜 회차 4번이 다른 브라우저만 보고 끝났습니다

  7. 끊긴 브라우저는 여전히 사람이 붙입니다

커밋하고 10분 뒤 하위 에이전트가 멈췄습니다

11월 3일 오전 9시 5분, 한글 맞춤법 앱의 아침 작업(데일리)이 시작됐습니다. 이 작업은 claude -p로 실행되는데, -p는 대화 창 없이 지시 하나를 처리하고 끝나는 모드입니다. 에이전트는 9시 11분에 그날 점검 결과를 커밋 890de43으로 올렸고, 쇼츠 영상 두 편을 만드는 일은 하위 에이전트(subagent)에게 맡겨 백그라운드로 돌려 두었습니다. 마지막 답은 이랬습니다. "커밋 890de43 push 완료. 영상 생산 에이전트가 끝나면 독립 심사 → 큐 등록 → Notion 보고로 이어갑니다."

로그의 다음 줄은 Claude Code가 직접 찍은 안내입니다.

그때 버전의 -p는 마지막 턴 뒤 10분이 지나도 백그라운드 작업이 돌고 있으면 그 작업을 멈추고 끝났습니다. 안내 문구에는 끝까지 기다리게 하는 환경 변수 CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0도 적혀 있었습니다. 회차는 커밋 10분 7초 뒤 정상 종료로 기록됐습니다. 멈춘 하위 에이전트는 영상 생성기 코드와 생산 기록 CSV를 고치던 중이었고, 그 두 파일이 커밋되지 않은 채 작업 트리에 남았습니다.

한글 앱만 30시간 먼저 멈췄습니다

하네스는 회차를 시작하기 전에 준비 단계(prepare)에서 작업 트리를 검사합니다. 커밋되지 않은 변경이 있으면 DirtyWorktree로 거부하고 exit 3으로 끝납니다. 당시 설명서는 이 경우 자동으로 지우지 않는다고 적고 있었습니다. 같은 날 14시 한글 앱 소셜 회차가 처음 거부됐고, 이 원인으로만 회차 4번이 시작하지 못했습니다.

11월 4일 저녁부터는 원인이 하나 더 겹쳤습니다. 하네스 자체 코드에 커밋하지 않은 편집이 남아 모든 앱의 예약 작업이 약 38시간 멈췄습니다. 이 정지는 클로드 코드 매일 예약 실행: 윈도우 작업 스케줄러에 따로 적어 두었습니다. 11월 5일과 6일 아침 알림은 세 앱 모두 "exit 3 준비(prepare) 실패" 한 줄이었습니다. 이것만 보면 하네스가 한 번 크게 멈춘 사고로 보입니다.

게임과 유틸 앱은 11월 4일 저녁 회차 전까지 정상으로 돌았고, 한글 앱만 그보다 30시간 앞선 11월 3일 14시부터, 다른 원인으로 멈춰 있었습니다. 하네스 코드를 커밋해 정지를 풀었더라도 한글 앱 작업 트리에는 두 파일이 그대로 있었을 것입니다. 당시 하네스 설명서는 "DirtyWorktree로 exit 3을 내면 그 레포 작업은 다음 날에도 계속 멈춘다. 자동으로 지우지 않으므로 직접 정리한다"고 적고 있었습니다. 11월 4일 아침 알림에는 한글 앱의 실패만 있었지만 이유는 빠져 있었습니다.

결과는 저장소에 그대로 남았습니다. 한글 앱 저장소의 커밋은 11월 3일 1개, 4일과 5일 0개였고, 이 사이 영상 생산과 게시도 0건이었습니다.

다음 회차의 기록도 틀렸습니다

11월 6일 아침, 남아 있던 두 파일의 변경은 별도 브랜치에 커밋으로 보존됐고(004f642), 1분도 안 돼 하네스 실행기에 하위 에이전트를 끝까지 기다리는 설정이 들어갔습니다(1ac160a). 몇 분 뒤 예약 실행기가 한글 앱 데일리를 다시 돌렸고 정상으로 끝났습니다. 보존 커밋은 대화 세션이 만든 것이지만, 어떤 대화였는지와 그 전에 누가 그날 실행 상태를 되돌렸는지는 기록에 없습니다.

다시 시작한 회차는 공백을 이렇게 적었습니다. 남은 변경이 "11-06 시작 전에 원복된 것으로 보이며 q005·q006 mp4만 남음". 실제로는 변경이 별도 브랜치로 옮겨진 뒤 작업 트리가 원래 커밋으로 돌아간 것입니다. 그 회차의 커밋 e795981도 11월 3일 커밋 바로 위에 올라갔고, 보존 브랜치와는 이어지지 않았습니다. 11월 6일 회차가 본 것은 작업 트리와 앱 기록뿐이었고, 보존 브랜치는 어디에도 적혀 있지 않았습니다.

이 글과 비슷한 문제를 겪고 있다면 메일로 상황을 알려 주세요. 읽고 답하겠습니다. 메일로 문의하기

소셜 회차 4번이 다른 브라우저만 보고 끝났습니다

두 번째 사건은 11월 11일 저녁에 시작됐습니다. 소셜 게시 회차는 Claude in Chrome 확장으로 하네스 전용 Chrome을 움직여 틱톡, 인스타그램, 유튜브에 올립니다. 그날 저녁 첫 회차는 정상으로 올렸지만, 다음 회차부터 다음 날 저녁까지 세 앱의 소셜 회차 4번이 "연결된 브라우저는 Browser 1뿐"이라며 한 건도 올리지 못했습니다. 연결된 Chrome에서 틱톡을 열면 로그인 화면이 나왔습니다. 하네스 브라우저가 아니었습니다.

이때 규칙은 연결된 브라우저 목록에서 하네스 브라우저의 기기 ID(연결 목록에 브라우저마다 나오는 고유 값)를 찾고, 없으면 다른 브라우저를 고르지 말고 건너뛰라고 했습니다. 소셜 회차들은 그 규칙대로 Browser 1을 쓰지 않았습니다. 하지만 규칙은 "브라우저가 여러 대 연결돼 있고 선택되지 않았다"는 오류가 날 때 고르는 법만 다뤘고, 브라우저가 한 대만 연결돼 있으면 도구는 묻지 않고 그 브라우저로 갔습니다(하네스 기록). 11월 12일 밤 색인 작업은 이 길로 다른 계정의 Chrome에서 Search Console을 열었습니다. 규칙과 보고는 하네스 브라우저를 "Browser 2"라고 불렀지만 이 이름은 연결 순서로 붙어서, 다시 연결한 다음 날 아침에는 하네스 Chrome이 "Browser 1"이었습니다.

그날 밤 하네스 규칙이 바뀌었습니다(e9fc042). 첫 Chrome 단계 전에 연결 목록을 먼저 부르고, 기기 ID만 보고, 그 ID가 없으면 Chrome 도구를 하나도 부르지 않습니다. 규칙이 바뀌기 몇 분 전 회차는 하네스 브라우저가 다시 연결돼 있었다고 적었습니다. 누가 어떻게 다시 붙였는지는 기록에 없습니다.

게임과 유틸 회차는 실패한 채널을 게시 예정 목록(큐 표)에 "2026-11-12 20 인스타 실패: Chrome 연결 안 됨"처럼 적고 커밋했습니다. 다음 회차는 그 칸부터 채웠습니다. 유틸 앱은 11월 13일에 빈 두 채널을 채웠고, 게임은 11월 14일까지 계획했던 세 채널을 모두 올렸습니다. 한글 앱 회차는 큐를 고치지 않고 끝나 커밋이 없었고, 다음 날 데일리는 "11-12 14시 한글 소셜 게시 기록·커밋 없음"이라며 판단을 미뤘습니다.

남은 변경은 보존하고, 브라우저는 기기 ID로만 고릅니다

남은 변경을 지우고 진행하위 에이전트가 고친 생성기 코드가 사라짐쓰지 않음
보존 브랜치에 커밋하고 기준 커밋으로 돌린 뒤 진행(11-07)같은 작업 트리를 쓰는 작업은 한 번에 하나만 돌게 막아 두므로, 남은 변경은 죽은 이전 회차의 것으로 봄채택

예약 실행에서 하위 에이전트를 쓴다면 지시문 규칙만 믿지 마십시오. 기다림은 실행기 설정으로, 정리는 다음 회차의 준비 단계로 강제합니다.

회차 끝과 시작에 둘 검사

하네스는 이제 회차가 남긴 작업 트리를 다음 회차의 준비 단계에서 보존 브랜치로 옮기고, 브라우저 연결을 첫 Chrome 단계 전에 검사하고, 못 한 일은 다음 회차가 읽는 파일에 남깁니다. 아래는 여기에 회차 끝 검사를 더한 순서입니다(2번은 이 하네스에 아직 없습니다).

  1. 실행기 환경에 CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0을 넣고, 작업마다 시간 한도를 정합니다. 로그에서 Background tasks still running 줄이 보이면 그 회차는 일을 덜 끝낸 것입니다.

  2. 회차가 끝난 뒤 git status --porcelain이 비어 있고 push하지 않은 커밋이 없을 때만 완료로 셉니다. 남은 것이 있으면 파일 목록을 실패 이유로 적습니다.

  3. 다음 회차의 준비 단계에서 작업 트리가 더러우면 지우지 말고 harness-rescue/<시각>-<작업> 같은 브랜치에 커밋해 보존하고, 기준 커밋으로 돌린 뒤 진행합니다. 알림에는 파일 목록과 브랜치 이름을 넣습니다.

  4. 브라우저가 필요한 작업은 첫 Chrome 단계 전에 Claude in Chrome의 list_connected_browsers 도구를 부르고, 기대하는 기기 ID가 있을 때만 select_browser로 고릅니다. 없으면 Chrome 도구를 하나도 부르지 않습니다. 표시 이름은 보지 않습니다.

  5. 못 한 일은 다음 회차가 읽는 파일에 "날짜 시각 채널 실패: 이유"로 적고 커밋합니다. 다음 회차는 그 칸부터 합니다.

하네스 없이 작업 스케줄러에서 claude -p를 바로 부른다면, 실행 스크립트 앞뒤에 1~3번을 아래 정도로 넣으면 됩니다. 보존과 완료 판정 부분은 11월 21일 임시 저장소에서 PowerShell 5.1로 돌려, 남은 파일 두 개가 보존 브랜치로 옮겨지고 트리가 비는 것과, 고친 파일이나 push하지 않은 커밋이 있으면 exit 4로 끝나는 것을 확인했습니다.

$env:CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS = '0'

# 시작 전: 남은 변경은 지우지 않고 보존 브랜치로
if (git status --porcelain) {
  $b = "harness-rescue/$(Get-Date -Format yyyyMMdd-HHmm)-daily"
  git switch -q --create $b
  git add -A
  git commit -q -m "rescue: leftovers from the previous run"
  git switch -q -
}

claude -p "..."

# 끝난 뒤: 트리가 비고 push 안 한 커밋이 없을 때만 완료
if ((git status --porcelain) -or (git log '@{u}..' --oneline)) { exit 4 }

git add -A는 추적하지 않는 새 파일도 담으므로, 영상 같은 큰 생성물은 먼저 .gitignore에 넣습니다. 추적 브랜치(upstream)가 없는 브랜치에서는 마지막 줄의 push 검사가 빠지므로 먼저 git push -u로 연결해 둡니다. 판정 줄을 보고서 끝에 쓰는 방법은 Claude Code 하네스 17일 운영과 시작 순서에 있습니다.

끊긴 브라우저는 여전히 사람이 붙입니다

끝까지 기다리면 회차가 길어지고, 시간 한도에 걸리면 실행기가 프로세스를 끊어 같은 잔재가 생길 수 있습니다. 그때는 다음 준비 단계가 보존 브랜치로 옮기지만, 보존이 실패하면(커밋 hook 등) 예전처럼 멈춘 채로 남습니다. 보존 브랜치는 쌓이므로 사람이 지워야 합니다.

자동 보존은 남은 변경이 죽은 이전 회차의 것이라는 전제로 돌아갑니다. 사람이 예약 실행과 같은 작업 트리에서 편집하면 그 편집도 보존 브랜치로 옮겨지므로, 운영용 작업 트리는 따로 두어야 합니다. 이 하네스는 사람 작업 트리와 다른 운영용 사본에서 돌아갑니다.

기기 ID 검사는 잘못된 브라우저로 가는 것을 막을 뿐, 끊긴 연결을 다시 붙이지는 못합니다. 11월 12일 하루 동안 "Chrome 확장 연결 확인"을 요청하는 알림이 여러 번 나갔고, 다시 연결된 것은 그날 밤이었습니다. 회차의 종료 코드도 여전히 0이라, 11월 11일과 12일 하루 상태판은 "실패·빠짐 0건"으로 보고하고 이 회차들은 "일부 실패"로 집계했습니다. 다음에 확인할 것은 연결이 끊긴 원인과, 대기 시간 10분이라는 기본값이 이후 Claude Code 버전에서도 같은지입니다.
