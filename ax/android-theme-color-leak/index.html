XML 어디에도 흰색이 없는데 다이얼로그 글자가 사라졌다: 테마 색이 새는 자리 3곳

Android 다이얼로그나 하단 시트의 버튼 글자가 안 보이면, 앱바용 테마 색이 새는 경우가 많습니다. 그 창에만 테마를 덮고, 대비는 띄운 화면에서 재십시오.

글자 대비를 재는 검사 1/3

한글 띄어쓰기 앱의 삭제 확인 창에서 취소·확인 버튼 글자가 흰 바탕 위에 거의 흰색으로 그려졌습니다. 대비(명암비)는 1.02:1로, 보통 글자에 요구하는 4.5:1에 한참 못 미쳤습니다. 2026년 9월 16일 이걸 고칠 때 레이아웃 XML 어디에도 흰 글자는 없었고, 앱바를 밝게 칠하려고 정해 둔 테마 색이 버튼 글자색으로 흘러 들어가 있었습니다.

고친 뒤 열하루 만에 새로 만든 하단 시트 두 곳에서 같은 색이 다시 나왔고, 이번에는 릴리스 빌드를 올린 갤럭시 S21 실기기에서야 보였습니다. 첫 수정은 다이얼로그만 덮었고, 교정 시트의 테스트는 글자색이 정해 둔 색과 같은지만 확인했으며 미니창 테스트는 색을 보지 않았습니다. 앱바 색을 테마 기본 색으로 정해 둔 앱이라면 다이얼로그나 시트를 새로 만들 때마다 같은 자리로 샐 수 있습니다.

앱바 색이 버튼 글자로 간 자리는 세 곳이었습니다

9월 16일 13시 25분, 운영자가 활동 내역 삭제 팝업의 버튼 글자가 라이트 모드에서 흰색이라 안 보인다고 알려 왔습니다. 에이전트(Claude)가 구글의 UI 라이브러리 Material Components 1.14.0의 스타일 정의를 따라가 보니, 버튼 글자색은 아래 순서로 테마 속성 하나에 닿았습니다.

AlertDialog 버튼
  → buttonBarButtonStyle
  → Widget.MaterialComponents.Button.TextButton
  → mtrl_text_btn_text_color_selector (활성 상태 색)
  → ?attr/colorPrimary

colorPrimary는 테마가 정하는 기본 색 자리이고, 이 앱의 앱 테마(AppTheme)가 여기에 넣어 둔 값은 앱바 색(라이트 #fafdff, 다크 검정)입니다. 다크에서는 흰 다이얼로그 위 검은 글자가 21:1로 잘 보였기 때문에 라이트에서만 문제가 났습니다.

전역 colorPrimary를 바꾸면 앱바 색까지 바뀌어서 그 방법은 버렸습니다. 앱 액센트 파랑으로 덮는 안도 흰 바탕에서 3.80:1이라 기준에 못 미쳤습니다. 첫 수정은 다이얼로그 창에만 씌우는 테마 오버레이 alertDialogTheme을 라이트·다크 양쪽에 걸고, 그 안의 colorPrimary 하나만 더 진한 파랑으로 덮었습니다. 오버레이의 부모는 원래 쓰던 다이얼로그 테마 그대로입니다.

9월 27일에 들어온 두 화면은 다른 경로로 같은 색을 받았습니다. 색칠된 교정 어절을 누르면 뜨는 교정 시트와 텍스트 선택 메뉴의 미니창은 둘 다 화면 아래에서 올라오는 BottomSheetDialog인데, 내용 뷰를 액티비티 컨텍스트로 부풀렸습니다(inflate: 레이아웃 XML을 뷰 객체로 만드는 일). 그러면 뷰는 시트의 테마 오버레이를 거치지 않고 액티비티의 AppTheme에서 바로 colorPrimary를 읽습니다. "왜 틀렸나요?" 채움 버튼의 바탕과 "확인", "교정문 복사", "앱에서 열기"의 글자가 #fafdff가 되어, 흰 시트 위에서 1.00~1.02:1이었습니다.

다크 모드는 원인이 하나 더 있었습니다. 이 앱의 다크 AppTheme도 부모가 밝은 테마(Theme.MaterialComponents.Light)여서, 교정 시트는 다크에서도 흰 바탕으로 떴습니다. 그 위에 다크용으로 밝게 잡은 교정 글자색이 얹혀 3.2:1이 됐습니다. 미니창은 반대였습니다. 바탕은 어두운 #212121인데 결과 글자는 테마 기본 글자색인 검정을 받아, 계산하면 1.30:1이었습니다.

고친 방법은 시트 내용 뷰를 시트 자신의 컨텍스트(dialog.context)로 부풀리고, AppTheme에 시트 전용 오버레이(bottomSheetDialogTheme)를 걸어 시트 바탕과 버튼 색 토큰을 따로 정하는 것이었습니다. 9월 28일 교정 시트를 먼저 고치면서 오버레이를 걸었고, 21분 뒤 미니창은 그 오버레이 아래에서 컨텍스트와 버튼 색만 바꿨습니다.

첫 테스트는 XML을 읽었고, 다시 쓴 테스트는 띄운 버튼을 읽습니다

13시 54분 첫 수정에 붙은 테스트는 리소스 XML을 글자로 읽어, 오버레이 줄이 있는지와 버튼 색 값이 흰 바탕 위 4.5:1을 넘는지를 봤습니다. 흰 글자는 실행 중에 테마가 속성을 풀 때 생기므로, XML 값을 읽는 검사에는 이 결함이 보이지 않습니다.

14시 10분 운영자가 전부 고친 게 맞는지, 배포해도 되는지 교차 검증하라고 했습니다. 그 요구를 받고서야 에이전트는 "XML에 그렇게 적혀 있다"와 "실제로 그 색이 나온다"는 다르다며 Robolectric(기기 없이 JVM에서 안드로이드 코드를 돌리는 테스트 도구) 테스트를 썼습니다. AppTheme을 씌운 컨텍스트로 다이얼로그를 만들어 show()하고, 버튼이 실제로 그리는 글자색(currentTextColor)을 읽습니다. 라이트 설정에서 오버레이 한 줄을 지우고 돌리자 아래처럼 원래 증상이 숫자로 나왔습니다.

확인 #fafdff on #ffffff = 1.02:1   FAIL
취소 #fafdff on #ffffff = 1.02:1   FAIL
다크 모드에서도 버튼이 읽힌다         pass

9월 27일 교정 시트에도 Robolectric 테스트는 있었습니다. 다만 교정 글자의 currentTextColor가 정해 둔 빨강 하이라이트 색과 같은지만 비교했습니다. 색이 맞으면 통과하므로, 그 글자가 흰 시트 위에 있든 검은 시트 위에 있든 결과가 같습니다. 9월 28일 S21 실기기 점검 뒤 고친 테스트는 띄운 시트의 실제 바탕을 먼저 읽습니다.

// 시트 바탕 뷰
val sheet = dialog.findViewById<View>(com.google.android.material.R.id.design_bottom_sheet)
// 시트 배경 도형의 채움색 = 실제 바탕색
val bg = (sheet.background as MaterialShapeDrawable).fillColor!!.defaultColor
check("교정(유형 색)", dialog.findViewById<TextView>(R.id.correction_corrected).currentTextColor, bg, 4.5)

이 방식으로 시트의 글자와 버튼을 라이트·다크에서 모두 재고, 채움 버튼은 글자 대 버튼 바탕 4.5:1과 버튼 바탕 대 시트 3:1을 따로 봅니다. 테마 색 결함은 띄운 화면의 currentTextColor와 그 뒤에 깔린 실제 바탕으로 재십시오.

이 글과 비슷한 문제를 겪고 있다면 메일로 상황을 알려 주세요. 읽고 답하겠습니다. 메일로 문의하기

하이라이트는 색조를 두고 명도만 움직였습니다

다이얼로그 제보 4분 전에 에이전트가 먼저 짚은 문제는 오류 유형을 색으로 구분하는 맞춤법 하이라이트였습니다. 빨강은 맞춤법, 청록은 띄어쓰기, 파랑은 통계 기반 교정, 주황은 표준어 의심, 보라는 네이버 검사 결과가 따로 보라로 표시하는 유형입니다. 다크 모드용 색 폴더(values-night)에 이 다섯 색이 하나도 없어서 다크에서도 라이트 값이 그대로 쓰였고, 다크 바탕 #212121 위 보라는 2.70:1이었습니다.

13시 21분, 더 테스트할 것이 없느냐는 운영자 물음에 에이전트는 이 보라를 꼽고, 고친다면 다크용 밝은 보라 한 줄이면 된다고 했습니다. 대비로는 충분한 색이지만, HSL로 풀면 색상각이 5도 가까이 돌고 채도가 100%까지 올라가 다른 보라가 되는 값입니다. 운영자가 제대로 고치라고 하자, 에이전트는 다크용 다섯 색을 새로 넣었지만 라이트에서는 주황 하나만 바꾸고 빨강·청록은 익숙한 색이라며 파랑과 함께 그대로 두었습니다.

13시 40분 4.5:1 기준으로 만든 테스트가 셋 다 걸렀고, 에이전트는 "테스트가 제 판단을 반박했습니다"라고 보고했습니다. 출력의 temp1은 파랑, temp2는 청록, temp4는 빨강입니다.

light/temp1 #3982ff on #fafdff = 3.54:1
light/temp2 #009a9a on #fafdff = 3.38:1
light/temp4 #ee4b4b on #fafdff = 3.58:1

라이트 보라와 다크 주황만 그대로 두고, 나머지 8칸(기준 아래 7칸과 4.67:1로 여유가 없던 다크 청록)은 색상각을 고정한 채 명도를 옮겼습니다. 라이트는 어둡게, 다크는 밝게 옮겼고, 다시 계산해 보면 색상각이 가장 많이 돈 파랑도 0.2도입니다. 처음에는 4.5:1에 딱 맞춘 값을 계산했다가, 다크는 여유를 두려고 5.0:1을 목표로 다시 잡았습니다.

첫 수정 커밋 본문은 이 결정을 "빨강은 빨강, 초록은 초록으로 남는다"고 적었습니다(이 초록이 위의 청록입니다). 의미가 붙은 색은 색조를 돌리지 마십시오. 명도만 움직이고, values와 values-night 양쪽에 값을 두십시오. 웹 쪽에서 같은 생각으로 다크 글자색을 명도 1%씩 올려 찾는 방식은 색 대비 4.5:1을 빌드 게이트로 재기에 적었습니다.

띄운 화면에서 대비를 재는 순서

  1. 안 보이는 글자의 색을 스타일 정의 끝까지 따라가, 끝에 닿은 테마 속성(?attr/colorPrimary 등)에 다른 용도의 색이 들어 있지 않은지 봅니다.
  2. 전역 테마 색은 두고 그 창에만 오버레이(alertDialogTheme, bottomSheetDialogTheme)를 겁니다. 내용 뷰는 dialog.context로 부풀립니다. 다이얼로그 쪽은 이렇게 걸었습니다. 
    <!-- AppTheme 안(values, values-night 양쪽) -->
<item name="alertDialogTheme">@style/AlertDialogTheme</item>

<style name="AlertDialogTheme" parent="ThemeOverlay.MaterialComponents.Dialog.Alert">
    <item name="colorPrimary">@color/dialog_button_text</item> <!-- #0063c6 -->
</style>
  3. 매니페스트에 적힌 테마마다 오버레이가 걸렸는지, parent="Theme.…"로 점 앞 테마와 끊기지 않았는지 봅니다.
  4. 의미 색은 HSL 색상각을 고정하고 명도만 옮겨, 라이트·다크 값을 따로 찾습니다.
  5. Robolectric으로 화면을 show()한 뒤 currentTextColor와 실제 바탕색(시트는 MaterialShapeDrawable의 fillColor)의 대비를 라이트·다크에서 측정합니다.
  6. 수정을 한 줄 되돌려 테스트가 원래 숫자(이번에는 1.02:1)로 실패하는지 봅니다. 9월 16일에는 이런 되돌리기 6건을 넣어 모두 잡히는 것을 확인했습니다.
  7. 릴리스 APK를 실기기에 올려 새 화면을 라이트·다크로 한 번 엽니다.

측정 테스트는 화면마다 따로 써야 해서, 테스트가 없는 새 화면은 9월 28일처럼 실기기에서 처음 드러납니다. 그날의 S21 점검은 에이전트 코드 리뷰, 반박을 버틴 20건만 고쳤다에 있습니다. Robolectric은 실제 기기 렌더링이 아니고, 이 앱의 화면은 XML 뷰라 Jetpack Compose 화면에는 재 보지 않았습니다.

오버레이가 닿지 않는 두 곳: NoActionBar와 프레임워크 AlertDialog

9월 16일 14시 19분, 다이얼로그 호출과 매니페스트 테마를 맞춰 보던 에이전트가 하나를 더 찾았습니다. AppTheme.NoActionBar는 이름만 보면 AppTheme의 자식이지만 정의에는 parent="Theme.AppCompat.NoActionBar"가 적혀 있습니다. Android 스타일은 parent 속성을 적으면 점 앞의 이름으로 상속하지 않으므로, 이 테마에는 두 오버레이가 하나도 걸려 있지 않습니다.

이 테마를 쓰는 화면은 앱 시작 화면 하나입니다. 거기 뜨는 버전·권한 팝업은 자체 레이아웃으로 만든 창이라 colorPrimary 경로를 타지 않고, 그래서 아직 샌 적이 없습니다. 앱 1.6.018 버전의 변경 기록(CHANGELOG)은 이 화면에 AlertDialog를 추가하면 수정이 적용되지 않는다고 적어 두었고, 11월 10일 원격 개발 브랜치에서도 parent는 그대로입니다.

9월 16일 점검표는 다이얼로그를 만드는 세 곳(활동 내역 삭제, 인사카드 화면, 구독 화면)이 모두 AppTheme 아래라 덮였다고 적었습니다. 그런데 androidx 다이얼로그는 제보가 온 활동 내역뿐이었고, 나머지 둘은 안드로이드 프레임워크 기본 클래스 android.app.AlertDialog였습니다. 인사카드 호출은 그 뒤 없어졌지만, 11월 10일 원격 개발 브랜치에는 구독 화면의 한 곳(구독을 둘 이상 가진 경우에만 뜨는 분기)이 아직 프레임워크 클래스입니다. 9월 16일의 측정 테스트가 띄우는 것은 androidx 다이얼로그라, 이 한 곳의 버튼 색은 아직 재 보지 않았습니다.

기준일 2026년 11월 11일. 한글 띄어쓰기 앱 저장소의 git 기록과 1.6.018 변경 기록, 9월 16일 작업 세션 기록을 바탕으로 썼고, 대비는 WCAG 상대 휘도 식으로 다시 계산했습니다. 현재 상태는 11월 10일 원격 개발 브랜치 기준입니다.
