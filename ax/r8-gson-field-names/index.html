단위 테스트 203개가 놓친 릴리스 전용 빈 값: R8과 Gson 필드 이름

@SerializedName이 없는 Gson 필드는 R8이 이름을 바꾸면 예외 없이 빈 값으로 남아, 릴리스 산출물을 직접 열어 봐야 드러납니다.

작성 SugarMount · Android 개발 · 읽는 시간 12분 · 최종 업데이트 2026년 11월 7일

한글 띄어쓰기 앱의 두 번째 맞춤법 경로(첫 경로가 실패하면 Chat 모드가 넘어가는 폴백)는 릴리스 빌드에서만 교정문을 공백으로, 오류 개수를 0으로 돌려줄 상태였고, 예외는 나지 않았습니다. 2026년 9월 14일 이 결함을 찾았을 때 단위 테스트 203개는 전부 통과하고 있었습니다. R8이 Gson 필드 output과 etype을 a와 b로 바꾼 것이 원인이었고, 커밋 3791c2c가 @SerializedName과 불변식 테스트를 넣었습니다.

근거: 앱 저장소(sugarspeller)의 git 기록과 CHANGELOG, 세션 기록, 2026-10-09 빌드 1.6.026 APK와 mapping.txt, 2026-11-04 재현.

이름이 바뀐 필드에서 Gson은 예외를 내지 않습니다

Gson은 @SerializedName이 없으면 Java 필드 이름을 JSON 키로 씁니다. R8은 응답 모델 Result의 필드 이름을 아래처럼 바꾸었습니다.

# 3791c2c 직전 release mapping.txt, 2026-09-14
output -> a
etype  -> b

서버는 그대로 "output"과 "etype"을 보내는데 객체에는 a와 b뿐이니, Gson은 맞는 필드가 없는 키를 그냥 넘어가고, 필드에는 초기값 ""이 남습니다.

단위 테스트는 R8을 거치지 않은 클래스로 돌기 때문에 이름이 바뀐 필드를 만나지 못합니다. 203개는 3791c2c 직전 커밋의 @Test를 다시 센 값입니다(CHANGELOG에는 "200여 개"). 필드는 2024-06-14 경로 추가 때부터 애노테이션 없이 있었지만, 이 경로는 응답 자체를 못 받고 있다가 2026-09-13 커밋 0b74357에서야 살아났습니다. 0b74357과 3791c2c는 하루 차이로 함께 1.6.017에 들어갔습니다. 그 전에 경로가 살아 있던 기간에 사용자가 빈 결과를 봤는지는 기록에서 확인하지 못했습니다.

mapping.txt가 가리킨 14개 중 결함은 2개였습니다

찾는 데는 28분이 걸렸습니다. 9월 14일 20시 50분 운영자가 "문제 없는지 교차 검증"을 요청했고, 에이전트는 앱과 같은 요청을 실서버에 보내 13/13을 통과시킨 뒤 proguard 규칙을 읽다가 애노테이션 없는 모델 필드를 의심했습니다. 클린 릴리스 빌드의 mapping.txt에서 스크립트로 모델 필드 19개를 대조하자 14개가 이름이 바뀐 것으로 나왔습니다.

이름이 바뀐 필드개수판정
@SerializedName이 이미 있음5값으로 매핑되니 안전
JSON이 아니라 코드가 채움7Gson과 무관
output, etype2결함

첫 번째 경로가 릴리스에서 정상이던 이유는 절반만 이 표에 있습니다. 값을 담는 키들은 애노테이션이 있어서 이름이 바뀌어도 매핑됐습니다. 애노테이션이 없던 message와 result가 살아남은 이유는 뒤에 적었습니다. 21시 18분에 커밋한 수정은 두 경로의 필드 7개에 애노테이션을 붙였습니다. 이때 기기는 없어서 빈 화면은 mapping.txt와 dex로 판정했고, 같은 빈 값을 실행으로 본 것은 아래 재현에서입니다.

'디버그도 같은 난독화 상태'는 이틀 뒤 틀린 것으로 드러났습니다

그날 밤 계측 테스트를 더한 커밋 4d29ca4의 메시지에 에이전트는 디버그 빌드에도 minify가 켜져 있으니 "출시 빌드와 같은 난독화 상태"에서 돈다고 적었습니다.

9월 16일 8시 31분, 운영자가 KVM 권한을 열어 준 에뮬레이터(Android 14)에서 계측 테스트를 다시 돌리기 직전, 에이전트가 디버그 mapping.txt를 열었습니다. release는 output -> a인데 debug는 이름이 그대로였고, 10월 9일 빌드의 mapping.txt도 같습니다. 왜 그런지는 확인하지 못했습니다. 디버그 configuration.txt에 -dontobfuscate는 없고, 아래 재현을 R8 --debug로 돌리면 이름이 유지됐습니다.

에이전트는 릴리스 APK를 디버그 키로 서명해 설치하고, 첫 번째 경로를 에뮬레이터 hosts 파일로 막아 폴백을 유도했습니다. 8시 45분에 두 번째 경로의 교정 결과가 난독화된 빌드 화면에 나왔습니다. v16017 태그는 그보다 앞선 7시 47분에 찍혔습니다.

'lateinit이라 우연히'의 실제 이유는 keep 규칙이었습니다

틀린 설명은 3791c2c에도 있습니다. 애노테이션이 없던 필드 중 lateinit 5개는 이름이 유지됐는데, 커밋과 메모리는 이것을 "R8이 우연히 이름을 유지"라고 적었습니다. 11월에 javap로 보니 Kotlin의 lateinit var는 public 필드이고, var output = ""는 private 필드에 getter였습니다. 당시 빌드에는 쓰지도 않는 Kakao SDK용 규칙 -keepclassmembers class * { public static <fields>; public *; }가 있었고, 이 규칙이 public 필드의 이름을 붙잡고 있었습니다. 9월 25일 커밋 e05f8e3이 이 규칙을 지운 뒤(Play Console 'DEX 최적화 39%'의 범인) 1.6.026 mapping.txt에는 message -> a가 있습니다.

아래는 같은 가시성의 Java 모델을 R8 9.4.14, Gson 2.14.0, 3791c2c의 proguard 파일로 줄여 JVM에서 파싱한 재현이고, 실제 앱을 빌드한 결과는 아닙니다.

애노테이션구성결과
없음R8 없음(단위 테스트 쪽)정상
없음Kakao 규칙 + -dontobfuscate(디버그 흉내)정상
없음Kakao 규칙(9월 14일 릴리스)output=[] etype=[], 예외 없음
output, etype만Kakao 규칙정상
output, etype만Kakao 규칙 삭제JsonIOException
필드 5개 전부Kakao 규칙 삭제정상, message -> a

셋째 줄이 사고를 그대로 재현합니다. 넷째와 다섯째 줄을 보면 output과 etype만 고쳐도 9월 14일에는 통과했겠지만, 11일 뒤 Kakao 규칙이 사라지면 message 이름이 바뀌어 깨집니다. 이 재현은 모델을 코드가 생성하지 않아 JsonIOException으로 끝났습니다. 코드가 생성자를 불러 객체를 밖으로 넘기게 하면 9월 14일 구성과 최적화를 사용한 9월 20일 이후 구성 모두 NullPointerException이었습니다. 실제 앱에서 어느 예외가 날지는 빌드해 보지 않았습니다. 3791c2c가 lateinit 필드까지 애노테이션을 붙인 판단은 이유를 잘못 알고도 맞았습니다. JSON에서 값을 받는 필드에는 lateinit이든 아니든 @SerializedName을 전부 붙이십시오.

dex에 etype이 있어도 고쳐졌다는 증거는 아닙니다

수정 전 APK에서 grep -a etype은 이미 classes2.dex와 classes3.dex에 걸렸고, 모델이 든 classes4.dex에는 없다가 수정 뒤 생겼습니다. 그런데 같은 날 밤의 AAB 검사와 9월 16일 배포 직전 점검은 모든 dex를 도는 루프로 etype이 "있음"이면 통과시켰고, 보고에도 근거로 적혔습니다. 그 루프는 수정 전 APK도 통과시켰을 가짜 검사입니다.

10월 9일 빌드의 APK는 classes.dex 하나뿐이라 파일로 범위를 줄일 수도 없습니다. 문자열 43,818개를 직접 읽어 보니 etype을 포함한 문자열이 3개였고(mimetype이 든 문구, closetype, etype), output은 43개, message는 97개, result는 104개였습니다. build-tools의 dexdump -a는 애노테이션을 값까지 출력합니다.

unzip -o app-release.apk 'classes*.dex' -d dex
dexdump -a dex/classes.dex | grep -c 'value="etype"'   # 1

출력 줄은 VISIBILITY_RUNTIME Lkt1; value="etype"입니다. 애노테이션 클래스도 R8이 kt1로 바꾸어서 클래스 이름으로 찾으면 0건이 나옵니다. 이 방식으로 세면 맞춤법 응답 키 11종, 애노테이션 13건이 있습니다.

불변식 테스트는 애노테이션 하나만 떼도 실패합니다

ResponseModelSerializedNameTest는 응답 모델 8개 클래스의 모든 필드에 애노테이션이 있는지 리플렉션으로 봅니다. 아래는 그 핵심을 줄인 형태입니다.

private val models = listOf(Response::class.java, Response.Result::class.java)
private val codePopulated = setOf("com.example.Response#requestId")

@Test fun `JSON 필드에는 SerializedName이 붙어 있다`() {
    val missing = models.flatMap { type ->
        type.declaredFields
            .filterNot { Modifier.isStatic(it.modifiers) || it.isSynthetic }
            .map { it to type.name + "#" + it.name }
            .filter { (_, key) -> key !in codePopulated }
            .filter { (f, _) -> f.getAnnotation(SerializedName::class.java) == null }
            .map { it.second }
    }
    assertTrue(missing.joinToString("\n"), missing.isEmpty())
}

실제 파일은 애노테이션 값과 JSON 키 대조, 면제 목록 codePopulated(지금 10개)의 죽은 항목 검사까지 테스트 3개입니다. 에이전트는 커밋 전에 etype의 애노테이션을 지우고 돌려, 위 테스트와 키 대조 테스트 2개가 FAILED로 끝나는 것을 확인한 뒤 복구했습니다.

패키지 keep은 넣지 않았고, 계측 테스트는 디버그에서 못 봅니다

가장 넓은 대안은 모델 패키지를 통째로 -keep하는 것입니다. 3791c2c는 이것을 넣지 않았고, 당시 세션에서 따져 본 기록도 없습니다. 지금 평가하면 빈 값은 사라져도 안전이 규칙 한 줄에 달려서, 규칙이 빠지는 날 같은 사고가 되돌아옵니다.

계측 테스트는 남겨 두었지만 디버그 빌드에서 돌면 이 결함을 볼 수 없고, testBuildType을 release로 돌리는 방법은 써 보지 않았습니다. AI가 만든 Android 앱, 출시 전에 무엇을 검사하나의 R8 사고는 시작 직후 크래시였지만 이번 결함은 예외 없이 값만 비어서, 콜드 스타트 실행 검사도 통과합니다. 모델을 R8 --classfile로 줄여 JVM에서 파싱하는 재현 방식은 기기 없이 빈 값을 보여 줬지만 저장소에 넣지는 않았습니다.

릴리스 APK를 경로 끝까지 실행하는 것이 가장 강한 증거인데, 9월 16일에는 다른 확인까지 포함해 8시 23분부터 8시 46분까지 걸렸고 KVM 권한과 hosts 차단이 필요했습니다. 그래서 매 테스트에서 도는 불변식을 앞에 두고, 릴리스 APK 실행은 회귀가 의심될 때 하는 수동 절차로 문서에 남겼습니다.

fromJson 찾기부터 릴리스 APK 실행까지 점검 순서

  1. rg 'fromJson|TypeToken|GsonConverterFactory' app/src/main으로 Gson이 채우는 모델을 모읍니다. Retrofit을 쓰면 인터페이스의 반환 타입까지 따라가야 합니다.
  2. 릴리스 빌드의 mapping.txt에서 이름이 바뀐 필드를 위 표의 세 종류로 구분합니다.
  3. 불변식 테스트를 넣고 애노테이션 하나를 지워 실패를 봅니다.
  4. 키마다 dexdump -a로 value="키"를 세어 소스의 애노테이션 수와 비교합니다. dex가 여러 개면 전부 합산합니다. 1.6.026의 message는 두 모델에 있어 2건이므로, 1건 이상이면 통과로 보면 한쪽이 빠져도 모릅니다.
  5. 릴리스 APK를 디버그 키로 서명해 설치하고, 그 파서를 지나는 화면까지 갑니다. 폴백 뒤의 경로는 앞 경로를 막아야 지나갑니다.

새 모델이나 keep 규칙 삭제는 이 테스트가 못 봅니다

models는 손으로 적은 목록이라 새 응답 클래스를 빼먹으면 검사 대상이 아닙니다. 테스트는 소스 모델의 애노테이션만 보므로, 애노테이션을 보존하는 keep 규칙이 사라지거나 클래스가 abstract가 되는 경우에는 그대로 통과합니다. 그 두 경우는 5단계의 릴리스 APK 실행에서 드러납니다. 기존 두 모델은 Gson을 그대로 썼고, 맞춤법 앱에 처음 LLM을 붙였다의 설명 기능은 응답을 Map으로 받아 이 문제가 없습니다. 코드를 생성하는 직렬화 라이브러리는 써 보지 않았습니다.

테스트 주석의 틀린 문장과 수동으로 남은 dex 검사

  • 테스트 머리 주석과 메모리의 "minify가 켜진 디버그도 이름을 바꾼다", 메모리의 "lateinit은 우연히 유지"는 고쳐야 합니다.
  • 문서의 dex 확인은 아직 수동 grep입니다. dexdump -a 값 세기로 바꿔 릴리스 빌드 스크립트에 넣고, 키 목록은 테스트의 기대값에서 가져와야 합니다.
  • 이 경로를 난독화 빌드로 확인한 기기는 기록상 에뮬레이터뿐입니다. 다음 릴리스는 실기기에서 폴백까지 지나가야 합니다.

자주 묻는 질문

@SerializedName만 붙이면 keep 규칙은 필요 없나요?

Gson 버전에 따라 다릅니다. Gson 2.14.0은 jar 안의 META-INF/proguard/gson.pro가 애노테이션 달린 필드를 지키는 규칙을 넣어 줍니다. 로컬 캐시의 2.11.0 jar에는 이 파일이 있고 2.10.1 jar에는 없었습니다.

Abstract classes can't be instantiated 오류도 같은 원인인가요?

증상이 다릅니다. 이번 재현에서는 애노테이션 달린 필드가 없는 최상위 모델이 abstract 클래스가 됐고, Gson이 JsonIOException을 던졌습니다. gson.pro는 @SerializedName 필드가 있는 클래스의 <init>()을 지키는데, 그 클래스의 필드에도 애노테이션을 붙이자 오류가 사라졌습니다.
