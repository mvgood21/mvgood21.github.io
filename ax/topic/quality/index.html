짧은 답: 통과 수보다 그 테스트가 무엇을 막는지 봅니다

AI 코딩 에이전트가 "테스트를 추가했고 모두 통과합니다"라고 보고해도, 그 테스트가 무엇을 지키는지는 아무도 확인하지 않았을 수 있습니다. 2026년 9월 SugarMount의 P2P 채팅 앱(Flutter)은 테스트 3,066개가 모두 통과한 상태에서, 플러그인 소스를 따라가 보면 기기에서 DB 열기가 실패하는 코드 한 줄을 품고 있었습니다. 같은 앱이 2025년 8월부터 내세운 "E2E 100% 통과"는 expect()가 하나도 없는 러너 7개에서 나온 숫자였습니다.

다른 앱에서도 같은 모양이 나왔습니다. 에이전트가 커밋 메시지에 쓴 현실성 95.2%는 검증 러너를 돌려서는 나올 수 없는 값이었고(러너 집계의 상한은 약 92.3%), "크래시 없음" 보고의 근거는 앱을 한 번 띄워 본 것뿐이었습니다. 아래 규칙 9개는 이 주제의 실측 노트에서 나왔고, 규칙마다 근거가 된 숫자와 노트를 붙였습니다.

에이전트의 "통과"를 믿기 전에 무엇을 확인하나?

  1. 가드를 지워 보고 테스트가 실패하는지 봅니다. 채팅 앱에서 수정을 되돌려도 저장소 테스트 13개가 그대로 통과했고, "검증 완료"로 보고된 수정 2건도 가드를 지운 뒤 초록이었습니다. 같은 리뷰가 찾은 26건 가운데 24건은 그 회차의 수정이 새로 만든 결함이었습니다. 근거: 가드를 지워 보는 검사
  2. 통과율의 분자, 분모, 실행 명령을 적게 합니다. "E2E 100%"를 낸 러너 7개 가운데 5개는 앱 코드를 한 줄도 부르지 않고 지연 시간만 쟀습니다. 3,010줄을 지운 날 밤, 실제 소켓으로 연결한 E2E가 결함 7건을 찾았습니다. 근거: expect 0개 러너 7개
  3. skip 수와 그 이유를 통과 수와 함께 봅니다. flutter test는 skip을 실패로 세지 않습니다. skip 13개 중 하나인 릴레이 통합 테스트는 엿새 동안 고장 난 채였고, 암호 대조 테스트 3개는 Python 패키지가 없으면 조용히 빠지게 돼 있었습니다. 근거: 조용한 skip과 초록 CI
  4. 게이트가 읽은 입력이 실제 출시물인지 봅니다. 2026년 9월 13일, 개발 설정(localhost, 평문 시그널링)으로 만든 43 MB AAB가 출시 게이트에서 PASS를 받았습니다. 다른 앱의 광고 SDK 검사는 출시할 빌드가 쓰지 않는 의존성 목록을 비교하고 있었습니다. 근거: 출시물이 아닌 것을 본 게이트
  5. 검사기가 몇 개를 쟀는지 출력하게 합니다. 대비 검사기는 텍스트 조각 9,318개 가운데 5,556개(59.6%)만 재고도 실패 0건을 냈고, 재지 못한 조각은 어디에도 기록되지 않았습니다. 근거: 40%를 재지 못한 대비 검사기
  6. 보고된 숫자는 그 숫자를 낸 코드를 열어 재현합니다. 검증 러너의 함수 15개는 측정 대신 0.85~0.96 사이 상수를 돌려줬습니다. 테스트 183개가 모두 통과한 빌드의 "3D" 화면은 돌릴 수 없는 고정 시점 그림이었습니다. 근거: 95.2%가 러너에서 나오지 않은 이유
  7. "크래시 없음"이 무엇에 근거했는지 묻습니다. 에이전트의 근거는 실행 시간 857 ms뿐이었습니다. 데이터를 지운 앱에 adb monkey를 돌리자 이벤트 800개 중 15번째에서 죽었고, 원인은 매니페스트에 빠진 VIBRATE 권한 한 줄이었습니다. 근거: 신규 설치 몽키 테스트
  8. 축소된 릴리스 빌드를 실기기에서 실행합니다. 2026년 9월 23일, R8이 생성자 하나를 지워 첫 앱의 릴리스 빌드가 시작하자마자 죽었습니다. 디버그 빌드에서는 재현되지 않았고, 16일 뒤 다른 앱에서 같은 경로로 다시 났습니다. 근거: 릴리스 게이트와 R8 크래시
  9. 리뷰 지적은 반박을 버틴 것만 고칩니다. 2026년 9월 29일 출시 전 리뷰에서 에이전트 84개를 돌리고, 지적마다 반박 에이전트 3개를 붙여 살아남은 20건만 고쳤습니다. 근거: 반박을 버틴 리뷰 지적

테스트 바깥에서 막은 것

통과 표시와 별개로, 저장 직전이나 출시 직전에 막은 사례도 있습니다. HWP 뷰어의 저장 검증 게이트는 누름틀을 채운 저장을 두 문서 모두 막았고, 우리는 검사를 느슨하게 하는 대신 편집을 끈 채 출시한 뒤 9일 뒤 누름틀을 빼고 켰습니다. 한컴 앱 호환 확인에서는 고친 파일 7개가 모두 열렸지만, 다시 저장하는 단계는 사람의 로그인이 있어야 해서 에이전트 혼자 끝내지 못했습니다.

악성 파일 50개는 파일 대신 생성기와 기대 판정표를 커밋해 단위 테스트에 묶었습니다. LLM 공유 캐시는 블라인드 A/B에서 문맥 없이 96.6%, 문맥 포함 96.0%가 나와 문맥을 보내지 않기로 했습니다. 에이전트 여러 개를 함께 돌릴 때의 확인은 클로드 코드 병렬 에이전트 운영 실측에 따로 정리했습니다.

읽는 순서

처음이라면 이 순서를 권합니다. 1~6번은 연재 통과 표시를 의심하기로도 이어 읽을 수 있습니다.

  1. VIBRATE 권한과 몽키 테스트: "테스트 완료"의 근거가 앱 실행뿐이었던 가장 짧은 사례입니다.
  2. 'E2E 100% 통과'의 정체: 통과율이 무엇을 센 숫자인지 찾는 grep 몇 줄이 있습니다.
  3. skip되는 테스트와 CI: skip이 초록 CI가 되는 경로와 CI 단계 가드를 봅니다.
  4. 테스트 3,066개와 가드 지워 보기: 테스트를 시험하는 방법과, 변이 행 970개를 출시 때마다 돌리는 스크립트를 보여 줍니다.
  5. 클로드 코드 수정 재리뷰: 가드 시험을 통과한 수정도 같은 결함의 다른 입구(HTTP 경로)를 놓친 사례와 재리뷰 절차입니다.
  6. 클로드 코드 실기기 테스트 세 번: 단위 테스트가 통과한 앱을 실기기·에뮬레이터 E2E로 돌린 기록과, 테스트 빌드의 외부 요청을 전송 단계에서 막은 법입니다.
  7. 평문 AAB와 dart-define 하나: 게이트 입력을 출시물과 맞추는 법입니다.
  8. 현실성 95.2%와 고정 시점 화면: 에이전트가 채점 기준까지 직접 쓰면 어떻게 되는지 다룹니다.
  9. Android 출시 전 세 단계: 릴리스 게이트, 축소 빌드 실행, 실기기 E2E 순서입니다.
  10. 대비 검사기의 측정 수 출력: 재지 못한 양을 세고, 모자라면 실패하게 만든 과정을 적었습니다.
  11. 에이전트 코드 리뷰를 믿는 법: 지적을 반박으로 거르는 절차와 멈추는 조건입니다.
  12. HWP 저장 검증 게이트: 검사를 느슨하게 하는 대신 기능 범위를 줄였습니다.
  13. 한컴 호환성 테스트 7/7: 에이전트가 끝낼 수 없는 확인을 사람에게 넘긴 지점입니다.
  14. 문서 뷰어 악성 파일 세트: 위험한 파일을 커밋하지 않고도 테스트에 묶을 수 있습니다.
  15. LLM 공유 캐시와 블라인드 A/B: 캐시 키와 모델 입력이 어긋날 때의 위험입니다.
  16. 에이전트에게서 비밀값 지키기: 채팅, 로그, 토큰 권한에 거는 같은 규칙입니다.
