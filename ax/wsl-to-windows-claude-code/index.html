WSL을 접고 Windows 네이티브로: Claude Code 개발 환경 이전 체크리스트

저장소는 복사 뒤 git 설정 세 가지로 끝나지만 세션 기록은 cwd와 보관 기간을 따로 고쳐야 합니다. 판정은 R8 릴리스 빌드와 몽키 1,500회로 냈습니다.

작성 SugarMount · 에이전트와 일하는 법 · 읽는 시간 15분 · 최종 업데이트 2026년 11월 4일

Windows로 옮긴 sugar-utils의 사진 용량 줄이기 앱을 R8 릴리스 빌드로 묶는 데 5분 50초가 걸렸고, 그 APK에 몽키 이벤트 1,500개를 넣어도 크래시와 ANR은 0건이었습니다. 이전은 2026년 10월 18일 오전 11시 2분에 시작했고, 저장소와 도구 설치는 그날 오후 4시 무렵 이 확인으로 마무리됐습니다. 세션 기록과 Docker까지 정리된 것은 10월 22일이었고, 그 사이 에이전트가 틀린 곳이 다섯 군데 나왔습니다.

근거는 이전 작업을 한 Claude Code 세션 기록(jsonl) 3개, 이전 내용을 적은 메모리 파일, 이전 전후의 전역 지침 파일입니다. 숫자는 2026년 11월 2일에 세션 기록에서 다시 확인했고 시각은 한국 시간입니다.

이전 체크리스트 8단계

WSL을 쓴 이유는 예전에 Windows 터미널에서 Claude Code가 안 되는 기능이 많고 느렸기 때문입니다. 10월 18일 운영자가 이제 Windows에서 써도 되느냐고 묻자, 에이전트는 써도 된다면서 한 프로젝트만 하루 이틀 먼저 써 보라고 권했습니다. 운영자는 한 번에 옮기라고 했고, 도구 설치를 승인하면서 빌드까지 해 보라고 했습니다. 프로젝트를 WSL에 둔 채 Windows에서 WSL 네트워크 경로로 여는 방식은 에이전트가 아주 느리다며 권하지 않았습니다(속도는 재지 않았습니다).

  1. WSL 홈의 프로젝트를 Windows 홈으로 복사합니다. 옮기지 않습니다. node_modules, build, .gradle, .dart_tool, .next, .cxx는 제외합니다.
  2. 저장소마다 git status --porcelain | wc -l을 양쪽에서 세어 맞는지 확인합니다.
  3. core.filemode=false(서브모듈 포함), 링크가 있는 저장소는 core.symlinks=true로 바꾸고 링크를 다시 체크아웃, 워크트리는 git worktree repair, Android는 local.properties의 sdk.dir.
  4. 도구 버전을 확인하고 관리자 권한 없이 사용자 범위로 설치합니다.
  5. Claude Code 지침 파일의 환경 절을 다시 쓰고, WSL에서만 필요했던 우회 규칙을 삭제합니다.
  6. 세션 기록을 옮기기 전에 cleanupPeriodDays부터 올립니다. 그다음 폴더 이름을 바꿔 복사하고, 기록 안의 cwd를 바꾸고, WSL root 계정 홈의 .claude/projects에 있는 기록도 찾습니다. 이전 뒤에도 WSL에서 이어 쓴 세션은 마지막에 한 번 더 복사합니다. 끝나면 각 프로젝트 폴더에서 claude --resume을 열어 옛 세션이 보이는지 봅니다. 다른 폴더에서 실행하면 기록이 별도 프로젝트 폴더로 저장됩니다.
  7. Ubuntu를 깨우는 것을 끄고, Docker Desktop을 쓰면 wsl --terminate <배포판>으로 Ubuntu만 종료합니다. wsl -l -v에서 Ubuntu가 Stopped, docker-desktop이 Running이면 끝입니다. .wslconfig를 고쳤다면 적용하는 데 wsl --shutdown이 한 번 필요하고, 그때 Docker도 잠깐 내려갑니다.
  8. R8 릴리스 빌드를 에뮬레이터에 설치하고 몽키 1,500회, crash 버퍼, 프로세스 생존을 봅니다.

1단계와 3단계에 쓴 명령을 따라 하기 쉽게 한데 모은 것입니다. 저장소 이름은 자리표시자로 바꿨습니다. 저장소 안의 링크는 git이 모드 120000으로 기록한 파일로 찾았습니다.

# 1단계 (WSL 안에서)
rsync -a --no-links --exclude=node_modules --exclude=build --exclude=.dart_tool \
  --exclude=.gradle --exclude=.next --exclude=.cxx <폴더 목록> <Windows 홈>/

# 3단계 (Git Bash, 저장소마다)
r=<저장소>
git -C "$r" config core.filemode false
git -C "$r" submodule foreach --quiet 'git config core.filemode false'
export MSYS=winsymlinks:nativestrict
git -C "$r" config core.symlinks true
git -C "$r" ls-files -s | awk '$1=="120000"{ $1=$2=$3=""; sub(/^ +/,""); print }' > "$TMP/links.txt"
while IFS= read -r p; do rm -f "${r:?}/${p:?}"; done < "$TMP/links.txt"
tr '\n' '\0' < "$TMP/links.txt" | xargs -0 git -C "$r" checkout --
git -C <주 저장소> worktree repair <워크트리 경로...>

복사한 저장소에 거는 git 설정

WSL 안에서 rsync -a --no-links로 홈 폴더 35개(sugar-game 워크트리 16개 포함)와 bundle 파일 1개를 Windows 홈으로 복사했습니다. 빌드 산출물을 뺀 크기는 약 1.5GB였습니다. WSL 원본은 지우지 않고 백업으로 남겼습니다. 운영자가 정한 규칙이고, 나중에 빠진 세션 기록을 이 원본에서 두 번 되살렸습니다.

--no-links 때문에 심볼릭 링크는 "skipping non-regular file"로 모두 건너뛰었습니다. 링크가 든 저장소 3개는 core.symlinks=true로 바꾸고, Git Bash에서 MSYS=winsymlinks:nativestrict를 건 뒤 링크 파일을 지우고 git checkout으로 다시 받았습니다. 모든 저장소와 서브모듈에는 core.filemode=false를 걸었습니다. sugar-game의 워크트리 16개는 .git 파일이 옛 경로를 가리켜 git worktree repair가 "gitdir incorrect"를 고쳤습니다.

확인은 저장소별 git status --porcelain 줄 수를 WSL 원본과 맞춰 봤습니다. sugar-game 23, sugar-utils 0처럼 한 저장소만 빼고 모두 같았습니다. 그 하나는 브라우저 다운로드 메타데이터인 …pptx:Zone.Identifier 파일이 실수로 커밋돼 있었고, Windows는 파일 이름에 쌍점을 허용하지 않아 만들 수 없었습니다. git update-index --skip-worktree로 그 파일만 무시하게 했습니다.

도구 버전과 지워진 우회 규칙

WSL 시절 전역 지침의 환경 절에는 node 20, python 3.10이 적혀 있었습니다. Windows에는 이미 node 22와 python 3.12가 깔려 있어서, 이전 날 오전에 새로 쓴 환경 절은 그 판을 기준으로 했습니다. PATH의 java는 JRE 8뿐이라 javac가 없었고, Gradle용 JDK 21은 사용자 폴더에 zip으로 풀어 ~/.gradle/gradle.properties의 org.gradle.java.home으로 지정했습니다. gcloud는 winget 설치가 관리자 권한(UAC) 요청에서 막혀, 공식 zip을 사용자 폴더에 풀고 사용자 PATH에 넣었습니다. WSL 때부터 없던 jq와 Windows 쪽에 없던 rg는 winget --scope user로 넣었습니다.

WSL에서는 Windows 드라이브에 있는 Android 프로젝트를 9p 파일시스템으로 붙여 빌드했고, 거기서 Gradle 락이 깨져 --project-cache-dir을 따로 주거나 Linux 쪽 사본에서 빌드한다는 줄이 지침에 있었습니다. Windows 네이티브에서는 그 드라이브를 직접 쓰므로 새 지침에서 이 줄을 삭제했습니다. "PATH의 flutter는 Windows SDK이니 Linux SDK는 절대경로로 부른다"는 줄도 Windows용 SDK 하나만 남으면서 빠졌습니다. 이전 뒤 그 드라이브 프로젝트의 세션 5개(서브에이전트 기록까지 jsonl 81개)를 Timeout waiting to lock, Could not lock으로 찾아보니 0건이었습니다. 다만 그 기간 이 드라이브에서 빌드가 끝까지 돈 기록은 많지 않습니다.

세션 기록은 프로젝트 폴더 밖에 있다

프로젝트를 다 옮긴 뒤에도 Windows에서 claude --resume을 열면 옛 세션이 보이지 않았습니다. Claude Code의 세션 기록은 ~/.claude/projects/ 아래, 작업 폴더의 절대 경로를 바꾼 이름의 폴더에 있습니다. Linux 홈의 sugar-utils는 -home-<사용자>-sugar-utils이고, Windows 홈의 같은 폴더는 C--Users-<사용자>-sugar-utils입니다. 10월 18일 밤 기록이 있는 폴더 14개(원본 약 3.1GB)를 새 이름으로 복사했습니다.

그래도 10월 21일까지 목록에 안 잡혔습니다. 기록 파일 한 줄마다 들어 있는 "cwd" 값이 여전히 Linux 경로였기 때문입니다. 에이전트가 이 값을 일괄로 바꾸려 하자 Claude Code의 자동 권한 검사가 "세션 기록 변조"로 막았습니다. 우회하지 않고 cwd만 바꾸는 스크립트를 만들어 운영자가 ! 명령으로 직접 실행했고, 31개 파일이 바뀌었습니다.

스크립트는 각 기록 파일에서 cwd 값만 Linux 경로에서 Windows 경로로 바꾸고, 대화 본문과 파일 수정 시각은 건드리지 않습니다. 세션 본체 파일만 고칩니다. 하위 폴더의 서브에이전트 기록은 건드리지 않습니다. 홈 밖(예: 다른 드라이브)에서 연 세션은 그 경로에 맞는 줄을 따로 추가해야 합니다. 아래는 실제 스크립트에서 두 번째 드라이브 처리와 사용자 이름을 빼고, Windows 홈 경로를 자동으로 잡도록 고친 판입니다. Git Bash에서 !로 돌릴 때 스크립트 경로를 역슬래시로 넘기면 Bash가 역슬래시를 지워 파일을 못 찾습니다. 처음 실행이 이것 때문에 실패했고, 슬래시 경로로 다시 돌렸습니다.

# 옮겨 온 세션 기록(.jsonl)의 cwd만 Windows 경로로 바꾼다. 수정 시각은 유지한다.
import os, re, glob

LINUX_HOME = '/home/<사용자>'
WIN_HOME = os.path.expanduser('~')          # %USERPROFILE%
root = os.path.join(WIN_HOME, '.claude', 'projects')
pat = re.compile(r'"cwd":"' + re.escape(LINUX_HOME) + r'((?:/[^"]*)?)"')

def rep(m):
    # JSON 문자열 안이므로 역슬래시를 두 번 쓴다
    path = (WIN_HOME + m.group(1).replace('/', '\\')).replace('\\', '\\\\')
    return '"cwd":"%s"' % path

n = 0
for f in glob.glob(os.path.join(root, '*', '*.jsonl')):
    with open(f, encoding='utf-8') as fh:
        s = fh.read()
    if '"cwd":"' + LINUX_HOME not in s:
        continue
    st = os.stat(f)
    with open(f, 'w', encoding='utf-8', newline='') as fh:
        fh.write(pat.sub(rep, s))
    os.utime(f, (st.st_atime, st.st_mtime))
    n += 1
print('rewritten', n)

바로 그때 9월 18~20일 기록 5개가 사라진 것이 보였습니다. 에이전트가 복사하면서 원래 수정 시각을 유지했는데, Claude Code는 기본값으로 30일 넘게 손대지 않은 기록을 시작할 때 삭제합니다. ~/.claude/settings.json에 "cleanupPeriodDays": 3650을 넣고 WSL 원본에서 5개를 다시 복사했습니다.

놓친 root 기록 8개와 shutdown

10월 22일 밤 운영자가 "세션 기록이 제대로 안 옮겨진 것 같다"고 짚었습니다. 에이전트는 그 전에 이전이 끝났다고 보고했지만, 다시 보니 WSL root 계정의 기록 8개를 통째로 놓쳤고, 이전 뒤에도 WSL에서 이어진 세션 1개가 옛 상태였습니다. 9개를 옮기고 cwd를 바꾼 뒤에야 Linux 경로가 남은 기록이 0개가 됐습니다.

WSL 끄는 법도 에이전트가 틀렸습니다. 10월 18일부터 22일 낮까지 보고 여섯 번에 "wsl --shutdown을 요청해 주세요" 같은 안내를 적었고, 10월 22일 밤 운영자가 그대로 실행하자 Docker까지 내려갔습니다. 에이전트는 그걸 모른 채 그 뒤 보고 두 개에도 같은 안내를 붙였습니다. --shutdown은 WSL2 가상 머신 전체를 내리고, Docker Desktop도 같은 가상 머신 위의 docker-desktop 배포판에서 돕니다. Ubuntu만 끄는 명령은 wsl --terminate Ubuntu-22.04입니다. shutdown 뒤 Ubuntu가 다시 켜진 원인도 에이전트가 앞서 Ubuntu 안에서 돌린 세션 기록 검색 find가 남아 있던 것으로 보였습니다.

플러그인 하나를 지워 달라는 요청을 에이전트가 설치된 플러그인 전체로 읽고, 사용 기록을 보지 않은 채 user 범위 플러그인 22개를 지웠습니다. 운영자가 쓰는 것은 왜 지우냐고 되묻자 그제야 최근 60일 세션 기록의 MCP 호출 수를 확인했습니다. 직접 등록한 github MCP와 context7 MCP는 0회였고, 지운 것 중 Notion 플러그인이 1,437회, playwright 플러그인이 59회였습니다. 둘은 다시 설치했습니다. 플러그인을 지우기 전에는 호출 수부터 세십시오.

Ubuntu를 다시 깨우던 네 가지

시작프로그램 폴더에서 WSL 안의 봇을 띄우던 스크립트, Docker Desktop 설정의 Ubuntu WSL 연동, Ubuntu에 영구 연결해 둔 네트워크 드라이브, 그리고 위에 쓴 남은 find 프로세스가 Ubuntu를 깨웠습니다. 스크립트와 Docker 설정은 지우지 않고 백업 폴더로 옮기거나 설정에서 해제했고, 네트워크 드라이브는 net use의 /delete로 연결을 풀었습니다.

Docker Desktop이 쓰는 WSL2 가상 머신은 계속 떠 있으므로 .wslconfig에서 memory=3GB, processors=2, swap=1GB, autoMemoryReclaim=dropCache로 줄였습니다. 탐색기의 Linux 항목이나 WSL 네트워크 경로를 여는 것만으로도 Ubuntu가 켜집니다. 그럴 때는 다시 --terminate로 종료합니다.

끝났다는 판정: R8 빌드와 몽키 1,500회

릴리스 게이트 글에 쓴 R8 크래시는 디버그 빌드에서는 보이지 않았습니다. 그래서 환경 이전도 sugar-utils의 사진 용량 줄이기 앱을 --no-daemon으로 assembleRelease까지 돌려 판정했습니다. 빌드는 337개 태스크(298개 실행, 39개 캐시)에 minifyReleaseWithR8을 거쳐 5분 50초에 끝났습니다. Windows에서 처음 돌린 빌드(구성 캐시도 없던 상태)입니다.

adb -s emulator-5554 install -r app-release.apk
adb -s emulator-5554 logcat -c
adb -s emulator-5554 shell monkey -p <패키지> --throttle 200 --pct-syskeys 0 -v 1500
adb -s emulator-5554 shell pidof <패키지>
adb -s emulator-5554 logcat -d -b crash

Pixel 8 Pro API 35 에뮬레이터에서 "Events injected: 1500"과 "Monkey finished"가 나왔고, pidof가 프로세스 번호를 돌려줬고, crash 버퍼는 비어 있었습니다. 연결돼 있던 실제 폰 2대에는 Play에서 받은 판이 덮어써질 수 있어 설치하지 않았습니다. 이번 몽키는 install -r(있으면 덮어쓰는 설치)로 넣고 돌렸고, 앱 데이터를 지운 신규 설치 상태였는지는 확인하지 않았습니다. 신규 설치 상태에서만 드러나는 결함은 VIBRATE 권한과 신규 설치 몽키 테스트에 따로 적었습니다.

심볼릭 링크를 못 만드는 PC

네이티브 심볼릭 링크를 만들 수 없는 PC에서는 core.symlinks=true로 링크를 되살리는 3단계를 그대로 쓸 수 없습니다.

빌드 시간 비교는 없고, /resume 목록은 운영자만 봤습니다

Windows 네이티브와 WSL의 같은 조건 빌드 시간은 재지 않았습니다. /resume 목록은 에이전트가 직접 띄워 본 적이 없고, 10월 22일 운영자가 "된 거 같다"고 한 것이 마지막 확인입니다. 옮겨 온 세션은 대화 본문에 옛 Linux 경로가 남아 있어, 이어 가면 에이전트가 처음에 그 경로를 쓰려 할 수 있습니다. 에이전트가 당시 보고에 적은 대응은 이어 갈 때 새 경로를 한 번 말해 주라는 것이었고, 더 나은 방법은 아직 찾지 않았습니다.

자주 묻는 질문

WSL에서 쓰던 Claude Code 세션 기록을 Windows로 옮길 수 있나요?

옮길 수 있지만 폴더 복사만으로는 안 됩니다. ~/.claude/projects/ 아래 폴더 이름을 Windows 경로 기준으로 바꾸고, 기록 안의 cwd 값도 바꿔야 합니다. 이번에는 바꾼 뒤 운영자가 /resume에서 된 것 같다고 확인했습니다. 먼저 cleanupPeriodDays를 올려 두지 않으면 30일 넘게 손대지 않은 기록이 지워집니다.

wsl --shutdown과 wsl --terminate는 무엇이 다른가요?

--shutdown은 WSL2 가상 머신 전체를 내리므로 그 위의 Docker Desktop도 함께 내려갑니다. --terminate <배포판>은 그 배포판만 종료합니다.
