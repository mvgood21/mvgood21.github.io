안드로이드에서 HWPX는 octet-stream으로도 온다: 보낸 앱별 인텐트 18행과 intent-filter 설계

hwpx를 받는 뷰어는 문서 MIME만으로는 부족합니다. octet-stream을 받는 alias 하나를 두고, 판정은 파일 이름 대신 바이트로 하십시오.

작성 SugarMount · Android 개발 · 읽는 시간 15분 · 최종 업데이트 2026년 11월 1일

Galaxy S21(Android 15)의 Chrome 다운로드 목록에서 hwpx를 누르자 뷰어에 도착한 MIME은 application/octet-stream이었습니다. 같은 휴대폰에서 삼성 내 파일로 hwpx를 열면 application/vnd.hancom.hwpx가 왔습니다. 2026년 10월 5일, 한글뷰어 슈가독의 릴리스 빌드로 보낸 앱과 동작을 바꿔 가며 18행짜리 인텐트 행렬을 만들었고, 매니페스트는 그 행렬과 이어진 E2E 결과에 맞춰 고쳐 나갔습니다. 행렬을 채우는 동안 권한 없이 공유된 문서에서 크래시가 1건 나왔고, 하루 뒤에는 고친 매니페스트 때문에 */*로 공유할 때 선택 창에 앱이 두 번 뜨는 결함이 생겼습니다.

근거는 앱 저장소의 인텐트 행렬 QA 문서(2026-10-05), 기기 E2E 보고서(10-05~10-07), 1.0.0 출시 기록(10-08~10-09), 매니페스트와 SendEntryActivity 코드(커밋 ca1ade4)입니다. 기기 시리얼과 문서 이름은 적지 않았습니다.

같은 hwpx가 보낸 앱에 따라 MIME 두 가지로 왔습니다

18행 가운데 11행은 실제 앱에서 보낸 기록입니다(삼성 내 파일 4, Chrome 4, Files 3). 나머지는 디버그 송신 앱 2행과 adb 5행입니다. 리더가 떠 있는 동안 dumpsys activity activities에서 typ=과 flg=를 읽어 적었습니다.

보낸 앱 (기기)hwpxhwppdfNEW_TASK
삼성 내 파일 (S21)vnd.hancom.hwpxx-hwppdf없음 (0x3000001)
Chrome 다운로드 목록 (S21)octet-streamx-hwpChrome 자체 뷰어있음 (0x13000003)
Files (에뮬레이터 API 35)octet-streamx-hwppdf없음 (0x23000003)

MIME이 갈린 것은 보낸 앱마다 MIME을 정하는 곳이 달라서입니다. Chrome은 다운로드 서버가 보낸 값을 그대로 넘겼고, Files(DocumentsUI)가 쓰는 에뮬레이터 이미지의 MIME 표에는 hwpx가 없었습니다(10월 4일에 본 AOSP MIME 표도 x-hwp만 있고 hwpx는 없습니다). 한컴 MIME을 붙인 것은 삼성 내 파일뿐입니다. 10월 3일 엔진 실험에서는 MediaStore에 application/octet-stream으로 기록된 hwpx를 내 파일이 vnd.hancom.hwpx로 넘겼습니다.

조사 초기에 적어 둔 가정은 ".hwp도 octet-stream으로 온다"였습니다. 행렬에서 hwp는 세 앱 모두 application/x-hwp로 왔고, 이름 모를 파일로 넘어오는 것은 hwpx뿐이었습니다. 그래서 문서 MIME만 등록한 뷰어는 사용자 화면에서 "hwp는 열리는데 hwpx를 열 때만 목록에 없는" 모양이 됩니다. 사용자가 할 수 있는 대처는 카톡·휴대폰에서 HWPX 파일이 안 열릴 때에 따로 정리했습니다.

PDF는 Chrome이 자기 뷰어로 열어 우리 앱까지 오지 않았고, 다운로드 완료 메시지의 '열기'도 다운로드 목록만 띄웠습니다. 필터로는 바꿀 수 없는 경로라 행렬 결론에는 "Chrome의 PDF는 내 파일을 거쳐야 온다"고만 적었습니다.

octet-stream을 받는 alias 하나에 판정은 바이트로

VIEW를 받는 컴포넌트는 activity-alias 하나입니다. 이름은 .reader.OpenUnknownFile이고, 한 필터에 문서 MIME 11종과 범용 MIME 5종을 같이 넣었습니다. 필터가 하나여야 선택 창에 항목도 하나만 생깁니다.

<activity-alias android:name=".reader.OpenUnknownFile"
    android:enabled="true" android:exported="true"
    android:targetActivity=".reader.ReaderActivity">
  <intent-filter>
    <action android:name="android.intent.action.VIEW" />
    <category android:name="android.intent.category.DEFAULT" />
    <data android:scheme="content" />
    <!-- 문서 11종: pdf, x-pdf, x-hwp, haansofthwp, vnd.hancom.hwp,
         vnd.haansoft-hwp, hwp+zip, x-hwp+zip, haansofthwpx,
         vnd.hancom.hwpx, x-hwpx -->
    <data android:mimeType="application/vnd.hancom.hwpx" />
    <!-- 범용 5종 -->
    <data android:mimeType="application/octet-stream" />
    <data android:mimeType="binary/octet-stream" />
    <data android:mimeType="application/x-download" />
    <data android:mimeType="application/download" />
    <data android:mimeType="application/force-download" />
  </intent-filter>
</activity-alias>

x-download가 들어간 것은 10월 4일 확인에서 korea.kr 첨부가 이 MIME으로 왔고 Chrome이 그 값을 다시 매핑하지 않았기 때문입니다. MIME은 모두 소문자로 적었습니다. Android 문서에 따르면 프레임워크는 MIME을 대소문자를 구분해 비교합니다.

octet-stream을 받으면 이름 모를 파일 전부의 선택 창에 우리 앱이 나옵니다. 그래서 들어온 파일은 리더가 첫 64KB를 읽어 형식을 정하고, 증거가 그 뒤에 있으면 전체를 복사한 다음 정합니다. PDF는 첫 1KB 안의 %PDF-, HWP 5는 CFB 컨테이너의 FileHeader에 있는 "HWP Document File", HWPX는 ZIP 첫 항목이 압축 없이 저장된 mimetype이고 내용이 application/hwp+zip인지, HWP 3는 그 형식의 서명을 봅니다. MIME과 파일 이름은 판정을 누그러뜨리는 데만 쓰고, 문서라고 정하는 근거로는 쓰지 않습니다. 로컬 문서 묶음 635파일(문서 255개와 거절해야 하는 파일)에서 오판은 0건이었습니다.

행렬의 마지막 두 행이 이 판정을 기기에서 확인한 기록입니다. m4a 헤더(ftyp M4A)로 만든 4 KiB 파일을 .hwp 이름과 application/x-hwp로 보내자, S21에서는 VIEW 시작 뒤 197~215ms에 선택 창이 시작됐습니다. 받을 다른 앱이 하나뿐이라 시스템은 그 기기의 다른 오피스 뷰어를 바로 띄웠고, 우리 앱에는 사본이 남지 않았습니다. 에뮬레이터에는 HWP를 받는 다른 앱이 없어 같은 파일을 application/pdf로 보냈고, 435ms 뒤 Google Drive PDF 뷰어로 넘어갔습니다.

권한 없이 공유된 문서에 SendEntryActivity가 죽었습니다

SEND(공유)는 SendEntryActivity가 받아 리더로 넘깁니다. 화면 없이 onCreate에서 넘기고 바로 끝나는 Activity입니다. 10월 5일 행렬의 adb 행에서 --grant-read-uri-permission 없이 EXTRA_STREAM만 담아 pdf를 공유하자, 이 Activity가 SecurityException으로 프로세스째 죽었습니다.

  1. 보낸 쪽이 URI는 넘기면서 읽기 권한은 주지 않았습니다.
  2. 에이전트가 작성한 코드는 리더로 넘기는 인텐트에 FLAG_GRANT_READ_URI_PERMISSION을 붙여, 우리 앱이 받은 적 없는 읽기 권한을 다시 넘기려 했습니다.
  3. 시스템은 그 startActivity를 SecurityException으로 거절했고, 예외가 onCreate 밖으로 나가 프로세스가 내려갔습니다.

고친 코드(SendForward)는 그 예외만 잡아 권한 플래그와 ClipData를 지운 인텐트로 한 번 더 넘깁니다. 리더는 URI를 읽어 보고, 읽을 수 없으면 '접근 불가' 화면(E1)을 보여 줍니다.

fun start(forward: Intent, start: (Intent) -> Unit) {
    try {
        start(forward)
    } catch (e: SecurityException) {
        start(withoutGrant(forward))  // 권한 플래그와 ClipData 제거
    }
}

같은 경로를 JVM 테스트(SendForwardTest)가 막고, 기기 점검 스크립트의 send_twice가 권한 없는 SEND를 매번 다시 보냅니다. 10월 8일 1.0.0 (3) 회귀에서 이 단계를 포함한 점검 8항목이 S21(Android 15)과 S20(Android 13) 모두 8 PASS, 0 FAIL이었습니다. 행렬에서 이 크래시를 낸 것은 adb로 일부러 권한을 빼고 보낸 행 하나였고, 실제 앱 행에는 없었습니다. 어느 앱이 이렇게 보내는지는 모릅니다.

SEND alias를 더하자 선택 창에 앱이 두 번 나왔습니다

10월 5~6일 E2E의 entry-intents-10(메일 공유를 흉내 낸 시나리오)은 마지막 라운드에서 25건 중 S21 21건, S20 20건만 첫 쪽을 그렸습니다. 실패는 모두 hwpx를 octet-stream으로 공유한 경우였습니다. 처음 설계는 SEND를 문서 MIME 11종으로만 받았기 때문입니다. E2E 보고서는 메일 앱 실측 뒤에 판단하라고 권했지만, 10월 6일 운영자는 octet-stream 공유도 먼저 받기로 정했고, 코드 주석에는 그 이유가 "메일 앱이 hwpx를 그렇게 공유한다"로 남았습니다.

에이전트는 octet-stream SEND를 받는 alias SendUnknownFile을 새로 더했습니다. 그러자 */*로 보낸 공유가 기존 SendEntryActivity의 필터와 새 alias 두 곳에 걸렸습니다. Android는 */* 인텐트를 타입 필터 어느 것에나 맞추기 때문입니다. S20 선택 창에는 같은 아이콘의 우리 앱 항목이 2개 나왔고, S21에서는 항목 하나짜리 선택 단계가 하나 더 생겼습니다.

10월 7일에는 같은 인텐트에 걸리는 컴포넌트가 하나만 켜지도록 고쳤습니다. SendEntryActivity의 필터를 지우고 exported=false로 바꾸었고, SEND는 alias 둘 중 하나만 사용합니다. 스위치가 켜져 있으면 SendUnknownFile(문서 11종과 octet-stream), 꺼져 있으면 SendDocument(문서 11종)입니다. SEND를 고친 뒤 재검증에서 VIEW */*도 ReaderActivity와 OpenUnknownFile 두 곳에 걸린다는 것이 드러났습니다. 10월 5일 행렬 때부터 있던 구조였고, 테스트가 ReaderActivity 필터를 전제로 짜여 있어 처음에는 따로 남겼다가 같은 날 같은 방식으로 고쳤습니다. 스위치를 바꿀 때는 넘겨받는 alias를 먼저 켜고, 다른 쪽은 그 뒤에 끄도록 했습니다. 잠깐 두 개일 수는 있어도 0개인 순간은 생기지 않습니다.

cmd package query-activities로 보면 S21 릴리스 빌드에서 스위치를 켤 때 */*, pdf, hwpx, octet-stream VIEW가 모두 OpenUnknownFile 하나로, 끌 때 ViewDocument 하나로 나왔고 octet-stream은 0개였습니다. 같은 날 재검증에서는 '연결 프로그램'과 '공유' 선택 창에 보이는 우리 앱 항목도 하나씩이었습니다.

VIEW와 SEND 각각, 같은 MIME을 받는 컴포넌트는 하나만 켜 두십시오.

이 글과 비슷한 문제를 겪고 있다면 메일로 상황을 알려 주세요. 읽고 답하겠습니다. 메일로 문의하기

*/* 필터, pathPattern, 기본 OFF를 버린 이유

*/* 필터는 처음부터 선언하지 않았습니다. 사진이든 녹음이든 모든 파일의 목록에 뜨는 뷰어가 되기 때문입니다. octet-stream도 같은 위험이 있지만 범위가 이름 모를 파일로 좁고, 바이트 판별이 문서가 아닌 파일을 바로 넘깁니다. application/zip과 application/unknown은 실제 앱에서 그 MIME으로 오는 것을 보기 전까지 넣지 않았습니다.

확장자 pathPattern으로 .hwpx만 받는 방법은 content URI에서 맞지 않습니다. 삼성 내 파일이 넘긴 URI는 content://media/external/file/N 꼴이라 경로에 파일 이름이 없습니다. Android 문서도 <data>의 path 속성은 host가 함께 지정된 필터에서만 의미가 있다고 적습니다. host를 *로 넓히면 보낸 앱과 상관없이 path 조건을 걸 수는 있지만, 이런 URI에는 맞을 확장자가 없습니다. 10월 4일 경쟁 앱 매니페스트를 보니 한 앱이 octet-stream을 pathPattern 조건으로만 받았고, 그 앱 리뷰에는 "hwpx가 연결 목록에 안 뜬다"는 글이 있었습니다(리뷰와 매니페스트의 연결은 추정입니다).

범용 alias를 기본으로 끄는 안도 있었습니다. 행렬에서 스위치를 끄고 octet-stream VIEW를 보내자 선택 창에서 우리 앱이 사라졌습니다. 기본 OFF면 Chrome과 Files에서 받은 hwpx가 처음부터 목록에 없는 셈입니다. 10월 5일 운영자가 기본 ON을 승인한 결정표의 영향 칸에는 "연결 목록 노출 vs 가로채기 반감"이 함께 적혀 있었습니다. 설정의 '모든 파일 형식 목록에 표시' 스위치로 사용자가 끌 수 있고, PRD에는 범용 alias의 거절률이 높으면 기본 OFF나 MIME 축소로 되돌린다는 규칙을 적었습니다.

카톡에서 HWPX는 열렸지만 MIME은 적지 못했습니다

카카오톡 경로는 에이전트가 시험할 수 없었습니다. 다른 계정이 파일을 보내야 받은 쪽에서 열 수 있어서, 행렬 문서는 카톡·네이버 메일·Gmail을 '소유자 몫' 표에 따로 적었습니다. 10월 9일 출시 기록에는 운영자가 Galaxy S23에서 다른 카톡 계정이 보낸 테스트 폴더 4개(HWPX 공문, HWP5 공문, PDF, HWP3 옛 버전)를 '한글뷰어'로 열어 모두 정상이었다는 실측이 남아 있습니다. 다만 이 기록에는 카톡이 보낸 MIME과 NEW_TASK 여부가 없습니다. 지금 필터는 문서 MIME과 octet-stream을 함께 받으므로, 열린 것만으로는 카톡이 어느 쪽으로 보냈는지 알 수 없습니다.

행렬의 기기 범위도 좁습니다. 행렬은 S21(Android 15)과 에뮬레이터 API 35, 회귀는 S20(Android 13)까지입니다. 다른 제조사의 파일 앱은 보지 않았고, Files by Google은 시험 기기 어디에도 깔려 있지 않아 확인하지 못했습니다.

adb로 내 앱의 인텐트 행렬을 만드는 순서

  1. 보낸 앱마다 hwpx, hwp, pdf를 엽니다. 리더가 떠 있는 동안 받은 MIME, 플래그, authority를 적습니다. 파일 이름은 적지 않습니다.
    adb shell dumpsys activity activities | grep -A3 <패키지>
  2. 타입별로 내 패키지가 몇 번 잡히는지 셉니다. VIEW와 SEND 모두, */*, 문서 MIME, octet-stream에서 하나여야 합니다.
    adb shell cmd package query-activities --brief \
  -a android.intent.action.VIEW -t '*/*' -d content://x/y
  3. 읽기 권한 없이 공유합니다. 앱이 죽지 않고 '접근 불가' 화면으로 끝나야 합니다.
    adb shell am start -a android.intent.action.SEND \
  -t application/pdf --eu android.intent.extra.STREAM <content URI>
  4. m4a 같은 다른 파일을 .hwp 이름과 문서 MIME으로 VIEW합니다. 선택 창으로 넘어가는지, 앱 저장소에 사본이 남지 않는지 봅니다.
  5. 범용 MIME 스위치를 끄고 octet-stream VIEW를 보냅니다. 선택 창에 내 앱이 없어야 하고, 다시 켜면 돌아와야 합니다.
  6. 카톡과 메일 앱은 두 번째 계정에서 보내야 합니다.

엔진 쪽 실험은 안드로이드 한글 뷰어 만들기: rhwp + WebView를 문서 222개로 실측한 기록에, 같은 앱의 PDF 경로 문제는 androidx.pdf beta01: 격리 프로세스에서 Application.onCreate가 한 번 더 돌아 PDF가 조용히 안 열렸다에 적었습니다.

남은 일: 메일 앱 MIME, 열린 리더와 스위치

네이버 메일과 Gmail 첨부는 아직 열어 보지 않았습니다. octet-stream SEND를 받기로 한 근거가 메일 앱이었으니, 이 두 앱의 MIME을 dumpsys로 적는 것이 먼저입니다. 리더가 열려 있는 동안 설정에서 스위치를 바꿔 그 리더를 연 alias가 꺼지는 경우도 기기에서 보지 않았습니다. 시스템이 리더를 정리하거나 최근 앱에서 다시 들어오지 못할 수 있습니다. 거절률이 높으면 기본값을 되돌린다는 규칙은 적어 두었지만, 그 숫자를 본 기록은 아직 없습니다.

자주 묻는 질문

hwpx의 MIME 타입은 무엇인가요?

보내는 앱마다 다릅니다. 2026년 10월 5일 기록에서 삼성 내 파일은 application/vnd.hancom.hwpx, Chrome 다운로드 목록과 에뮬레이터 Files는 application/octet-stream으로 넘겼습니다. 한글뷰어 슈가독의 필터에는 application/haansofthwpx, application/vnd.hancom.hwpx, application/x-hwpx, application/hwp+zip과 octet-stream을 함께 넣었습니다.

intent-filter에 pathPattern으로 .hwpx를 받으면 안 되나요?

content URI에서는 맞지 않습니다. 삼성 내 파일이 넘긴 URI(content://media/external/file/N) 경로에는 확장자가 없었습니다. MIME으로 받고 바이트로 판정하십시오.
