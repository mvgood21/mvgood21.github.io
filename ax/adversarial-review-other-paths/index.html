클로드 코드 재리뷰: 닫은 결함이 HTTP로 남았다

클로드 코드가 고친 코드를 네 번 다시 리뷰했지만 Blocker와 High는 0건이 된 적이 없고, 3차에서는 닫힌 결함이 HTTP로 살아 있었습니다.

작성 Stephen · 검증과 출시 · 읽는 시간 10분 · 최종 업데이트 2026년 11월 16일

클로드 코드(Claude Code) 에이전트가 고친 코드를 적대적 리뷰(이 코드를 공격한다면 어디가 뚫리는지 묻는 리뷰)에 다시 넣자, 두 번째 리뷰는 첫 수정이 새로 만든 결함을 찾았고 세 번째 리뷰는 "닫았다"고 기록된 같은 결함이 다른 접속 경로로 살아 있는 것을 찾았습니다. SugarMount의 P2P 채팅 앱(Flutter)을 2026년 9월 출시 준비하며 네 번 다시 리뷰한 기록입니다.

두 번째 결함은 두 수정이 만나는 자리에, 세 번째 결함은 수정이 닿지 않은 HTTP 경로와 사실이 아닌 보증을 적은 서버 문서에 있었습니다. 세 번째 결함이 나왔을 때 수정 보고서, 서버 문서, 서버 테스트는 모두 '닫힘'이라고 말하고 있었습니다.

첫 수정 1시간 9분 만에 찾아 고친 로비 잠금

1차 리뷰(9월 8일)는 출시 준비 변경분에서 42건을 찾아 발견마다 Blocker(출시를 막는 등급), High, Medium, Low 가운데 하나를 붙였고, Blocker 둘 다 신원 문제였습니다. 앱은 상대가 보내는 peer id(채팅 상대를 가리키는 식별자)를 그대로 믿었고, 시그널링 서버(같은 네트워크의 상대를 찾아 주는 로비 서버)는 남의 id로 들어오는 접속을 막지 않았습니다.

수정은 에이전트 다섯이 파일을 나눠 맡아 9월 9일 0시 36분 커밋 하나로 들어갔습니다. 이제 id는 공개키에서 계산되어 바뀌지 않고 서버는 id를 처음 잡은 쪽에 묶는데, 둘 다 1차 리뷰가 제안한 방향이었습니다.

2차 리뷰는 코드를 한 줄도 고치지 않고 보고서만 쓰는 별도 에이전트가 이 커밋 하나를 기준으로 읽은 것입니다. 두 수정을 겹치면, 바뀌지 않는 id를 누군가 먼저 잡는 순간 진짜 주인은 거부되고 앱은 그 거부를 치명 오류로 여겨 다시 접속하지 않으므로, 주인은 로비에 다시 나타나지 못합니다. 보고서는 이 로비 영구 잠금을, 수정 전에는 두 번째 join이 허용됐으니 새로 생긴 결함이라고 판정했습니다. 2차 수정 커밋 메시지도 이 결함을 "introduced by the previous round"라고 적었습니다.

같은 보고서의 첫 항목인 말풍선 위조도 수정 사이에서 떨어진 결함이었습니다. 동기화 경로를 맡은 에이전트는 메시지의 방과 발신자를 확인하는 검사를 넣었지만, 실시간 메시지 경로는 다른 에이전트의 파일이라 그 검사가 없었습니다. 연결된 상대가 내 화면에 "내가 보낸 말풍선"을 심을 수 있었고, 보고서는 이를 "두 에이전트의 경계에서 떨어진 항목"이라고 불렀습니다.

새 점유 규칙은 WebSocket에만 걸렸습니다

서버 쪽 지적을 맡은 수정 에이전트(보고서 이름 R8)는 id 점유를 접속이 살아 있는 동안과 짧은 유예 시간으로 제한했습니다. 보고서에는 "영구 잠금이 불가능하다"고 적었고, 같은 뜻의 문장이 서버 README와 프로토콜 문서에도 들어갔으며, 서버 테스트도 통과한 상태였습니다.

3차 리뷰는 그날 새벽 3시 38분 커밋을 git archive로 풀어 고정된 사본에서 읽었습니다. 작업 트리에는 다른 에이전트들이 아직 커밋하지 않은 변경이 있었기 때문입니다. 이 리뷰가 "즉시 고쳐야 하는 것" 맨 위에 올린 문장은 아래와 같습니다. 리뷰 문서는 항목에 번호를 붙여, 2차 항목은 RR-, 3차 항목은 TR-로 시작합니다.

서버에 들어오는 길은 WebSocket과, 그것이 안 될 때 쓰는 HTTP 두 갈래입니다. 점유를 풀어 주는 새 규칙은 WebSocket 접속에만 걸렸고, HTTP로 등록한 쪽은 다른 분기를 타서 만료가 일어나지 않았습니다. 소켓 없이 HTTP 요청만으로 id를 계속 붙잡을 수 있었고, 별도 리뷰 트랙의 실측에서 주인의 WebSocket 접속 10번이 모두 거부됐습니다.

같은 리뷰는 같은 모양을 세 곳에서 더 찾았습니다.

  • 서버는 id를 처음 잡은 쪽에 참가 비밀값(다시 들어올 때 주인임을 증명하는 값)을 줍니다. 앱 재시작 뒤 id를 되찾는 복구 경로가 기존 참가 비밀값을 그대로 돌려줘서, 좁은 조건을 한 번 통과하면 주소와 상관없이 그 id를 가질 수 있었습니다(TR-2).
  • 웹 빌드는 기기끼리 직접 잇지 않고 서버를 거치는 릴레이 전송을 씁니다. 차단한 상대에게 우리 hello(접속 직후 공개키와 닉네임을 알리는 첫 메시지)를 먼저 보내지 않게 바꾼 핸드셰이크가 이 전송에는 적용되지 않았습니다. 릴레이 전송이 새 인터페이스를 구현하지 않아 조용히 예전 동작으로 돌아갔습니다.
  • 메시지 시각이 시간대 표시 없이 오가서, 시간대가 다른 두 기기는 서로의 메시지 해시 검증에 모두 실패했습니다. 같은 PC의 에뮬레이터 두 대는 시간대가 같아 이 결함을 만들 수 없었습니다(TR-26).

오전 10시 10분 3차 수정 커밋은 제목부터 "앞선 수정이 덮지 않은 경로를 닫는다"였습니다. HTTP 점유에도 참가 비밀값을 요구하고, 복구 경로는 비밀값을 새로 만들어 주도록 바꾸었습니다.

가드가 빨개지면 닫혔다고 본 가정

이 라운드의 수정 규칙은 "가드를 지우면 빨개지는 테스트로 고정한다"였습니다. 리뷰어들은 그 주장을 직접 확인했습니다. 2차 리뷰는 가드 제거 실험 3건을, 3차 리뷰는 8건을 다시 돌렸고, 모두 가드를 지우면 테스트가 실패했습니다. 한 건은 보고보다 실패가 하나 더 많았을 뿐 나머지는 실패 수와 이름까지 같았습니다. 그 상태에서 HTTP 잠금이 나왔습니다.

가드 제거 실험은 가드가 있는 경로만 시험합니다. HTTP 경로에는 지울 가드가 처음부터 없었고, 3차 리뷰의 테스트 공백 표는 HTTP 잠금이 "처음부터 덮이지 않았다"고 적었습니다. 재시작 복구 경로에서는 테스트가 오히려 결함을 정상으로 고정했습니다. 수정 에이전트가 쓴 서버 테스트 하나가 같은 비밀값을 다시 받는 동작을 단언하고 있어서, TR-2는 테스트로 잡힐 수 없었습니다.

가드 제거로 테스트를 검사하는 방법은 테스트 3,066개가 초록인데 DB를 못 여는 코드가 숨어 있었다: 가드 지워 보기에 적었습니다. 이 글의 결함들은 그 검사를 통과한 뒤에도 남아 있던 것입니다.

서버 수정 에이전트는 WebSocket 경로만 고친 채 보고서와 서버 문서에 "영구 점유 불가"라는 보증을 적었고, 그 보증을 받친 테스트는 고친 경로만 덮었습니다. 결함을 잡은 쪽도 에이전트였고, 그 리뷰어도 한 번은 틀린 가설을 세웠습니다. 3차 리뷰어는 "거부된 hello가 소켓을 계속 붙잡는다"고 의심했다가, 사본에 테스트를 써서 돌려 가설이 틀린 것을 보고 결함 없음으로 적었습니다. 보고서에 남은 이유는 "추측으로 보고하지 않기 위해 실행했다"입니다.

기록으로 확인되는 사람 손은 규칙 하나입니다. 지금 운영자의 공통 작업 지침에는 큰 수정 뒤 적대적 리뷰를 한 번 더 하고, 같은 결함의 다른 경로를 함께 찾고, 프로덕션 호출자 수를 grep으로 확인한다는 줄이 있습니다. 어느 리뷰를 누가 다시 돌리자고 했는지는 그때 세션 기록이 이 PC에 남아 있지 않아 확인하지 못했습니다.

수정 커밋을 리뷰할 때는 가드가 빨개지는지 묻기 전에, 그 가드가 같은 결함의 모든 입구에 걸려 있는지부터 세십시오.

같은 결함의 다른 입구를 세는 여섯 축

3차 리뷰는 결론에서 덮이지 않은 경로가 반복해서 결함의 위치였다고 적고, 다음 라운드는 "이 가드가 프로덕션의 모든 전송/경로에 적용되는가"를 물어야 한다고 했습니다. 네 번의 리뷰에서 결함이 지나간 입구를 묶으면 여섯 축이 나옵니다.

축이 앱에서 걸린 예확인한 방법
전송 경로WebSocket만 고치고 HTTP는 열림(TR-1), 웹 릴레이에 새 핸드셰이크 미적용(TR-8)인터페이스 구현체마다 가드 유무를 대조
데이터 경로방·발신자 검사가 동기화에만 있고 실시간 메시지에는 없음(RR-1)같은 데이터를 받는 함수끼리 검사를 비교
재발급·복구재시작 복구가 기존 비밀값을 그대로 돌려줌(TR-2)비밀값을 내주는 분기마다 새로 만드는지 확인
문서 보증서버 문서의 "영구 점유 불가"(TR-1), 설계 문서의 "하한은 두지 않는다"(4차)문서의 "never·항상·불가" 문장을 코드와 테스트에 대조
호출자닉네임 마스킹 등록 호출 0곳(RR-5), 옛 대화 페이지 API 호출 0곳(TR-19)새 API마다 프로덕션 코드의 호출자 수를 grep
실행 환경시간대 없는 시각을 같은 시간대 에뮬레이터가 못 드러냄(TR-26)테스트 환경이 만들 수 없는 조건을 따로 적음

여섯 축은 이 앱의 모양에서 나왔습니다. 서버 접속은 WebSocket과 HTTP, 채팅 연결은 TCP와 웹 릴레이로 두 갈래씩이라 전송 축이 길었고, 전송이 하나뿐인 앱에는 이 목록을 써 본 적이 없습니다. 실행 환경 축은 표에 적어도 닫히지 않습니다. 3차 리뷰는 QA 항목에 두 기기의 시간대를 다르게 두는 경우를 넣으라고 권했습니다.

호출자 축은 이 앱에서만 나오지 않았습니다. 한 달 뒤 가족 일정 앱 AXFamily의 기기 E2E 수정 커밋(10월 10일)에도 받은 사진·PDF를 정리 화면으로 넘기는 호출자가 없었다는 줄이 있습니다. 그 앱의 통합 리뷰는 브랜치마다 AI 리뷰를 통과해도 합친 코드에는 결함이 남습니다에 있습니다.

  1. 수정 커밋마다 막은 결함을 한 문장으로 적습니다. 무엇이, 어느 입구로 들어와, 무엇을 하는지입니다.

  2. 여섯 축마다 그 결함이 들어올 입구를 적습니다. 해당이 없는 축은 "없음"이라고 적고 넘어갑니다.

  3. 입구마다 같은 가드가 걸려 있는지 grep으로 셉니다. 3차 리뷰가 센 것은 인터페이스 구현체 수, 한도 검사 함수의 호출 지점 수, 새 API의 프로덕션 호출자 수였습니다.

    # 전송 클래스들이 함께 구현하는 인터페이스의 구현체 전부
grep -rn "implements TransportService" lib/
# 옛 대화를 페이지로 읽는 API의 프로덕션 호출자
grep -rn "getMessagesPage\|MessageCursor" lib/

  4. 수정 diff를 수정에 참여하지 않은 리뷰 에이전트에게 보고서 전용으로 넘기고, 직전 지적마다 닫힘·부분·미해결 판정표를 만들게 합니다.

  5. 수정 에이전트가 쓴 테스트 가운데 지금 동작을 정상으로 못 박는 것을 따로 읽습니다. 같은 값을 다시 받는다고 단언하는 테스트는 결함까지 함께 고정할 수 있습니다.

  6. 리뷰를 돌리기 전에 멈춤 조건을 정합니다. 이 앱의 마지막 리뷰 지시서는 새 검증 영역을 열지 않고, Blocker·High만 고치고, Medium 이하는 백로그로 넘긴다고 정했습니다.

네 번 돌려도 0건이 되지 않았습니다

차수별 발견 수는 네 번 모두 18건 아래로 내려가지 않았고, Blocker와 High를 합친 수도 한 번도 0이 되지 않았습니다. 2차 리뷰는 수정 커밋 하나(83개 파일)만 읽었고, 문서에 집계 줄이 없어 심각도가 붙은 항목만 세었습니다.

4차 리뷰는 직전 수정 묶음을 읽고 26건 가운데 24건을 그 묶음이 만든 결함으로 판정했습니다. 지시서는 앞선 리뷰마다 직전 수정이 만든 결함이 나왔다는 기록을 들어 멈출 자리를 미리 정해 두었습니다. 0건을 기다리는 대신 이 규칙으로 멈추었고, Medium 이하 16건은 백로그 후보로 표시됐습니다.

수정 보고서의 "닫힘"과 가드 제거 실험의 일치는 이번에 둘 다 닫힘의 근거가 되지 못했습니다. 수정 에이전트는 자기 수정을 가드 제거 실험으로 확인했지만, 자기 수정을 적대적 리뷰로 다시 보게 한 기록은 없어 비교 자료가 없습니다.

2차 리뷰의 로비 잠금과 말풍선 위조는 코드 판독으로만 확인한 결과이고, 두 클라이언트로 재현하는 일은 다음 라운드로 넘어갔습니다. 웹 릴레이 결함은 웹 빌드를 띄워 확인한 적이 없습니다. 결함 보고가 틀린 경우도 있었습니다. 4차 지시서는 이 라운드에 결함으로 보고됐다가 철회된 것을 5건으로 적었습니다(대비·스플래시·시뮬레이션 착시 등).

아직 확인하지 않은 것은 두 가지입니다. 4차 리뷰가 백로그 후보로 돌린 16건 가운데 다른 경로로 다시 살아난 것이 있는지, 그리고 9월 11일 뒤 이 앱의 수정 커밋에서 여섯 축을 실제로 적었는지입니다.

2026-11-15 확인. P2P 채팅 앱 저장소 git 기록(커밋 df1dddc, 684ff8c, 5c44c96, 6c99027, 8f5a0a5, Claude Opus 5 공동 작성), 적대적 리뷰 문서 4개(2026-09-08~09-11)와 서버 수정 보고서, 4차 리뷰 지시서, 출시 준비 라운드 프로젝트 메모리, 가족 일정 앱 저장소 커밋 6a51d59(2026-10-10).
