클로드 코드 안드로이드 광고 SDK, 빌드로 막기

클로드 코드로 만든 광고 0 게이트는 의존성 그래프와 병합 매니페스트를 함께 봐야 했습니다. 의존성만 보면 AD_ID가 들어와도 통과했습니다.

작성 Stephen · 스토어와 수익화 · 읽는 시간 11분 · 최종 업데이트 2026년 11월 18일

광고 SDK를 한 줄도 넣지 않은 안드로이드 앱에도 광고 ID 권한은 들어옵니다. 한글뷰어 슈가독은 광고를 아예 넣지 않기로 한 앱인데, 통계용 Firebase Analytics가 끌고 오는 라이브러리 4개가 AD_ID 권한을 선언하고, 빌드가 그것을 앱 매니페스트에 합쳐 넣습니다. 그대로 두면 스토어에는 "광고 없음, 광고 ID 안 씀"이라고 신고해 놓고 AAB에는 그 권한이 들어가게 됩니다.

클로드 코드(Claude Code) 에이전트가 처음 만든 게이트는 의존성 그래프만 봤고, 리뷰 에이전트가 그 구멍을 짚었습니다. 2026년 11월 18일 같은 저장소를 임시 사본으로 풀어 다시 돌려 보니, 의존성만 보는 게이트는 병합 매니페스트에 AD_ID가 든 빌드를 그대로 통과시켰습니다.

목차 (5)
  1. 광고 0을 고른 날, 게이트는 의존성만 봤습니다
  2. Firebase가 AD_ID를 다시 넣는 경로
  3. 같은 앱을 네 상태로 돌린 결과
  4. 의존성과 병합 매니페스트를 한 작업에 걸기
  5. 목록 밖 광고 SDK와 테스트 없는 배선

광고 0을 고른 날, 게이트는 의존성만 봤습니다

같은 저장소의 사진 앱 세 개는 배너, 전면, 앱 오프닝 광고를 넣습니다. 문서 뷰어를 시작할 때 에이전트는 광고안을 두 가지로 올렸고(광고 SDK 0, 또는 홈 배너 1개), 운영자는 10월 5일 새벽 "광고 0"을 골랐습니다. 저장소 설정 파일에는 adsMode=NONE 한 줄이 생겼습니다.

두 시간쯤 뒤 구현 에이전트가 게이트를 만들었습니다. 릴리스 설정 검사 작업 verifyReleaseConfig에 광고 ID 칸은 비어 있어야 하고, 릴리스 의존성 그래프에 구글 광고 SDK(Google Mobile Ads, 줄여서 GMA)나 동의 화면 SDK(UMP)가 없어야 한다는 규칙이 들어갔습니다. 앱 매니페스트에는 광고 ID 권한을 지우는 tools:node="remove" 줄 4개를 넣었고, 병합된 릴리스 매니페스트를 읽는 단위 테스트 2개가 그 줄을 지켰습니다.

워크플로 지시문에는 "가드를 하나 넣을 때마다 잠깐 지워 보고 테스트가 실패하는지 확인하라"는 줄이 있었고, 구현 에이전트는 일부러 깬 사본을 여러 개 만들어 돌렸습니다. 다만 광고 ID나 광고 모듈을 넣은 사본은 AAB 빌드가 의존하는 verifyReleaseConfig까지 돌렸지만, remove 줄을 지운 사본은 단위 테스트로만 돌렸고 그 작업으로는 확인하지 않았습니다.

구현이 끝나자 곧바로 리뷰 에이전트 4명이 붙었고, 규칙·게이트 관점의 리뷰어가 이렇게 적었습니다. "bundleRelease는 게이트 하나, verifyReleaseConfig에만 의존하고, 그 작업은 의존성 그래프는 보지만 병합 매니페스트는 보지 않는다." remove 줄을 지우고 AAB를 만들어 올리면, 스토어에는 광고 ID 없음이라 신고했는데 AAB에는 AD_ID가 있게 된다는 지적이었습니다. 리뷰어는 이 지적을 minor로 분류했고, 매니페스트를 읽는 단위 테스트는 출시 스크립트에서만 돌고 AAB 빌드 명령으로는 돌지 않는다고 함께 적었습니다.

수정 에이전트는 20분쯤 걸려 규칙을 별도 파일로 빼고, 병합 매니페스트 검사를 같은 작업 안에 넣었습니다. 같은 날 오전 운영자는 "광고가 전혀 없는 거냐"고 다시 물었고, Play Console 앱 콘텐츠의 광고 항목과 광고 ID 항목을 모두 "없음"으로 입력했습니다. 수정까지 거친 이 게이트가 10월 8일 커밋 ca1ade4로 저장소에 들어갔습니다. 의존성만 보던 첫 게이트는 커밋되지 않았습니다.

Firebase가 AD_ID를 다시 넣는 경로

뷰어의 통계 모듈은 Firebase Analytics에 의존합니다. 11월 18일 다시 뽑은 릴리스 의존성 그래프에서 firebase-analytics 23.2.0은 측정 라이브러리 묶음을 끌고 오고, 그 안에 광고 ID를 읽는 play-services-ads-identifier 18.0.0이 있습니다.

매니페스트 병합 보고서는 권한마다 어느 라이브러리가 넣었는지 적습니다. remove 줄을 지운 상태에서 AD_ID는 라이브러리 4개가 선언했고, 안드로이드의 새 광고 측정 API(AdServices) 권한 2종은 그중 2개가 넣었습니다. 앱 매니페스트가 함께 지우던 ACCESS_ADSERVICES_TOPICS는 이번 버전에서는 아무 라이브러리도 선언하지 않아, 병합기가 "지울 대상이 없다"는 경고만 냈습니다.

의존성 검사가 조용한 것은 거부 목록에 play-services-ads-identifier가 없기 때문입니다. 넣으면 Firebase Analytics 자체가 막히므로 코드 주석에 "이것은 광고 SDK가 아니다"라고 적어 두고 일부러 목록에서 제외했습니다. 권한은 매니페스트에 선언되므로, 의존성 목록만 보는 검사는 처음부터 이 경로를 볼 수 없습니다.

거부 목록을 넓히는 방법지금 그래프에서 생기는 일고르지 않은 이유
play-services-ads-identifier도 거부Firebase Analytics가 끌고 오므로 항상 실패통계를 빼야 함
모듈 이름에 ads가 있으면 실패ads-identifier와 privacysandbox ads-adservices가 Firebase 경유로 걸림오탐
설정값만 검사광고 모듈을 넣은 D 상태에서도 설정은 깨끗함광고 모듈이 들어와도 못 봄
bundleRelease가 릴리스 단위 테스트 전체에 의존리뷰어가 낸 두 번째 안기록에 고르지 않은 이유가 없음

remove 줄이 사라지면 Firebase의 라이브러리 4개가 AD_ID를 다시 넣고, 허용된 의존성이라 의존성 검사는 조용하고, 매니페스트를 보는 테스트는 AAB 빌드 경로 밖에 있었습니다. 수정 에이전트는 이 가운데 마지막 고리를 끊었습니다. 병합 매니페스트 검사가 verifyReleaseConfig 안으로 들어가, 앞의 세 고리가 그대로여도 bundleRelease가 실패합니다.

같은 앱을 네 상태로 돌린 결과

원본 저장소는 건드리지 않고 origin/main을 임시 폴더로 풀어 뷰어 앱의 verifyReleaseConfig를 네 번 돌렸습니다. Firebase 설정 파일은 저장소에 있는 가짜 템플릿을 넣었습니다(없으면 모든 실행에 "google-services.json is missing" 한 줄이 붙습니다).

상태바꾼 것결과병합 매니페스트의 AD_ID
A없음통과없음
Bremove 줄 4개 삭제실패, 매니페스트 3줄있음
CB + 매니페스트 검사 호출 제거통과있음
D사진 앱 광고 모듈 의존 추가실패, 의존성 3줄 + 매니페스트 12줄없음

C가 10월 5일 처음 만든 게이트에 가까운 상태입니다. 광고 ID 권한이 들어 있는데 빌드가 성공합니다. D는 반대 방향입니다. remove 줄이 그대로라 AD_ID는 지워졌지만, 광고 SDK와 UMP, 광고 SDK가 끌고 오는 WorkManager가 의존성에 걸리고, 매니페스트에는 광고 화면 하나와 WorkManager 컴포넌트 11개가 걸립니다. B는 매니페스트 검사만 잡고, D는 두 겹이 모두 잡습니다.

같은 사본에서 매니페스트 검사 호출을 지운 채 규칙 테스트(./gradlew -p build-logic test)도 돌렸습니다. 15개가 모두 통과했습니다. 규칙 함수는 테스트가 지키지만, 작업이 그 함수를 부르는지는 아무 테스트도 보지 않습니다.

의존성과 병합 매니페스트를 한 작업에 걸기

컨벤션 플러그인(여러 모듈이 같이 쓰는 Gradle 빌드 설정 플러그인)이나 앱 모듈의 build.gradle.kts 어디에 둬도 됩니다. 이 저장소는 모든 앱이 쓰는 컨벤션 플러그인에 두고, 앱별 설정 파일의 adsMode로 적용 여부를 정합니다.

  1. 앱 설정에 광고 모드 항목을 만듭니다. NONE이면 광고 ID 칸은 모두 빈 값, 광고 플래그는 모두 false여야 통과하게 합니다.

  2. 릴리스 런타임 의존성 그래프(releaseRuntimeClasspath)를 끝까지 따라가 외부 모듈의 group:name을 모으고, 정확한 이름 목록과 대조합니다. 뷰어의 목록은 구글 광고 SDK 4종, UMP, WorkManager 2종을 합쳐 7개이고, play-services-ads-identifier는 넣지 않습니다.

  3. 앱 매니페스트에 광고 ID 권한을 지우는 줄을 넣습니다.

    <uses-permission android:name="com.google.android.gms.permission.AD_ID" tools:node="remove" />
<uses-permission android:name="android.permission.ACCESS_ADSERVICES_AD_ID" tools:node="remove" />
<uses-permission android:name="android.permission.ACCESS_ADSERVICES_ATTRIBUTION" tools:node="remove" />
<uses-permission android:name="android.permission.ACCESS_ADSERVICES_TOPICS" tools:node="remove" />

  4. 같은 작업 안에서 릴리스 변형의 병합 매니페스트를 읽고, AD_ID와 ACCESS_ADSERVICES_* 권한, GMA 메타데이터, GMA·UMP·WorkManager 컴포넌트가 있으면 실패시킵니다. 3번 줄이 사라졌을 때 잡는 것이 이 단계입니다. 저장소 코드에서 권한 부분만 옮기면 이렇습니다.

    // 플러그인: 릴리스 변형의 병합 매니페스트를 작업 입력으로 연결
onVariants(selector().withBuildType("release")) { variant ->
    mergedReleaseManifest.set(variant.artifacts.get(SingleArtifact.MERGED_MANIFEST))
    releasePackage.set(variant.applicationId)
}
// 규칙 함수: 권한 이름 대조
(elements("uses-permission") + elements("uses-permission-sdk-23")).map { it.name() }
    .filter { it == "com.google.android.gms.permission.AD_ID" || it.startsWith("android.permission.ACCESS_ADSERVICES_") }
    .forEach { problems += "adsMode=NONE but the merged manifest requests $it" }

  5. AAB를 만드는 작업이 이 작업에 의존하게 합니다.

    tasks.matching { it.name == "bundleRelease" }.configureEach { dependsOn(verifyReleaseConfig) }

  6. 규칙은 Gradle 타입이 없는 함수로 빼서 규칙마다 "깨면 실패한다"는 단위 테스트를 붙입니다. 그다음 실제 프로젝트를 위 A~D 네 상태로 돌려, A와 C는 통과하고 B와 D는 실패하는지 봅니다. 깨뜨린 상태 가운데 통과하는 것은 C뿐이어야 합니다.

  7. 어느 라이브러리가 권한을 넣는지는 build/outputs/logs/manifest-merger-release-report.txt에서, 무엇이 끌고 오는지는 ./gradlew :app:dependencies --configuration releaseRuntimeClasspath에서 확인합니다.

2번과 4번 목록은 기억으로 채우지 말고, 지금 프로젝트에서 뽑은 의존성 그래프와 병합 보고서를 보고 쓰십시오.

목록 밖 광고 SDK와 테스트 없는 배선

이 게이트가 아는 광고 SDK는 구글 것뿐입니다. 의존성 목록은 정확한 모듈 이름 7개이고, 매니페스트 접두사는 4개로, GMA(2개)·UMP·WorkManager를 봅니다. 다른 광고 네트워크 SDK가 들어오면 두 겹 모두 통과합니다. 뷰어에 그런 SDK를 넣어 돌려 보지는 않았습니다.

WorkManager를 막는 규칙은 뷰어가 WorkManager를 전혀 쓰지 않아서 성립합니다(받은 문서함 정리도 WorkManager 없이 합니다). 예약 작업이 필요한 앱이라면 이 줄부터 바꿔야 합니다. 게이트는 bundleRelease에만 걸려 있어서, 릴리스 APK를 만드는 assembleRelease로는 돌지 않습니다.

작업이 규칙 함수를 부르는지는 지금 출시 스크립트가 돌리는 릴리스 단위 테스트가 대신 지킵니다. 이 테스트도 같은 병합 매니페스트를 보지만, AAB 빌드 명령 하나로는 돌지 않습니다. 다음에 할 일은 C 상태를 빌드 로직 테스트로 고정해, 배선을 지우면 테스트가 실패하게 만드는 것입니다.

다른 앱에서 게이트의 입력 자체가 출시물과 달랐던 사례는 출시 게이트가 출시물이 아닌 것을 검사하고 있었다에 썼습니다. 이 글은 같은 빌드에서 매니페스트 겹을 안 본 경우입니다. 사진 앱 쪽 게이트 전체 순서는 바이브코딩 앱 출시 전 점검에 있습니다.
