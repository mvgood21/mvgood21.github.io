클로드 코드 윈도우 CRLF로 깨진 검사 세 종류

클로드 코드를 돌리는 윈도우에서 core.autocrlf=true면 새로 꺼낸 텍스트 파일이 CRLF가 돼 바이트 검사가 깨집니다. 고칠 곳은 배포물이 정합니다.

작성 Stephen · 에이전트와 일하는 법 · 읽는 시간 11분 · 최종 업데이트 2026년 11월 22일

같은 저장소의 같은 파일인데, 한 작업 트리에서는 빌드가 되고 다른 작업 트리에서는 35초 만에 실패했습니다. 한글 문서 뷰어 앱의 엔진 파일이 디스크에서 11,548바이트 커져 있었고, 늘어난 바이트 수는 그 파일의 줄 수와 같았습니다.

윈도우의 git은 저장소를 새로 꺼낼 때 텍스트 파일의 줄바꿈을 CRLF로 바꾸었고, 클로드 코드(Claude Code)를 돌리는 하네스는 저장소마다 작업 트리를 이렇게 새로 꺼내 사용합니다. WSL에서 파일째 복사해 온 원래 작업 트리는 대부분 LF로 남아 있어서 차이가 드러나지 않았습니다. 이전하고 한 달 사이 같은 원인으로 검사가 네 번 깨졌고, 고친 자리는 매번 달랐습니다.

엔진 파일이 11,548바이트 커져 빌드가 실패했습니다

11월 4일 오전 9시 18분, 하네스의 하루 점검 회차가 한글 뷰어 SugarDoc의 디버그 빌드를 돌렸습니다. 빌드는 자산 검사 단계인 verifyRhwpAssets에서 실패했습니다. 이 검사는 문서 엔진 rhwp의 두 파일(rhwp.js, rhwp_bg.wasm)을 npm 배포본과 같은 바이트로, 글꼴과 글꼴 CSS, 라이선스 원문은 자산 목록 파일에 적어 둔 바이트로 고정해 두고, 빌드할 때마다 크기와 SHA-512 해시를 비교합니다.

실패 메시지 첫 줄은 rhwp.js: size 444510 != pinned 432962였습니다. 에이전트는 1분 안에 줄바꿈 자동 변환 설정 core.autocrlf가 true인 것을 찾았습니다. 하네스 트리의 fonts.css는 CRLF였고, 같은 저장소의 원래 작업 트리에 있는 같은 파일은 LF였습니다. 원래 트리에서는 10월 25일에 이 앱이 문제없이 빌드됐습니다.

11월 21일에 임시 폴더로 새로 클론해 같은 상황을 다시 만들어 보니, 고정된 파일 28개 가운데 텍스트 파일 16개가 맞지 않았습니다. 그대로였던 12개는 바이너리 11개(글꼴 10개, wasm 1개)와, 원본 자체에 CRLF가 섞여 있어 git이 건드리지 않은 라이선스 파일 1개(러스트 크레이트 고지문)입니다. 출력에서 CRLF로 변환된 파일이 31개로 16개보다 많은 것은 같은 폴더에 고정 목록 밖의 파일(직접 작성한 뷰어 코드)도 있기 때문입니다.

복사해 온 트리는 LF, 새로 꺼낸 트리는 CRLF

core.autocrlf=true는 Git for Windows 설치본의 시스템 설정 파일에 있었습니다. git config --show-origin core.autocrlf가 그 위치를 출력했고, 전역 설정과 저장소 설정에는 이 값이 없었습니다. 이 설정이 켜져 있으면 git은 커밋에 LF로 들어 있는 텍스트 파일을 꺼낼 때 줄마다 CR 한 바이트를 붙입니다.

10월 18일 WSL에서 윈도우로 이전할 때 저장소는 rsync로 파일째 복사했습니다. 복사는 LF 바이트를 그대로 가져왔습니다. 복사해 온 트리에도 지금은 커밋은 LF인데 디스크는 CRLF인 파일이 40개 있지만, 윈도우의 git이 처음부터 꺼낸 트리는 텍스트 파일 대부분이 CRLF입니다. 하네스는 저장소마다 자기 작업 트리를 따로 만드는데, 유틸 앱 저장소의 하네스 트리는 10월 25일, 사이트 저장소의 것은 11월 1일 저녁에 생겼습니다.

깨진 날짜는 트리마다 달랐습니다. CSS 한도는 사이트 하네스 트리가 생긴 11월 1일 저녁에, 자산 검사는 하네스 기록상 유틸 하네스 트리에서 SugarDoc을 처음 빌드한 11월 4일에 깨졌습니다. 10월 23일 실패는 하네스 트리가 생기기 전이라 어느 트리에서 났는지 기록에 없지만, 그 테스트가 읽는 뷰어 코드 3개(viewer.js, edit.js, protocol.js)는 지금 복사해 온 트리의 '커밋은 LF, 디스크는 CRLF' 파일 40개에 들어 있습니다. 이 40개가 언제 CRLF가 됐는지는 파일별로 확인하지 않았습니다.

CSS 한도 초과는 4바이트 여유가 사라진 결과였습니다

사이트 쪽 실패는 11월 1일 저녁 8시대 기록에 먼저 나옵니다. 빌드 검사가 BUDGET-CSS 오류(site.css 41,055바이트, 한도 40,960바이트)를 냈고, 기록은 이 오류를 다른 세션의 레이아웃 커밋에서 났다고 적고, 발행 전에 해결할 일로 넘겼습니다.

같은 날 23시 13분 회차의 에이전트는 git이 커밋에 저장한 파일 내용(blob)의 크기를 먼저 확인했습니다. 40,595바이트로 한도 안이었고, 디스크 크기와의 차이 460은 그 파일의 줄 수와 같았습니다.

검사기 checks.py는 CSS 크기를 디스크 파일 그대로(os.path.getsize) 계산했습니다. HTML 한도 쪽은 파일을 Python 텍스트 모드(읽을 때 CRLF를 LF로 변환해 주는 기본 방식)로 읽어서 재기 때문에 같은 결함이 우연히 막혀 있었습니다. GitHub Pages는 커밋된 파일을 내보내므로 에이전트는 CSS 검사가 CR을 빼고 세도록 고쳤습니다(eed841d).

오류를 본 때부터 커밋까지 2분쯤 걸렸고, 그 사이에 에이전트가 두 번 틀렸습니다. 처음 쓴 테스트는 CRLF로 변환해도 한도를 넘지 않는 크기라 고친 코드를 시험하지 못했고, 에이전트는 실행 전에 크기를 키웠습니다. 다음은 운영자가 정해 둔 규칙대로, 고친 줄을 되돌려도 새 테스트가 실패하는지 보는 단계였습니다. sed 치환식의 이스케이프가 틀려 실제로는 아무 줄도 변경되지 않았는데, 결과는 OK로 나왔습니다. 에이전트가 값을 직접 찍어 본 뒤 줄 번호로 다시 바꾸자 그제야 테스트가 실패했습니다.

사이트 도구에는 지금 이렇게 CRLF를 LF로 바꾸는 줄이 6곳 있고, 10월 18일부터 11월 15일 사이 네 날에 걸쳐 따로따로 들어갔습니다.

정규식 테스트는 \n만 기다렸습니다

세 번째 종류는 파일 내용을 정규식으로 보는 테스트입니다. 10월 23일, 이전 뒤 윈도우에서 처음 돌린 유틸 앱 단위 테스트가 5가지 이유로 실패했는데, 그중 하나가 웹 뷰어의 보안 정책 테스트였습니다. LF를 기대한 패턴이 CRLF 파일에서 맞지 않았고, 읽을 때 \r\n을 \n으로 바꾸는 한 줄로 고쳤습니다(62488f2).

11월 16일에는 이 노트를 쓰는 에이전트가 같은 일을 겪었습니다. 가족 일정 앱 AXFamily의 E2E 격리 테스트를 옛 커밋으로 다시 돌리다가, git archive(커밋을 폴더로 풀어내는 명령)로 풀어 놓은 사본에서 사례 하나가 실패했습니다. 이 테스트는 보호 장치를 하나씩 지운 사본을 만들어 판정기가 그것을 잡는지 봅니다. 지우는 정규식이 줄 끝을 \n으로만 기대해서, CRLF 파일에서는 아무것도 지우지 못했습니다.

11월 21일에 다시 돌려 보니 CRLF 사본은 21개 중 20개, LF 사본은 21개 모두 통과했습니다.

그 실패 메시지는 "사례가 파일을 바꾸지 못했다"였습니다. 치환이 실제로 일어났는지부터 단언하는 테스트라 조용히 넘어가지 않았습니다. 11월 1일 되돌림 검사에는 이 단언이 없어서, 치환이 일어나지 않았는데도 OK로 넘어갔습니다(그때 원인은 CRLF가 아니라 sed 이스케이프였습니다).

파일을 고칠지 검사기를 고칠지는 배포물이 정합니다

APK에는 빌드할 때 디스크에 있는 파일이 들어갑니다. CRLF 트리에서 그대로 빌드했다면 npm 배포본과 다른 rhwp.js가 앱에 들어갔을 것이므로, 자산 검사는 맞게 실패했습니다. 이쪽은 파일을 고쳐야 했습니다. 사이트는 반대로, 배포가 커밋된 파일을 쓰므로 디스크 크기를 계산한 검사가 틀렸습니다.

"검사는 커밋된 파일 기준으로"를 모든 검사에 일괄로 걸지 마십시오. APK 자산 검사에 그렇게 했다면 텍스트 자산 16개에 CRLF가 든 APK가 검사를 통과했을 겁니다.

아래 표의 .gitattributes는 경로마다 git의 처리 방식을 적어 두는 저장소 파일이고, -text는 그 경로를 텍스트로 보지 않게 해 git이 줄끝을 바꾸지 않게 하는 속성입니다.

eol=lf는 꺼낼 때 줄끝을 LF로 맞추라는 속성입니다. 러스트 크레이트 고지문은 -text를 걸면 그대로 남지만, eol=lf를 건 뒤 git add --renormalize(이미 커밋된 파일에 지금 속성을 다시 적용하는 명령)를 하면 원본에 있던 CRLF 줄에서 CR이 빠진 채 커밋 대상이 됩니다. 11월 4일 기록에는 eol=lf도 core.autocrlf=false도 검토한 흔적이 없고, 표의 아래 세 줄은 11월 21일에 따로 시험한 결과입니다.

속성을 바꾸어도 이미 꺼낸 파일은 그대로였습니다

11월 4일 에이전트는 .gitattributes에 주석 한 줄과 -text 두 줄을 쓰고 git checkout-index -f로 파일을 다시 꺼냈지만, 파일은 여전히 CRLF였고 빌드도 다시 실패했습니다. fonts.css 하나로 다시 해 봐도 고정값 6,410바이트가 아닌 6,465바이트 그대로였고, 11월 21일 임시 클론에서도 결과가 같았습니다.

에이전트는 이어서 sed로 그 폴더의 텍스트 파일에서 CR을 모두 지웠고, git diff --stat에 변경되면 안 되는 파일이 하나 나왔습니다. 앞에서 말한 러스트 크레이트 고지문인데, 원본에 원래 있던 81줄의 CR까지 sed가 지운 결과였습니다. 이 파일만 커밋된 바이트로 다시 써 넣자 9시 22분에 빌드가 통과했습니다.

그날 점검 기록에는 "새로 체크아웃한 트리에서는 다시 시험하지 않았다"는 문장이 있습니다. 11월 21일에 재 보니 이미 CRLF로 꺼낸 트리는 그 폴더를 치우고 다시 꺼낸 뒤에야 맞았습니다.

새 작업 트리에서 바이트 검사 전에 볼 것

  1. 설정이 어느 파일에서 오는지 봅니다.

    git config --show-origin core.autocrlf

  2. 꺼낼 때 변환된 파일 수를 확인합니다. 커밋은 LF, 디스크는 CRLF인 파일이 i/lf w/crlf로 나옵니다.

    git ls-files --eol | cut -f1 | sort | uniq -c

  3. 검사 대상 파일 하나를 디스크와 커밋 양쪽에서 크기를 비교합니다.

    wc -c < assets/site.css
git cat-file -s HEAD:assets/site.css

  4. 바이트를 재는 검사마다 배포물이 디스크 파일인지 커밋된 파일인지 적고, 위 표에서 고칠 곳을 선택합니다.

  5. .gitattributes를 바꾸었다면 해당 폴더를 작업 트리 밖으로 치우고 다시 꺼낸 뒤 2·3단계를 다시 봅니다(git 2.45.2, 2026년 11월 21일 확인).

    git checkout-index -a -u

  6. 가드를 지워 테스트가 실패하는지 볼 때는 지우는 치환이 실제로 파일을 바꾸었는지부터 확인합니다.
