서치콘솔 사이트맵 '가져올 수 없음' 열흘: 새 도메인 속성에서는 몇 초 만에 처리

화면의 '가져올 수 없음'은 API에서 isPending=True, lastDownloaded 없음이었고, 그 열흘 동안 색인은 직접 요청한 URL로 늘었습니다.

작성 SugarMount · 웹사이트와 검색 · 읽는 시간 13분 · 최종 업데이트 2026년 11월 2일

Search Console(서치콘솔)에 낸 sitemap.xml을 Google은 사이트를 옮기기까지 열흘 동안 한 번도 내려받지 않았습니다. 첫 제출은 2026년 10월 21일(API 날짜 기준)이고 그 뒤로 API 값이 바뀌지 않았는데, 10월 25일 URL 검사 실제 테스트에서 Googlebot은 그 파일을 정상으로 가져갔고, 같은 날 Bing도 sitemap.xml을 처리했습니다. 10월 31일 사이트를 맞춤 도메인으로 옮기고 새 도메인 속성에 같은 사이트맵 4개를 내자 제출 7초 안에 모두 처리됐습니다.

근거는 Search Console API(sitemaps, URL Inspection) 조회 기록, 이 사이트의 사이트맵 감사 스크립트 출력, Bing Webmaster Tools 화면, 사이트 저장소의 git 기록입니다. 시각은 한국 시간이고, 기준일은 2026년 11월 1일입니다.

옛 속성은 11월 1일에도 대기, 새 속성은 몇 초

11월 1일 오전, 두 속성의 사이트맵 목록을 API로 다시 읽었습니다. 옛 github.io 주소로 만든 URL 접두어 속성에는 sitemap.xml과 하위 사이트맵 3개가 isPending=True, lastDownloaded 없음, errors=0으로 남아 있습니다. 마지막 제출은 모두 10월 30일입니다(sitemap.xml 03시 43분, 하위 사이트맵 3개 15시 43분). 새 도메인 속성의 같은 4개는 isPending=False, errors=0이고, lastDownloaded가 10월 31일 17:05:08~17:05:14에 찍혀 있습니다. 제출 시각이 17:05:07~17:05:08이니 네 개 모두 제출 7초 안에 내려받았습니다(가장 빠른 것은 1초가 안 걸렸습니다).

이전 작업은 사이트 안의 옛 주소를 새 도메인으로 바꾼 것이고, 사이트맵 구성(인덱스 1개, 하위 3개)과 생성 규칙은 그대로입니다. 옛 주소는 같은 경로의 새 주소로 301 한 번에 넘어가고, 새 도메인에서 사이트맵 감사를 다시 돌렸을 때 URL 196개가 모두 200이고 canonical이 자기 주소였습니다. 이전 11시간 뒤 새 속성의 URL 검사 전수(198개)에서는 114쪽이 'Discovered - currently not indexed'였습니다.

실제 테스트에서 Googlebot은 파일을 가져갔습니다

10월 25일 오후, 운영자가 사이트맵이 Search Console에 안 뜨고 robots.txt도 없는 것 같다고 지적했습니다. 에이전트가 확인해 보니 robots.txt는 200으로 있었고 Allow: /와 Sitemap 줄이 들어 있었습니다. sitemap.xml은 sitemaps.org 0.9 형식의 urlset에 hreflang·이미지 확장을 붙인 것이었고, 브라우저에서 표처럼 보인 것은 사람이 볼 때만 쓰는 xml-stylesheet 때문이었습니다. 감사 스크립트로 URL 154개를 모두 열어 보니 전부 200, canonical은 자기 주소, noindex 없음, hreflang 상호 연결, lastmod 형식 정상이었고 이미지 261개도 200이었습니다.

14시 38분, URL 검사에 sitemap.xml 주소를 넣고 실제 URL 테스트를 돌렸습니다. Googlebot은 파일을 받아 'URL을 Google에 등록할 수 있음'으로 판정했습니다. 같은 날 오후 사이트맵 화면의 '가져올 수 없음'을 API 값과 맞대 보면 isPending=True, lastDownloaded 없음, 오류 0입니다. 가져오기를 시도한 기록 자체가 없었습니다.

형식 교체, 재제출 4번, 하위 직접 제출: 모두 대기

운영자는 구조를 의심했고, 에이전트는 17시대에 sitemap.xml을 일반 sitemapindex로 바꿨습니다(커밋 3d93937, c18cf30, 4879355). 하위 사이트맵 3개에는 loc·lastmod·priority·changefreq만 남기고 XSL, hreflang, 이미지 태그를 지웠습니다. lastmod는 사이트맵 lastmod가 전부 같은 날짜였다: 본문 해시로 수정일 정하기에 적은 규칙 그대로입니다. 사람이 보는 HTML 사이트맵도 만들어 URL 156개를 모두 홈에서 두 번 클릭 안에 두었습니다. 같은 17시대에 운영자가 Bing Webmaster Tools에 사이트를 등록했고(Search Console에서 가져오기), Bing은 바꾼 sitemap.xml을 그날 가져가 Success로 처리하고 하위 사이트맵 3개를 찾았습니다. 그날 저녁 Google 쪽은 여전히 대기였습니다.

sitemap.xml은 10월 25일에 두 번, 27일과 30일 새벽에 한 번씩 API로 다시 냈고 응답은 매번 204였습니다. 30일 오후 API는 sitemap.xml을 isSitemapsIndex=False로 보여 줬는데, 한 번도 내려받지 않은 파일이라 인덱스인지도 모르는 상태였습니다. 인덱스를 거치는 첫 처리만 늦은 것이라면 하위 파일이 먼저 처리될 것이라 보고, 하위 3개(URL 94개, 44개, 48개)를 따로 제출했습니다. 네 개 모두 대기로 남았습니다.

10월 25일 아침 첫 기록에서 에이전트는 이 상태를 "새 속성에서 흔한 지연"으로 적고 1주를 기다려 보자고 했는데, 옛 속성은 11월 1일에도 대기였습니다. 10월 25일 재제출 때는 rss.xml과 en/rss.xml까지 사이트맵으로 다시 냈는데, RSS는 사이트맵으로 내지 않는다는 이 사이트 규칙과 어긋났습니다. 따로 낸 sitemap.xml?v=20261025는 중복이라 그날 17시대에 지웠고, RSS 두 개는 운영자 승인을 받아 지워 sitemap.xml 하나만 남겼습니다.

'가져올 수 없음'이 보이면 파일부터 고치지 마십시오. API의 lastDownloaded와 실제 URL 테스트를 먼저 보십시오. 이 사이트에서는 lastDownloaded가 비어 있고 테스트가 성공한 상태에서 형식을 바꿔도 대기가 풀리지 않았습니다.

호스트, 속성 종류, 제출 시점이 한꺼번에 바뀌었습니다

직접 색인 생성을 요청한 URL은 대부분 요청 뒤 1~4시간 안에 크롤됐으니 Googlebot이 사이트에 못 들어온 것은 아닙니다. 남는 설명은 그 속성의 사이트맵 처리 차례가 오지 않았다는 것인데, 차례가 왜 오지 않았는지는 Google 안의 일이라 확인할 수 없습니다. Search Console의 사이트맵 보고서 도움말은 '가져올 수 없음'의 원인으로 robots 차단, 해결되지 않은 수동 조치, 404, 서버 오류 같은 일반 오류, 사이트맵의 낮은 크롤링 수요를 듭니다. 앞의 넷 가운데 robots·404·서버 오류는 위에서 확인해 지웠고, 수동 조치 보고서는 확인하지 않았습니다(요청한 URL은 몇 시간 안에 색인됐습니다). 낮은 크롤링 수요는 확인할 방법이 없는 가설로 남습니다.

새 속성에서는 세 가지가 함께 바뀌었습니다. 호스트가 github.io에서 자기 도메인이 됐고, 속성 종류가 URL 접두어에서 DNS TXT로 인증한 도메인 속성이 됐고, 제출이 열흘 늦었습니다. 이 관찰로는 셋 중 무엇이 차이를 만들었는지 가를 수 없어서, 이 글은 github.io를 원인으로 적지 않습니다.

옛 속성의 URL 검사는 사이트맵을 한 번도 읽지 않은 동안에도 coverageState를 'Submitted and indexed'로 보여 줬습니다(10월 25일 전수, 11월 1일 재조회). 이 사이트에서는 'Submitted'가 사이트맵 처리가 끝났다는 표시가 아니었습니다.

기다린 열흘, 색인은 직접 요청한 URL로 늘었습니다

10월 25일 아침 URL 검사 전수에서 148쪽 중 색인은 7쪽(4.7%)이었고, 141쪽이 'URL is unknown to Google'(아래에서는 '모름')이었습니다. 그날 운영자가 Search Console 쓰기 작업을 맡겼고, 에이전트가 화면에서 색인 생성 요청을 시작했습니다. 14시 29분 API 재검사에서 요청 10건 중 7건이 'Submitted and indexed'였습니다. 요청하고 1~2시간 뒤입니다. 요청하지 않은 URL은 하루가 지나도 그대로여서, 10월 26일 03시 전수의 색인은 22쪽으로 전날 오후와 같았고 모름은 133쪽이었습니다.

그 뒤로 매일 새 글과 대기열을 요청했습니다. 색인은 44쪽(10월 27일), 73쪽(28일), 146쪽(30일), 162쪽(31일)으로 늘었습니다. 10월 27일 전수에서 요청한 쪽은 거의 다 색인됐고, 요청하지 않은 쪽은 대부분 모름이었습니다. 여러 번 요청해도 모름으로 남은 글도 있었습니다.

요청 한도는 에이전트가 처음에 잘못 읽었습니다. 10월 25일 15건이 접수된 뒤 '할당량 초과'가 뜨자 "하루 15~16건"으로 적었는데, 27일에는 40건을 내는 동안 한 번도 뜨지 않았습니다. 29일에는 49번 눌러 44건이 접수됐고, 중간에 다섯 번 뜬 '할당량 초과'는 매번 바로 다음 요청이 받아들여졌습니다. 지금은 짧은 간격에 걸리는 속도 제한으로 봅니다. 이 숫자는 이 속성 하나에서 본 값이고 Google이 밝힌 한도가 아닙니다. 브라우저를 조작해 요청하면 한 건에 2분 30초쯤 걸렸습니다.

이 글과 비슷한 문제를 겪고 있다면 메일로 상황을 알려 주세요. 읽고 답하겠습니다. 메일로 문의하기

이전 뒤 요청 7건 중 5건이 4시간 안에 색인

주소 이전은 사이트맵과 별개의 이유로 정해 둔 일이었고, 10월 31일 17시에 했습니다. 새 URL은 몇 분 만에 'Discovered - currently not indexed'로 나왔고, 홈은 3시간 만에 새 주소로 색인됐습니다. 19시 47분부터는 옛 속성에서 노출이 있던 7쪽을 새 속성에 요청했고, 4시간 뒤 5쪽이 'Submitted and indexed'였습니다. 요청에서 색인까지 걸린 시간은 옛 속성 때(1~4시간)와 비슷합니다.

7쪽 중 하나인 /ax/hwp-viewer-rhwp-webview/는 'Duplicate, Google chose different canonical than user'였습니다. 옛 속성에서 옛 URL을 검사하니 'Submitted and indexed', Google이 고른 대표 URL은 옛 주소 자신, 마지막 크롤은 10월 27일이었습니다. 301을 걸기 전입니다. 11월 1일 03시 새 속성 전수에서는 Duplicate가 10쪽이었고, 옛 속성에서 노출이 있던 쪽이 많았습니다. 11월 1일 오전에 다시 검사한 5쪽은 모두 Duplicate 그대로였고, googleCanonical은 3쪽이 비어 있고 2쪽은 github.io URL이었습니다.

Duplicate 쪽은 옛 속성에서 옛 URL로 색인 생성을 요청합니다. 새 주소는 이미 크롤됐고 대표로 남은 쪽이 옛 URL이라, Google이 옛 URL을 다시 크롤해 301을 읽어야 대표가 넘어갈 것으로 봤습니다. 10월 31일 밤에 1건, 11월 1일 아침에 10건을 냈습니다.

새 속성의 검색 실적은 11월 1일 아침까지 0행이었고, 같은 날 아침 기준 옛 속성의 일별 행은 10월 29일(노출 84회, 그때까지 하루 최고)이 마지막입니다. 실적 데이터는 보통 2~3일 늦게 들어오므로 아직은 집계 지연과 가를 수 없습니다.

Google에 남은 길은 화면의 색인 생성 요청뿐

열흘을 기다리는 동안에도 새 글이 하루 ko·en 6쪽씩 나와서, 1주를 더 기다릴 수 없었습니다. Indexing API는 채용 공고와 라이브 영상 페이지 전용이라 노트 페이지에는 쓸 수 없습니다. IndexNow는 발행 때마다 보내고 있었지만 Bing·네이버 등이 받고 Google은 쓰지 않습니다. 남은 길이 URL 검사의 색인 생성 요청이었고, 화면에서만 되는 일이라 에이전트가 브라우저로 했습니다.

lastDownloaded가 찍혔다면 다른 문제입니다

lastDownloaded가 찍혀 있고 errors가 0보다 크면, Google이 파일을 받아 읽다가 걸린 것이니 이 글과 다른 문제입니다. 오류 내용을 고쳐야 합니다. 실제 URL 테스트가 404, robots 차단, 리디렉션으로 실패해도 진짜 가져오기 문제입니다. 사이트 하나, 속성 둘에서 본 기록이라 github.io 위의 다른 사이트가 같은 대기를 겪는지는 모릅니다.

'가져올 수 없음'이 떴을 때 확인할 순서

  1. Search Console API로 사이트맵 목록을 읽고 isPending, lastDownloaded, errors, isSitemapsIndex, lastSubmitted를 봅니다. lastDownloaded가 없고 오류가 0이면 Google이 아직 한 번도 내려받지 않은 상태입니다. 대기인지 실패인지는 다음 단계의 실제 테스트로 가립니다.
  2. URL 검사에 sitemap.xml 주소를 넣고 실제 URL 테스트를 돌립니다. 등록할 수 있다고 나오면 가져오기는 됩니다.
  3. 사이트맵 안 URL을 모두 열어 200, 자기 canonical, noindex 없음, hreflang 상호 연결, lastmod 형식을 확인합니다.
  4. Bing Webmaster Tools에 같은 사이트맵을 냅니다. Bing이 같은 파일을 처리하면 형식과 접근이 정상이라는 근거가 하나 늘어납니다.
  5. 대기로 판단했으면 새 글마다 색인 생성 요청을 합니다. '할당량 초과'가 뜨면 잠시 뒤 같은 URL을 다시 요청합니다.
  6. 하루 한 번 URL Inspection API로 전수를 돌려 coverageState와 lastCrawlTime을 기록합니다.
  7. 주소를 옮겼다면 새 속성의 Duplicate 쪽을 골라 옛 속성에서 옛 URL로 요청합니다.
# 사이트맵 상태 (읽기 전용)
GET https://www.googleapis.com/webmasters/v3/sites/<속성>/sitemaps
  → path, isPending, lastDownloaded, isSitemapsIndex, errors, lastSubmitted
# URL 하나의 색인 상태
POST https://searchconsole.googleapis.com/v1/urlInspection/index:inspect
  {"inspectionUrl": "<URL>", "siteUrl": "<속성>"}
  → coverageState, lastCrawlTime, googleCanonical
# <속성>: URL 접두어는 https://example.github.io/ (URL 인코딩), 도메인 속성은 sc-domain:example.com

Duplicate 10쪽과 옛 사이트맵 4개

옛 URL /ax/hwp-viewer-rhwp-webview/의 마지막 크롤은 11월 1일 오전에도 10월 27일이었습니다. 아침에 옛 속성에 낸 요청 10건이 301을 다시 읽게 하는지 다음 URL 검사에서 봅니다. 옛 속성의 사이트맵 4개가 언제 처리되는지, 10월 30일 이후 옛 속성의 일별 행이 다시 들어오는지도 봅니다.

자주 묻는 질문

Search Console 사이트맵 '가져올 수 없음'은 파일 오류인가요?

이 사이트에서는 아니었습니다. API 값은 isPending=True, lastDownloaded 없음, 오류 0이었고, 실제 URL 테스트는 성공했습니다.

사이트맵이 처리되지 않으면 새 글은 색인되지 않나요?

색인 생성 요청을 직접 하면 됐습니다. 대기한 열흘 동안 요청한 URL은 대부분 1~4시간 안에 색인됐습니다.

github.io에서 맞춤 도메인으로 옮기면 사이트맵이 바로 처리되나요?

이 사이트에서는 제출 7초 안에 처리됐습니다. 호스트와 속성 종류, 제출 시점이 함께 바뀐 한 번의 관찰입니다.
