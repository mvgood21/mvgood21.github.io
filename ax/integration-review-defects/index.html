AI 에이전트 병렬 브랜치 13개를 합친 뒤 통합 리뷰가 확정 결함 12건을 찾았다

브랜치마다 리뷰와 CI를 통과한 뒤 합친 코드만 다시 읽자 확정 결함 12건이 나왔고, 작성자 분류로는 그중 10건이 두 패키지 사이에 있었습니다.

작성 SugarMount · 에이전트와 일하는 법 · 읽는 시간 13분 · 최종 업데이트 2026년 11월 1일

에이전트 여럿을 한 저장소에서 5/6

합친 코드만 다시 읽은 리뷰 에이전트 여섯이 blocker 2건과 major 10건을 냈고, 반박을 맡은 에이전트는 그중 하나도 깨지 못했습니다. 브랜치 13개는 그 전에 각자 에이전트 3명의 적대적 리뷰와 CI를 통과한 상태였습니다. 2026년 10월 10일 새벽, 가족 일정 앱 AXFamily의 첫 병렬 개발분(Wave 1)을 합칠 때의 일입니다. 12건 모두 기존 테스트에 걸리지 않았고 git 충돌로도 드러나지 않았습니다. 이 글을 쓰며 다시 분류해 보니 10건은 서로 다른 패키지가 만든 두 코드 사이의 약속이 어긋난 것이었습니다.

근거는 git 기록(머지 58920b9~ff0c975, a0351cf, 941d79e·c153fae·74d3685, 5d51b5b, cee9d0f), 통합 PR과 결제 패키지 PR의 본문, 수정 보고, 통합 워크플로 스크립트와 실행 기록(에이전트별 발견과 반박 판정)입니다. 시각은 한국 시간이고, 2026-10-31에 다시 확인했습니다.

01시 51분 머지부터 05시 34분 PR 머지까지

Wave 1은 워크플로 하나 안에서 패키지마다 같은 순서를 돌렸습니다. 에이전트 하나가 구현하고, 보안·비용·정합성 관점의 에이전트 3명이 그 브랜치를 리뷰하고, 수정 에이전트가 고친 뒤 PR을 CI 초록으로 만드는 순서입니다. 1시 51분부터 2분 남짓 동안 13개를 합친 과정과 2시 9분 a0351cf의 최소 수정 6쌍은 Claude 세션 여러 개가 한 저장소를 고칠 때: 머지 13개로 확인한 파일 주인 표에 적었습니다.

그 뒤 리드 세션이 정한 패키지 간 결정을 계약, 서버, 앱 순서로 반영하는 배선 커밋 3개(2시 53분 941d79e, 3시 42분 c153fae, 4시 23분 74d3685)가 올라갔습니다. 리뷰가 읽은 통합본에는 이 배선 커밋까지 들어 있습니다.

리뷰는 4시 29분에 여섯 에이전트가 동시에 시작해 6~9분 만에 끝났습니다(에이전트마다 도구 호출 30~95번). blocker와 major로 올라온 12건은 4시 38분에 건마다 반박 에이전트 한 명씩에게 넘어갔고, 1분 안에 12건 모두 실제 결함으로 판정됐습니다. 수정 에이전트가 5시 28분에 5d51b5b(115파일, 2,088줄 추가)를 올렸고, CI 11개 잡이 통과한 뒤 5시 34분에 통합 PR이 develop에 머지됐습니다.

처음 가정은 테스트가 초록이면 통합이 끝난다는 것

계획서는 Wave 1을 "병렬 기능 구현 (서로 다른 파일만)"으로 정의했고, 충돌 규칙 표도 공유 파일 단위였습니다. 통합 단계 지시문은 충돌을 양쪽 의도대로 풀고, 전체 테스트를 돌리고, 통합 때문에 깨진 곳을 최소로 고치라는 것이었습니다.

통합 에이전트는 그 기준대로 일을 끝냈습니다. PR 본문에 "통합 때문에 깨진 부분만 최소로 고쳤습니다"라고 쓰고 숫자를 붙였습니다. Flutter 테스트 977개, 함수 단위 274개와 에뮬레이터 291개, Rules 테스트 441개(5개 skip), 미디어 Worker 132개가 모두 통과였습니다. 뒤에 나온 12건은 이 숫자 어느 것도 바꾸지 않았습니다. 리드 세션은 워크플로 끝에 리뷰 단계를 미리 넣어 두었고, 결함은 그 단계에서야 나왔습니다.

여섯 관점이 낸 32건, 반박 뒤 남은 12건

여섯 관점은 Rules·계약, 함수 보안, 비용, 앱 보안·개인정보, 앱 UX, 그리고 로그인부터 계정 삭제까지 핵심 흐름을 코드에서 끝까지 따라가는 관점이었습니다. 발견은 모두 32건이었고 minor가 20건, blocker와 major가 12건이었습니다. 비용 관점은 minor만 3건 냈습니다. Rules·계약의 1건과 함수 보안의 1건은 같은 결함을 양쪽에서 따로 찾은 것이라, 서로 다른 결함으로는 11가지입니다.

반박 지시문은 코드를 읽어 이 발견을 반박하고, 입증할 수 없으면 기각하라는 것이었습니다. 반박 에이전트는 건마다 도구를 3~6번 부르고 16~25초 만에 판정했습니다. 판정문은 파일과 줄 번호를 근거로 들었고, 색인 건에서는 같은 모양으로 조회하는 comments와 assets에는 복합 색인이 있다는 대조까지 했습니다.

작성자 분류로는 12건 중 10건이 두 패키지 사이

확정 결함을 "어느 두 코드가 서로 다른 것을 믿었나"로 다시 적으면 아래와 같습니다. 분류는 이 글을 쓰며 한 것이고 원본 기록에는 없습니다. 앱 기능의 세부는 줄였습니다.

브랜치 리뷰는 자기 diff만 읽었습니다

브랜치 리뷰 지시문은 git diff origin/develop...origin/<branch>를 읽게 했습니다. 색인 파일은 develop에 이미 있었고 Rules 패키지가 따로 고치고 있었지만, 자료 화면의 정렬 쿼리를 리뷰한 에이전트가 읽은 diff에는 나오지 않았습니다. 앱 캡처 리뷰어도 같아서, PDF에 application/pdf만 받는 서버 검사는 develop에 있었지만 그 리뷰어의 diff에는 없었습니다.

결제 패키지 리뷰는 이 결함 중 하나를 이미 찾았습니다. 그 브랜치 리뷰의 정합성 관점은 새 API마다 프로덕션 호출자를 grep으로 찾으라는 지시를 받았고, 이것은 지금 운영자 전역 지침에 있는 규칙과 같은 내용입니다. 이 리뷰는 결제 진입 컴포넌트를 부르는 곳이 0이라는 것을 찾았지만 minor로 매겼고, 통합 직전에 결제 패키지를 다시 리뷰했을 때 major로 올라왔습니다. 고칠 자리는 가족 화면 파일이었고, 파일 주인 규칙상 결제 패키지의 수정 에이전트는 그 파일을 고칠 수 없었습니다. 그래서 PR 본문의 "다른 패키지와 맞출 것" 절에 통합 필수 항목으로 올렸습니다. 통합 워크플로의 배선 작업 목록은 1시 28분 워크플로를 띄울 때 이미 스크립트에 적혀 있었고, 결제 패키지 재리뷰 결과는 그 뒤에 나왔습니다. 이 항목은 4시 29분에 시작한 통합 리뷰에서 blocker로 다시 올라왔습니다.

테스트는 패키지마다 자기 가짜 객체와 에뮬레이터 위에서 돌았습니다. 색인 테스트 파일의 첫 줄 주석에도 적혀 있듯 Firestore 에뮬레이터는 복합 색인을 강제하지 않습니다. 계약 문서 6절의 쿼리 표는 sources도 목록 쿼리 대상으로 적었지만, 같은 절의 필수 복합 색인 목록에는 sources가 없었습니다. CI는 통과하고 운영 Firestore에서만 FAILED_PRECONDITION이 났을 것입니다(운영 배포 전에 찾아서 실제로 나지는 않았습니다).

에이전트가 쓴 코드와 테스트도 어긋남을 가렸습니다. 오늘·일정 화면 코드의 주석은 활성 가족 키를 "A1 가족 전환이 쓴다"(A1은 가족 화면 패키지)고 적었지만, git grep으로 찾으면 그 키를 쓰는 코드는 저장소에 없었습니다. 하단 버튼 테스트의 이름은 "자료 정리 FAB은 모든 탭에 있다"였습니다. 명세가 금지한 문구와 위치를 테스트가 정답으로 고정하고 있었습니다.

병렬 브랜치를 합친 뒤에는 브랜치 리뷰를 몇 번 했든 통합본만 읽는 리뷰를 따로 돌리십시오.

고치면서 남긴 검사: 정렬 쿼리-색인 표

수정 보고에 따르면 5d51b5b는 결함마다 수정 전 코드에서 실패하도록 만든 테스트를 붙였습니다. 실제로 수정을 되돌려 실패를 본 것은 Rules, 색인, 동의 판정 쪽입니다(가드를 지워 보는 방법은 가짜 테스트 찾기: 가드를 지워 보는 검사에 적었습니다). 결함 종류를 다음 어긋남을 잡는 검사로 바꾼 것은 두 곳입니다.

색인 쪽은 Rules 테스트에 "앱이 orderBy를 붙이는 쿼리 표"를 넣었습니다. 행마다 앱 파일, 쿼리 이름, 필요한 색인을 적고, 색인 파일에 그 색인이 있는지 봅니다. 마지막 테스트는 표에 있는 파일마다 orderBy: '가 나오는 횟수를 세어 표의 행 수와 비교하고, 앱 코드 전체에서 그 문자열이 나오는 파일 목록도 표와 비교합니다. 새 정렬 쿼리를 쓰는 사람은 표부터 고쳐야 합니다.

const count = (rel) => (readFileSync(resolve(appRoot, rel), 'utf8').match(/orderBy:\s*'/g) ?? []).length;
// …
expect(actual).toEqual(expected);
// 표에 없는 파일에서 orderBy: '<필드>'를 쓰면 실패
const all = execSync(`grep -rlE "^\\s*orderBy: '" lib || true`, { cwd: appRoot, encoding: 'utf8' })
  .split('\n').filter(Boolean).map((f) => f.trim());
expect(all.sort()).toEqual(files.sort());

10월 13일까지 새 정렬 쿼리가 든 앱 파일 3개가 이 표에 올라갔습니다. 표가 먼저 실패해서 올라간 것인지는 기록으로 확인하지 못했습니다. 가족 선택 쪽은 정본을 앱 세션의 현재 가족 값 하나로 정하고, 가족이 둘 이상인데 선택이 없거나 목록 밖이면 첫 가족으로 넘어가지 않고 null을 돌려주게 했습니다. 이 규칙에는 테스트 3개가 붙었습니다.

스테이징 프로젝트와 공유 벡터라는 다른 길

색인 누락은 실제 Firestore 프로젝트에서 돌렸으면 바로 드러났을 결함입니다. 계획서는 스테이징 프로젝트를 출시 뒤 항목으로 보류했고, 이유는 "위험 대비 이득 작음, 결제 지점 증가"였습니다. 같은 날 오전의 기기 E2E도 비용을 0으로 묶으려고 에뮬레이터 백엔드를 썼으니, 거기서도 색인 누락은 보이지 않았을 겁니다.

이미 한 번 통한 방법도 있었습니다. 결제 패키지의 테스트는 결제 서버 패키지가 둘 공유 벡터 파일(이용권 활성 여부의 기대값 표)을 읽도록 미리 쓰여 있었고, 파일이 아직 develop에 없으면 "머지되면 자동으로 돈다"며 건너뛰었습니다. 머지 직후 이 테스트가 돌아 앱과 서버의 이용권 판정이 다르다는 것을 잡았고, a0351cf가 고쳤습니다. 동의 자격이나 가족 선택처럼 벡터 파일이 없던 계약은 이 테스트로는 잡을 수 없었습니다.

코드만 읽은 리뷰가 못 본 것: 기기 E2E 3회차

같은 날 7시 37분 E2E 하네스 커밋 뒤에 돌린 기기 E2E 3회차가 실행 시점 결함을 더 찾았습니다. 그중 d3fde30은 Firestore 트리거가 기본 Admin 앱 없이 죽던 문제였고, 5d51b5b의 수정 보고도 Android 쪽은 Kotlin 단위 테스트만 돌렸다고 적었습니다. 리뷰가 확정 0건으로 끝나도 기기 점검을 따로 돌리는 이유는 에이전트 코드 리뷰, 반박을 버틴 20건만 고쳤다에 정리했습니다.

반박 에이전트는 건마다 한 명이 16~25초씩만 봤습니다. 12건이 모두 남았다는 결과를 반박 단계를 빼도 된다는 근거로 쓰지는 않습니다. 앱 UX 관점은 화면을 UI 명세 문서와 대조하라는 지시를 받았고, 4건 중 하단 버튼과 배너 건은 명세 조항을 근거로 들었습니다. 명세 문서가 없는 프로젝트라면 이 관점은 비교할 기준이 없습니다.

통합 리뷰를 따로 돌리는 순서

  1. 브랜치 PR마다 "다른 패키지와 맞출 것"을 모아 통합 작업 목록에 넣습니다. 배선 목록은 모든 브랜치 리뷰가 끝난 뒤에 확정합니다.
  2. 전부 머지하고 전체 테스트가 초록이 된 다음, 통합본 diff를 영역별 에이전트가 읽기 전용으로 읽게 합니다. 증거가 있는 구체적 결함만 보고하고, 보고하기 전에 스스로 반박해 보라고 지시합니다. AXFamily의 여섯 관점은 Rules·계약, 함수 보안, 비용, 앱 보안·개인정보, 앱 UX(화면과 UI 명세 대조), 흐름 추적(로그인부터 계정 삭제까지)이었습니다.
    git diff --stat origin/develop...origin/<integration-branch>
  3. 새로 만든 컴포넌트, 함수, 인자마다 정의 파일을 빼고 프로덕션 호출자 수를 셉니다. 0이면 그 자체로 발견입니다.
    git grep -n "BillingPlanRow(" -- apps/app/lib ':!apps/app/lib/features/billing/plan_row.dart'
  4. blocker와 major는 건마다 다른 에이전트에게 반박을 맡기고, 입증 못 하면 기각하게 합니다(절차는 에이전트 코드 리뷰, 반박을 버틴 20건만 고쳤다).
  5. 확정 결함마다 수정 전 코드에서 실패하는 테스트를 붙이고, 수정을 되돌려 실패를 확인합니다.
  6. 결함 종류마다 검사를 하나씩 만듭니다. 쿼리와 색인처럼 양쪽을 세어 맞출 수 있으면 표 검사, 판정 규칙이면 양쪽 테스트가 같이 읽는 공유 벡터 파일입니다.

다음에 확인할 것은 서버 쿼리와 표의 빈칸

정렬 쿼리 표는 앱 코드의 orderBy: ' 문자열만 셉니다. 서버 함수의 쿼리는 10월 13일에도 필수 색인 목록에 손으로 추가됐고, where 조건의 모양은 표를 쓴 사람이 맞춰야 합니다. 서버 쪽 쿼리도 같은 방식으로 셀 수 있는지가 다음 확인 대상입니다.

자주 묻는 질문

브랜치마다 AI 리뷰를 했는데 통합 리뷰가 또 필요한가요?

필요합니다. AXFamily에서는 브랜치마다 에이전트 3명이 리뷰했는데도 합친 코드에서 blocker·major 12건이 나왔고, 작성자 분류로는 그중 10건이 두 패키지에 걸친 결함이었습니다. 브랜치 리뷰는 자기 브랜치의 diff만 읽기 때문에 계약의 반대쪽이 그 diff에 없으면 보지 못합니다.

Firestore 에뮬레이터 테스트로 색인 누락을 잡을 수 있나요?

잡을 수 없습니다. 에뮬레이터는 복합 색인을 강제하지 않아 테스트가 통과합니다. 앱의 정렬 쿼리 목록과 색인 파일을 대조하는 정적 검사를 두거나 실제 프로젝트에서 쿼리를 돌려야 합니다.

통합 리뷰는 얼마나 걸렸나요?

리뷰 6~9분, 반박 1분 안쪽이었고, 수정은 커밋까지 약 49분, CI를 거쳐 PR 머지까지 약 55분이었습니다. 앞단의 머지와 배선까지 합치면 1시 51분 머지부터 5시 34분 PR 머지까지 3시간 43분입니다.
