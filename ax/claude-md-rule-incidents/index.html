exit 144는 메모의 2회보다 많았다

pkill -f나 pgrep -f+kill로 프로세스를 끄려던 명령이 에이전트 자신의 셸까지 끊었습니다. Bash 도구가 명령을 bash -c '...패턴...'으로 감싸기 때문에, 패턴이 호출한 셸의 명령줄과도 일치합니다. 호출은 exit 144로 끝나고 같은 호출의 뒤 명령은 실행되지 않습니다. 메모에는 대상이 그대로 남는다고 적혔지만, 확인한 4건에서는 대상이 멈춰 있었습니다. 값이 왜 144인지는 확인하지 못했습니다. SIGTERM이면 관례상 143인데, 10월 18일에 셸이 바뀌어 재현할 수 없었습니다.

에이전트는 10월 4일 16시 53분 이 사고를 게임 프로젝트 메모리에 적으며 두 번 났다고 썼습니다. 세션 기록에서 exit 144로 끝난 Bash 호출을 세어 보니 그 프로젝트에서만 5건, 9월 14일부터 메모까지 집계한 프로젝트 전체에서 24건이었습니다. 메모 뒤까지 합한 31건 모두 호출 안에 pkill -f나 pgrep -f+kill이 있었습니다.

메모 뒤 10월 18일까지 게임 프로젝트에서는 Bash 호출 1,348건 가운데 exit 144가 0건이었고, pkill -f 호출도 0건이었습니다. pgrep -f는 2건 남았지만 끝나기를 기다리거나 프로세스를 확인하는 호출이었고 kill로 이어지지 않았습니다.

다른 프로젝트에서는 10월 5일에 4건, 10월 11일에 3건이 났습니다. 공식 문서는 자동 메모리의 범위를 저장소 단위로 적습니다. 이 메모는 게임 프로젝트 메모리에 있었고, 전역 지침에서 pkill을 찾으면 0건입니다. 다른 프로젝트의 세션에는 이 규칙이 실리지 않았습니다. 그중 한 프로젝트는 그날 자기 메모리에 같은 줄을 따로 적었습니다.

10월 18일 개발 환경을 옮기며 셸이 바뀌어 그 뒤 기록은 비교에서 뺐습니다. 다른 프로젝트도 10월 11일 오후부터는 exit 144가 없었으니, 메모가 원인이라고 단정하지는 않습니다.

한국어 규칙은 첨부된 뒤에도 깨졌다

운영자는 이 요구를 전역 지침에 기록하라고 했습니다. 지침 첨부가 확인된 세션에서는 이틀이 안 돼 10월 4일 01시 23분에 같은 요구가 다시 나왔습니다. 직전 답변은 한글 0자, 라틴 문자 1,691자였습니다.

처음 세운 가설은 세션 수명이었습니다. 재발한 세션은 규칙보다 이틀 먼저 시작했으니 규칙을 못 봤을 것이라는 생각이었는데, 그 세션에는 10월 3일 첫 압축 직후 전역 지침이 첨부됐고 재발은 그 뒤였습니다. 규칙 뒤에 시작해 처음부터 지침이 첨부된 세션도 10월 4일과 5일에 영어로 답했습니다. 다섯 날짜는 이렇게 첨부가 재발보다 앞선 세션 4개에서 운영자가 항의한 날이고, 첨부를 확인하지 못한 요구 3건은 뺐습니다.

메모리와 세션 기록을 보면 깨진 경로는 여러 갈래였습니다. 10월 4일은 다른 세션의 영어 메시지가 이어진 뒤 답변이 영어로 흘렀고, 10월 5일은 선택지를 보여 주는 질문 도구의 질문과 선택지가 영어였습니다. 10월 8일은 한국어로 답하던 세션이 영문 표 출력 뒤 마지막 보고만 영어로 냈고, 10월 24일은 한국어 질문을 받은 턴의 첫 답변부터 끝까지 영어였습니다. 10월 11일에는 맞춤법 앱 프로젝트의 영어 질문을 운영자가 거절하고 한글로 다시 질문하게 했습니다.

항의는 운영자가 말한 날만 잡으므로 답변도 따로 세었습니다. 한국어 메시지 뒤 턴의 마지막 답변 가운데 코드를 빼고 80자 이상이며 한글이 10% 미만인 것 55건을 뽑아 모두 읽었고, 오류 메시지와 자동 분류 턴 21건은 오탐이라 분모에서도 뺐습니다. 남은 34건 중 16건은 다른 세션 메시지 같은 자동 입력이 끼어든 뒤였습니다.

규칙을 지키게 할 설정 세 가지는 문서로만 확인했다

공식 문서는 CLAUDE.md와 메모리를 "context, not enforced configuration"으로 적습니다. Claude가 맥락으로 읽을 뿐 강제 설정으로 다루지 않는다는 말이고, 동작을 확실히 막으려면 도구 실행 직전에 도는 PreToolUse 훅을 쓰라고 안내합니다. 답변 문장은 도구 호출이 아니어서 이 훅이 볼 자리가 없습니다. pkill은 막을 명령이 하나인 데 비해, 언어는 10월 4일처럼 앞선 메시지가 영어면 답변 전체가 따라간다고 저희는 봅니다. 10월 24일처럼 앞선 메시지가 한국어여도 영어로 나온 날은 이 설명으로 풀리지 않습니다.

다음 셋은 2026-11-07에 문서로 확인한 내용입니다. 저희 사용자 설정에는 지금 셋 다 없고, 규칙을 지키게 하는 용도로 써 본 적이 없습니다.

  • language 설정: 값을 "an instruction to always respond in that language"로 Claude에게 넘깁니다. 지시가 하나 늘 뿐 강제는 아닙니다.
  • Stop 훅: 답변이 끝날 때 돌며 last_assistant_message로 마지막 답변을 받고, exit 2를 돌려주면 Claude가 멈추지 않고 이어 갑니다. 답변 언어를 검사할 수 있는 자리는 여기입니다. 코드 위주 답변의 오탐과 재시도 비용은 재 보지 않았습니다.
  • permissions.deny의 Bash(pkill *): ~/.claude/settings.json에 두면 모든 프로젝트에 적용되고, 복합 명령의 하위 명령도 잡습니다. 문서는 bash -c처럼 다른 호출 형태는 못 잡는다고 적으며, 31건 중 2건인 pgrep -f+kill도 이 규칙의 대상이 아닙니다.

프로젝트마다 답이 갈린 규칙 두 가지

exit 144만 보면 모든 규칙을 전역에 적는 답이 쉬워 보입니다. 기기 규칙과 커밋 규칙은 프로젝트마다 답이 다릅니다.

2026년 10월 5일 S21에서 minigame_check 실패가 7건 나왔습니다. 에이전트는 12시 17분에 실패가 진짜인지 에뮬레이터에서 확인하겠다고 했고, 같은 스위트가 에뮬레이터에서 58/58로 통과했습니다. 원인은 S21을 함께 쓰던 다른 세션이 실행 도중 자기 앱을 띄운 것이었습니다. 에이전트는 같은 날 프로젝트 메모리에 이 사고를 적으면서, 기기 logcat에서 다른 패키지의 START u0를 찾는 진단 절차를 남겼습니다.

10월 5일 게임 프로젝트 메모는 에뮬레이터를 좋은 대안으로 적었고, 10월 11일 가족 앱 프로젝트에서 운영자는 PC 에뮬레이터를 켜지 말고 S20으로 하라고 지시했습니다. 커밋도 같습니다. 전역 지침은 요청 없이 커밋하지 않는다고 적지만, 10월 22일 게임 프로젝트는 작업 단위마다 커밋하도록 이 규칙을 뒤집었습니다.

대화로만 준 지시는 압축 뒤 사라질 수 있다고 공식 문서가 적는데, 실제로 무엇이 남았는지는 Claude Code 자동 압축 뒤에 남는 것: 요약, 최근 파일, 메모리 색인에 적었습니다. 이 기록은 혼자 쓰는 전역 지침 기준이고, 여러 사람이 공유하는 지침에서는 써 보지 못했습니다.

피해 직전에 들어간 규칙 두 가지

비밀값 규칙은 아슬아슬한 순간에 들어갔습니다. 10월 2일 08시 47분, 에이전트가 작업 환경을 파악하려고 셸 기록 마지막 150줄을 출력했고 그 안에 API 키가 있었습니다. 47초 뒤 에이전트는 전역 지침에 비밀값을 출력하지 말라는 한 줄을 스스로 적었고, 08시 55분 운영자 요청으로 확인 방법까지 담은 규칙이 됐습니다(AI 코딩 에이전트에게서 비밀값 지키기: 채팅, 로그, 토큰 권한에 거는 같은 규칙).

돈 규칙도 비슷합니다. 10월 8일 운영자가 마케팅을 모두 맡기자 에이전트는 광고 계정 생성부터 하겠다고 답했고, 5분 뒤 돈이 나가거나 이상한 일은 먼저 물으라는 지시가 나왔습니다(예약 실행하는 AI 에이전트의 권한 표: 혼자 할 일과 사람이 누를 클릭). 둘 다 되돌리기 어려운 피해가 나기 전이었습니다. 돈과 비밀값 규칙은 사고를 기다리지 말고 먼저 적으십시오.

사고 직후 규칙을 넣는 다섯 단계

  1. 규칙 한 줄과 Why를 함께 적습니다. Why에는 날짜, 실행한 명령, 결과를 넣습니다.
  2. 세션 기록에서 같은 증상을 셉니다. 아래 스크립트는 도구 결과가 인자로 준 문자열로 시작하는 호출만 세므로 메시지나 메모 안의 언급은 잡지 않습니다. 다른 증상은 인자만 바꿉니다. 저희 기록에서는 공개하지 않는 폴더를 제외 인자로 빼면 31이 나옵니다. 
    # python count_results.py "Exit code 144" [제외할 폴더 문자열 ...]
import glob, json, os, sys
needle, skip, ids = sys.argv[1], sys.argv[2:], set()
for path in glob.glob(os.path.expanduser("~/.claude/projects/*/*.jsonl")):
    if any(s in path for s in skip):
        continue
    for line in open(path, encoding="utf-8"):
        if needle not in line:
            continue
        try:
            content = json.loads(line).get("message", {}).get("content")
        except (ValueError, AttributeError):
            continue
        for block in content if isinstance(content, list) else []:
            if isinstance(block, dict) and block.get("type") == "tool_result":
                body = block.get("content")
                text = body if isinstance(body, str) else " ".join(
                    x.get("text", "") for x in body or [] if isinstance(x, dict))
                if text.startswith(needle):
                    ids.add(block["tool_use_id"])
print(len(ids))
    범위에 주의하십시오. 프로젝트 폴더 바로 아래 기록만 읽고 서브에이전트 기록은 세지 않으며, 기간 제한도 없습니다. 도구 결과에 남지 않는 재발은 다른 방법이 필요합니다. 영어 답변이라면 턴 마지막 답변의 한글 비율로 후보를 뽑고 전부 읽으십시오.
  3. 범위를 고릅니다. 두 프로젝트 이상에서 나왔으면 전역에 적고, 조건이 프로젝트마다 다르면 프로젝트 메모리에 적습니다.
  4. 특정 명령을 막는 규칙이면 deny 규칙이나 PreToolUse 훅 후보로 표시합니다. 예: {"permissions": {"deny": ["Bash(pkill *)"]}}
  5. 재발하면 날짜와 새 경로를 How to apply에 덧붙입니다.

같은 사고가 두 번 나면 문장을 고치기 전에 세션 기록부터 다시 세십시오.

전역에 없는 pkill 줄과 10월 24일 뒤의 재발

pkill 줄은 아직 전역 지침에 없고 프로젝트 메모리 두 곳에만 있습니다. 3단계 기준대로면 전역 대상이지만, 10월 18일에 셸을 옮긴 뒤 exit 144가 없어 올릴지 정하지 않았습니다. 다섯 날짜는 10월 24일까지 운영자가 항의한 날만 센 하한입니다. 세션 기록은 11월 7일까지 있고, 위 표에는 10월 30일, 31일, 11월 1일의 영어 답변도 들어 있습니다. 다음에는 자동으로 도는 세션까지 넣어 다시 셉니다.

전역 CLAUDE.md와 프로젝트 메모리 중 어디에 적어야 하나요?

프로젝트 메모리는 다른 저장소의 세션에 실리지 않습니다. 여러 프로젝트에서 같은 사고가 나면 전역 지침이 맞고, 에뮬레이터 사용처럼 프로젝트마다 답이 다른 규칙만 프로젝트 메모리에 적습니다.

Claude Code에서 pkill -f를 쓰면 왜 exit 144가 나오나요?

패턴이 호출한 셸 자신과 일치해 그 셸까지 끊기기 때문입니다. 저희는 정확한 PID를 찾아 끄고, 대상을 찾을 때는 grep "[b]lock_full_e2e.py"처럼 대괄호를 넣습니다.
