문서 뷰어 악성 파일 세트: ZIP 폭탄·CFB 루프·XSS를 생성기로 만들어 테스트에 묶기

받은 파일을 여는 앱은 악성 표본 대신 생성기와 기대 판정표를 커밋하십시오. 단위 테스트가 50행을 대조하고, 화면 검사는 기기에서 따로 합니다.

한글뷰어 슈가독 만들기 8/8

메신저나 메일로 받은 파일을 여는 앱은 언젠가 일부러 망가뜨린 파일을 받습니다. 풀면 1GiB가 되는 ZIP 폭탄, 끝없이 도는 섹터 체인, 본문에 숨긴 스크립트(XSS) 같은 것입니다. 한글뷰어 슈가독은 이런 문서 50개를 Python 표준 라이브러리만으로 만드는 생성기와 파일마다 기대 판정을 적은 표를 저장소에 두고, 단위 테스트가 한 행씩 Kotlin 가드와 대조합니다. 악성 파일 자체는 커밋하지 않습니다. 세트는 2026년 10월 5일 36개로 시작해 같은 날 리뷰를 거쳐 50개가 됐습니다. 이 테스트가 지키는 것은 컨테이너 판정이고, 스크립트가 화면에서 실행되지 않는지는 기기 테스트가 따로 봅니다.

파일과 기대 판정을 한 행에 적는 생성기

generate.py는 682행입니다. ZIP, CFB(Compound File Binary, HWP 5 문서를 담는 컨테이너), HWPX, PDF를 표준 라이브러리로 직접 써서 파일 50개와 manifest.tsv를 내놓습니다. 같은 입력이면 같은 바이트가 나오고, 산출물은 커밋하지 않습니다. 계열은 ZIP 폭탄, 파서 차이, 픽셀 폭탄, CFB 등 10개에 대조군 2행입니다.

file                   family    sniff    guard        preview
bomb_1gb_lying.hwpx    zip_bomb  HWPX     RATIO        shown
multi_bomb_noisy.hwpx  zip_bomb  HWPX     TOTAL_BYTES  shown
cfb_bomb.hwp           cfb_bomb  HWP5     LOOP         shown
xss_text.hwpx          content   HWPX     OK           shown

세트 테스트는 이 표를 한 행씩 읽어 형식 판별, ZIP·HWP 5 가드, 미리보기의 판정과 비교합니다. 어긋난 행을 모아 한 번에 보여 주고, 파일 하나가 1,000ms를 넘거나 행이 30개보다 적어도 실패합니다. Gradle 태스크가 단위 테스트 앞에서 세트를 만들고, 출시 전 검사 스크립트도 같은 테스트를 부릅니다. 폭탄 행은 엔진을 막은 뒤 미리보기를 보여 주므로 shown입니다.

비율 규칙이 막는 폭탄과 예산이 막는 폭탄

ZIP 폭탄은 세 겹으로 막습니다. 크기를 정직하게 적은 1GiB 항목은 풀기 전에 ENTRY_TOO_LARGE로 끝납니다. bomb_1gb_lying.hwpx처럼 1000바이트라고 속이면 풀면서 세는 비율 규칙(1MiB를 넘긴 뒤 1000:1 초과)에 걸립니다. 10월 5일 JVM 측정에서 둘 다 2ms였고, 1GiB를 담은 파일은 1.07MB였습니다.

비율 규칙은 이 세트의 0 폭탄을 겨우 잡습니다. 생성기의 식을 메모리에서 다시 계산하면 압축비가 약 1,012:1이라 한도와 1.2% 차이입니다. 코드 주석의 약 1030:1은 같은 0을 한 번에 deflate한 값(다시 계산하면 약 1,029:1)에 가깝고, 생성기는 블록을 나눠 쓰기 때문에 조금 낮습니다. 0 사이에 난수 바이트를 드문드문 넣은 multi_bomb_noisy.hwpx는 항목별 약 103.8:1로 규칙 아래에 있습니다. 40MiB 항목 16개, 합계 640MiB인 이 파일은 네 번째 항목에서 BinData/ 밖 실제 바이트 합계 128MiB를 넘습니다. BinData/는 문서 속 그림 폴더로 합계 상한(기본 256MiB)이 따로 있고, 그 밖의 항목은 폴더 밖에 둔 그림까지 128MiB 안에서 셉니다.

64MiB(항목)와 128MiB(합계)는 정상 문서 측정값에 여유를 둔 상한입니다. 로컬 코퍼스 HWPX 46개의 BinData/ 밖 최대 항목이 2.9MB, 최대 합계가 3.4MB였고, 코드는 이 상한을 20배 여유로 적었습니다.

CFB 루프는 방문 집합으로 끊고, 경로마다 행이 필요합니다

cfb_bomb.hwp는 스트림의 FAT 체인(섹터 연결표)이 자기 시작으로 되돌아가는 파일입니다. CFB 읽기 코드는 체인과 디렉터리를 방문 집합과 길이 상한으로 걷기 때문에, 같은 섹터를 두 번 만나면 LOOP로 끝납니다.

세트가 이 판정을 지켜도 같은 결함의 다른 경로는 남아 있었습니다. 10월 24일 가드 제거 확인 표에서 스트림을 읽는 두 함수를 따로 시험하자, 가드를 지워도 통과하는 행이 하나 나왔습니다. 받은 파일의 미리보기 스트림을 덮어쓰는 코드가 쓰는 함수였는데 루프 테스트가 없었고, 세트 테스트가 지나가는 경로도 아니었습니다. 지금은 그 함수에 루프 테스트가 따로 있습니다.

XSS 행은 컨테이너 판정만 받습니다

xss_text.hwpx는 마크업 문자열을 본문에, xss_font.hwpx는 글꼴 이름에 담습니다. 세트 테스트는 두 파일이 열어도 되는 컨테이너인지만 봅니다. 글감 목록에는 'XSS를 매 빌드에 돌린다'고 적혀 있었지만, 코드를 다시 읽어 보니 렌더링 결과를 보는 곳은 다음 세 군데였습니다.

  • 기기 계측 테스트: 문서를 실제로 연 뒤 DOM을 검사합니다. 기기에 문서를 미리 올려야 돌고, 없으면 skip합니다. CI와 출시 전 검사 스크립트에는 들어 있지 않습니다. 10월 5일 S21(WebView 153)과 API 33 에뮬레이터(WebView 103)의 debug 빌드에서 xss_text, xss_font, nest 모두 script는 viewer.js 1개뿐이었고, on* 속성, javascript:, 금지 요소, CSS url()은 0개였습니다.
  • node 엔진 테스트: 생성 파일을 rhwp로 그린 첫 두 쪽을 정화해 검사합니다. 파일이 캐시에 없으면 skip하고, 웹 테스트 태스크는 세트 경로를 넘기지 않습니다.
  • node 단위 테스트: 웹 테스트 태스크로 돌지만 인라인 문자열만 씁니다.

WebView에서는 앱의 요청 처리기가 모든 요청을 받아 자산, 1회용 문서 토큰, 403 중 하나로 답합니다. 시험 구현은 null을 돌려줘 blockNetworkLoads와 CSP만 막고 있었고, 제품은 null을 금지했습니다.

CSP는 403을 포함한 모든 응답에 붙입니다. module Worker는 자기 응답의 CSP를 따르므로 viewer.html에만 붙이면 Worker가 풀립니다. 엔진이 낸 SVG 원문은 inert 문서에서 파싱해 허용 목록으로 정화한 뒤에야 페이지로 들어옵니다.

카나리 테스트는 로컬 서버에 접속을 시도합니다. 메인 14경로, Worker 9경로, external_link 문서 모두 hit 0이었고, 하드닝 없는 대조 WebView는 hit 1을 냈습니다. 대조가 빠지면 서버에 아예 닿지 않는 고장 난 테스트와 구별하지 못합니다.

75/75가 전체 가드가 아니었음을 리뷰가 드러냈습니다

세트와 가드는 Claude가 공동 작성한 코드입니다. 10월 5일 구현 단계의 결과 보고는 가드 75개를 지우면 75개가 모두 실패한다고 적고 완료 조건 4개를 충족했다고 판정했습니다. 그 75개는 골라 둔 가드였습니다. 같은 날 리뷰에서 ZIP·CFB 읽기 코드의 테스트 없는 가드 약 15개와 HWP 5 가드의 픽셀 합계 검사가 나왔습니다.

HWP 5 가드는 스트림의 압축 크기만 세고 있었는데, 리뷰 뒤 스트림을 조금씩 풀어 실제 바이트를 세도록 고쳤습니다. ZIP 가드에는 BinData/ 밖 예산이 들어갔고, 크기를 못 읽는 이미지는 거부합니다. 세트는 36개에서 50개로 늘었고, 가드 제거 확인은 146/146이 됐습니다.

생성기도 틀렸습니다. CFB 형제 링크를 잘못 쓰는 버그가 Kotlin 판정과의 첫 대조에서 드러났습니다.

저장소 기록은 그 리뷰를 누가 했는지 적지 않고, 사람이 코드를 고친 기록도 없습니다. '가드를 지우면 실패해야 한다'는 운영자 규칙이 그 단계의 완료 조건에 들어가 75/75 측정을 만들었습니다. 예산 64MiB와 128MiB에는 [소유자 확인 필요] 표시가 지금도 코드에 남아 있습니다.

이 글과 비슷한 문제를 겪고 있다면 메일로 상황을 알려 주세요. 읽고 답하겠습니다. 메일로 문의하기

Windows에서 이 테스트는 조용히 skip됐습니다

2026년 10월 18일 빌드 기계를 Windows로 옮겼습니다. 빌드 스크립트는 PATH에서 python3라는 이름만 찾았고 Windows에는 python.exe뿐이어서 세트를 만드는 태스크가 등록되지 않았습니다. 세트 경로가 없으니 assumeTrue가 테스트를 skip했습니다.

10월 23일 새벽 커밋은 이전 뒤 Windows에서 테스트를 돌린 적이 없었다고 적고, 전체 단위 테스트를 1,254건, 실패 0, skip 7로 기록했습니다. skip 7건의 이름은 적혀 있지 않습니다. 약 8시간 뒤 찾는 이름을 고쳤고, 그 검증 기록은 "1 test run, 0 skipped, 51 set files"입니다(문서 50개와 manifest). skip을 이름으로 대조하는 장치는 없었습니다. skip이 초록에 묻히는 구조는 조용히 skip되는 테스트가 CI를 초록으로 만든다에 적었습니다. python이 없으면 지금도 skip이고, 출시 전 검사 스크립트만 BLOCK으로 멈춥니다. 같은 스크립트가 node를 두고는 "no node → failure, never a skip"이라고 적었습니다.

운영 기록은 1.2.0과 1.3.0 AAB를 어느 기계에서 빌드했는지 모른다고 적었습니다. 그래서 10월 18~23일 사이 출시 빌드가 세트를 건너뛰었는지는 확인하지 못했습니다.

CI 99회 중 성공 0: CI는 세트의 게이트가 못 됩니다

2026년 11월 7일 기준 GitHub Actions에서 조회되는 CI 99회 중 성공은 없습니다(실패 78, 취소 21). 로그를 읽은 1회는 python 문제가 아니었습니다. 세트 생성은 wrote 50 files를 찍었고, 빌드는 다른 모듈(디자인 시스템)의 단위 테스트 1건 실패로 끝났으며, 세트 테스트가 있는 모듈의 테스트 태스크 줄은 로그에 없었습니다. 99회는 모두 main push이고 main에는 브랜치 보호가 없어, 실패한 CI가 코드를 막지 않습니다. 세트 실패가 릴리스 AAB 빌드를 멈추는 곳은 출시 전 검사 스크립트이고, 이 스크립트를 돌리는 일은 출시 체크리스트에 맡겨져 있습니다.

표본 대신 생성기, rhwp 상한은 재 보지 않았습니다

생성기 주석은 산출물을 "no real documents, no binary blobs"라고 적고, 저장소에 남는 것은 682행과 기대 판정뿐입니다. 테스트가 행마다 대조하므로 주석 표현대로 생성기와 가드가 "cannot drift apart"이고, 표본 파일과 달리 판정이나 내용을 바꾸면 코드 diff로 보이고, 악성 파일이 저장소에 남지 않습니다. 같은 파일은 기기 E2E에도 들어가, S21·S20에서 manifest 50/50을 확인했습니다.

세트는 아는 패턴의 회귀를 막고, 모르는 입력을 찾는 일은 퍼저 몫입니다. 저장소 문서와 테스트에서 퍼징 기록은 찾지 못했습니다.

rhwp 자체 상한에 맡기는 길은 버렸습니다. wasm 안에 해제 상한 문구가 있지만 재 보지 않은 값이라, HWP 5 가드 주석은 "does not rely on them"이라고 적었습니다.

세트에 없는 실제 암호 문서와 S21의 29.1초 TIMEOUT

flags 계열은 플래그 비트만 세운 합성 파일이고, 실제 암호·DRM 문서는 세트에 없습니다.

1,000ms는 개발 기계의 JVM 시간입니다. 50,000문단 paras_50k.hwpx는 2026년 10월 5일 데스크톱의 node 20과 rhwp 0.8.6에서 1,220쪽, 파싱 약 21초로 10초 안내와 30초 강제 대체 사이에 들어왔지만, S21에서는 26.1~27.9초에 첫 쪽이 나오거나 29.1초에 TIMEOUT이었고 에뮬레이터는 29.3초 TIMEOUT이었습니다.

10월 5~6일 기기 E2E에서 64단 중첩 표 nest.hwpx는 다 그렸다고 보고하면서 빈 쪽을 보여 줬고, 후속 수정 뒤 릴리스 빌드 3회 모두 손상 안내와 '다른 앱으로 열기'로 끝납니다. 이 결함은 세트 테스트로는 보이지 않습니다.

기대 판정부터 적고, 가드를 지워 확인합니다

  1. 위협을 계열로 나누고 파일마다 기대 판정을 먼저 적습니다.
  2. 외부 의존 없는 결정적 생성기로 파일과 manifest를 함께 쓰고, 만든 개수를 출력합니다.
  3. 테스트가 manifest를 행 단위로 대조하고, 파일당 시간 상한과 행 수 하한을 단언합니다.
  4. 정상 문서 코퍼스의 최대값에 여유 배수를 곱해 예산을 정합니다. 이 앱은 46개에서 얻은 2.9MB·3.4MB로 64MiB·128MiB를 잡았습니다.
  5. 단위 테스트 태스크에 묶습니다. 이 앱은 python이 없으면 아직 skip하지만, 보안 세트를 skip으로 두지 마십시오. 아래는 저장소에 없는 제안입니다. 
    val dir = System.getProperty("sugardoc.malicious")?.let(::File)
if (System.getenv("CI") == "true") check(dir?.isDirectory == true) { "security set missing" }
assumeTrue(dir != null && dir.isDirectory)
  6. 렌더링은 기기에서 따로 측정합니다. 하드닝 없는 대조 WebView가 hit 1을 내는지 먼저 확인합니다.
  7. 가드를 하나씩 지워 빨개지는지 봅니다. 같은 가드가 경로 둘에 있으면 행도 둘로 만듭니다.

남은 일: CI 초록, skip 금지, webTests 연결

2026년 11월 7일 기준 세 가지가 반영되지 않았습니다. 다른 모듈 테스트 실패를 고쳐 CI를 끝까지 돌게 하는 일, python이 없는 CI에서 skip을 실패로 바꾸는 일, 웹 테스트 태스크에 생성한 세트를 넘기는 일입니다. 세트 테스트가 CI에서 skip 없이 도는지는 로그로 확인하지 못했고, 보고서 파일은 내려받지 않았습니다.

자주 묻는 질문

Android 앱에서 ZIP 폭탄은 어떻게 막나요?

선언 크기를 믿지 말고 풀면서 실제 바이트를 세어 끊습니다. 이 앱은 항목당 상한, 1MiB를 넘긴 뒤 1000:1 비율 규칙, 합계 예산을 함께 씁니다.

HWP나 HWPX 파일도 압축 폭탄이 될 수 있나요?

될 수 있습니다. HWPX는 ZIP이고 HWP 5는 CFB 안에 deflate 스트림을 둡니다. 이 앱의 세트에는 두 형식 모두 1GiB로 풀리는 행이 있습니다.
